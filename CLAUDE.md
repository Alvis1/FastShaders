# FastShaders

Bi-directional TSL (Three.js Shading Language) visual shader editor. Users author and execute their own shader code inside the app, and `.fastshader` files can be shared between users — treat any loaded `.fastshader` or pasted shader source as adversarial input.

> **Before changing node visuals, the glyph system, `ShaderNode`, `NodePreviewCard`, or the Node Designer (`node-designer.html`), read `private/NODE_DESIGN_REQUIREMENTS.md` — the authoritative spec for node appearance/layout.** It is internal working material: `private/` is gitignored, so the file is not in a fresh clone and the path is deliberately not a link (it would 404 on GitHub). Elsewhere in this file and in source comments the spec is cited by bare name — that is the file.

## Stack

- React 18 + TypeScript + Vite (ES modules, base path `/FastShaders/`)
- `@xyflow/react` v12 — node graph editor
- `@monaco-editor/react` — code editor
- `zustand` v5 — state management
- `@babel/parser` + `@babel/traverse` — code→graph parsing
- `@dagrejs/dagre` — auto-layout (LR direction)
- `three` (WebGPU build) — shader runtime; FastShaders uses only `three/tsl`
  built-in functions including the MaterialX noise family (`mx_noise_*`,
  `mx_fractal_noise_*`, `mx_worley_noise_*`, `mx_cell_noise_float`)
- Path alias: `@/*` → `./src/*`

## Commands

- `npm run dev` — start dev server (port 5173)
- `npm run build` — typecheck + build (`tsc -b && vite build`)
- `npx tsc --noEmit` — typecheck only
- `npm test` — run the vitest suite once (CI-friendly)
- `npm run test:watch` — run vitest in watch mode
- `npm run tauri dev` / `npm run tauri build` — desktop (Tauri v2) shell; needs a local Rust toolchain. Releases are built in CI (no local Rust required)

## Deployment

**When the user says "deploy" (or "deploy to all"), it ALWAYS means: commit the pending work, push, and ship to BOTH targets** — never stop after the release pipeline:

0. **Commit + push first**: commit whatever is pending in the working tree (and push the `a-frame-shaderloader` submodule first if it changed) — "deploy" is standing authorization to commit and push; don't ask again.
1. **Release pipeline** (web on GitHub Pages + desktop binaries, in lockstep): `npm version patch && git push --follow-tags`. The `v*` tag triggers `.github/workflows/release.yml` → tests, macOS `.dmg` + Windows installers, gh-pages deploy.
2. **alvismisjuns.lv**: `npm run deploy:alvismisjuns` — builds with `FS_BASE=/fastshaders/` + the alvismisjuns CSP origins and uploads `dist-alvismisjuns/` via psftp to `https://alvismisjuns.lv/fastshaders/` (credentials in the gitignored `.vscode/sftp.json`; needs `brew install putty`). `-- --no-build` re-uploads the existing snapshot. Run it from the SAME committed/tagged state as step 1 so both hosts serve the same version — it deploys the working tree, not the last tag. The script curl-verifies the deployed version meta at the end.

Loading an entry ADOPTS that file's identity as the shader name (`adoptShaderName`: the authored name is kept when `toKebabCase` says it denotes the same file, so `my-shader.js` stays "My Shader"; the DISK name wins when they diverge, so `waves.js` whose graph is called "Untitled" becomes "waves"). That "did the user rename it?" test is `toKebabCase` on both sides, never raw strings (`exportShader.shaderBaseName` is the shared derivation, so a predicted name can't drift from the written one): a file name is what identity MEANS here, so "My Shader" → "My  Shader" is not a rename, while re-typing a prettier spelling of an adopted stem would otherwise take the save-as branch back to the file it was already on. The flip side is inherent to deriving names by kebab and cannot be fixed in the rules — `toKebabCase` is many-to-one, so **"Zīle" and "Zāle" are one file** (`z-le.js`) — which is why a save that would land somewhere OTHER than the tracked file lists the folder first and `window.confirm`s when that name already exists. **The provenance of the document on screen is therefore THREE states, not a nullable file name** (`DocOrigin`), because two of them are indistinguishable if you only track a name: `file` (loaded from / last written to it — writing back is the point and stays silent), `new` (NEW built a blank document, which resolves to `my-shader.js` via `DEFAULT_SHADER_NAME` often enough that Save must look before replacing), and `null` — unknown provenance, a session restored from the autosave or an import from another surface — which writes the derived name SILENTLY, exactly as it did before any of this existed. That last one is a deliberate limit rather than an oversight: the app cannot tell the user's own file from a stranger's there, so prompting would fire on the first save of every launch, which is noise, not safety. The listing is fetched only on the asking branches, so ordinary re-saves pay nothing for it; on confirm the write uses the spelling already on disk. Four things ride on this. The origin is COMPONENT state, not a store field (one reader, one writer, the control never unmounts on desktop, and the web build never mounts it at all). It is dropped on `fs:graph-imported` and set to `new` on **`fs:graph-new`** — a dedicated event `newGraph()` dispatches, deliberately NOT a reuse of `fs:graph-imported`, which would arm NodeEditor's import auto-fit on top of the one `startNewShader` already schedules. Both listeners are guarded by a `loadingRef`, because `announceGraphImport` runs SYNCHRONOUSLY inside `importShaderText` and would otherwise clear the very origin the load is about to set. Re-tracking happens ONLY in the write's success path AND only if an `originEpoch` counter is unchanged across the awaited write: claiming a file that was never written — or one belonging to a shader some other surface imported during the await — would aim the next Save at whatever really is at that name. And `newGraph()` also resets `shaderName` (see the NodeEditor bullet); the reset alone is NOT what severs the tracking, and assuming it was is the trap — a document already AT the default name kebabs to the same file, so the tracked target survives the reset and only the event breaks the link. **A kind flip forks the pair**: adding an image turns `waves.js` into `waves.zip` and there is no delete command in the IPC surface, so the stale sibling stays; the Save tooltip names the exact target so at least the flip is visible before it happens. The row still shows ONE name — it used to lead with the AUTHORED name and repeat the file name underneath, and `waves.js` whose graph said "Untitled" read as an unrelated shader; loading now closes that divergence at the SOURCE, so the example survives only for foreign or hand-renamed files, where the disk name wins and the authored name is overwritten on the next save (not undoable — `shaderName` is absent from `snapshotOf`). `display_name` is no longer dead: it is the exact answer to "did THIS file supply a name?", which the store cannot give (`applyProjectToStore` skips an empty `shaderName`, so a post-import read cannot tell "the file said nothing" from "the previous shader was called this" — which degraded "My Shader" to "my-shader" on the most ordinary flow there is, reopening the shader you just saved). The `MAX_NAME_SCAN_BYTES` scan behind it therefore stays, and the store before/after diff is only the fallback for zips and oversized `.js`. `src/bench_server.rs` — the LAN bench server (`bench_server_start/stop/status` commands; GET-only, path-sanitized tiny_http file server on 0.0.0.0:5199, ephemeral-port fallback) that serves the bundled ShaderCarousel to headsets on the local network; the suite is staged into `src-tauri/carousel-dist/` (gitignored) by the vite desktop profile and bundled via `tauri.conf.json`'s `bundle.resources`. Preview-iframe asset URLs resolve via `new URL(base + path, location.href)` (`resolveAssetUrl` in `tslToPreviewHTML.ts`) so they survive non-http schemes (tauri://) — don't revert to `location.origin` concatenation.
- **Feedback ("!" toolbar button)**: the red `!` in the toolbar's right cluster opens `Modals/FeedbackModal` — a composer that assembles a plain-text report and hands it to the user's own mail client via `mailto:`, with a clipboard fallback. **Nothing is uploaded, and that is a constraint rather than a preference**: the build CSP is `connect-src 'self' blob: <deploy origin>` + `form-action 'self'` (`vite.config.ts`), so a POST to Formspree / Google Forms / any hosted endpoint is blocked by the app's OWN policy; the desktop build must work with no network at all; and a third-party form would make someone else a data processor for grant-funded research feedback. A `mailto:` navigation is CSP-exempt (navigation, not a fetch) and works in every build. If a server-side endpoint is ever wanted, it needs a `connect-src` widening plus the mailto path kept underneath for the offline case — don't quietly swap one for the other. Report assembly is PURE and tested in `utils/feedbackReport.ts` (the DOM reads live in the modal): the opt-in technical block carries version/build, **graph counts (nodes, how many are connected, connections, groups, notes), cost points vs the selected headset profile, and the preview mesh (built-in geometry name, or a custom model's name + vertex count + size)**, then browser/platform/renderer/display. Counts only — no graph content leaves. It reports the AUTHORED vertex count, not what THREE ends up with (the OBJ loader emits non-indexed geometry and `fit-bounds` then welds duplicates), so don't reason about GPU cost from it. Also: `MAILTO_SAFE_CHARS` steers over-long reports to "Copy report" because Windows' shell truncates `mailto:` URLs around 2000 chars — a silently truncated bug report is worse than none, since the user believes they sent it. `previewBackend()` RESTATES the `__fsForceWebGL2` rule that `tslToPreviewHTML` emits as source text into the iframe (it can't be imported and called); `feedbackReport.test.ts` extracts that emitted function from the generated HTML, evaluates it, and fails if the two disagree — so a change to the WebKit-forcing rule can't silently make feedback reports lie about which renderer the user was on.

- **The glyph modal's point editor** (marquee, multi-move, corner-grip scale, Delete, arrow nudge — `designerApp.ts`): **the selection is a set of INDICES into `glyphPoints()`**, because nothing else survives a frame — `renderGlyphPts()` destroys and rebuilds the whole handle layer on every pointermove and `collectGlyphPoints` mints fresh point defs each pass, so neither a DOM node nor an object identity can hold it. An index is meaningful exactly as long as the art's STRUCTURE is, which is what `ptsSig()` measures: it folds tag + delete-kind + anchor/control and deliberately NOT coordinates, so a gesture that only MOVES points keeps its selection while adding or removing a shape or a path segment drops it — and the renderer re-checks the sig every pass as the backstop for the invalidation sites an explicit `clearGlyphSel()` misses (a delete re-indexes every point it did not remove). The `PT_CAP` truncation therefore belongs to `glyphPoints()` and NOT to the renderer: a point past the cap gets no handle, so a selection able to reach it would be invisible, un-clickable and un-deletable. **`mApply` is the SOLE commit path** — every gesture writes only `#mPreview`'s DOM and `#mSvg`, and nothing in the modal calls `stash()` — so **Cancel is the session-level undo** (which is why closing a dirty modal confirms first: a whole session of moves, scales, nudges and deletes lives in that textarea and nowhere else). The 20-entry `glyphUndo` stack is a SEPARATE, coarser thing: whole `#mSvg` strings, one per gesture, one per HELD arrow run (keyed on `e.repeat` — auto-repeat fires ~30 keydowns/s and a snapshot each would evict the ⌘A+Delete entry the stack exists for), and one per whole-document replacement, which is why Clear / Built-in / Load / Upload / .svg-drop all route through `replaceGlyphSource` — assigning `.value` by hand fires no `input` event, so ⌘Z after a replacement restored the document from before it. Typing in the textarea clears BOTH the stack and the selection: those snapshots describe a document the user has since rewritten, and the textarea has the browser's own undo. **Hit order is the handle layer's contract** (SVG hit-testing is topmost-wins, i.e. last-appended wins): the full-canvas marquee backdrop is appended FIRST so everything after it still gets the pointerdown, the selection bbox and its corner grips next, and the point handles LAST — grips appended after the handles swallowed the pointerdown of any UNSELECTED point within ~15px of a padded bbox corner, and the only escape was clearing the very selection being extended. Traps a future gesture would re-introduce: (a) every mutating gesture gates on `el('mApply').disabled` FIRST, above the selection bookkeeping and the listeners — `refreshMPreview` injects the raw text whether or not it parses, so a gesture on the HTML parser's RECONSTRUCTION of half-typed markup writes that reconstruction back into `#mSvg`, which then parses, clears the red error and enables Apply, reading as the typo having been accepted; (b) the gestures focus `#mPrevBox` with `preventScroll: true`, since `.modal` is `max-height: 92vh` and a plain `focus()` scrolls the layer between the browser's hit test and the gesture's own `viewPtOf` read (measured: 139px of scroll = 27.8 of the canvas's 56 view units, so the first drag after focus was elsewhere teleported the point half the canvas — intermittent, because a repeat focus on an already-focused element does not re-scroll); (c) pointer capture goes on `#mPtsLay`, never on the pressed handle, which the next frame's re-render deletes; (d) every multi-point write runs TWO ASCENDING passes over a snapshot taken up front, never a read-back — relative path args rebase on the segments before them, and a setter can clamp against a sibling on its own element that the same gesture is moving (a rect's top-left reads the live bottom-right); (e) `pruneEmptyGroups` runs before the `innerHTML` commit, because 26 of the 34 shipped glyphs are wrapped in a `<g transform>` and an emptied wrapper is a TRUTHY `innerHTML` — "delete everything" would save a glyph that draws nothing while `glyphCoverage.test.ts`'s balanced-tag/no-URL checks all stay green, which is precisely the bare-titled-box failure that test exists to catch; (f) the modal's keydown gate is `activeElement === #mSvg`, NOT the page's `INPUT|TEXTAREA|SELECT` `typing` regex — the modal's other controls are two checkboxes and the load `<select>`, none of which take a character, so gating on `typing` silently killed Del/⌘A/the arrows while the selection stayed drawn, with no click able to return focus without destroying that selection; and the keys bail outright while a gesture owns the pointer, since they replace the `<svg>` that gesture still holds a reference to.
- **The glyph modal's TOOLS, rotation, source link and paint bar** (the same file; `glyphEditorGuards.test.ts` greps source for the invariants below, because none of them fails loudly). A tool row (Select · Pen · Draw · Line · Rect · Ellipse · Add point · Rotate) re-routes the marquee backdrop's pointerdown by mode; nothing about the existing marquee/move/scale code changed, it simply is not reached while another tool is armed. Five things are load-bearing. (1) **`renderGlyphPts` is now a WRAPPER** — `renderGlyphPtsInner()` then `syncGlyphHl()` then `renderPaintBar()` — because the renderer returns early three times (no layer, "drag points" unticked, no parsed root) and both new surfaces must refresh past all of them: hooked inside, unticking the checkbox left `<mark>` rectangles painted behind a textarea with no selection to explain them, and the paint bar reading "5 shapes" against an empty one. For the same reason the **Format** button is gated in `refreshMPreview` (the TEXT funnel) and not in the renderer, or it stays disabled with a tooltip blaming an SVG error the user has already fixed. (2) **Every new overlay element carries `.pt-dec`** — `#mPtsLay circle{pointer-events:all}` is an ELEMENT rule written when every circle in the layer was a draggable handle, so a decorative one is hittable by default and swallows the exact press it invites: the pen could not be finished by clicking its own first anchor, and the Add-point marker, drawn under the cursor by construction, ate every insert click. `.pt-off` is the same mechanism for the opposite reason — outside Select the handles are a read-only picture and a press belongs to the armed tool. (3) **A shape is created into the group that owns the SELECTION** (then the document's single top-level `<g>`, then the root), and both drag corners are converted through the inverse CTM before `width`/`height`/`rx` are measured — transforming an EXTENT would be silently right on the 24 `translate(28 28)` glyphs and 12.5% wrong on the one `scale(0.875)` wrapper. A rotated or sheared container makes an axis-aligned `<rect>`/`<ellipse>` unauthorable, so those two tools fall back to the root — decided inside `resolveDrawTarget`, which is also what draws the "· into `<g …>`" label, so the label cannot promise a container the tool will refuse. **⇧ on a box tool means SQUARE, not the point-drag angle lock**: `angleLockVec` snaps the drag VECTOR to the 30/45 families, which on a rect is a different thing entirely (a 35° drag locks to 30° and comes out 1.73:1, not square). (4) **Rotation has two mechanisms and the split is not cosmetic**: point coordinates rotate for lines, polylines, text/circle centres and path anchors/controls, but a `<rect>` is axis-aligned by construction and an `<ellipse>`'s rx/ry ARE its axes — rotating their points just drags the corners, which reads as the shape being resized and skewed — so `rect`/`ellipse`/`text` (and any element carrying its own transform, whose numbers already live in a turned frame) get a `rotate()` folded into their own `transform` instead, composed in the PARENT's space from the ORIGINAL attribute every frame (never from the last frame's output, which would accumulate a rotate() per pointermove), negated under a mirroring parent, and refused outright under a non-similarity one. The pivot comes from `getBBox()` for any element whose handles do not describe its extent — a rect's two handles are a top-left ANCHOR and a bottom-right SIZE handle, and size handles are excluded from the writes, so a pivot built from writable handles alone swung the shape around its own corner. The gesture accumulates an UNWRAPPED per-frame delta; measuring against the gesture's first angle folds at half a turn and spins the art backwards. **The KEYBOARD path (⌥←/→) is a RUN, not a series of presses**, and that is not an optimisation: applying a per-press delta to the art the previous press produced re-derives the pivot from already-rotated geometry, and the AABB centre of a rotated point set is not the rotated AABB centre — MEASURED on the shipped `dataviz` polyline, six ⇧⌥→ presses land the whole shape 1.38 view units from where one 90° drag puts it, as a pure translation (an L-shaped selection spanning the canvas goes 9.3), and it stacked one `rotate()` per keypress into the saved art. So `rotRun` keeps the run's ORIGINAL source text plus the accumulated total, restores that source and RE-PLANS against it each press — the plan cannot be cached, because `refreshMPreview` replaces `#mPreview`'s innerHTML and every element reference in it goes with the old tree. The run is validated by comparing the SOURCE TEXT (plus `selSig`) rather than by enumerating invalidation sites: typing, an undo, a paint change and a tool gesture all move it, so one comparison covers every way it can stop being valid. `rotateTransform` also FOLDS a leading same-pivot `rotate()` rather than prepending another, which is what keeps the attribute one call long. The undo snapshot stays THIS press's pre-state, so ⌘Z steps back one tap. Rotation is a TOOL and not a grip on the selection frame because a grip has to live outside that frame, and on art that fills the canvas there is ~1.6 units of room out there — it would be drawn on top of the very handles that (correctly) win an ambiguous press, i.e. visible and unclickable in exactly the select-all case people reach for first. (5) **The source link joins two halves by DOCUMENT ORDER and VERIFIES it** — the Nth drawable in the text is the Nth in the DOM, checked with `tagsAlign` on every pass rather than assumed, because the preview is built by the HTML parser and foreign-content rules can close the `<svg>` early on a breakout tag and shift every index by one; a mismatch shows a note and no highlight, never a wrong one. The highlight is a mirror div behind a transparent textarea (a textarea cannot style its own content) whose wrap-deciding metrics — `white-space`, `overflow-wrap`, `word-break`, the border widths — are COPIED at runtime, not hardcoded, and which never measures while the modal is hidden (`clientWidth` is 0 there, and the width would be cached negative) — which is exactly why `openGlyph` adds `.show` BEFORE its first `refreshMPreview`: refreshing first left the mirror holding the PREVIOUS glyph's text and that session's `<mark>` spans, i.e. blue blocks over unrelated lines of a different document, cleared only by the next real gesture. **Format** is a button and never automatic: a "reformat if it already looks formatted" heuristic false-positives on any newline inside an attribute, which is ordinary Illustrator output, so pasted art would silently reflow on the first drag. It calls `focusPtCanvas()` for the reason `replaceGlyphSource` documents — WebKit does not focus a `<button>` on click, so the caret stays in `#mSvg`, the keydown bails above the ⌘Z branch, and the undo entry it just pushed would be unreachable. **Escape's `!caret` term is gone**: clicking a line of markup selects that shape and deliberately leaves the caret where the user is reading, so a selection held with the caret in the box went from rare to ordinary — and from there Escape discarded the whole session. It still closes on the second press. The paint bar reads EFFECTIVE values through `getComputedStyle` (the only thing that resolves a presentation attribute, an inline `style` and inheritance from a `<g fill="none">` alike) and converts the `rgb()` it answers in back to hex, or a shape painted the palette's own colour matches no swatch; it writes presentation ATTRIBUTES to match the shipped art, skips what the container already supplies, and commits on `change` rather than `input` so typing a width is one undo entry and not three. With nothing selected the swatches set what the next drawn shape uses — session-only, deliberately not persisted.
- **Node selection is an ELEVATION change, not a band**: every node shell (`.node-base`, `.output-node`, `.note-node`, `.color-node`, and the collapsed group pill) rests on `--shadow-node` (a hard `2px 2px 0` contact shadow) and marks selection by swapping the WHOLE property for `--shadow-node-selected` (`8px 8px 0`) — the same card, lifted toward the viewer under the app's fixed top-left light. Nothing else changes. The coloured `box-shadow: 0 0 0 <n>px` band this replaces (and `--node-selection-width`, and `.node-base__stack-frame`, and the `--node-cat` custom property six node components published solely to feed it) are all GONE — a band drawn in the node's own category colour sat directly on top of the node's 1.5px category BORDER, so a selected node read as one fat mis-drawn border rather than as a highlight, and the 4× offset jump is legible on one node among fifty in a way a ring is not. Consequences to respect: box-shadow REPLACES rather than adds, which is now the point — each selected rule is ONE token and must not re-state `--shadow-node` beside it; neither token is redefined in the dark block, since graph nodes render identically in both themes; and a STACKED (multi-channel) node still suppresses the card's own shadow entirely (`box-shadow: none`, set inline by ShaderNode and mirrored in CSS) because the DEEPEST stack layer carries the group shadow — so it is that layer, not the card, whose inline `boxShadow` switches to `--shadow-node-selected`, lifting the whole stack as one object. Two shells are deliberately outside the rule: an EXPANDED group frame keeps a faint band (it is a transparent frame with no fill and no resting shadow, so it has no elevation to raise — and `getGroupFrameColors` gives it a full-strength border when selected as the second channel), and `.fs-connect-target`'s drag-connect ring stays an `outline`, which is now the ONLY outline-style node indicator on the canvas and therefore unmistakably not selection. `NodeVisual` (the inert replica behind asset cards, the node-editor overview and the Node Designer stage) has no `selected` concept at all and hardcodes the resting token — a documented divergence from ShaderNode, not drift. `cssTokens.test.ts` is the guard that makes retiring a token safe: a `var()` naming a property nothing declares is invalid at computed-value time, so CSS drops the ENTIRE declaration — which is exactly how the first cut of this change left a selected Color node with no shadow at all while every one of the 152 test files stayed green. **HOVER uses the same lift**, and both are driven by ONE inherited custom property, `--fs-node-lift`, published on React Flow's node WRAPPER (`.react-flow__node`, rising on `:hover` and `.selected`) and read by every shell as `box-shadow: var(--fs-node-lift, var(--shadow-node))`. The wrapper is the one element the card AND its multi-channel stack layers both descend from, which is what lets a stacked node rise as a single object instead of highlighting its top card; the fallback in that `var()` is what every NON-React-Flow surface renders at (asset cards, the node-editor.html overview, the Node Designer stage), and each shell ALSO sets the property on its own `--selected` modifier so selection still draws where React Flow's class is absent. Every shell carries `transition: box-shadow var(--transition-fast)`, so hover and box-selection both ease rather than snap — selection differs from hover in exactly one way, it STAYS. Asset tiles join the same system rather than copying it: `.node-preview-card:hover` publishes the same variable (plus a `transform` of its own), which keeps the card layer scaling a node instead of RESTYLING one — the rule `assetCardGeometry.test.ts` enforces. **The lift MOVES the node too**, on the canvas as well as on a tile — `--fs-node-rise` (−3px, tokens.css) on both axes, because a shadow stepping out without the object rising reads as having grown a shadow rather than as having come forward. On the canvas that is written as the standalone **`translate`** property, never `transform`: React Flow OWNS the node wrapper's `transform` (it is the node's x/y, rewritten every frame of a drag) and ShaderNode's inner wrapper uses `transform: scale()` for the cost scale, and the used matrix is translate → rotate → scale → transform, so `translate` composes with both instead of destroying them. **It is applied by the SHELLS, never by React Flow's node wrapper** — a second inherited property, `--fs-node-shift`, published beside `--fs-node-lift`. The wrapper IS the hover target, so moving it moves the box that decides whether the pointer is still over the node: sweeping along a node's lower edge became a feedback loop (lift → the card slides out from under the pointer → unhover → drop → hover), MEASURED at **38 hover flips across a 40-step creep** along the bottom edge, i.e. a jitter on almost every mouse move. Shell-applied, the wrapper stays put and that drops to the correct 2 (one enter, one leave). **The expensive nodes need one thing more**: `getCostScale` is a `transform`, which does not affect layout, so their card PAINTS past the wrapper (17.3px on a noise node) and out there the card is the only thing under the pointer — hover is driven by the very element that moves, and the loop came straight back (47 flips). `.node-base::before` fixes it by extending the card's hit area right and down by exactly the distance the card travels up and left (`inset: 0 var(--fs-node-shift) var(--fs-node-shift) 0`), so the union has a boundary that does not move; the top/left side is left alone because the card moves TOWARD it and that side only ever grows. At rest the shim adds nothing, so no node grabs an event it did not grab before, and `z-index: -1` keeps it behind the card's own content so it can never intercept a widget or socket. Noise then goes 47 → 1. 3px is a CEILING, not a taste: moving the wrapper moves the node's SOCKETS while React Flow keeps drawing its wires to the handle positions it measured earlier, and a diagonal 3px is 4.24px against a socket of radius 5px (`--handle-size` / 2), so the wire's endpoint stays inside the disc that paints over it and the wire still reads as landing on the port (MEASURED at canvas zoom 1.59: socket moved 6.76px, radius 7.96px). The ratio is zoom-invariant — node and sockets scale together — but it moves with `--handle-size`, which coarse pointers bump to 12px. Past ~3.5px hovered nodes start to look unplugged. The ONE node excluded from the movement is an EXPANDED group frame: its members are separate nodes that stay put, so a frame sliding 3px would visibly detach from the cluster it encloses. A COLLAPSED pill stands in for a node and travels like one (`:has(.group-node--collapsed)`). A node's settings menu holds the same lift for its own node: NodeEditor puts `fs-menu-active` on the wrapper for the life of the menu, keyed on the `contextMenu.nodeId` the store already carries, so the panel you are editing never sits beside a graph that has forgotten which node it belongs to. Imperative (the `clearConnectPreview` idiom, `CSS.escape` included — node ids come from `.fastshader` files) rather than a className on the node OBJECT, because node data changes push through history and the autosave and opening a menu is not an edit; the effect's cleanup covers every way a menu ends WITHOUT enumerating them, including a second right-click MOVING the menu to another node, which only re-renders and would otherwise leave the class behind. **The cost-badge numbers cast the same hard shadow as everything else** — `1px 1px 0`, replacing a `0 1px 2px` blur: dark `rgba(0,0,0,0.45)` on an asset tile (the number is drawn in the user's cost-gradient colour there, and a white halo did nothing against the near-white bar and vanished into the dark one), and `--node-cost-text-shadow` on the canvas, which is already the contrast-flipped companion of the colour the number itself takes. **The marquee itself is BOUNDARY ONLY** — a 1px dotted `--border-focus` outline with no fill, because the translucent blue wash it replaces tinted every node it swept over, and on a canvas whose whole job is colour a selection must not change what the shader looks like. It is an `outline` rather than a `border` so the line can sit outside the box without touching the rect React Flow sizes inline: the LIVE band stays at `outline-offset: 0` (its edge has to mean exactly "what is inside this"), while the box that REMAINS after the pointer is released — `.react-flow__nodesselection-rect` — stands off at **5px**, clearing the 8px shadow and 3px rise its selected nodes now carry. `outline-offset` moves only the line, so dragging the selection still grabs where it always did. Both need `!important` on the outline: React Flow ships `.react-flow__nodesselection-rect:focus { outline: none }` to suppress the UA focus ring, that rect really IS focused after a marquee (it is focusable so the selection can be nudged by keyboard), and without the override the released box drew no line at all while its offset still applied — a silent failure that looks like the rule never matched. **Clicking also THICKENS the node's border** — `--fs-node-border-scale` 1 → 1.5 on `.selected` and `fs-menu-active` (NodeBase.css), read by every shell: the canvas components set their frame INLINE (the colour is the node's category and is only known in JS), so the width rides `NODE_BORDER_WIDTH` from `nodes/nodeFrame.ts` — one place holds the 1.5px the node spec fixes, and its `var(…, 1)` fallback is what keeps asset tiles, the node-editor overview and the Designer stage at rest. A SCALE and not a width, so each shell scales ITS OWN base (1.5px card, 1px note, 2px group frame) rather than all snapping to one number. Hover deliberately does NOT thicken: the lift alone made hovering and selecting render identically, so sweeping the pointer across the canvas looked like it was selecting everything it passed — a committed state gets weight, a passing one only gets height. **A lifted node's WIRES move with it.** The card's sockets travel with the card, but React Flow computes edge endpoints from node POSITIONS and knows nothing about a CSS `translate`, so every wire on a lifted node hung a few px off its port and read as unplugged. `TypedEdge` therefore offsets each endpoint by `nodeRisePx()` (which READS `--fs-node-rise` off the DOM rather than duplicating the literal, so geometry and CSS cannot drift) when THAT end's node is lifted — only that end, since the other node has not moved. It costs two subscriptions per edge, both folding to a small NUMBER (`selected` from React Flow's `nodeLookup`; hover + open-menu from the app store's `hoveredNodeId`/`contextMenu` in ONE selector), so the value is 0 for every edge that does not touch the node and a hover re-renders only the one or two wires that actually moved — MEASURED: hovering a node moved exactly 2 of 6 paths, by exactly −3,−3. **Dragging a WIRE suppresses hover entirely** (`fs-connecting` on the canvas root + NodeEditor pausing `hoveredNodeId`): a connection drag sweeps the pointer across every node between the socket and the target, and lifting each in turn is noise on top of a gesture that already has its own target affordance. The CSS and JS halves must stay in step — if one suppresses and the other does not, the card lifts while its wires stay put, which is the very defect the offset exists to fix. Selected nodes and the menu-active node keep their lift throughout, so the suppression rule carries `:not(.selected):not(.fs-menu-active)`.

- **Vertex WELD for displaced primitives lives in the LOADER, not the app** (`a-frame-shaderloader-0.6.js`: `weldByPosition` + `shouldWeld`/`syncWeld`/`unweld`). A BoxGeometry gives every face its own vertices with per-face normals, so normal-driven displacement drives the 3 copies at each corner apart and the faces separate. The editor preview fixed this with an inline `weld-verts` component and was the ONLY surface that had it — podest, the copy-ready A-Frame page and every page embedding an exported module all rendered a displaced box as six floating squares. Moving it into the loader (2026-08-31) fixed all of them at once, needed ZERO podest changes, and kept the A-Frame page's zero-script property, because every one of those surfaces already loads the loader. Four things are load-bearing. **The displacement gate is `material.positionNode != null`, NOT `!== undefined`** — three's NodeMaterial constructor assigns `null`, so an undefined test is true for every material ever built and would weld every primitive shader, failing silently (spheres and planes look fine; only a non-displacing cube gives it away, by rendering smooth). The loader is the one layer holding the BUILT material, so it answers this structurally where the app must regex module text. **PRIMITIVES ONLY** (`el.components.geometry`): the rebuild keeps position/uv/index, so welding a MODEL would drop vertex colours, skinIndex/skinWeight and morphAttributes — models normalize (and weld) through `fit-bounds`' own `regen` flag, which is also why a displaced model on an EXPORTED page stays unwelded. **WHICH groups merge is the correctness of the thing**: a group welds when its members could displace APART — normals differ, or UVs differ AND the shader reads `uv()`. MEASURED against r184: a-sphere(36,18) has 19 coincident groups with ZERO differing normals and 19 differing UVs (largest a 37-vertex POLE FAN), 64x64 gives 65/0/65, a-box gives 8/8. So a position-driven shader must NOT weld a sphere (every member moves identically; welding keeps one representative uv and smears the whole polar cap — a bug the old always-weld component shipped), while a uv-driven one MUST (measured ~0.2 world units of separation on a radius-1 sphere, so the surface cracks). **The author's choice travels as `mergeVertices: false`** in the module's return object — opt-OUT only, `=== false` (the settings menu writes a literal `true` on re-tick, so a truthiness gate would add the key to a default node), which is what keeps every already-exported module and all 23 built-in snapshots byte-identical. It is the first key there that is NOT a THREE.Material property: the loader reads it off the return object rather than copying it onto the material, so it is inert on 0.4/0.5. `scriptToTSL` strips and recovers it, so the setting now survives an export→import round trip. `src/shaderloaderWeld.test.ts` runs the REAL vendored file against REAL three.
- **Per-mesh materials (ONE Output node, N materials → `parts` → shaderloader 0.6)**: a dropped multi-mesh glTF can have a DIFFERENT shader per sub-mesh. There is exactly ONE Output node; per-mesh shading lives INSIDE it as stacked material sections (`utils/outputMaterials.ts`). **A material names a LIST of meshes, and material 0 is the DEFAULT while its list is empty** — it is the node's own `values`/`exposedPorts`/`materialSettings`, and untargeted it shades every mesh no other material claims, i.e. the whole-model behaviour that predates the feature. The list is `meshTargets: string[]` (on the node for material 0, on the entry for the rest) and is read ONLY through `materialTargetNames` — which also still reads the older single `meshTarget: { name }`, never written any more, so a graph, a saved group or a one-Output-per-mesh session from before the list keeps what it shaded (that field meant exactly what a one-entry list means). `materialTargetName` survives as "the first one", for the surfaces that show one name and abbreviate the rest; "is this the default" is `materialTargetNames(m).length === 0` and never `materialTargetName(m) === null` plus an assumption. Only ADDED materials ride `data.materials`, so **a document with no added materials carries no new key and emits byte-identically** — that is what keeps all 23 built-in snapshots and every already-exported shader valid, and the whole feature is gated on it. (An earlier design gave each targeted mesh its OWN Output node; `foldExtraOutputs` folds such a graph — a working session, a shared file, or a hand-edited one — back into the single node on every restore path, re-pointing the edges that fed the extras. Without it those Outputs sit inert and their wiring is silently lost.) Rules that are load-bearing. (1) **Handles are namespaced, and material 0's are BARE** (`channelHandle`/`parseChannelHandle`): material 0 keeps `color`/`emissive`/… — every saved edge, every `generateEdgeId` string and every `targetHandle === 'color'` reader was authored against them — while material N uses `m<n>:<channel>`. Collapse the two and one material silently feeds another. Anything that drops edges BY PORT must pass the handle, not the bare id: `toggleExposedPort` takes an explicit `handleId` for exactly this, since hiding a channel on material 2 would otherwise delete the DEFAULT's wire. (2) **The UI CAN author a parts-only module** — by targeting material 0, or by leaving it unwired — and that is a supported shape, not a hazard. An empty (or targeted) default emits `parts` ALONE (loader 0.6 then leaves unclaimed meshes on their AUTHORED glTF materials, the KHR_materials_variants fallback shape): the red `vec3(1, 0, 0)` sentinel is deliberately NOT emitted beside parts, because it means "nothing is wired yet" for a shader with nothing else to say, and once a mesh material exists the user HAS said something — painting every other mesh red would throw the model's own materials away to announce a state visible on the node. It also round-trips: parts-only parses to an empty material 0 and re-emits parts-only. **That last rule is why a TARGETED material 0 is normalized away by an Apply**: a `parts` map has nowhere to record which material was the default, so `{ parts: { Body } }` is the same text whether material 0 named Body or sat empty beside a Body material — the parse resolves it the historical way, and the node grows the empty default section back. Nothing is lost (every wire is re-created from the code, the module re-emits byte-identically, and the shape is stable from then on), and the alternative — giving the first part to material 0 — would collapse the far more common "unwired default + one mesh material" instead. `outputPartsFixes.test.ts` pins both halves. A lone unwired Output with NO materials still emits `return vec3(1, 0, 0);` exactly as it always has. **An emitted part with NO channels is dropped by `buildShaderModule`** (`props.length > 0`), so a mesh material you have added but not yet wired changes nothing in the preview — pre-existing, and deliberate: the alternative is that one press of + Add output throws every other mesh back onto its authored material to announce an empty section. (3) **Emission and the parse must land in ONE commit.** Emission alone is byte-stable, node-count-stable and `errors: []` while silently deleting every secondary binding on the first code-panel Apply — no pre-existing round-trip invariant can fail on it, so `outputParts.test.ts` asserts parts SURVIVE an Apply and that the graph does not grow across TWO successive ones. A targeted material with nothing wired still emits its `{}` entry, or the parse cannot re-create it and the material plus its edges vanish. (4) **A part's discard is a KEY, never a statement** — a `Discard()` statement belongs to the module, so it is the DEFAULT material's cutout and lands on material 0's bare `discard` handle — and `buildShaderModule` gives each part its own INDEXED `__partPixel<n>` wrapper (indexed because a mesh name is not an identifier: `Body.001` and `my mesh` are both legal). That builder also maps every part's inner keys through the SAME `CHANNEL_TO_PROP` table as the default; re-emitting them verbatim hands the loader keys it does not know and silently renders the default material on every mesh — right-looking source, wrong picture, no error. A part's wrapper falls back to the part's own **emissive** before white, exactly as the default path's `discardColor` does and for the same reason (the loader copies emissiveNode→colorNode only when colorNode is undefined, and a wrapper always defines it): falling straight to white made the ordinary glow-cutout wiring — Emissive + Discard, no Colour — render correctly on the default and wash out to lit white on a targeted material. (5) **Mesh names are a REJECT-list, not an ASCII whitelist** (`isUsableMeshName`): three's `PropertyBinding.sanitizeNodeName` strips only `[ ] . : /` and maps whitespace to `_`, so non-ASCII SURVIVES — measured, `Ķermenis_āda 2` → `Ķermenis_āda_2`. A `[A-Za-z0-9_.-]` whitelist would make every Latvian/CJK mesh permanently untargetable in a Latvian-first app while admitting `Body.001`, which the glTF loader can never produce. Refused instead: empty, control chars/U+2028-9, over-length, and `__proto__` — and every map keyed by a mesh name is a `Map` or null-prototype object, because a plain-object lookup resolves `toString`/`constructor` to FUNCTIONS and assigns one as `node.material` (measured in a browser). Names are validated on every restore path (`loadGraph`, `applyProjectToStore`, `loadSavedGroups` — a saved group may contain the Output — plus a re-run over the COMBINED list in `instantiateSavedGroup`, since a group's claim is only checkable against the graph it lands in) AND again at emission, the gate that decides what becomes code. **`parts` is keyed by MESH, so a material naming N meshes emits N entries carrying the same expressions** — the channels are resolved ONCE per material, not once per mesh. `codeToGraph` merges byte-identical part bodies back into one material naming several meshes, which is what makes the feature survive its own round trip (without it a three-mesh material split into three sections on the first Apply, each with a copy of the wiring). EMPTY bodies are deliberately NOT merged: they carry nothing to match on, and two freshly added mesh materials — the state right before you wire them differently — are exactly the pair that would be collapsed. The flip side is inherent: two SEPARATE materials that happen to be wired identically merge into one, which renders the same and shows one section instead of two. **A mesh belongs to exactly ONE material: ticking it MOVES it** (`assignMeshTargets`, the single writer behind the picker). No row is ever disabled — locking them was what made swapping two materials' meshes impossible short of deleting one and rebuilding its wiring — and moving makes the swap the ordinary two clicks. So the UI can no longer author a duplicate at all; one still ARRIVES from a hand-edited or foreign file, where emission resolves it first-claim-wins per MESH (a partial overlap costs only the shared mesh, not the whole material) and the node marks the shadowed section. **A material stripped of its LAST mesh is KEPT, empty**, and reads "No mesh" in the missing-mesh colour: that is the state a swap of two single-mesh materials must pass through, and both alternatives are worse — deleting it destroys a section and its wiring on a checkbox tick, and refusing the tick makes the checkbox silently do nothing. Empty means "shades nothing", NOT a second default (only material 0's empty list means "everything else"); it emits no `parts` entry, which also means an Apply DROPS it, since there is no key in the code to carry it — visible on the node beforehand, unlike the states this file's other normalizations describe. `sanitizeOutputMaterials` and `foldExtraOutputs` therefore keep both an empty material and a duplicate claim, so a live graph and a reloaded one still emit the same module. `MAX_PARTS` is `MAX_ADDED_MATERIALS + 1` for the same reason the sanitizer's cap is: a targeted material 0 is one more part, and an Apply turns it into one more ADDED material, so a bound at `MAX_ADDED_MATERIALS` in emission, the parse or the sanitizer would each delete a material the UI still draws. **The emitted key is `JSON.stringify` plus TWO escapes, and neither is optional**: the star-slash, because the exported `.js` carries the project block as a block comment; and `<` → `\u003C`, because the generated module is inlined into an HTML `<script>` by `tslToPreviewHTML`, and the tokenizer ends that element at the first `</script` in the raw text no matter that it sits inside a JS string literal. A mesh name is attacker-chosen and `isUsableMeshName` admits `<` and `/` by design, so the one-escape version let a name spelling `x</script><svg onload=…>` close the script and run as live markup — contained in the sandboxed preview by its opaque origin, but the XR popup is a TOP-LEVEL document at the app's REAL origin (verified in Chromium: `executed=true` before, no injected element after). `tslToPreviewHTML` escapes the whole embedded module the same way — a deliberate second copy, because the sink covers every OTHER string reaching that document while the source-side escape covers the key wherever else it is written; `outputPartsFixes.test.ts` pins each half independently. Both escapes preserve the string's VALUE, so the loader's exact-name dispatch is untouched. The parts SPLITTER may not use `indexOf(':')` — a mesh name can contain a colon (OBJ names skip three's sanitizer, so `g Char:Body` really lands as `Char:Body`), and splitting at the first one cut inside the JSON key and dropped the part silently, with the mesh falling back to the default material and NO ⚠, because the name IS in the inventory. It also accepts an UNQUOTED key, since the code panel is a real editing surface and `parts: { Glass: {…} }` is valid JS the parse already takes. (6) **The inventory is session-only and NEVER persisted.** `previewMeshInventory` holds what the SANDBOX reported (`fs:model-meshes`, keyed `custom:<id>` so a report from a torn-down document is identifiably stale) — the trusted side may not parse model bytes, and sub-mesh names are not knowable from the file anyway since GLTFLoader rewrites and de-dupes them. Portalled for the reason every other menu here is — a list inside the node would scale with the canvas zoom, paint under the nodes below it, and grow the node's own box while open, moving every socket beneath it mid-gesture. The CLOSED control shows the FIRST mesh plus an ellipsis (`.mesh-picker__more`, a SEPARATE span so the label's own `text-overflow` clip cannot eat the "there are more" signal exactly when a long name makes it matter), and it says "All meshes" where the list row says "All meshes (default)" — at 104px the longer string clipped to "All meshes (…", which reads as a cut-off NAME rather than as the default state. - **Canvas navigation — the ONE model, by input device.** Everything below is an implementation detail of these four sentences; if a change makes one of them false on any platform, the change is wrong.
  - **Mouse (macOS and Windows alike): the WHEEL ZOOMS, the MIDDLE BUTTON PANS.** Wheel-to-zoom is React Flow's `zoomOnScroll`, which the custom wheel handler falls through to (see the next bullet for how a mouse wheel is told from a trackpad); middle-drag is `panOnDrag={DESKTOP_PAN_ON_DRAG}` = `[1, 2]`, i.e. middle AND right button — right is included because it costs nothing and some users reach for it, while LEFT stays free for marquee selection and node dragging.
  - **iPad and touchscreen: TWO FINGERS PAN, PINCH ZOOMS.** There are no wheel events on a real touch screen, so the gesture is re-created from raw pointers by the touch-nav effect: centroid drag = pan, finger distance = pinch-zoom anchored to the pinch centre. Unambiguous, because the raw pointers say how many fingers are down.
  - **Trackpad: the user SAYS so — `trackpadScroll`, right-click the toolbar → "Trackpad scrolling".** With it on, a two-finger vertical swipe pans (pinch still zooms, which is the trackpad's native zoom anyway); with it off, the mouse model above applies. Two-finger HORIZONTAL pans in both modes — `deltaX` on its own is unambiguous whatever the device — and pinch / `Ctrl`/`Cmd`+wheel pass straight through to React Flow in both, so **zoom is never unreachable**.
  - **Why a setting and not a device sniff.** A trackpad's two-finger swipe and a mouse's wheel notch arrive as the SAME event. A heuristic was built (`wheelKind.ts`: pixel-vs-line delta mode, then the legacy `wheelDelta` detent of 120), shipped, and REVERTED, because it read a real macOS mouse as a trackpad and took that user's zoom away — almost certainly because macOS accelerates mouse wheels too, so `wheelDelta` is rarely a clean multiple of 120, and the per-gesture latch let one such event poison a whole scroll. **Two properties make the class unsafe to guess at**: the failure is ASYMMETRIC (misreading a trackpad costs a pan you repeat; misreading a mouse removes a primary control), and it is UNTESTABLE from here — CDP's `Input.dispatchMouseEvent` hardcodes `wheelDeltaY` to ±120 whatever delta you request, and a constructed `WheelEvent` leaves it at 0, so neither reproduces the hardware the rule must be right about. `trackpadScroll.test.ts` fails on `wheelDeltaY`/`wheelDeltaX`/`deltaMode` reappearing in NodeEditor: do not reintroduce a sniff without ground truth measured on a real mouse AND a real trackpad. The flag DEFAULTS to the mouse model — historical behaviour, and a wrong default must cost the recoverable thing. It is read with `getState()` INSIDE the wheel handler, never closed over: the listener is bound once, so a captured value would freeze the setting at mount and the toggle would read as doing nothing until a reload.
  - The toolbar's right-click popup (`.toolbar__prefs-popover`) is that toggle's home and the natural place for any later app-wide input preference. It is ONE line per setting — the explanation is the row's `title`, raised by the app-wide `TooltipLayer`, the same "a list you scan, the detail on hover" rule the Add-node menu follows. The title sits on the LABEL, which wraps both the box and its text, so either half raises it (TooltipLayer resolves its host with `closest('[title]')`). It refuses to open on a text input — a field's context menu is the one place users genuinely rely on the OS one — and on the EXPORT / Download-app / ☰ controls, which own right-click for their own popovers; EXPORT's handler `preventDefault`s but does NOT `stopPropagation`, so without that guard both popovers opened at once.
  - **One finger on touch never navigates** — it drags nodes and edges, draws, and marquee-selects, which is why `panOnDrag` and `selectionOnDrag` are both OFF on coarse pointers (`isCoarsePointer`). With React Flow's drag-to-pan on, the FIRST finger of a two-finger pan lands on the pane and opens a rubber band instead, so an empty-canvas two-finger pan came out as a selection box; dropping both leaves the touch-nav effect unopposed. The desktop model is untouched by any of this.
  - **Escape hatches that must keep working**: `Ctrl`/`Cmd`+wheel zooms on every device, and double-tap-and-drag pans on a trackpad, where the natural "grab" gesture is tap-tap-hold-drag and `panOnDrag={[1, 2]}` gives it no button.

- **A canvas gesture takes the preview iframe out of hit-testing** (`:root.fs-canvas-busy .shader-preview__iframe { pointer-events: none }`, armed by NodeEditor's `setCanvasBusy`). The preview is a SANDBOXED, opaque-origin document, so the instant the pointer crosses into it the parent stops receiving mouse events at all — including the `mouseup` d3-zoom listens for on the window. A middle-button pan dragged over the preview therefore **never ended**: release the button there and the canvas kept panning, because as far as the parent knew the button was still down (reproduced, and re-reproduced as a negative control by disabling just this rule). Node drags and connection drags cross the same boundary and hang the same way, so all three bracket it: `onMoveStart`/`onMoveEnd`, `onNodeDragStart`/`onNodeDragStop`, `onConnectStart`/`onConnectEnd`. The counter is REFCOUNTED because those overlap — React Flow fires `onMoveStart` for the pan under a selection drag — and a boolean would let whichever ended first re-arm the iframe under the one still running. Each release sits ABOVE the early returns in its handler (the drag-chrome rule), and NodeEditor's unmount clears the class outright: a stranded flag leaves the 3D view permanently unclickable. At rest the iframe keeps every event, so orbiting is untouched.

- **Podest unattended / pedestal mode** (`public/podest.html`): the viewer is meant to run for WEEKS with nobody touching it, which is a different problem from "a page that works". The presentation layer is the ⛶/⤡ fullscreen button (bottom-right) plus an optional top-centre title (auto-derived from the dropped file name, `_`→space, click it to edit text + colour; `textContent` only). **Presentation mode is deliberately WIDER than the Fullscreen API**: fullscreen needs a user gesture, and an unattended pedestal has nobody to give one after a browser auto-update — it would come back windowed with the panel over the artwork and, far worse, no wake lock, so the display blanks at the OS idle timeout and stays black for the week. Everything that must survive the reload asks `presenting()`, never `fsElement()` — **including the release-race guard inside `requestWakeLock`**, which gated on fullscreen would release every lock the instant its promise resolved and silently undo the whole thing. Behind that sit five long-run guards, each fixing something that actually breaks on that timescale: (1) **the stage iframe is disposable** — `applyStateToStage()` replays background/spin/geometry/shader on every `fs:ready`, so the pending queue is DISCARDED rather than flushed (replaying both would recompile the shader twice) and any restart is invisible; (2) **`time` is folded back every ~4.4 h** — three's `time` is a float32 accumulating seconds since boot, so its resolution decays to 7.8 ms after a day, 62 ms after a week and 250 ms after a month (a slideshow); the stage takes `renderer._nodes.nodeFrame.time %= TIME_WRAP` where `TIME_WRAP` is an exact multiple of 2π (2π × 2520 ≈ 15833 s), so `sin(time)`/`cos(time)` cross the fold with NO visible jump and the quantum never exceeds ~1 ms (a shader's own `time.mul(20)` multiplies it) — modulo not zeroing, so the fold stays 2π-aligned however far behind the beat has fallen; if that private path ever disappears the beat reports `wrapNeeded` (rebasing as it fires, so it can't latch) and the parent restarts the stage instead. The stage also rebases `nodeFrame.lastTime` on `visibilitychange`→visible, or the first frame after an overnight sleep would dump the whole hidden gap into `time` in one step; (3) **device loss is terminal and silent** — the stage wraps `renderer.onDeviceLost` (keeping three's own handler) AND hooks the raw `backend.device.lost` promise, because three returns early on `reason === 'destroyed'` and would never call the callback, plus a `webglcontextlost` listener; all report `fs:stage-dead`, and a 5 s `fs:beat` carrying the cumulative `info.render.calls` lets the parent catch a stall with no throw at all (best-effort: it proves the loop ran, not that pixels landed); restarts are floored at 30 s apart and after 6 in a row back off to one retry every 10 min — never a permanent give-up, since a transient driver fault must not end the exhibit (watchdog is suspended while the document is hidden — a frozen counter there is normal); (4) **the last drop is mirrored to IndexedDB** (`fs-podest`/`session`, throw-safe, shader ≤24 MB + model ≤64 MB) and replayed at boot, because a browser auto-update or power blip otherwise leaves a grey sphere — the record carries the tuned **uniform values** too (losing the exhibitor's tuning shows the wrong artwork), a drop that lands first always wins, and a user-typed title outranks the replayed one; (5) **the screen wake lock** is requested at boot, on entering presentation mode, on `visibilitychange`, and again on every 5 s watchdog tick — the platform can drop a lock on its own and a UA may refuse it until it can grant it, so the only robust pattern is to keep asking (it early-returns when a lock is already held). Also: the error relay is rate-limited IN the sandbox (identical repeats/minute + 20/minute cap) since a per-frame `console.error` would otherwise postMessage forever, banners self-dismiss after 20 s, and 90 s of idle in fullscreen returns the camera to the framing pinned by `fs:save-view` at entry (a visitor's spin must not outlive them). **Checked and deliberately NOT fixed**: the bundle's anime.js calls the undeclared `activeInstance[i].pause()` on visibilitychange, but A-Frame builds its instances with `autoplay:false` and ticks them by hand, so anime's active list is always empty and that line never runs (verified in a browser).

- **The Perlin family is SIGNED, and the four signed types carry a per-node range flag.** `perlin`/`perlinVec3` (`mx_noise_*`) and `fbm`/`fbmVec3` (`mx_fractal_noise_*`, which sums Perlin octaves) emit MaterialX's raw ~[-1,1]; `cellNoise` and the three `voronoi` types are already [0,1] and must NEVER carry the flag — a remap there would halve a range that was already correct. That signedness surprises people in two specific ways: `round(noise)` returns −1/0/+1 rather than 0/1, and the Output node's Discard culls on ANY non-zero so BOTH tails cull. Nodes the user ADDS now therefore default to a 0–1 remap. The whole scope rule is one storage decision: **the flag lives in `values.signed` as 0/1 and an ABSENT key means SIGNED**, so every graph saved before this, every noise member of the built-in textures/presets, and every re-imported `.js` keep emitting byte-identically (pinned by `graphToCode.test.ts`'s junk-value sweep and `registry/noiseRangeCorpus.test.ts`). `utils/noiseRange.ts` is the ONE coercion point (`SIGNED_NOISE_TYPES` + `isUnsignedNoise`), and its read is an EXACT `=== 0 || === '0'` — deliberately NOT `Number(v) < 0.5`, which maps `null`/`false`/`''`/`[]`/`0.4` all to "unsigned", and `null` is what the `fs:graph` autosave turns a non-finite into, so a coercing read would change a shader's appearance across a reload. The flag is deliberately NOT in `def.defaultValues`: on a noise node that map is the SOCKET list (`PreviewNode` builds a param handle per key), so a key there becomes a wireable dead socket with an "expose as input socket" checkbox beside it, and flips `isAtDefaultValues` to false on every legacy node — which is also why the "booleans get no expose toggle" rule is structural here rather than a special case. `resetNodeValues`' `PRESERVED_KEYS` carries `signed` so a Reset restores pos/scale without silently flipping the range back. Emission wraps the FINISHED call (`mx_noise_float(pos.mul(4)).mul(0.5).add(0.5)` — method chain, no new import), never `posExpr`, and gates on the def TYPE as well as the stored value: a tampered `.fastshader` putting `signed:0` on a voronoi node would otherwise emit a remap `codeToGraph` is required to refuse, and the round trip would grow junk nodes on every Apply. `matchNoiseUnsignedRemap` collapses that exact shape back into ONE node and is MANDATORY, not tidiness — `useSyncEngine`'s `mergeMatch` carries no `data.values` across a resync, so without it every code-panel Apply would reset the node to signed AND grow a Multiply/Add pair. The matcher is narrow on purpose: bare-Identifier callee (keeps it off dataRange's symlog `.mul(0.5).add(0.5)` tail), exactly ONE noise argument (`mx_noise_float(p, 2)` would otherwise collapse with the amplitude silently dropped), and an inline call receiver never a variable (a variable can have several consumers, so one flag couldn't mean "raw here, remapped there"). Unlike the Time-speed collapse it is SEMANTICS-PRESERVING, so it can only change how many nodes a shader is drawn with, never what it renders. **fBm is only APPROXIMATELY 0–1** — three's `mx_fractal_noise_float` sums 3 octaves from amplitude 1.0, so the remap lands ≈[-0.375, 1.375]; deliberately NOT clamped, because a clamp is a third chain link that breaks round-trip stability and flat-tops the peaks (wire a real Clamp node if you want one). A signed node shows a `±1` chip on its card (`ClockNode`'s `×speed` precedent — the SURPRISING state is the one marked). `cpuEvaluator` follows the flag for both the value and the range: that block used to assert [0,1] for the whole noise category, which is exactly why the signed GPU output was a surprise — the editor's own edge cards had been reporting 0…1 for a shader emitting −1…1. `edgeValueLabel` prefers the inferred RANGE over the probe value for anything with a noise node upstream (see the sampled-field bullet below), because the fixed sample UV lands on an integer lattice where Perlin is exactly 0, which on a card reads as a dead wire. The CPU thumbnail deliberately still renders 0–1 for legibility (raw signed values would clamp half of every legacy card to black, which is ambiguous as a mode signal in a way the chip is not).
- **Scientific colormaps (`colormap` node + `colormaps.ts`)**: the catalogue is the perceptually uniform / colour-vision-safe families the scivis community actually uses (viridis · magma · inferno · plasma · cividis · batlow · lajolla · L*-linear grey; cool-warm · vik · roma; two CET isoluminant maps; turbo as the one rainbow option), stored as sRGB hex ANCHORS in the GENERATED `colormapData.ts` and reconstructed piecewise-linearly. Three things are load-bearing. (1) **The LUT is baked in LINEAR light.** The catalogue is sRGB-encoded — that is what matplotlib/Crameri/CET publish — but the texture carries no colour-space tag and the renderer's working space is linear, so `buildColormapLut` converts. Interpolating sRGB values as if they were linear is the exact error that destroys the uniformity these maps exist to provide, and it is invisible: the picture merely looks "a bit washed". The SAME bug was live in Stripes/Data Viz, whose ramp endpoints went out as `vec3(hex/255, …)` while a Color node's identical hex went out as `color(0x…)` (which THREE.Color decodes); both now emit `color(0x…)`, so one hex means one colour app-wide. (2) **The half-texel inset is not cosmetic**: `t → t·(N−1)/N + 0.5/N` is what puts t=0 and t=1 on the ramp's true endpoints, and the endpoints are what people recognise a map by (`#440154`…`#fde725` IS viridis). (3) **The isoluminant entries are there for the 3D case specifically.** On a lit, spinning mesh a strong lightness ramp competes with shape-from-shading and flattens the geometry; an isoluminant map leaves luminance to the lighting and carries value in hue alone (Kindlmann et al. 2002; Kovesi, arXiv:1509.03700). It buys that by giving up fidelity — vision resolves luminance far better than hue — so both families ship and the picker labels the trade-off rather than choosing for the user. `colormaps.test.ts` pins the published endpoints AND the properties (sequential = monotone lightness, diverging = lightest centre with equally dark arms, isoluminant = flat lightness), so a regenerated table that quietly stops being perceptual fails.
- **`toHsl` (RGB to HSL) exposes h/s/l as SWIZZLES of one emitted call, and `out` stays `outputs[0]`.** The node has four outputs: the vec3 `out` plus float `h`/`s`/`l`. Codegen emits ONE `const toHsl1 = toHsl(rgb);` and `resolveEdgeRef` maps h/s/l → `.x/.y/.z` of that variable — never three calls, which would inline the helper Fn three times (~2.5× the GLSL, measured through GLSLNodeBuilder) and make `complexity.json`'s flat `"toHsl": 15` a lie. `codeToGraph.resolveMemberExpr` carries the INVERSE map so `toHsl1.x` parses back to the `h` handle: without it every member expression mints a **Split node**, so each Apply would splice one between toHsl and its consumers and the graph would grow without bound — while the code text and the rendered picture stayed correct, which is why the test asserts a zero split-node count rather than relying on byte-equality. `TOHSL_HANDLE_TO_COMPONENT`/`TOHSL_COMPONENT_TO_HANDLE` (graphToCode) are a drift pair — swapping one direction silently exchanges S and L across a round trip. **`out` is deliberately NOT replaced by the three sockets**: it is the defensive default the codebase assumes everywhere (`?? 'out'`, `outputs.find(id === 'out') ?? outputs[0]`, the designer's literal `sockets['out']` key, `tryInsertOnEdge`'s `def.outputs[0]`), and a removed handle has no migration path — `applyProjectToStore` runs none of `loadGraph`'s migrations and codeToGraph re-creates `'out'` on every Apply, so a shared `.js` would carry a dead handle forever. React Flow renders such an edge as NOTHING while keeping it in the store and still emitting its code: it fails silently, with the picture intact. h/s/l are `float` (not `any`) so the Output-channel scalar→vec3 widening fires.
- **Edge VALUES are read per SOURCE SOCKET, not per node** (`cpuEvaluator`: `handleSlice` + `evaluateEdgeSource`/`evaluateEdgeRange`/`getEdgeOutputShape`). `evaluate` stays keyed by node id and returns the whole vector; the socket is applied at the CONSUMER. That split is load-bearing: `evaluate`/`computeRange` write a null sentinel under the node id BEFORE recursing (their cycle guards), so a per-handle cache key would give a cycle re-entering the same node through a different socket its own sentinel and it would recurse until the stack blows — reachable from a hand-edited `.fastshader`, since `topologicalSort` only warns. Handle-blindness was harmless until `toHsl` because no node returned different numbers per socket (split/dataNode/dataviz evaluate to null, a mic channel is a uniform 0), so a wrong socket degraded to an honest `…`; with three real values it would print Hue in live blue beside a Saturation wire. `portShapeForHandle` is the ONE per-handle port lookup, shared by codegen's `shapeOfEdgeSource` and the visual layer — necessary even for declared floats, because `computeShape` resolves `outputs.find(id === 'out') ?? outputs[0]` and would report the vec3 width for every socket of a node that has an `out` port (the live Data Viz `value` bug). **Every cheap-string memo key that folds `e.source` must also fold `e.sourceHandle`** (ShaderNode's `edgeKey` + its `bySource` map, Mic/Output/Clock keys, PreviewNode's `inputsKey`, MathPreviewNode's `xKey`, LiveEdgeValue's rAF deps, EdgeInfoCard's effect deps): re-wiring between two sockets of the SAME source leaves source/target/targetHandle identical, so `Object.is` bails and the surface shows the old channel forever. `TypedEdge` must read the handle off the UNWRAPPED edge, never React Flow's `sourceHandleId` prop — `unwrapCollapsedGroupEdges` rewrites the handle too, and a collapsed group's synthetic socket id matches no registry port, so the projection would fall back to the whole vector and draw a plausible, wrong-width ribbon. `preferRange` is decided on the SOURCE NODE before any projection (see the sampled-field bullet), and a noise range is PROJECTED, never re-derived.
- **A SAMPLED FIELD's value is not its range, and that has to survive every operator below it** (`analyticalRange` + `getFieldUpstreamSet` in `cpuEvaluator`, `preferRange` in `edgeValueLabel`). `uv`, `screenUV`, the geometry attributes and the whole noise family vary across the surface, so `evaluate` returns ONE arbitrary sample of them — the uv centre, or the integer lattice where Perlin is exactly 0. `computeRange` special-cases each with an analytical interval, but then took a finite deterministic eval as a degenerate range for everything DOWNSTREAM, which collapsed the whole chain: a `mul` between a `0…1` gradient and a `-1…1` noise reported a flat `0.00` sitting between two inputs that each read as a range, and the same `0` then propagated through clamp, mul and add to the Output. Reported from the canvas as "the value range goes in and comes out 0, although it is visible that it is not just zero". The block comment above that section had always CLAIMED interval arithmetic carried those chains; it never ran, because `evaluate` learned to sample noise on the CPU after the shortcut was written and short-circuited it from then on. **The gate is one predicate used twice**: `analyticalRange(node)` is the single table of field types (returning their bounds), and `getFieldUpstreamSet` seeds a memoized forward BFS from `!== null` — so a field added to the table is a seed by construction and cannot be forgotten. Three consequences. The deterministic shortcut still runs for every field-FREE chain, so constants keep their exact degenerate range (`2 × 5` is `10`, not a widened interval). Interval arithmetic is an over-approximation, so a long chain reports a BOUND rather than the true span (the dependency problem — `x - x` is not 0 to an interval); that is the honest trade against a number that is simply wrong. And the ops that had no interval rule became reachable for the first time, so `exp`/`log2`/`pow`/`mod`/`dot`/`hsl`/`toHsl` gained one and `length`/`distance` lost their flat `[0, Infinity]` — without those, `pow(oneMinus(dot(…)), k)` (all four fresnel presets) would have gone from a wrong number to a bare `…`. MEASURED across all 32 built-ins: 184 of 858 edge labels change, **zero** lose information, and 22 that read `…` now report a real bound. `edgeValueLabel` asks the same set, so the node ROWS and the wire CHIPS agree — they disagreed before, which is what made the defect visible.
- **Every input port needs a registry `defaultValues` entry unless 0 is genuinely its neutral value.** `resolveArguments` (graphToCode) resolves an unwired port as stored value → `def.defaultValues[id]` → `chainIdentity` (chainable only) → the bare string `'0'`. That last fallback is silent and was wrong for six nodes: `clamp(x, 0, 0)` pinned the output to a constant, `remap(x, 0, 0, 0, 0)` divided by zero, `hsl(0, 0, 0)` rendered BLACK beside a card showing red (saturation 0 and lightness 0 each annihilate independently, so wiring a hue ramp — the node's whole purpose — still rendered black), `mix(0, 0, 0)` discarded a wired B, and `log2(0)`/`smoothstep(0, 0, x)` are hard **WGSL/Tint compile errors** that kill the entire module on the WebGPU preview path while GLSL merely degrades to undefined behaviour (which is why the damage looked machine-specific). All six now declare identities that MATCH `cpuEvaluator`'s own per-port fallbacks — the evaluator's numbers were right all along and the registry simply never declared them. Two guards enforce it now: `engine/unwiredDefaults.test.ts` snapshots what every node emits unwired and asserts the RULES (log2's argument is never 0, smoothstep's edges differ, clamp's min ≠ max…), and `registry/builtinByteStability.test.ts` pins the emitted code of all 23 built-in textures/presets, which is the check each of these fixes previously needed by hand. `registryDrift.test.ts` section (b) used to catalogue these as "deliberate divergences" — that framing is what hid the class, so it now asserts registry and evaluator AGREE. Deliberately left at 0: the vec constructors, eight of the nine unary maths, the comparisons, the chainable folds (they use `chainIdentity`), and `length`/`distance`. **`defaultValues` is the SOCKET LIST on PreviewNode/ClockNode/MicNode-rendered nodes** (the 8 noise nodes, `time`, `micNode`) — a key there becomes a wireable dead socket, so never add one for emission purposes. A unary can declare a default through the optional 4th element of the `.map()` tuple (`['log2', 'Log2', '…', { x: 1 }]`) rather than being lifted into its own def — registry ORDER is the add-menu tie-break — but `descriptionSplice.ts`'s `isStringTuple` must keep accepting that arity or the Node Designer silently loses the ability to rename it.
- **`select`'s condition is a TRUTHINESS test, like Output.discard.** three builds it as `bool(cond)` (ConditionalNode), so `0.2` takes the TRUE branch on the GPU; `cpuEvaluator` used `>= 0.5` and therefore showed the OPPOSITE branch for any condition in (0, 0.5) — a window noise sources land in constantly now that the editor remaps them to 0…1. Second instance of the trap already documented for Discard; if a third appears, look for a `>= 0.5` beside a `bool()`.
- **`resolveExposedParam` consults the registry before its hardcoded `?? 1`.** It is the OTHER resolution path (noise `pos`/`scale`, the uv params) and never read `def.defaultValues` at all, so a node whose stored `values` are missing a key emitted `uv(1)` plus a full 1-radian rotation while the evaluator assumed 0. Unreachable from today's creation paths (both `newNodeValues` and codeToGraph seed `values` from defaultValues) — it is hardening for legacy graphs and hand-edited `.fastshader` input, and it matters more the more defs declare defaults.
- **Emit `mix(a, b, t)` as a FUNCTION — never the `a.mix(b, t)` chain.** TSL registers the method as `mixElement = (t, e1, e2) => mix(e1, e2, t)` (three's `MathNode.js`), so **the RECEIVER lands in the FACTOR slot**. `color(lo).mix(color(hi), t)` therefore built `mix(highColour, t, lowColour)` — the low colour used as a per-channel blend factor and the scalar `t` as an endpoint. Verified by dumping the built node (`.mix` wraps its result in a VarNode; unwrap `.node`): the chained form gives `a=#ffd24d, b=SplitNode, c=#1b2a4a`, the function form `a=#1b2a4a, b=#ffd24d, c=SplitNode`. With a dark low end the output sat within ~2% of the high colour across the whole range, so **the Data Stripes / Data Viz ramp was effectively a constant and the low swatch did nothing**; the Stripes and Isolines moiré fades were inverted the same way. All four sites emit the function form now, `dataVizTslContract.test.ts` pins the operand ROLES structurally against the real `three/tsl` (a text assertion cannot catch this — the buggy source looks perfect), and `mix` is imported wherever they emit. **`mix` is NOT the only one** — this line used to claim it was, and that was wrong. Measured against the shipped r184: `a.smoothstep(b, c)` builds `smoothstep(b, c, a)` and `a.step(b)` builds `step(b, a)`, i.e. all THREE displace the receiver, while `a.clamp(b, c)` and `a.pow(b)` really are positional. (Nothing was broken by the error — Isolines' `.smoothstep(float(0.0), hw)` means `smoothstep(0, hw, d)`, which is what it wants — but the guidance was.) `dataVizTslContract.test.ts` now pins the free-vs-method operand roles for all three as executable fact. The safe rule when emitting a named function you have not measured: **write the free-function form**, which is positional for every one of them; that is why `utils/dataRangeFormula.ts`'s emitter never chains a named function at all. Check `addMethodChaining` before assuming any other one is positional.
- **Data Stripes / Data Viz ramp ends are WIREABLE colour sockets** (`RAMP_COLOR_NODES` / `RAMP_COLOR_PORTS` / `effectiveRampDef` in `utils/exposedPorts.ts`). `lowColor`/`highColor` are REAL `def.inputs` (dataType `color`) that KEEP their `defaultValues` entries — the documented micNode trap: a param living only in `defaultValues` can be ticked "expose as input socket" and still render nothing, because ShaderNode builds sockets from `def.inputs`; the retained default is what still draws the inline swatch. They follow the opt-in `exposedPorts` rules, but through the two nodes' BESPOKE settings menus (the generic `NodeSettingsMenu` never opens for them), which mount the shared `menus/RampColorPorts.tsx` — deliberately NOT a copy per menu, and deliberately offering only the ramp ports, since `baseFrequency`/`density` have no `def.inputs` entry and ticking them would author a socket that never renders. `effectiveRampDef` is the ONE filter, shared by ShaderNode and the card replica, so a palette tile cannot advertise a socket a freshly dropped node lacks. Emission goes through `colorRefOf`, the deliberate INVERSE of `scalarRefOf`: a 1-channel source is WIDENED with `vec3()` rather than narrowed with `.x` (three's `MathNode.getInputType` picks the longest operand and pads/truncates silently, so a scalar endpoint would make the whole ramp a scalar with no error, which the Output node then splats into alpha). `resolveExposedParam` is unusable here — its unwired fallback is `Number(raw)` and `Number('#1b2a4a')` is NaN. An unwired node emits the identical `color(0x…)` as before, so every already-exported shader is byte-stable.
- **The dataviz family is emitted by hand and is ONE-WAY through codeToGraph** (`stripes`, `dataviz`, `colormap`, `dataRange`, `isolines` — same standing as `imageNode`). Each has an empty `tslFunction` and a `CUSTOM_EMISSION_BASENAMES` entry; without that entry the var name falls through to the empty-string base and every instance collides. Two rules they all follow. **Inputs are scalars, so a non-scalar source is coerced with `.x`** (`scalarRefOf` → `shapeOfEdgeSource`): nothing in the editor validates connection types, and `vec2(<vec3>, 0.5)` is a compile error rather than a wrong picture. **Stored numbers are re-emitted through `num(Number(…))`, never `String()`** — `resolveExposedParam` interpolates the stored value verbatim, and these modules are executed by the XR popup at the app's REAL origin, so a value out of a `.fastshader` file must be a number or nothing (`numericParam` is the safe local equivalent).
- **`dataRange` decides its DOMAIN on the CPU, not per fragment** (`planNormalize` in `dataViz.ts`): min/max, robust 2–98%, zero-centred, ±3σ, log, symlog, manual. Choosing a domain is a judgement about the data and needs the whole column, which only code-gen can see — the shader then evaluates a plain affine/log/symlog chain with baked constants. The tracing is deliberately ONE HOP from a Data node's `colN` handle (`columnForHandle`, shared with the settings menus so the numbers on screen are the numbers baked in); anything else means "no statistics" and falls back to the manual domain rather than guessing. Every degenerate case resolves to something that still renders: a flat column widens to a unit domain instead of dividing by zero, and `log` over data touching zero floors the low end instead of taking log of a non-positive. The menu prints the column's statistics for the same reason the Data node's own menu lists per-column ranges: every tone control downstream is in normalized units, so without them the user tunes against numbers they cannot see. **The settings menu is three stacked parts** — *From/To* (the resolved domain, always visible and always editable: an automatic mode is otherwise invisible, since "robust 2–98%" produces a number the user never sees, and editing either box switches to `manual` seeded with the numbers currently on screen, in ONE `updateNodeData` so it is one undo entry). Then *Method*, a `<select>` over the seven modes with the selected one's hint beneath it (they were seven tall stacked buttons; the hints are the feature and survive the collapse). Then *Formula* — see the next bullet.
- **The Data Range formula box is PARSE-THEN-RE-EMIT, and that is the whole design** (`utils/dataRangeFormula.ts`). A user can type an expression like `(v - lo) / (hi - lo)` and the shader evaluates it. That string travels inside a shared `.fastshader`, and the generated module is EXECUTED at the app's real origin by the XR popup and shipped inside every downloaded `.js` — so it must never become code. The `unknown` node's `rawExpression` precedent (`isSafeUnknownExpression`) is validate-**then-pass-through**, which is defensible for a string this app's own parser produced but is the wrong shape for one a human types and shares. So the input is tokenized into a closed AST **carrying no free-form strings at all** — identifiers resolve to `VarId` union members at parse time, function names to `FuncId` — and the emitter writes TSL from its own literal tables. **Emission closure**: every character emitted comes from a finite statically-known alphabet (the `FUNCS` TSL names, the fixed method names, `( ) , .`, `num()`-formatted finite numbers, and the `scalarRefOf` upstream reference); the user's string contributes ZERO characters, so injection is *unrepresentable* rather than filtered, and `dataRangeFormula.test.ts` asserts it mechanically by Babel-parsing the output and checking every identifier against the allowed set. Consequences that are load-bearing: **an absent (or unusable) `values.formula` emits byte-identically to what this node emitted before the feature existed** — the built-in chain is *wrapped*, never edited, and a formula equal to its method's default is not stored — so every saved graph and exported `.js` is unchanged (pinned by a 7-mode × 22-junk-value sweep in `dataVizNodes.test.ts`); the language is ASCII **by explicit code-unit range** and `normalize()` is never called (normalizing would MAP homoglyphs onto real names, manufacturing the vulnerability it looks like it prevents, and `Number('٥') === 5` is why digit detection is never delegated to `Number()`); `VARS`/`FUNCS` are `Map`s, not `Record`s (the `VALID_SWIZZLE`/`TOHSL_*` prototype-chain class — a bare object resolves `constructor`/`__proto__`/`toString` to truthy values); **every rejection falls back to the built-in chain**, so a hostile file still compiles (`dataVizExecution.test.ts` executes both the accepted and the rejected paths); depth/token/node budgets are EXPLICIT counters, so 500 unary minuses — which never pass through `parseExpr` — cannot reach the JS stack; and `mod`/`%`, two-arg `atan`, comparisons and vector constructors are deliberately absent (floor-vs-truncated modulo disagree across backends; scalar-ness is a grammar invariant because the node's output port is declared `float`). `sanitizeDataRangeNodes` at the three store boundaries is a **resource** bound (the string rides ~50 history clones, every autosave and every export), NOT the security control — that lives at the emitter, which every import path reaches by construction. **A refused formula announces itself in the GENERATED CODE**, as a `// Data Range: custom formula ignored (<reason>) — using the <mode> formula.` line beside the fallback chain — the code panel, the A-Frame tab and the downloaded `.js` all carry it, so the recipient of a shared file sees it too. That is deliberately not the canvas's job: half the rejections are `non-finite` (a divisor folding to zero), which depends on the wired column's STATISTICS, and reaching those from a node component costs a whole-graph subscription per node. The canvas chip is therefore scoped to what it can cheaply know and its meaning is exact — `ƒ` = carries a grammar-valid formula, `ƒ!` = carries one the GRAMMAR rejects (wrong everywhere it is opened); it never claims the shader is running the formula. `hasCustomFormula` is the ONE predicate all three surfaces ask, so a whitespace-only string (which `parseFormula` trims to `absent`, meaning the shader is already emitting the plain chain) cannot red-flag a node on one surface and read as normal on another. The chip is NOT `pointer-events: none` — it carries `title={formula}`, and TooltipLayer resolves its host via `closest('[title]')` from `elementFromPoint`, so a non-interactive chip's tooltip silently never fires (the neighbouring `.shader-node__colormap-strip` carried exactly that dead `title` until 2026-09-03; it is gone now — see the socket-label convention). Not mirrored into `NodeVisual`: `formula` is not a `defaultValues` key, so the replica can never be handed one. **And `sanitizeDataRangeNodes` reads `values.formula` by plain property access, NEVER `'formula' in values`** — `getNodeValues` is `data.values ?? {}`, which guards nullish and nothing else, so a tampered `values: 5` arrives as a primitive and `in` THROWS: inside `loadGraph` that throw hits the outer catch, returns null, and the 300 ms autosave then overwrites the user's ENTIRE saved graph with the demo one; on the import path it escapes after `pushHistory` + `setShaderName` have already run, which is the mid-apply failure `extractProjectState`'s shape gate exists to prevent. `sanitizeDataNodes` has the correct shape. (`sanitizeOriginKeys` in `utils/imageNode.ts` still has the `in` form and the same defect — unfixed, separate file.)
- **`isolines` reuses the Stripes AA construction, and the ordering is the whole trick**: the derivative is taken of the CONTINUOUS phase, never of `fract(phase)` — `fract` is discontinuous once per level, so `dFdx(fract(p))` spikes exactly at each contour and draws a spurious line through the one it is meant to smooth. The derivative is floored (`.max(0.00001)`) so a flat region cannot collapse the smoothstep's two edges onto each other, and contours packed tighter than a pixel fade to their average coverage instead of aliasing into moiré. `dataVizTslContract.test.ts` builds these chains against the REAL `three/tsl` — every other test compares generated source to expected source, which cannot catch a method that does not exist (`.sign()`, `.oneMinus()`): that produces perfect-looking source and a blank preview pane.
- **Live microphone (`micNode`)**: the Mic node emits four ORDINARY NUMERIC UNIFORMS — `const mic1_bass = uniform(0);`, one per CONSUMED channel (`level`/`bass`/`mid`/`treble`, the Data node's `usedCols` rule). One-way through codeToGraph (an Apply demotes it to plain `property_float` nodes — pinned as a known shape in `engine/micNode.test.ts`), and its branch must stay BEFORE the generic `inputs.length === 0 && defaultValues` branch, which would emit `(0.8)` from the analyser settings — the same trap the Time node avoids. `micChannelForHandle` is shared by the emitter and `resolveEdgeRef` so a hand-edited handle in a `.fastshader` can never reference an undeclared variable. **The Mic node is its own React Flow component** (`MicNode.tsx`, flow type `mic`), NOT a ShaderNode. Both nodes were compacted 2026-08-22 (mic 80×156 → 68×136 while GAINING the meter; audio 150×202 → 88×158) and the shared arm light went 64px → 40px, which is what had been setting both nodes' height. The arm light's wrapper is likewise a transform-made stacking context at `z-index: 1`, so it out-painted every tooltip reaching over it and the lower outputs' labels were simply clipped away mid-word. The rule is a DESCENDANT selector (the param handles are nested one level deeper, inside MicNode's per-input wrapper, and their tooltips can be covered by the value chip above them) while the positioning pair beside it stays a CHILD selector, governing outputs only — the params keep React Flow's own centring. Any future node that puts a z-indexed transformed element beside handles inherits this same trap. Offsets are px from the BODY, not the card, so a wrapping header cannot drag the sockets with it. Consequences of living off ShaderNode: it is OUT of the Node Designer's designable set (`ndData.designerNodes()` derives exactly the ShaderNode-rendered registry), it has no `customGlyphs` entry, `layoutEngine` needs its fixed footprint, `loadGraph` re-derives `type` for graphs saved while it was still a ShaderNode, and **every extra React Flow surface must REGISTER `mic` in its `nodeTypes`** — `GraphModal` (node-editor.html) didn't, so the mic rendered there as React Flow's DEFAULT node, a bare white box with top/bottom handles; it registers the real MicNode now, safe because the arm light gates on the node being wired and no modal graph wires one. The card is deliberately NARROW (`MIC_W`) — the 64px arm light nearly fills it, because the light IS the node's face and a wide frame around it read as a box with a dot in it rather than a control. **A param carrying an edge shows the VALUE ARRIVING, not the word "wired"**: it reuses ShaderNode's exported `edgeValueLabel` (live value, inferred `min…max` range, or `…` when underivable) through the same two-step selector — subscribe to a cheap string key so a position-only graph notify bails on `Object.is`, then rebuild the map from `getState()`. It renders as PLAIN TEXT with no plate, blue when live, because on a node a fill means "you can edit this" and plain text means "this is derived"; the stored number is dead once an edge overrides it, so offering an editable box would be a lie. `NodePreviewCard` replicates the arm light as an inert `<div>`, never a `<button>` — a palette tile must not become another way to switch the microphone on — and that `<div>` needs the explicit `--inert` class, since a `<div>` can never match `:disabled` and the tile would otherwise show enabled-green beside a grey unwired canvas node. **Capture is parent-side only and gated on a click**: `getUserMedia` is denied to the preview iframe's sandbox-issued opaque origin *below* the Permissions-Policy layer, so `allow="camera *"` would not help and `allow-same-origin` would hand adversarial shader code `fs:graph`/`fs:savedGroups`/the IndexedDB caches. Since a node's presence in a graph IS its execution here (`fs:graph` restores with no gesture), `micCapture.ts` is the ONE `getUserMedia` call site and `micSession.armMic` is the ONE path to it, reachable from exactly TWO real clicks (the node's light and the preview's MicControl) — never from an effect, a message handler, a store subscription, or anything a loaded `.fastshader` can reach. **There is deliberately no persisted grant and no "remember this"**: `projectImport`'s `writeLs` block copies preview prefs straight out of an imported file, so a consent key would be one line of attacker-supplied JSON from being pre-granted; not having the key makes that unreachable. `gain` is an exposed input socket applied SHADER-side as a SEPARATE statement (`const _mic1_bass = mic1_bass.mul(g);`) — never folded into `uniform(0).mul(g)`, which would stop `uniformLineRe` matching and silently drop both the export schema property and the live uniform binding; gain 1 + unwired emits byte-identically to the ungained form. The analyser therefore does NOT apply gain (it would scale twice). `smoothing` is ALSO an exposed socket, but it resolves differently: it sets the AnalyserNode's `smoothingTimeConstant` on the CPU, so ShaderPreview's `micSettingsKey` selector resolves a wired edge with **`evaluateNodeOutput`** (the node-card evaluator) instead of emitting anything — it follows constants/sliders/arithmetic and reads 0 for GPU-only sources, and codegen must stay out of it entirely. **micNode and imageNode are the two nodes that DRAG-REVEAL their hidden param sockets (`revealHidden`) — not keyed off `usesExposedPorts`, since the Output node is in that set and deliberately does not. Without micNode there, its smoothing/gain were unreachable by wire: you had to know to tick them in the settings menu first. Both params are declared as real `def.inputs`, not just `defaultValues` keys** — ShaderNode builds sockets from `def.inputs`, so a param that lives only in `defaultValues` can be ticked "expose as input socket" and still render nothing at all (the noise nodes and Time get away with it only because they render through PreviewNode/ClockNode, which have their own socket handling). They keep their `defaultValues` entries too, so an unexposed param still shows its inline number widget, and ShaderNode filters `def.inputs` down to the exposed set exactly like `imageNode`. Mic uniforms are split out of `uniforms` in ShaderPreview BEFORE anything reads it, which in one move keeps them out of the overlay, out of `handleReset` (which would otherwise write mic-derived values to disk via `usePersistedState`, contradicting "nothing is recorded"), out of the `fs:preview-ready` re-push, and out of "Set as default". The rAF pump posts `fs:uniform` DIRECTLY and must never call `handleUniformChange`/`handleReset`; the meter is written imperatively; and disarming POSTS ZEROS, or the shader freezes on whatever the last captured frame happened to be. Arm/disarm carry a monotonic generation token written synchronously: the permission prompt is non-modal and can sit open for 30s, so mic→cancel→mic leaves two `getUserMedia` calls in flight, and without the token the loser's MediaStream is never stopped (OS indicator lit for the life of the tab). The auto-disarm on "no mic uniforms left" gates on INTENT, not on `captureRef.current` — during the prompt no capture exists yet AND `MicControl` unmounts, so a capture-gated check would let the answer install a live mic with no button anywhere to stop it. Targets come from the GENERATED CODE (avoiding an `s.nodes` subscription) but are GATED on the graph really containing a Mic node: an emitted `const mic1_bass = uniform(0);` is textually identical to a user property that happens to be named `mic1_bass`, so without the gate such a property would vanish from the Uniforms overlay in a graph with no microphone in it. ONE analyser serves the whole graph, so a second Mic node's settings are ignored (deterministically the first in node order). **podest CAN hear** (`public/podest.html`): capture lives in the TOP document — the stage iframe is the same opaque-origin sandbox and could never call `getUserMedia` — and values cross as ordinary `fs:uniform` messages, the same in-place `_propertyUniforms` write the sliders use, so a parent-held capture survives every stage restart (device loss, stall watchdog, time fold). Mic names are split OUT of the reported uniform map **before `onUniforms`**, which in one move keeps them out of the slider list, out of `state.values` and therefore out of the IndexedDB tuning record — reaching `onUniforms` would replay a frozen room-noise level at every boot (value/bounds seeding happens before the row is appended, so filtering later is too late). The arm light is bottom-left, deliberately **NOT** in the `:root.is-present` hide rule: everything else is hidden in presentation mode, but the blinking red light IS the privacy indicator and a pedestal has no visible tab strip. **A drop never arms; a drop always disarms** (both `loadShaderText` and the `fs:uniforms` branch, so a shader that fails to apply cannot leave a live mic driving names from the previous one). **Auto-arm is deliberately NOT implemented**: permission is keyed to ORIGIN, podest shares the editor's, `getUserMedia` needs no transient activation, and podest auto-replays its last drop at boot — so an auto-arm would let a shared `.js` open the microphone silently at every boot for weeks on an unattended machine. An unattended sound-reactive exhibit therefore needs a REMEMBERED-DECISION gate (a flag plus a digest of the exact shader it was granted for), which is a separate design decision, not a gap to quietly fill. The band maths is a hand-written twin of `micAnalysis.ts` (podest is a standalone vanilla page and cannot import the app's modules) — keep the floor/floor band partition in sync. **The XR popup and the LAN bench server are still deaf** (backgrounded rAF throttling; same sandbox with no parent; plain HTTP is not a secure context) — and fixing XR by capturing at the real origin would let an imported `.fastshader` open the mic using a grant given for the user's own shader, which is the one line this must not cross. **The DESKTOP build needs `src-tauri/Info.plist`, which is not optional garnish**: macOS TCC refuses a microphone request outright — no prompt, no grant, just a `NotAllowedError` — when the requesting process's `Info.plist` carries no `NSMicrophoneUsageDescription`, so without that file the Mic node works in every browser and is permanently dead in the `.dmg`. tauri-bundler picks the file up automatically because it sits beside `tauri.conf.json`. Nothing else was blocking it: wry 0.55.1's `webView:requestMediaCapturePermissionForOrigin:` handler grants unconditionally, `tauri://localhost` and `http://tauri.localhost` are both secure contexts, `csp: null` injects no policy, and the capabilities ACL governs IPC commands, not web APIs. Two consequences worth remembering — `tauri dev` runs the bare binary with NO `.app` bundle and therefore no `Info.plist` at all, so the microphone can only ever be tested from a real `tauri build`; and under today's ad-hoc signing TCC identifies the app by cdhash, so a grant will not survive an update until the build is properly signed (and if hardened runtime is ever enabled, `bundle.macOS.entitlements` must additionally grant `com.apple.security.device.audio-input`). Failure wording is shared by the two arm surfaces through `utils/micStatusMessage.ts` for one specific reason: they used to hold byte-identical copies of the switch, which is how the desktop build ended up telling users to fix a permission in an address bar it does not have — `denied` is the one status that branches on `__FS_DESKTOP__`.
- **Audio Input (`audioInput`) — reacting to sound the machine is PLAYING.** The Mic node hears the room; this one hears a media player, a browser tab, or any chosen input. It emits the IDENTICAL shape as micNode — four `uniform(0)` lines, one per CONSUMED channel — through the SAME branches in graphToCode (`isLiveAudioNodeType` guards the alias claim, the emission branch and `resolveEdgeRef`), so everything the mic convention above says about emission, gain-as-a-separate-statement, `uniformLineRe`, one-way `codeToGraph`, and branch ORDER before the generic `defaultValues` branch holds here verbatim. **The one thing that differs is the variable base — `mic` vs `aud` (`MIC_VAR_BASE`/`AUDIO_VAR_BASE` in micAnalysis) — and it is load-bearing**: a graph may hold BOTH nodes, each backed by its own capture, and the preview pump routes every uniform back to its own session by that prefix (`liveAudioVarBaseOf`). Collapse the two bases and the shader still compiles, still renders, and simply reacts to the wrong sound — no error anywhere. `LIVE_AUDIO_NODE_BASES` is a **Map**, not a plain object, because `registryType` arrives from `.fastshader` files (the documented `constructor`/`__proto__` trap). `engine/audioInputNode.test.ts` pins the disjointness. **Two capture APIs behind one dropdown, because no single one covers what users mean by "the audio playing on this machine"** (`utils/audioSource.ts`, pure + tested): `system` = `getDisplayMedia`, `device` = `getUserMedia` with an exact id — and a LOOPBACK driver (BlackHole, VB-Cable, VoiceMeeter) shows up in that same device list, which is how the device path hears system sound where the display path cannot. Measured against shipping browsers: Chromium gets TAB audio on every platform, whole-SYSTEM audio on Windows/ChromeOS and on macOS only with **Chrome 141+ on macOS 14.2+** (Apple exposed no third-party system-audio API before that); **Safari and Firefox implement `getDisplayMedia` and IGNORE the audio constraint entirely** — the share succeeds carrying video only. That is why `no-audio-track` is its own status rather than a failure: the user did nothing wrong, "try again" would just repeat it, and the fix differs (a missed checkbox is retryable; a browser that cannot share audio needs a loopback device). It is also the single likeliest FIRST-RUN outcome, so its wording names both causes. Consequence for the desktop shell: macOS Tauri is WKWebView and gets nothing from the display path, while **Windows Tauri is WebView2 (Chromium) and does** — so the option is never gated on `__FS_DESKTOP__`, only on runtime feature-detection plus the honest `no-audio-track` report. **`getDisplayMedia({ video: false })` REJECTS** — the spec requires a video track — so `systemAudioCapture.ts` asks for video and then never consumes it: `enabled = false`, no sink. It deliberately does NOT `stop()` that track, because a display session hangs off its video track and stopping it can tear the whole share down, taking the audio with it. **Source selection is SESSION-only and never reaches `node.data.values`**, the rule `setMicDeviceId` already states: a `deviceId` is origin-scoped, rotates when site data is cleared, is meaningless in a shared `.fastshader`, and would ride the autosave/undo/embed while adding fingerprinting surface. Keeping only the portable half (`system`) would leave the node half-remembered, which is harder to explain than either consistent answer. **An EMPTY `deviceId` is VALID and means the system default input** (`DEFAULT_DEVICE_SOURCE`) — not a hole in the model. Before the page holds any media permission `enumerateDevices()` returns a placeholder whose `deviceId` is the empty string TOO (not just the label), so without this entry the device half of the picker is unusable until the user grants a permission they can only reach through the picker; MEASURED in Chromium, selecting the only device on offer silently reverted to `system`. `selectableAudioDevices` drops that placeholder so it cannot render as a nameless twin of "Default input". `decodeAudioSource` returns **null** for anything unrecognised rather than falling back — silently resolving junk to `system` would put a screen-share picker in front of the user. **The picker and the level meter live ON the card, and that is the node's whole reason to exist as its own type** (the Mic node's device dropdown is buried in its right-click settings menu, so what it is listening to is invisible until you go looking). This is the codebase's FIRST real `<select>` inside the React Flow viewport — every other on-node non-numeric element is inert display. Three things make it safe: `nodrag` plus `stopPropagation` on pointerdown/click (NodeEditor's `isInteractive()`/`isChrome()` already list `select`, so the custom pan/draw capture was never the problem — React Flow's own drag is), and above all that **choosing a source can never START a capture** — `setAudioSource` only redirects a capture that is already running, so arming stays the button's job and the click remains the whole consent model. `armAudio` has exactly ONE click path (the node's arm light); `systemAudioCapture.ts` is the ONE `getDisplayMedia` call site, the same statement `micCapture.ts` makes for `getUserMedia`. Here the platform helps — `getDisplayMedia` requires transient activation and always shows the browser's own picker — but that is not licence to relax the rule. **The palette tile renders a DISABLED `<select>`, never the live one**: the card's `pointer-events: none` stops the pointer but not the keyboard, so a real picker there would make every tile a tab stop that opens a device list from a static replica. The meter is written IMPERATIVELY from an rAF loop reading `readAudioLevels()` straight off the session — never React state (a canvas node re-rendering 60x/s), and never fed from the preview's pump, so it keeps working while the shader is mid-rebuild. Geometry lives in `nodes/audioGeometry.ts` (canvas node + tile + `layoutEngine` footprint, the micGeometry rule), every CSS placement is scoped to `.audio-node__body` NOT `.audio-node` (the tile has no `.audio-node` ancestor — the exact bug MicNode.css documents), sockets are pinned to `z-index: 2` above the arm light's `1` for the same stacking-context reason, and the `<select>` sets `appearance: none` for a predictable 20px height and therefore has to draw its own caret, or it reads as a text FIELD. **The analyser half is SHARED, not copied**: `audioCaptureCore.ts` owns the AudioContext/AnalyserNode/`readLevels`/teardown that both capture paths use, so the fftSize-realloc rule, the never-connect-to-`destination` rule and the gain-is-applied-in-the-SHADER rule cannot drift between them. It also listens for `ended` on EVERY track (a display session's `ended` may arrive on the video track alone) so "Stop sharing" disarms instead of freezing every band at its last value. **Known limits, deliberate**: podest is DEAF to this node — its `MIC_RE` matches only `mic*`, so `aud*` uniforms stay 0 there, and that is intentional rather than an oversight, since `getDisplayMedia` needs a click plus a share picker and podest's whole point is running unattended for weeks (the standing "a drop never arms" rule); the XR popup and LAN bench server are deaf for the reasons the mic convention already gives; there is NO second control in the preview chrome (the node IS the control surface, unlike the mic's MicControl); and wording lives in `utils/audioStatusMessage.ts`, separate from `micStatusMessage` because the two fail differently enough that one shared switch would have to hedge every sentence.
- **Time node's `speed`**: the Time node's multiplier follows the SAME opt-in `exposedPorts` rules as the noise params — hidden until ticked in Node Settings, drag-revealed dimmed, auto-exposed when an edge lands, and a wired edge overrides the stored number. It lives in `defaultValues`, NOT `def.inputs`, and must stay there: `ensureBareInputNode` refuses to auto-create a node whose def declares registry inputs, so adding one would silently drop the Time node (and its edge) from `sin(time)`. graphToCode emits `time.mul(<literal|var>)` (method chain — no `mul` import, same convention as the noise `scale`); `tryParseTimeSpeed` collapses BOTH forms back into one Time node, wiring the variable form to the `speed` port. The collapse is deliberately narrow — bare `time` receiver, unshadowed, exactly one argument, and a variable that resolves to a real node — so the fixtures' `const t = time; mul(t, x)` idiom stays a genuine Multiply.
- **The Textures strip is OFF by default and unlocked for ONE page load by `…/textures`** (`utils/texturesUnlock.ts` + `public/textures/index.html`). The redirector arms a **sessionStorage** key and hands over to the app, which **CONSUMES** it at module init — that destructive read IS the mechanism, and it is what makes "any reload turns them off again" true without asking the browser a question it cannot answer: a page cannot tell Cmd+Shift+R from Cmd+R (`PerformanceNavigationTiming.type` is `'reload'` for both) and sessionStorage survives either, so the app has to end the unlock itself. Verified in Chromium: `/textures/` → tab present, F5 → gone, the app's own Hard reload → gone, a second tab (sessionStorage is COPIED into a tab opened from another) → locked, and the arm key is already absent from storage by the time the app has painted. Five rules. (1) **Two gate sites, not one.** The tab list is module-scope (`displayCategories` → `BROWSER_TABS` → the `fs:assetTab` validator, which is why a persisted `'texture'` falls back to `'all'` instead of booting into a strip with no tab drawn), but a live SEARCH appends texture cards to the generic strip on EVERY tab — so `filteredTextures` returns `[]` when locked, ABOVE its lazy build, which also means a locked session never pays the ~84 ms texture parse. Gating only the tabs leaves `marble` one keystroke away. (2) **It is an ADD-SURFACE filter, never a registry filter** — the `editorVisibility` rule verbatim. `getBuiltinTextures()` still builds all eight, `instantiateBuiltinTexture` is deliberately ungated, and a saved `.fastshader`, a saved group or a built-in preset holding a texture is untouched (a texture is dropped as a GROUP of ordinary nodes; nothing in a saved graph references a texture id). Folding it into `isTextureHiddenFromEditor` instead fails `editorVisibility.test.ts` outright — the vitest env is `node` with no sessionStorage, so a locked-when-unreadable read makes `('wood')` hidden — and would flip every row's checkbox off on node-editor.html, which must keep seeing everything. (3) **The DESKTOP build is unconditionally unlocked** (`__FS_DESKTOP__ ||`): the shell has no address bar and registers no Reload menu item, so `/textures` is unreachable there and shipping the lock would remove the library from the `.dmg`/`.exe` permanently — the WGSL/GLSL rule that a control vanishing per-platform reads as a regression. (4) The answer is memoised on `globalThis`, not merely module scope, so a vite HMR re-execution doesn't re-read the key it already consumed and silently re-lock mid-session while developing. (5) `PUBLIC_ENTRY_DIRS` in `vite.config.ts` must list the directory or `/textures` is answered in dev by the SPA fallback with the APP's own index.html — HTTP 200, a working editor, no unlock, no error — and the bug gets hunted in the flag reader. Known and accepted: an unrequested reload (a background-tab discard, a dev full-reload) re-locks; one locked boot overwrites a stored `fs:assetTab: 'texture'` with `'all'` for good, because `usePersistedState` writes its validated seed back on mount; and nothing in the app names the entry, by design.

The left/right insets must always be overridden as a PAIR — only `-right` was, so the shared `transform: translateY(-50%)` override (which also strips React Flow's own `translateX(-50%)`) left the speed socket floating ~6px INSIDE the card while the output sat on the edge. `graphToCode` has a dedicated `def.type === 'time'` branch placed BEFORE the generic `inputs.length === 0 && defaultValues` branch (which would emit the invalid `time(1)` — `time` is a uniform node OBJECT, not a callable): `speed === 1`, a missing key, or any non-finite value emits the historical bare `const time1 = time;` BYTE-FOR-BYTE, so no already-exported shader changes; otherwise it emits the method chain `const time1 = time.mul(k);` (no extra import, same convention as the noise `scale` param). `codeToGraph`'s `tryParseTimeSpeed` collapses that shape back — but ONLY when the receiver is the bare `time` identifier, `time` is unshadowed, there is exactly one argument, and it folds to a numeric constant. It deliberately does NOT collapse `mul(time, k)`, `mul(time1, k)` (the human idiom — ~51 occurrences across the `Tests/` corpus, usually two muls sharing one Time node) or a non-literal multiplier (`mul(t, speed)` in builtinTextures/builtinPresets). **`ensureBareInputNode` needs its `def.defaultValues` bail-out to except `time`** — without it, adding defaultValues silently drops the Time node AND its edge from `sin(time)`/`add(pos, time, normal)` with no error. `values.speed` is adversarial at all three read sites (graphToCode, cpuEvaluator, ClockNode): `Number()` then `Number.isFinite() ? … : 1`, never `String()` and never `resolveExposedParam`. ClockNode integrates `dt * speed` into a phase accumulator (never `Date.now() * speed`, which teleports the hand on every scrub frame) with the rAF deps kept `[]`. `complexity.json` keeps `"time": 0` — `nodeCostPoints` can only express value-dependent cost for `chainable` defs, and `node.data.cost` is a creation-time snapshot frozen into saved graphs.
- **Drop-time image conversion is ASKED, not assumed** (`Modals/ImageImportModal`): dropping image(s) opens one dialog per drop — a single line, "Convert image to optimized format?", **Yes** (green) / **No**, plus "Don't ask again" persisting to `fs:imageConvert` (`imageConvertMode: 'ask'|'always'|'never'`). **That preference MUST stay reversible from the UI** — it is offered in the Image node's settings menu ("Optimize on import": Ask each time / Always / Never) and in the "?" panel, and a remembered `never` announces itself on every drop via the one-liner. Without those, ticking the box next to "No" silently pins every future drop with no way back and no signal, which reads exactly like the feature being broken. **No is not Cancel** — the image imports either way, so Escape and the backdrop mean No; the explanation lives in the node's settings menu (Format / Resolution / Size / Original) rather than in a dialog standing between a drag and the canvas. - **What the conversion does (WebP + power of two)**: a dropped image is re-encoded to **WebP as far as the running browser will go** — lossless WebP for sources that must stay exact (PNG, and `.webp` re-drops whose container says VP8L), lossy WebP q0.85 for photographic sources, with a quality ladder (0.85→0.75→0.65) tried before any dimension is thrown away. Support AND losslessness are **probed at runtime** on an 8×8 gradient (`probeEncodeCaps`), never inferred: WebKit silently returns PNG from a WebP request (still true in 2026, and it covers the Tauri WKWebView build, not just Safari), and the HTML spec leaves `quality` UA-defined for WebP, so Chromium's "q=1 means lossless" is an implementation detail. `chooseFormat` is a FALL-THROUGH, not a preference — making the lossless branch absolute would hand every over-budget PNG to the halving retry and land a 2048² screenshot at 256-512px. **Alpha never yields JPEG** on any capability combination (pinned by test). Dimensions are then snapped to a power of two **only where that is nearly free** (`imageCodec.ts`): nearest POT per axis, declined above `POT_MAX_UPSCALE`/`POT_MAX_DOWNSCALE`, skipped entirely for binary-alpha cutouts and low-colour sources (pixel art / UI / masks, which the resample destroys AND inflates). The snap is worth knowing about: **nothing in this stack needs POT** — three r184 has no `makePowerOfTwo`/`textureNeedsPowerOfTwo` path left (that was WebGL1/ES2) and both WebGL2 and WebGPU sample NPOT with RepeatWrapping and full mipmaps — so it is hygiene, which is why it must cost near-nothing and why the resample goes through a **wrapped border** (`POT_WRAP_MARGIN`): plain `drawImage` clamps at the edges, so a seamless tile would come back with a seam on every boundary, in a node whose Repeat setting defaults ON. The pre-snap encode is ALWAYS produced first and kept as the node's "original", and the snap is declined outright when that stash can't be made — a destructive step never ships without its escape hatch. Conversion is automatic at drop with an in-flight ghost at the drop point (transform/opacity only, so the compositor keeps it animating while the encoder blocks) and multi-file drops are **serialized** (N concurrent encoders compounded into one freeze). Honest progress is impossible — `toBlob`/`toDataURL` are single opaque calls with no callback and no cancel.

- **Board drawings**: freehand ink annotations (DrawingLayer + DrawToolbar) are VISUAL-ONLY like notes/waypoints — invisible to graphToCode/cpuEvaluator/the sync engine. - **An import auto-frames the canvas**: importing a shader replaces the nodes but NOT the viewport, so a project whose nodes sit anywhere but where the user is looking lands off-screen and reads as a failed import (an empty canvas). Every import surface funnels through `projectImport.ts`, which dispatches **`fs:graph-imported`** whenever the graph is actually replaced — deliberately NOT `fs:project-imported`, which also fires for a model-only zip where the graph never changed and re-framing would throw away the user's viewport. NodeEditor **ARMS** a fit on that event rather than fitting on it: a project block writes its nodes in the same tick the event fires (React hasn't rendered them), and a bare script has NO graph at all until `useSyncEngine`'s code→graph pass finishes a commit or two later — so the fit runs from the `[nodes]` effect, on the next graph the editor actually renders, behind the same double-rAF measurement guard `startNewShader` uses (`fitView` frames the MEASURED box; unmeasured nodes fit as zero-size points at maxZoom). Two details are load-bearing: the pending rAF is held in a REF torn down only on unmount, never by the effect's own cleanup — the cost pass writes the Output node's new total straight back into `nodes`, so an imported graph re-renders inside the two-frame window and a cleanup-owned rAF would be cancelled by exactly the change proving the import landed — and the arm carries a `IMPORT_FIT_TIMEOUT_MS` disarm, so an import that never yields a graph (parse errors, a byte-identical re-import that the sync engine skips) can't leave a fit primed to hijack a later unrelated edit. (3) **`extractDiscards` scans `maskNonCode(body)`** and slices from the original, so a discard inside a comment or a string is not code: scanning raw text ate the body of `/* Discard(a); */` while injecting a live cutout, and turned `const s = 'Discard(1)';` into `const s = '';` plus an unconditional cull — the mesh vanished because of a string literal. (4) **Only STATEMENT-level discards are lifted**; `const k = Discard(n);` is left verbatim (inert) instead of being sliced into a dangling `const k =` (a SyntaxError that took the module down). (5) **A bare `Discard()` is unconditional and carries NO Fn parameter and NO call argument** — passing the empty condition through emitted `__pixel(, …)`; `scriptToTSL`'s reverse walks the wrapper BODY rather than correlating args to params, or the unconditional form would vanish on Load Script. (6) The wrapper's fallback colour is `channels.color ?? channels.emissive ?? vec3(1,1,1)` and `Discard` is force-imported: the loader copies emissiveNode→colorNode only when colorNode is undefined and the wrapper always defines it, so white washed out an emissive-only shader the moment a discard was added. The graph has ONE discard socket, so `codeToGraph` warns (never silently drops) on a second `Discard()` or an unconditional one.
- **Scalar→vec3 widening on Output channels**: a 1-channel source wired to a vec3-typed channel (`color`, `emissive`, `normal`, `position`) is emitted as `vec3(ref)`, NOT bare. three's `NodeMaterial.setupDiffuseColor` does `vec4(this.colorNode)` and TSL splats a 1-channel node across all FOUR components, so a bare `mx_noise_float(...)` on Color silently became the ALPHA too (`diffuseColor.a = noise`) — the surface flickered/vanished as if Opacity or Discard were wired when neither was. Scalar-ness comes from `getNodeOutputShape` (cpuEvaluator), not the registry port type, so an `any`-typed arithmetic chain is caught as well. codeToGraph MUST mirror this: `unwrapScalarWiden` collapses a single-argument `vec3(<identifier|member>)` in a channel position back to a direct edge — unambiguous because a real Vec3 node always emits three arguments — or the round trip grows a Vec3 node with y/z = 0 and re-emits `vec3(x, 0, 0)`, turning a grey ramp red. Both sides are pinned (`graphToCode.test.ts` + a `roundTrip.test.ts` case). Vec3-shaped sources emit byte-identically to before.
- **Unknown nodes**: unrecognized TSL functions in code→graph parsing create `unknown` nodes that store `functionName` and `rawExpression` in values. These round-trip through graphToCode (emitted verbatim), render as magenta `vec3(1,0,1)` fallback in live preview, and show as orange warnings (not errors) in the code editor. The `unknown` definition lives in `NODE_REGISTRY` but is excluded from `allDefinitions` (hidden from content browser/search)
- **Preview geometries**: five options — `sphere`, `cube`, `plane` (primitives) and `teapot`, `bunny` (OBJ models in `public/models/`). `isObjGeometry()` in `tslToPreviewHTML.ts` is the single source of truth for primitive vs OBJ branching. The inline `fit-bounds` A-Frame component recomputes vertex normals (after merging vertex duplicates so per-vertex displacement doesn't split the surface), auto-detects inverted winding (the bunny is CW), generates spherical UVs from each vertex's direction so `uv()` reads cleanly on OBJ meshes, and rescales so the longest axis = 1.6 to match primitive framing. The source OBJs themselves are **pre-normalized** (bbox center at origin, longest axis exactly 1.6), so the runtime recenter/rescale is a no-op for them and `positionGeometry` ranges are comparable across all five geometries.
- **`fit-bounds` BAKES the normalization into the geometry attributes** (`FIT_BOUNDS_SCRIPT`, pinned by `previewFitBounds.test.ts`), and this is load-bearing rather than stylistic: `positionGeometry` is three's RAW position attribute, so scaling the Object3D — what this used to do — is completely invisible to the shader. A dropped model therefore fed its AUTHORED units to every position-driven preset, texture and noise-node default (all of which are tuned for the ±0.8 the pre-normalized built-in OBJs deliver), which is what shredded Vertex Wave on a 180-unit statue. The bake also has to be MEASURED in the entity's own frame — the old world-space `Box3.setFromObject` included `#preview-entity`'s resting tilt and `#spin-parent`'s live animation, so a model was scaled by its rotated hull (teapot ~19% undersized) and a dropped model's centring depended on the spin phase it happened to load at. Order matters: bake BEFORE `mergeByPosition` so its 1e-4 weld quantization is a fraction of the preview box rather than of authored units. Geometries are CLONED, never mutated (a glTF may reach one BufferGeometry from several nodes with different transforms), every local matrix in the subtree is then flattened to identity, mirrored transforms (negative determinant) get `flipWinding`, and skinned/instanced meshes deliberately fall back to the legacy Object3D path rather than desync their bind matrices. `public/podest.html` carries a hand-minified twin covered by NO sync plugin — `previewFitBounds.test.ts` runs both through the same assertions to catch drift.
- **Environment maps (`env` socket on the Output node) + `metalness`**: an image wired into Environment becomes real IBL — graphToCode emits the TEXTURE, never the sampled vec3 (`env: texture(_imageN_tex)` referencing the image node's module-scope texture var), tslCodeProcessor maps it to `envNode:` and shaderloader 0.5's `nodeProps` now assigns `material.envNode`; three's `EnvironmentNode` auto-wraps a texture-valued envNode in `pmremTexture()` (per-renderer cached prefiltered radiance + irradiance, blur driven by the Roughness channel, reflectivity by the new Metalness channel — the loader always accepted `metalnessNode`, the graph just never emitted one). The image-source emission is GUARDED on `imageAssetFor` (memoized, same call the image branch makes): the invalid-payload fallback declares NO `_tex` var, and referencing it would be a module-killing ReferenceError — that case, and any non-image source, passes through as a plain node ref instead (legal envNode; a Color node = uniform ambient environment), vec3-widened when its shape isn't 3. Unlike image→normal, connecting image→env does NOT flip colorSpace — the map stays sRGB (PMREM decodes it). `OUTPUT_CHANNELS` appends `metalness` at the END so existing return-object key order stays byte-identical; the REGISTRY input order is the separate, user-facing arrangement (Color, Emissive, Roughness, Metalness, Opacity, Discard, Normal, Environment in the Pixel section, Displacement alone in Vertex) which `PIXEL_PORTS` and the ShaderSettingsMenu's `OPTIONAL_OUTPUT_PORTS` mirror — keep all three sequences aligned. Both new sockets are opt-in (not in `OUTPUT_DEFAULT_EXPOSED`), enabled via Shader Settings or auto-exposed when an edge arrives. **The preview's Light dropdown grows an env entry** named after the attached image (`envMapName` string-selector in ShaderPreview — the cheap-string subscription pattern; falls back to the generic "Environment" label for non-image env sources): selecting it applies `LIGHT_PRESETS.env`, an EMPTY rig on purpose, because envNode supplies radiance+irradiance itself and analytic lights on top would double-light; `effLighting` degrades a persisted `'env'` to studio the moment the map is unwired, so a stored pref can never boot a lightless void. Verified headless (Chrome, three r184 WebGL2 fallback — the Safari path): the real generated module lights an unlit sphere with correct angular mapping and roughness blur. Two caveats: PMREM needs a real-sized map (mip count is log2(height)−2, so a tiny test texture renders BLACK — an 8×4 did; real equirects are fine), and the canvas import pipeline is LDR, so no HDR sun intensities. Env cost is invisible to the point system (it is a channel, not a node) — pricing it needs a ShaderCarousel calibration entry.
- **Output node stored channel values (the on-node widgets)**: every exposed channel row carries a value cell — unwired `roughness`/`metalness`/`opacity`/`discard`/`position` render a compact DragNumberInput (shown defaults 1/0/1/0/0; 0-1-clamped except Displacement, which may go negative), unwired `color`/`emissive`/`normal`/`env` render a swatch showing the channel default (color WHITE, emissive/env BLACK, normal the flat tangent-space `#8080ff` — no unset state; every color popover leads with a "Default (none)" entry that CLEARS the stored key — the way a picked normal is re-applied back to default/none) opening `components/inputs/PaletteColorPicker` (the app-wide picker, see its own convention below). A wired channel shows the incoming value instead (`edgeValueLabel`, plain text, blue when live) via the two-step cheap-string selector — built on **`getTargetEdges`, never raw `s.edges`**, or a feeder inside a collapsed group degrades every row to a grey `…` (the group id has no registry def). Values live on `OutputNodeData.values` (**`getNodeValues()` still hard-returns `{}` for output — readers access the field directly**), and every cell shares ONE fixed width (`.output-node__val`, 20px — the compact box's step arrows are hidden at that width; drag-scrub and click-to-edit remain) so the label column stays perfectly vertical ("1" and "0.35" would otherwise render different box widths). The codegen contract, in order of precedence: an ABSENT key emits nothing (byte-stability — every pre-widget graph and builtin emits identically); a WIRED edge always wins; emission is EXPOSURE-GATED (what the node shows is what emits — a tampered file can't emit from a hidden channel, and ShaderSettingsMenu clears a channel's value when hiding it, incl. the auto-managed opacity path); values emit as inline `float(<num>)`/`color(0x<hex>)` (adversarial: Number()+num(), hexLiteral whitelist); a stored DISCARD emits the statement `Discard(float(v));`, a stored env color is a constant ambient envNode, and a stored NORMAL color emits `normalMap(color(0x…))` — DECODED as a normal-map texel ([0,1]→[-1,1] + TBN), never fed raw to normalNode — **zero discard/displacement and the default normal `#8080ff` (the identity texel) are literal no-ops and deliberately emit NOTHING**, so the widget default and an absent key are indistinguishable in code (a non-zero discard is an unconditional truthiness cull — the mesh vanishes, by design). codeToGraph's `matchStoredChannelValue` collapses exactly those inline shapes (and the bare `return color(0x…)` color-only form) back into stored values — identifiers stay real nodes — and `applyStoredOutputValues` seeds exposure for valued channels. Two resync rules in `mergeMatch` keep Apply honest: old exposedPorts union in only the VALUED channels (unioning the parse's whole seeded list resurrected defaults the user explicitly hid), and stored values SHADOWED by a wire are carried from the old node (they can't appear in the code text, so the parse could never legitimately clear them — without the carry, any Apply wiped the value a disconnect is supposed to restore). `scriptToTSL`'s `NODE_PROP_TO_CHANNEL` maps `metalnessNode`/`envNode` back to editor channels (missing entries made Load Script silently drop them). The asset-card mirror renders the real widgets inert (`.node-preview-card__inert` pointer-events wrapper, unset swatch span).
- **The colour picker is app-wide, and lives OUTSIDE the NodeEditor tree** (`components/inputs/PaletteColorPicker.tsx` + the pure `colorPickerModel.ts`; it has no React-Flow dependency, so CostBar / ShaderPreview / Toolbar can import it). It draws the shader's OWN palettes first, `BUILTIN_PALETTES` below them, and two bottom rows of globally-recent colours (`utils/recentColors`, which COLLAPSE when empty — placeholder cells read as a rendering bug). Seven rules are load-bearing. (1) **`history` is a REQUIRED prop with no default** (`'bracket' | 'none'`): `bracket()` opens `beginInteraction`, which snapshots the graph AND clears `future`, so bracketing a PREFERENCE site (canvas bg, draw ink, cost poles, preview bg, a live uniform) would push an undo entry that restores nothing and wipe the user's redo stack on every pick. The gate covers the CLEAR path too — `onClear` used to call `bracket()` directly. (2) **Live-apply and commit are different paths.** A native `<input type="color">` fires ~60 events/s while its wheel is dragged, so `applyLive` calls `onPick` per frame and records NOTHING; `createColorCommitStager` stages the value and one flush — on idle (600 ms, the `useHistoryBracket` window), blur, close, or unmount — records exactly ONE recent. The native `change` event is deliberately not the commit signal: browsers disagree about whether it fires during a drag, so a design keyed to it floods on one engine. A swatch click is neither: `pickSwatch` applies WITHOUT staging, so a palette or recent colour is never recorded. "Recent" is for colours the user MIXED — a palette colour is permanently one click away in the rows above, so recording it spends an MRU slot duplicating something already on screen and evicts a mixed colour that exists nowhere else, and re-recording a RECENT reorders the row under the pointer mid-click. It still flushes first, or a custom colour just dragged to would be dropped by the swatch click that follows it. (3) **Every effect is keyed on `open`** — the popover and its custom input only exist inside the portal, so an effect without it attaches to nothing; the custom input therefore uses React props (React treats `type="color"` as a text-like input, so `onChange` already covers native `input` AND `change`, deduped by its value tracker). (4) **A click inside an IFRAME closes it via window `blur`, not via the outside-pointerdown listener** — such a click never reaches this document, and the 3D preview is an iframe filling most of the right column, so "click elsewhere to dismiss" simply stopped working over the largest target on screen. Focus is the only signal that crosses: the browser focuses the `<iframe>` and blurs this window. Gated on `document.activeElement instanceof HTMLIFrameElement` and read on a macrotask (at blur time it is still the old element), because a bare close-on-blur also fires on an app/tab switch and, on macOS, when the "Custom" row opens the OS colour dialog — where it would kill the picker mid-pick. (5) **Escape `stopPropagation()`s** in its capture-phase listener: `ContextMenu.tsx` closes the whole settings menu on a bubbled Escape and skips only INPUT/TEXTAREA/SELECT/contentEditable — the swatches are `<button>`, so once a picker lives in a context menu a leaked Escape would take the menu with it. (6) **The portal host is RESOLVED, not `document.body`**: ShaderPreview fullscreens its own root and the top layer renders only that subtree, so a body portal would be invisible on exactly the controls kept usable in fullscreen — `pickPortalHost` adopts `fullscreenElement`/`webkitFullscreenElement` when it CONTAINS the anchor, and a `fullscreenchange` closes the popover so it can't be left in a torn-down host. (7) **Placement is measured** (`placePopover` + `useLayoutEffect` + `getBoundingClientRect`, the ContextMenu precedent) — the height is now variable, so the old `+130`/`-134` literals described a layout that no longer exists. Rows are a `grid-template-columns: repeat(5, 20px)`, NOT a flex row: every built-in is exactly 5 colours, which is why a bare `display: flex` never visibly failed, but user palettes run to 64 and spilled straight through the border; the 146px width is derived (5×20 + 4×4 = 116 content + 14 chrome + ~15 for a classic scrollbar) and the popover is `max-height`-bounded and scrolls. **`ColorPickerPopover` is exported separately** — anchor + `open` + `onClose`, no trigger — because the Color node IS the swatch (a 56px circle whose perimeter carries the output socket) and has nowhere to put one; it renders the popover anchored to itself, opened by the same double-click / long-press that used to click a hidden input. The canvas bar's background button does the same for the opposite reason: it is a `.fs-canvas-bar__btn` in a row of bar buttons with a small swatch inside, and a full-bleed colour chip there would break the bar's rhythm. **The rollout is complete and pinned**: `colorPickerHistory.test.ts` carries the reviewed `history` value for EVERY call site together with the writer that justifies it, fails on a picker in a file the table doesn't list, and fails on an `<input type="color">` rendered anywhere but the popover's own "Custom" escape hatch and `PalettesModal` (the palette EDITOR — it authors the very swatches the picker offers, so a picker there would be circular, and its rows run a bespoke draft-then-commit-on-blur model built around the native input's blur). TypeScript already catches a MISSING `history`; only a source pin catches a wrong one. Two consequences for the CSS: every site's size rule is written with TWO classes (`.shader-node__left .shader-node__input-color`, `.context-menu .context-menu__color`, …) because a single class ties with `.palette-swatch` and the winner would fall to whichever stylesheet the bundler emits last; and no site rule may set a `background` — the fill arrives as an inline `background` SHORTHAND, which also resets `background-clip`, so an inset (the preview's backdrop swatch) has to be drawn with an inset `box-shadow` instead. **`NodeVisual` is the one surface that does NOT get the picker**: it is the inert replica behind asset tiles and the node-editor overview, and the cards' `pointer-events: none` stops the pointer but not the keyboard — a real picker there would make every colour row a tab stop that opens a popover from a static replica. - **World normals: `normalWorld`, not `normalLocal`, whenever a normal meets a world-space direction.** The preview nests the mesh under `#preview-entity` (a resting tilt — 45/45/0 on sphere and cube) inside `#spin-parent` (a full 360° turntable animation while playing, restored from persisted `fs:previewRotation` even when paused), so the object→world rotation is essentially never identity. `dot(normalLocal, worldViewDir)` evaluates to `dot(N_world, R·V)`: a correctly-shaped fresnel measured about a view direction rotated by the model, so the rim slides off the silhouette and — past ~78° with edge-glow's `pow(inv,3)*2` — clips to solid glow across the whole model. All four fresnel presets (edge-glow, hologram, force-field, stylized-water) and top-cover use `normalWorld`. **Displacement keeps `normalLocal`** (vertex-wave): object-space position displaced along an object-space normal is correct, and a world normal there would shear the model as it spins. Caveat worth knowing: in the fragment stage `normalWorld` resolves through the material's SHADED normal, so it reflects anything wired into the Output node's Normal channel — desirable for a fresnel, but a coupling `normalLocal` doesn't have.

- **`hsl`/`toHsl` are NOT `three/tsl` exports — graphToCode emits its own branchless helper `Fn` at module scope**, and force-imports the `mul`/`add`/`sub`/`abs`/`mod`/`clamp`/`select`/… that only the helper BODY uses (`HSL_HELPER_LINES`/`TO_HSL_HELPER_LINES`; the import collector explicitly skips these two defs, since importing the node's own name would fail). `codeToGraph`'s visitors run over the WHOLE Program, so it `path.skip()`s a `const hsl|toHsl = Fn(…)` declarator BY NAME — without it the helper's own mul/sub/clamp statements parse back as standalone nodes and every Apply grows the graph. Emitted name and skip name are a DRIFT PAIR the guard test cannot catch: `codeToGraph.test.ts` feeds a synthetic `const hsl = Fn(…)`, so renaming the emitted helper keeps it green while real round-trips explode. The general rule: **anything graphToCode emits at module scope is graph content to codeToGraph until explicitly excluded** — the same class as the image node's ban on an async IIFE (its ReturnStatement visitor would hijack the output), and the next hand-emitted helper needs its own skip.
- **`setCode(code, 'code')` — the user typing in the TSL panel — writes `code` ONLY; `previewCode` advances on a graph→code sync or on Apply (`requestCodeSync`).** ShaderPreview subscribes to `previewCode`, so half-typed TSL never swaps `srcDoc`: without the split every keystroke would re-fetch and re-parse the ~1 MB A-Frame bundle under a fresh opaque origin — the same cost the 200 ms rebuild debounce exists to collapse. It is also the reason the preview looks frozen while you edit code until Apply; collapsing `setCode`'s two branches into one write is the accidental way to lose it.
- **A zero-input node's `defaultValues` KEY ORDER is a positional codegen contract in BOTH directions, and nothing in `nodeRegistry.ts` says so.** graphToCode's generic `inputs.length === 0 && def.defaultValues` branch emits `Object.keys(def.defaultValues)[0]` as the sole constructor argument (`graphToCode.ts`), and codeToGraph maps call argument `i` onto `Object.keys(def.defaultValues)[i]` — using that key as a real port id, so an identifier argument gets an EDGE wired to it. So the constructor value must stay FIRST: `slider`'s `{ value, min, max }` and `property_float`'s `{ value, name }` are the two multi-key defs riding on it today, and any future zero-input def joins them. Alphabetizing the literal or prepending a key is a tidy-up edit that silently changes what the node emits and what a parsed literal is stored under — `slider` would emit its `min`. The test pin covers float/int/slider/color only, so a reordered `property_float` passes CI. Order-INDEPENDENT and not to be confused with these: `property_color` is matched by name in a dedicated branch on both sides, the noise family's `{ pos, scale }` is wired by name in `processNoiseCall`, and `uv` declares real `def.inputs` so it never reaches `defaultKeys`.
- **Deleting a node SPLICES the chain, it does not cut it** (`utils/edgeUtils.ts` → `bridgeEdgesAcrossDeletedNodes`): each outgoing edge of a deleted node re-parents onto the live source reached by walking its first incoming edge upstream, crossing whole runs of deleted nodes — `X → A → B → C` with A+B selected becomes `X → C`. Single-input-per-port is preserved (first bridge to a `(target, targetHandle)` wins, later ones drop), an edge whose TARGET is deleted is dropped, and a chain that dead-ends upstream is dropped. React Flow's own delete is disabled (`deleteKeyCode={null}`) precisely so that every user-facing deletion path goes through that ONE helper — NodeEditor's keydown handler, `store.removeNode`, and the group-delete run. A fourth deletion path that skips it silently redefines what Delete means: the graph disconnects, the generated code changes, and nothing errors.
- **A baked lookup texture that is SAMPLED LINEARLY must be `HalfFloatType`, never `FloatType`**: WebGPU refuses to filter 32-bit float textures without the `float32-filterable` device feature, which the A-Frame bundle never requests — so a float32 LUT looks right on the WebGL2 preview and breaks only on WebGPU (exactly the split the WGSL/GLSL toggle exists to expose). `bakeHalfFloatTexture` (graphToCode) is the shared emitter for every linearly-sampled bake — the Stripes phase ramp, the Data-Viz value ramp, the 256-texel colormap LUT — and the phase ramp is normalized to [0,1] before encoding so float16's ~11-bit mantissa stays smooth. The Data node is the deliberate exception: it wants EXACT per-column values, so it keeps `FloatType` + Nearest, which needs no feature flag.
- **A node component that mounts or unmounts handles at runtime MUST call `useUpdateNodeInternals(id)` in an effect keyed on the handle SET** — `exposedPorts.join('|')`, the collapsed group's boundary-socket ids, the grown-operand count. React Flow never refreshes its handle-bounds map on its own, so an edge to a freshly mounted handle stays in the store and still emits correct code but simply never DRAWS, and existing edges snap to stale anchors when a socket count shifts. The symptom actively misleads: a page reload fixes it (every handle is measured on first mount), so it reads as a React Flow rendering glitch rather than a missing effect. All eight dynamic-handle components already do it — ShaderNode, OutputNode, PreviewNode, GroupNode, MicNode, AudioInputNode, ClockNode, ColorNode — so a NINTH node type is the only way to reintroduce the bug.
- **The A-Frame tab's `index.html` is DERIVED FROM THE MODULE, and it is DEFAULTS-ONLY ON PURPOSE** (`engine/tslToAFrameHTML.ts`). Two independent rules, both easy to erode:
  **(a) The uniform rows are parsed out of the `export const schema = { … }` block `buildShaderModule` emits** (tslCodeProcessor.ts), never re-derived from the node graph. That block IS the loader's uniform contract — declared properties, colours and live-audio channels all land in it — so a page built from it cannot list a uniform the shader lacks or miss one it has. Consequences: those emitted schema lines are a PARSED FORMAT now (change their shape and `parseShaderModuleSchema` must move with it — `tslToAFrameHTML.test.ts` pins both ends); every value is re-normalized on the way in (`Number()` for floats, `#rrggbb`-or-black for colours, a file-name whitelist for `src:`) because property defaults and the shader name arrive from a `.fastshader`; the attribute is emitted MULTI-LINE, one uniform per row, which is safe because A-Frame's style parser trims each `;`-separated chunk (`utils/styleParser.js`); and a uniform named **`src` is DROPPED from the rows** — that parser is last-wins and the `shader` component's own key is `src`, so emitting it would replace the module path with a number and the page would load no shader at all. That guard is `RESERVED_ATTRIBUTE_KEYS` in `tslToShaderModule.ts` and it is SHARED with the module's own usage header, which writes the same `<a-entity …>` example and had the identical collision; `buildHeader` also computes its unique-property list BEFORE branching on it, so a shader whose only property is named `src` prints the no-property example instead of a dangling `shader="src: shader.js; "`.
  **(b) The page sets NOTHING A-Frame would set itself.** No comments, no `<a-light>` rig, no `background`, no camera entity, no `orbit-controls`, no `vr-mode-ui`/`loading-screen` overrides, no geometry/material attributes — a bare `<a-scene>` with one primitive at `0 1.6 -3`. It is a page meant to be ENTERED IN VR, so the default camera, the default light rig and the default Enter-VR button are the point, not an omission; the editor preview's own lighting/background/spin/subdivision are deliberately NOT mirrored (only the primitive follows it). A test pins the ABSENCE of each of those attributes, because "helpfully" adding one back is the obvious wrong move. **The ONE exception to (b) is tessellation for a displacement shader, and it is a correctness fix rather than a taste one**: `<a-plane>` and `<a-box>` default to a SINGLE segment per axis (`aframe/src/geometries/plane.js`, `box.js`), so a plane is four vertices sharing one normal — a `positionNode` has nothing to move and the relief the editor shows is *absent*, not coarser (measured: a 0.2-amplitude wave becomes a bilinear quad off by 0.26), while a box's 24 per-face-normal vertices slide apart into six floating squares. So a module matching `/positionNode\s*:/` — this file's own predicate; the loader answers the same question structurally, off the BUILT material — gets explicit `segments-*` attributes at 64, which A-Frame maps onto `geometry.segments*` for every primitive (`extras/primitives/primitives/meshPrimitives.js`; the schema's `max: 20` is inspector metadata nothing enforces, and the app's own preview already passes 64-256). A displaced `<a-box>` used to split at its 12 shared edges at ANY segment count (BoxGeometry duplicates those positions with per-face normals) and the fix could not be inlined without costing the page its reason to exist — **shaderloader 0.6 welds them itself now**, so this page gets it free, and the same move fixed podest and every exported module. **The page carries NO script of its own**: the VR backend is forced declaratively by `<a-scene renderer="backend: webgl">` (the bundle's aframe#5847 carry — see the vendoring bullet), which is what makes three r184 take its WebGL2 backend, the only one that can enter a WebXR session (the WebGPU one hard-throws in `XRManager.setSession`). The SPELLING is load-bearing: only the raw key `backend:` reaches the patched branch and only the exact value `webgl` forces, so a typo silently does nothing and Enter VR throws on a headset much later (`aframeBackendProperty.test.ts` guards the patch; `tslToAFrameHTML.test.ts` pins the attribute AND the absence of any inline script). This replaced an inline `navigator.gpu`-hiding script on 2026-08-31; pages exported before then still carry it and keep working, since hiding gpu and forcing WebGL reach the same backend. **The two install facts live in the tab's `index.html` LABEL, not on the page** (`CodeEditor.tsx` + `lv.json`): put the `.js` beside it, and serve the folder over http(s). The second one is not pedantry — the loader `fetch`es the module, so a double-clicked `file://` page renders a plain white default-material primitive with a full working scene around it and says nothing. If the page ever stops being comment-free, that is the sentence to move onto it.
