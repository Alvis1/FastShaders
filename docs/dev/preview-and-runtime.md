### Vertex WELD for displaced primitives lives in the LOADER, not the app

- **Vertex WELD for displaced primitives lives in the LOADER, not the app** (loader 0.8, whose core carries the frozen 0.6's `weldByPosition` + `shouldWeld`/`syncWeld`/`unweld` verbatim). A BoxGeometry gives every face its own vertices with per-face normals, so normal-driven displacement drives the 3 copies at each corner apart and the faces separate. The editor preview fixed this with an inline `weld-verts` component and was the ONLY surface that had it — podest, the copy-ready A-Frame page and every page embedding an exported module all rendered a displaced box as six floating squares. Moving it into the loader (2026-08-31) fixed all of them at once, needed ZERO podest changes, and kept the A-Frame page's zero-script property, because every one of those surfaces already loads the loader. Four things are load-bearing. **The displacement gate is `material.positionNode != null`, NOT `!== undefined`** — three's NodeMaterial constructor assigns `null`, so an undefined test is true for every material ever built and would weld every primitive shader, failing silently (spheres and planes look fine; only a non-displacing cube gives it away, by rendering smooth). The loader is the one layer holding the BUILT material, so it answers this structurally where the app must regex module text. **PRIMITIVES ONLY** (`el.components.geometry`): the rebuild keeps position/uv/index, so welding a MODEL would drop vertex colours, skinIndex/skinWeight and morphAttributes — models normalize (and weld) through `fit-bounds`' own `regen` flag, which is also why a displaced model on an EXPORTED page stays unwelded. **WHICH groups merge is the correctness of the thing**: a group welds when its members could displace APART — normals differ, or UVs differ AND the shader reads `uv()`. MEASURED against r184: a-sphere(36,18) has 19 coincident groups with ZERO differing normals and 19 differing UVs (largest a 37-vertex POLE FAN), 64x64 gives 65/0/65, a-box gives 8/8. So a position-driven shader must NOT weld a sphere (every member moves identically; welding keeps one representative uv and smears the whole polar cap — a bug the old always-weld component shipped), while a uv-driven one MUST (measured ~0.2 world units of separation on a radius-1 sphere, so the surface cracks). **The author's choice travels as `mergeVertices: false`** in the module's return object — opt-OUT only, `=== false` (the settings menu writes a literal `true` on re-tick, so a truthiness gate would add the key to a default node), which is what keeps every already-exported module and all 32 built-in snapshots byte-identical. It is the first key there that is NOT a THREE.Material property: the loader reads it off the return object rather than copying it onto the material, so it is inert on 0.4/0.5. `scriptToTSL` strips and recovers it, so the setting now survives an export→import round trip. `src/shaderloaderWeld.test.ts` runs the REAL vendored file against REAL three.

### Preview renderer backend (WebGPU vs WebGL2)

- **Preview renderer backend (WebGPU vs WebGL2)**: the sandboxed preview iframe (`tslToPreviewHTML.ts`) and the standalone podest viewer (`public/podest.html`) both inject `<a-scene>` only AFTER a WebGPU pre-flight — three r184 auto-selects WebGPU on `navigator.gpu != null` ALONE, so the pre-flight requests a real adapter (2s timeout) and hides `navigator.gpu` (→ WebGL2 via GLSLNodeBuilder, TSL compiles identically) when it can't deliver. **Safari is force-hidden to WebGL2 up front** (the UA branch inside the emitted `__fsForceWebGL2`) — three r184's WebGPU backend can be handed an adapter yet never paint on Safari (flat-color pane, no error). A 6s watchdog turns any remaining no-paint into a visible sticky error. **The XR popups reach the same backend a DIFFERENT way** (2026-08-31): they force it declaratively with `<a-scene renderer="backend: webgl">` and run no pre-flight at all, since the decision is already made — the editor's XR popup, podest's XR popup and the A-Frame tab page all do this. The SANDBOXED preview deliberately keeps `hideGpu()`: its gpu-hiding is not about VR (it serves Safari-no-paint, adapter-less WebGPU and the WGSL/GLSL toggle), and the hidden-gpu state IS the truth that the `fs:backend` report, the watchdog wording and `AUTO_IS_WEBGL2` read — swap it for the attribute and that label silently lies.

### Podest unattended / pedestal mode

- **Podest unattended / pedestal mode** (`public/podest.html`): the viewer is meant to run for WEEKS with nobody touching it, which is a different problem from "a page that works". The presentation layer is the ⛶/⤡ fullscreen button (bottom-right) plus an optional top-centre title (auto-derived from the dropped file name, `_`→space, click it to edit text + colour; `textContent` only). **Presentation mode is deliberately WIDER than the Fullscreen API**: fullscreen needs a user gesture, and an unattended pedestal has nobody to give one after a browser auto-update — it would come back windowed with the panel over the artwork and, far worse, no wake lock, so the display blanks at the OS idle timeout and stays black for the week. So the mode is remembered (`fs:viewerPresenting`, or `?present=1` for a kiosk launcher) and `is-present` on `<html>` — not `is-fs` — is what hides the panel, hint and error banner; `is-fs` governs only the ⛶ button's own auto-fade, since in windowed presentation that button is the way back in (⛶ then Esc leaves the remembered mode). Everything that must survive the reload asks `presenting()`, never `fsElement()` — **including the release-race guard inside `requestWakeLock`**, which gated on fullscreen would release every lock the instant its promise resolved and silently undo the whole thing. Behind that sit five long-run guards, each fixing something that actually breaks on that timescale: (1) **the stage iframe is disposable** — `applyStateToStage()` replays background/spin/geometry/shader on every `fs:ready`, so the pending queue is DISCARDED rather than flushed (replaying both would recompile the shader twice) and any restart is invisible; (2) **`time` is folded back every ~4.4 h** — three's `time` is a float32 accumulating seconds since boot, so its resolution decays to 7.8 ms after a day, 62 ms after a week and 250 ms after a month (a slideshow); the stage takes `renderer._nodes.nodeFrame.time %= TIME_WRAP` where `TIME_WRAP` is an exact multiple of 2π (2π × 2520 ≈ 15833 s), so `sin(time)`/`cos(time)` cross the fold with NO visible jump and the quantum never exceeds ~1 ms (a shader's own `time.mul(20)` multiplies it) — modulo not zeroing, so the fold stays 2π-aligned however far behind the beat has fallen; if that private path ever disappears the beat reports `wrapNeeded` (rebasing as it fires, so it can't latch) and the parent restarts the stage instead. The stage also rebases `nodeFrame.lastTime` on `visibilitychange`→visible, or the first frame after an overnight sleep would dump the whole hidden gap into `time` in one step; (3) **device loss is terminal and silent** — the stage wraps `renderer.onDeviceLost` (keeping three's own handler) AND hooks the raw `backend.device.lost` promise, because three returns early on `reason === 'destroyed'` and would never call the callback, plus a `webglcontextlost` listener; all report `fs:stage-dead`, and a 5 s `fs:beat` carrying the cumulative `info.render.calls` lets the parent catch a stall with no throw at all (best-effort: it proves the loop ran, not that pixels landed); restarts are floored at 30 s apart and after 6 in a row back off to one retry every 10 min — never a permanent give-up, since a transient driver fault must not end the exhibit (watchdog is suspended while the document is hidden — a frozen counter there is normal); (4) **the last drop is mirrored to IndexedDB** (`fs-podest`/`session`, throw-safe, shader ≤24 M chars + model ≤64 MB — the model cap is the editor's `MESH_MAX_BYTES`, deliberately NOT the 96 MB zip cap; a payload over either is left out of the mirror (and when nothing is left to mirror both records are DELETED, so the pedestal restarts empty), so a user load of one — drop, picker, a manual work-folder pick, or re-ticking auto-restore — says so in the banner while the panel is up (`noteRestoreLimits`/`restoreLimitText`: never in presentation mode, never on a cycle tick, never with auto-restore off, never from the boot restore, and only for the part THIS load changed; called after BOTH halves of a drop land, because `loadShaderText` clears the banner)) and replayed at boot, because a browser auto-update or power blip otherwise leaves a grey sphere — the record carries the tuned **uniform values** too (losing the exhibitor's tuning shows the wrong artwork), a drop that lands first always wins, and a user-typed title outranks the replayed one; (5) **the screen wake lock** is requested at boot, on entering presentation mode, on `visibilitychange`, and again on every 5 s watchdog tick — the platform can drop a lock on its own and a UA may refuse it until it can grant it, so the only robust pattern is to keep asking (it early-returns when a lock is already held). Also: the error relay is rate-limited IN the sandbox (identical repeats/minute + 20/minute cap) since a per-frame `console.error` would otherwise postMessage forever, banners self-dismiss after 20 s, the zip reader is a hand-written twin of `utils/zipReader.ts` whose three caps (512 entries, 96 MB summed — `MESH_MAX_BYTES` + 32 MB, so a bundle the editor exports reopens — 512-byte names) `zipReader.test.ts` pins against the editor's, and a cap failure is a sentence rather than a parser error ('Could not open the zip: it unpacks to more than 96 MB.' / '… holds more than 512 files.', `zipLimitError`/`zipErrorText`, executed by `podestLimits.test.ts`) while every other failure keeps 'Could not read zip: …', and 90 s of idle in fullscreen returns the camera to the framing pinned by `fs:save-view` at entry (a visitor's spin must not outlive them). **Checked and deliberately NOT fixed**: the bundle's anime.js calls the undeclared `activeInstance[i].pause()` on visibilitychange, but A-Frame builds its instances with `autoplay:false` and ticks them by hand, so anime's active list is always empty and that line never runs (verified in a browser).

### Podest VR locomotion (`vr-nav`, in `buildXrDoc`'s popup document only)

- **Podest VR locomotion (`vr-nav`, in `buildXrDoc`'s popup document only)**: the immersive popup used to drop the visitor at the reference-space origin, which is exactly where the artwork is — `fit-bounds` normalizes every mesh to 1.6 units, so a headset opened on the INSIDE of the sphere. Raising the piece to eye height (the old `EYE` fix) addressed the wrong axis. Moving the ART cannot fix it either: `local-floor`'s yaw comes from the guardian, not from where the wearer is looking, so "in front" is unknowable until a pose arrives. `vr-nav` therefore steps the **camera rig** back `NAV_HOME` metres along the head's own forward on the first tracked frame. Load-bearing details, each a way this silently goes wrong. **The rig works because three composes the XR pose with the camera's PARENT world matrix** (`WebXRManager.updateUserCamera`) — moving the camera entity itself does nothing, the pose overwrites it every frame. **The head is read from the FRAME (`getViewerPose`), never from the camera object3D**: A-Frame ticks before it renders, so on a session's first tick the camera still carries its flat orbit-controls transform (`0 1.4 7`) and an entry framing measured off it lands metres away. The rig returns to the origin on `exit-vr`, which is what keeps the flat orbit view identical to before. **Input is read straight off `session.inputSources` + `targetRaySpace`**, not through A-Frame's controller components — `laser-controls`/`oculus-touch-controls` fetch their models from `cdn.aframe.io` and this page must run offline. **The HANDS are drawn by `vr-nav` itself** (joint beads on an InstancedMesh parented to the rig, from the same `fillPoses` output the gesture reads) and NOT by `hand-tracking-controls`: that component adds a `wristObject3D` to the **scene root** and registers a `child-attached` handler that reparents every child entity onto it — including the 25 joint dots it creates itself — so its hands render at `wristPose × jointPose` in scene-root space, bypassing the camera rig entirely (they ignore the entry framing and every teleport) and carrying the wrist transform twice. MEASURED ON A HEADSET as hands sitting metres from the real ones. Hands drawn from the same poses under the same rig as the head cannot drift from it; `podestVrNav.test.ts` asserts the mesh's parent IS the rig. Losing the component also means the scene's own `webxr="optionalFeatures: hand-tracking"` is now the only thing requesting the feature. Two triggers share one aim→commit path: `select` (controller trigger, or the runtime's hand pinch — press to aim, release to go) and a **Quest-style fist-with-thumb button classified here from the 25 joint poses**, because Meta's microgesture recognizer is an OpenXR extension WebXR does not expose. Its thresholds are fractions of the wearer's own hand (wrist→middle-metacarpal, ~9 cm), with a 4-frame arm and press/release hysteresis — the thumb is self-occluded by the fist at exactly the moment it is pressed, so tracking confidence is worst where the decision is made. **The button is the thumb tip's HEIGHT over the index knuckle, never its distance from it.** The first build used distance (press < 0.55, release > 0.85 of hand scale) and a thumbs-up fist sits inside that band: the button latched pressed on the very frame it armed, `commit()` no-op'd because `valid` is only computed later in `aim()`, and it could never release — so nothing teleported again, and the pinch path died with it since a fist-owned hand ignores `select`. Two rules came out of that: a press may not land on the arming frame (`st.armed > 1`), and RELEASE must sit BELOW ARM so re-arming cannot re-trigger. The unit tests did not catch it because they validated the classifier against a synthetic hand invented alongside it — they proved the code matched the assumption, not the anatomy. A tight fist can also cross the runtime's own pinch threshold, so a hand the fist detector owns ignores `select` outright. **The 30-unit bound is an annulus, not a nav mesh** — the scene has no floor geometry to walk on (an artwork on a background colour is all there is), so a mesh would have to be invented before it could be raycast; targets are clamped into `NAV_INNER`…`NAV_RADIUS` (the inner ring is what stops a visitor teleporting inside the piece). **A clamp is never a refusal**: aiming past the edge lands you at the edge, and the marker is drawn where you will ACTUALLY arrive — a marker that vanishes reads as a broken button, which is how an earlier 60 m ray cap put a dead zone exactly where "aim at the far edge" lives. The aim is shown as a **ring plus a bead arc** — a quadratic Bézier LOFTED above the straight aim, deliberately not a ballistic curve: targeting stays the straight ray so the whole ring remains reachable (a projectile caps range at v²/g and would silently make the outer bound unaimable), and the arc's only contract is that it ends on the marker, which it does by construction. Beads on an InstancedMesh rather than a `THREE.Line` because line width is capped at one pixel on every backend, and a one-pixel thread across a headset's field of view is not a visible control. The jump moves the **head** onto the marker, not the rig origin (someone who physically walked two steps would otherwise arrive two steps off), under a blink so the translation is never seen, and **physical walking is never counter-moved** — pulling the rig back under someone's feet is how you make them sick, so the bound leashes teleports only. Unattended recovery: 90 s of a MOTIONLESS head returns the visitor home (a worn headset is never still that long, so it can only fire when nobody is wearing it), skipped when the return is under 35 cm so an empty room doesn't blink every 90 s. All of this lives in the popup document, so it cannot touch the pedestal's own long-run loop. `src/podestVrNav.test.ts` runs the generated component against a real `three` and synthetic XR frames (entry framing from arbitrary yaw, the gesture state machine, the annulus, the idle return) — **but nothing here has run on a headset**; the gesture thresholds in particular are derived, not measured, and Horizon OS may claim the same hand pose for its own navigation. The editor's XR popup (`tslToPreviewHTML` xr mode) still centres the visitor on the artwork and has none of this.

### XR popup (preview "VR" button)

- **XR popup (preview "VR" button)**: opens the shader at the app's REAL origin (WebXR needs a top-level page; hidden on desktop builds). `tslToPreviewHTML`'s `xr` mode now (1) **auto-enters immersive VR** once `navigator.xr.isSessionSupported('immersive-vr')` confirms real support — never on the magic-window fallback, which would strand the user in pseudo-VR — while keeping an in-document `#vr-gate` button visible until a session actually starts (a `window.open`+`document.write` document may not inherit the opening click's transient activation, and an in-document gesture is what Quest Browser reliably accepts); on non-XR devices the same gate becomes a Fullscreen toggle (capability-resolved label, never a UA sniff); and (2) draws a head-locked frame-time/FPS panel (`fs-xr-stats`): a CanvasTexture quad added to the THREE camera OBJECT via `getObject3D('camera')` — a child `<a-entity>` would world-lock in XR — redrawn at ~4Hz so the readout doesn't bias the GPU cost it reports, rasterized to canvas because A-Frame's `<a-text>` fetches its MSDF font from a CDN (this app must run offline). The number is the presented frame PERIOD (includes vsync — reads 72/90/120Hz until the shader actually misses frames). It never runs a module found INSIDE a model: every preview copy is payload-free by construction (`createPreviewMesh`, and the popup's blob is `previewMesh.bytes`), no document the app itself runs spells loader 0.8's opt-in (the GLB-mode module header does, on purpose, for recipients), and the popup closes the loader's one-way latch (`embeddedModuleNeverRuns.test.ts` pins all three and runs the real vendored loader). A module-only RESTORE is a different thing: it goes through the bare-script path exactly like an imported `.js`, so the popup may run what the user chose to restore, never what merely rode in the model bytes.

### Loader 0.8 = core + component, and the component IS the core's state object

- **Loader 0.8 = core + component, and the component IS the core's state object** (`a-frame-shaderloader/js/a-frame-shaderloader-0.8.js`, vendored to `public/js`; since the loader switch it is the ONE loader every surface loads and every new export names — `LOADER_FILE` — and `loaderSwitch.test.ts` pins that, the loader internals the surfaces read, and every `FastShaders.<name>` the export header and the README spell). ONE classic-script IIFE installs `globalThis.FastShaders` (use / load / prepareSource / makeParams / setUniform / apply → Binding / weld / transforms / internals, plus the `fetch`/`importSource` hooks) and registers the A-Frame `shader` component only when `AFRAME` exists: evaluating it without A-Frame never throws, a second 0.8 include is a no-op, and a `shader` component that is already registered (0.6 on the same page) is skipped with a warning rather than a throw (A-Frame's `registerComponent` throws on a duplicate name). Five rules. (1) Every core function that mutates takes a STATE whose fields keep 0.6's component names — `originalMaterials`, `_shaderMaterial`, `_partMaterials`, `_appliedMaterials`, `_propertyUniforms`, `_weld*`, `_bary*`, `_tex*` — and the component passes ITSELF. The editor preview's highlight / uniform / hot-swap code and podest's parts picker and sliders read those fields off `entity.components.shader`, so a rename breaks them with no error. Plain three.js gets a fresh state per `apply`. (2) The component keeps 0.6's method names and signatures (the 3-argument `applyMaterialToMesh` included), its events (`shader-applied {src}`, `shader-error {src, message}`) and `_currentSrc` set before the first await. (3) The helpers are no longer globals. Tests reach them through `FastShaders.transforms` (0.6's five transforms, byte for byte, except that autoInjectTSLImports validates against the BOUND three) and `FastShaders.internals` (not a stable interface); `api.fetch`/`api.importSource` are what let a node test drive the component end to end. (4) The deltas from 0.6 are a closed list: no throw without A-Frame; a `materialParts` return counts as the object API (0.6 sends it down the Simple-API branch, which assigns the return object to colorNode — a near-black mesh, no error); a null-prototype uniforms map; TSL read off the bound three; a warn-only revision check (`THREE_REVISION` against the page, and a module's `threeRevision` against the page — a value that is not 1–4 digits is never printed); the IIFE; the glTF plugin and `materialParts` dispatch (see the glTF material-index bullet); the mesh decoders (`FastShaders.decoders`, section 13b: `configure`/`install`, a DEDICATED LoadingManager for Draco that never consults `DefaultLoadingManager`, `setDRACOLoader(null)` in manage mode when no Draco source resolves so a parse fails fast instead of hanging on A-Frame's gstatic loader, loader classes from `AFRAME.THREE` first, a lazy meshopt shim capped at 256 MiB decoded per model — a fresh one per PARSE, because `install` wraps the loader's `parse` (A-Frame's gltf-model reuses one GLTFLoader for every `src`), `decoders/` beside the loader's own script URL by default, and still when `configure()` is given no `resolve`), installed from the same `attachGltfModel` the glTF plugin uses, and configured by every surface that loads the loader (see the decoders convention); **and the KTX2 transcoder beside them** (section 13b-KTX2, same `FastShaders.decoders`: a lazy shim awaiting the memoized `renderer.init()` before `detectSupport` — a WebGPURenderer's `hasFeature` THROWS before it, which is exactly why A-Frame's own `basisTranscoderPath` route must never be written — one KTX2Loader per document, a dedicated manager that maps the two basis names and hands EVERY other URL to `DefaultLoadingManager.resolveURL` (unlike Draco's, this loader fetches the texture IMAGE too, so the page's allowlist must keep governing it), the 80-byte header read and capped before a transcode, `ktx2Stats`/`ktx2Formats` and ONE `console.info` naming the target, plus a same-name `KHR_texture_basisu` plugin that REPLACES GLTFLoader's builtin to add the one thing it lacks — a failed transcode falls back to the texture's own PNG/JPEG `source` instead of losing the texture. `getRenderer` rides `attachGltfModel`'s install context, read lazily off `el.sceneEl.renderer`. `shaderloaderKtx2.test.ts` runs all of it against the REAL vendored loader with three's real KTX2Loader and a real wasm transcode. The parent pushes the basis pair with the model whenever `needs.ktx2` (`decoderFilesFor`, 8.4), so the sandboxed preview transcodes like any other surface; the XR popup resolves both by real URL). The per-mesh dispatch ladder is name-keyed `parts` > the index part (`_indexPartResolver`, set by `applyResult` only when a signature-matched `materialParts` table applies) > the default > the single-mesh first-part fallback > the authored material. The authored rung is taken by any module carrying `parts` or `materialParts` (whatever its status) and it PUTS the authored material back: on a re-apply the mesh still wears the previous shader's material, which has just been disposed. (5) Every 0.8.x edit after the first push is ADDITIVE — no renamed state field, method, event or api key — because it ships to every shader already exported against 0.8 the moment the submodule is pushed. `use()` installs `globalThis.THREE` when absent, because module code that bakes a texture reads that global.

### Preview rebuild is debounced

- **Preview rebuild is debounced**: until 2026-09-08 only property uniforms had a postMessage hot-update path and every other edit swapped `srcDoc`, re-fetching/re-parsing the ~1MB A-Frame bundle under a fresh opaque origin. **A module edit is now HOT-SWAPPED** (`fs:shader` → `SHADER_HOT_SWAP_SCRIPT` in tslToPreviewHTML, gen-tagged ack, a watchdog that escalates an unanswered swap to a real rebuild); `srcDoc` rebuilds only for the COLD keys ShaderPreview's `coldDocKey` comment lists. **Image payloads no longer ride each hot swap** (GLB Phase 6 S3, `engine/previewAssetFeed.ts`): the sandboxed preview receives `fs:image-assets` once per key per document — the boot module's keys baked as `window.__fsBootAssets`, later ones posted by `postShaderSwap` immediately BEFORE the `fs:shader` that needs them (postMessage is FIFO per target) — and `window.__fsResolveAssets` turns the `fs-asset:` placeholders into that document's `blob:` URLs right before a module Blob is minted, the boot blob and every swap alike. So a scrub on a graph holding megabytes of images posts the small placeholder module, not the payloads, and the module text the parent compares (`runningModuleRef`, the receiver's `applied`) stays placeholder-only. `sentAssetKeysRef` is the parent's per-document record of what the live document holds: seeded with the boot list on every rebuild AND again on the fresh document's `load` (a feed posted during the srcDoc swap may have gone to the previous document, or to this one before its resolver parsed — re-sending a key the resolver already holds is a no-op there, skipping one it lacks leaves that image black for the life of the document), advanced by every post. The XR popup, the A-Frame and Three.js tabs and the export still inline the `data:` URLs (a top-level or standalone document has no parent to feed it). `previewAssetFeed.test.ts` executes the resolver against the real Blob/URL/atob and source-pins all three surfaces; NOT yet run in a browser — see the S3 owner checks (Chrome and Safari, both backends, an image swap without a rebuild, a rebuild then a scrub). **The swap's no-op bail compares against the module the live document is RUNNING (`runningModuleRef` — seeded with `bakedModule` by the rebuild effect, advanced by every post), never against `bakedModule`**: a document is baked once and swapped many times, and the boot document is baked while the graph is still the empty red-sentinel shader, with the real graph arriving by swap — so NEW, whose module is that same sentinel, was skipped as "already there" and the preview kept the previous shader (2026-09-11), as did any undo back to the boot shader. The load-event replay DOES compare against `bakedModule`, correctly: a freshly loaded document is running exactly that. `previewRebuild.test.ts` pins both. The debounce still matters: `useDebounced(previewCode, 200)` (trailing, so first paint isn't delayed) collapses a scrub's pointermove stream into a single rebuild on release. A "Compiling shader…" overlay covers the gap, cleared by `fs:preview-ready` (success) **or** `fs:preview-error` (failure — a broken shader never reaches the ready handshake, since `checkShaderReady` polls for bound uniforms and just gives up), with a 12s failsafe so it can never stick over the error text.

### Preview geometries

- **Preview geometries**: five options — `sphere`, `cube`, `plane` (A-Frame primitives), `teapot` (tessellated IN the preview document from Bézier patches — see the runtime-teapot convention) and `bunny` (the one remaining OBJ model file, `public/models/`). Three predicates in `tslToPreviewHTML.ts` are the source of truth: `isObjGeometry()` (bunny), `isTeapotGeometry()`, and `isModelGeometry()` (obj + `custom` — the geometries that ride the model feed, rebuild the iframe on change and HIDE the subdivision slider; the teapot is deliberately NOT one). The inline `fit-bounds` A-Frame component recomputes vertex normals (after merging vertex duplicates so per-vertex displacement doesn't split the surface), auto-detects inverted winding (the bunny is CW), generates spherical UVs from each vertex's direction so `uv()` reads cleanly on OBJ meshes, and rescales so the longest axis = 1.6 to match primitive framing. **Those UVs are SEAM-SPLIT** (`splitUVSeam`, and see its own convention below). The source OBJs themselves are **pre-normalized** (bbox center at origin, longest axis exactly 1.6), so the runtime recenter/rescale is a no-op for them and `positionGeometry` ranges are comparable across all five geometries.

### `fit-bounds` BAKES the normalization into the geometry attributes

- **`fit-bounds` BAKES the normalization into the geometry attributes** (`FIT_BOUNDS_SCRIPT`, pinned by `previewFitBounds.test.ts`), and this is load-bearing rather than stylistic: `positionGeometry` is three's RAW position attribute, so scaling the Object3D — what this used to do — is completely invisible to the shader. A dropped model therefore fed its AUTHORED units to every position-driven preset, texture and noise-node default (all of which are tuned for the ±0.8 the pre-normalized built-in OBJs deliver), which is what shredded Vertex Wave on a 180-unit statue. The bake also has to be MEASURED in the entity's own frame — the old world-space `Box3.setFromObject` included `#preview-entity`'s resting tilt and `#spin-parent`'s live animation, so a model was scaled by its rotated hull (teapot ~19% undersized) and a dropped model's centring depended on the spin phase it happened to load at. Order matters: bake BEFORE `mergeByPosition` so its 1e-4 weld quantization is a fraction of the preview box rather than of authored units. Geometries are CLONED, never mutated (a glTF may reach one BufferGeometry from several nodes with different transforms), every local matrix in the subtree is then flattened to identity, mirrored transforms (negative determinant) get `flipWinding`, and skinned/instanced meshes deliberately fall back to the legacy Object3D path rather than desync their bind matrices. `public/podest.html` carries a hand-minified twin covered by NO sync plugin — `previewFitBounds.test.ts` runs both through the same assertions to catch drift. The bake DEQUANTIZES position/normal/tangent to Float32 first (`dequantize`, in both copies). `applyMatrix4` writes back into the attribute's own typed array, and three r184 truncated a KHR_mesh_quantization model's unnormalized Int16 positions to integers and wrapped normalized ones (0.5×3 came back as −0.5), measured. That is gltfpack's default output alongside meshopt. Float32 geometry, i.e. every built-in and every OBJ, is untouched, and every other attribute (uv, color) keeps its quantized form, through the seam split too.

### The generated spherical UVs are SEAM-SPLIT, and the POLE is a documented limit

- **The generated spherical UVs are SEAM-SPLIT, and the POLE is a documented limit** (`splitUVSeam` in `FIT_BOUNDS_SCRIPT`, mirrored in podest's twin, 2026-09-04). `atan2` wraps from +π to −π across the **−X half-plane**, so u steps 1 → 0 there; on an INDEXED mesh both sides of that step share ONE vertex, so every triangle straddling it interpolates u backwards across the whole range — the entire texture crushed, and mirrored, into a band one triangle wide. MEASURED on the shipped models: **245 of the teapot's 6320 triangles** (u-span up to 0.996) and 584 of the bunny's 69451, and on the teapot **the seam plane runs straight through the HANDLE** — which is exactly how it was reported from the canvas, as the handle-side UVs being "rotated and squashed". The fix is the textbook one: a triangle whose u-span exceeds half the range is straddling, so its LOW-u corners are duplicated and re-issued at **u + 1** (a mesh with no straddling triangle is left untouched, so this costs nothing on geometry that never had the defect). Three things are load-bearing. The duplicate is a COPY of its original, which is what keeps the mesh **welded for displacement** — the whole reason `mergeByPosition` exists: two vertices at one point with one normal, differing by exactly one texture period in u, move identically under any position- or normal-driven displacement and by one period under a uv-driven one (before this they differed by a FULL period, so a uv-driven displacement *tore the surface open* along the seam — the split repairs that too). The copy reads through **stride/offset** (`rawComponent`), because the preserve path synthesizes UVs for a GLB that ships none and a glTF primitive may interleave its attributes — a shape the regen path never produces, so a flat-array read is silently someone else's vertex; **morphAttributes are expanded too**, or every target reads past its end. And what this does NOT repair is the **POLE**, the projection's other and genuinely unfixable singularity: near ±Y the horizontal radius goes to zero, so neighbouring vertices a fraction of a millimetre apart sit at completely different azimuths and no per-vertex u can make their shared triangle small — MEASURED after the split, 4 of the teapot's triangles and 2 of the bunny's still span, every one with a corner within 8° of an axis (the lid-knob apex and the base centre), each a few pixels. Escaping that needs a different parameterization, not a better seam pass, so the test pins the honest invariant — **zero spanning triangles away from the poles**, plus a bound on the polar residue so a regression into it fails loudly. TRAP for anyone writing a test here: an un-rotated `SphereGeometry`'s own duplicated seam column sits EXACTLY where atan2 wraps, so on the preserve path nothing straddles and the split never runs — the interleaved test rotates by half a segment (`rotateY(π/24)`) precisely so it executes the code it exists to cover. **The projection is now only the FALLBACK: an OBJ that carries its own `vt`/`vn` KEEPS them on the regen path** (`splitByAuthored`, same day, mirrored in podest). Until then `mergeByPosition` threw both away and every OBJ was re-projected whatever the file said — invisible while the built-ins were bare `f a b c` files, visible the moment the regenerated teapot shipped an atlas. The position weld still runs first (it is what produces the smooth normals and drives the winding heuristic); the welded mesh is then re-split into one vertex per distinct (welded position, authored uv, authored normal), so a chart boundary or an authored crease stays split and everything else stays welded, and a source with no normals of its own takes the welded smooth ones. Corner j of the welded index is corner j of the source, EXCEPT that `flipWinding` swapped corners 1 and 2 of every triangle — the split mirrors that swap when reading the source, or a CW file with UVs gets its neighbour's texture coordinate on two corners of every face. The fit-bounds tests that exercise the PROJECTION therefore strip a three primitive of its authored uv/normal first (`bare()`), and a separate one proves the regenerated teapot's atlas survives the regen path with 99.5%+ of vertices carrying an authored (uv, normal) pair — keyed AFTER fit-bounds' own centre-and-scale, which is not quite the identity even on the pre-normalized file (the spout tip sits between samples at resolution 16).

### The Utah teapot is TESSELLATED AT RUNTIME, and the subdivision slider is capped at 128 app-wide

- **The Utah teapot is TESSELLATED AT RUNTIME, and the subdivision slider is capped at 128 app-wide** (2026-09-05; `engine/teapotData.ts` + `engine/teapotGeometry.ts`, owner request: "replace the teapot with a UV'd one — the 1976 if it has UVs — offer the subdivision slider for it, cap the slider at 128 globally"). The old `teapot.obj` was a 6320-triangle mesh with no `vt` at all, so `uv()` on it was the spherical projection and the slider hid itself the moment it was selected. The official Utah Teapot page (graphics.cs.utah.edu/teapot, Cem Yuksel) publishes no control-point file — its teapots are generated client-side by a WASM module with an OBJ download and a 1–128 resolution slider (the origin of the 128) — so the data was RECOVERED: the 1976 mesh generated at resolution 8 under its "Patch Coordinates" layout exposes each patch's parameter grid, and a bicubic is determined by far fewer than 81 samples, so 16 control points per patch were solved by least squares (worst residual 4.35e-7, every coordinate one of Newell's own rationals — 0.784, 1.4375, 2.34375). The "Bijective Layout" turned out to be EXACTLY affine per patch (28 disjoint rectangles inside [0,1]², residual 4.5e-8), and its within-chart *t* is a per-column cubic Bézier whose control values are the normalized cumulative chord lengths of the column's control polygon measured in the UNSCALED 1975 frame (z × 4/3 before Blinn's 3/4) — verified to 7e-7 over all 252 sampled columns; arc length, chord length at any resolution and a bicubic texture patch were each 0.03–0.13 off. **One vacuous test almost sank this**: an early chord-length check accumulated with `cum.push(cum[j] + …)`, read an index that did not exist yet, produced NaN, and a `tot > 1e-9` guard then skipped every column — it reported an exact match of 0.00. `fixtures/utahTeapot1976Res4.json` is the official generator's own res-4 output, and `teapotGeometry.test.ts` proves every one of its face corners has a vertex of ours at the same position with the same texture coordinate (that includes the "triangulate tips" convention: each lid-apex triangle gets its own tip vertex with u at the midpoint of its two columns), plus the official triangle count 28·2N²−4N at every resolution. **Shape of the implementation**: `TEAPOT_SCRIPT` is one self-contained script string, the `FIT_BOUNDS_SCRIPT` precedent — the preview iframe evaluates it (registering the `teapot-mesh` component, which builds the BufferGeometry, hangs it on the entity and emits `model-loaded` so the shader, fit-bounds and the framing re-apply as for a swapped model), node tests and `scripts/gen-teapot-obj.mjs` evaluate the SAME text via `loadTeapot()` (the script binds to `window`, so node hands it a bare object under that name). It is in EVERY preview document so a primitive can hot-swap into the teapot — MEASURED 2026-09-05 at 19.2 KB, of which 16.1 KB is code and control points and 3.1 KB is comment and indent (the old "~16 KB, mostly control points" was the stripped figure). Two of these scripts are unconditional and they are most of the document: `FIT_BOUNDS_SCRIPT` is 22.7 KB of which nearly HALF is comment (11.9 KB stripped), `GLTF_ANIM_SCRIPT` — model geometries only — is 11.9 / 6.5 KB, and a default sphere document comes out ~31% comment bytes. Because these are TypeScript TEMPLATE LITERALS no minifier rewrites them, so those bytes also ship in the app bundle (~7.6 KB gzipped on the boot chunk, offline desktop build included) and are re-parsed by the iframe on every rebuild. Accepted, and to be fixed at BUILD time if ever: the scripts must stay unconditional (that is the hot-swap contract) and the comments must stay in the SOURCE, since they carry the measurement rationale the fit-bounds and teapot conventions rest on. The mesh is built IN the document rather than posted as OBJ text through the model feed on purpose: at the default 64 the teapot is 118k vertices / 229k triangles, ~15 MB of OBJ to serialize, post and re-parse per slider tick (60 MB at 128); the control points are 1.3 KB and the tessellation ~10 ms, so a slider tick is a tiny `fs:geometry {teapot: "resolution: N"}` and the XR popup, built from the same HTML, gets the teapot for free (`marchWindow.test.ts`'s rule: the popup renders what the pane renders). Positions come out in the preview frame directly (y up, centred, longest axis 1.6 — `TEAPOT_FRAME` from the res-64 bbox in the data module, so the normalization is resolution-independent), normals are analytic (cross(∂s, ∂t), the official generator's own orientation, with a step just inside the patch at the collapsed lid apex), and `fit-bounds` gets `regen: false` — it only bakes, since the weld+regen path had nothing to add and its projection would overwrite the atlas. The teapot is identified as a Utah Teapot in every OBJ header and the Model menu, per the page's terms ("freely available for any use, including commercial use … identify the model … as a Utah Teapot … acknowledge its origin as the historic Utah Teapot developed at the University of Utah"). ### World normals: `normalWorld`, not `normalLocal`, whenever a normal meets a world-space direction.

- **World normals: `normalWorld`, not `normalLocal`, whenever a normal meets a world-space direction.** The preview nests the mesh under `#preview-entity` (a resting tilt — 45/45/0 on sphere and cube) inside `#spin-parent` (a full 360° turntable animation while playing, restored from persisted `fs:previewRotation` even when paused), so the object→world rotation is essentially never identity. `dot(normalLocal, worldViewDir)` evaluates to `dot(N_world, R·V)`: a correctly-shaped fresnel measured about a view direction rotated by the model, so the rim slides off the silhouette and — past ~78° with edge-glow's `pow(inv,3)*2` — clips to solid glow across the whole model. All four fresnel presets (edge-glow, hologram, force-field, stylized-water) and top-cover use `normalWorld`. **Displacement keeps `normalLocal`** (vertex-wave): object-space position displaced along an object-space normal is correct, and a world normal there would shear the model as it spins. Caveat worth knowing: in the fragment stage `normalWorld` resolves through the material's SHADED normal, so it reflects anything wired into the Output node's Normal channel — desirable for a fresnel, but a coupling `normalLocal` doesn't have.


### The A-Frame tab's `index.html` is DERIVED FROM THE MODULE, and it is DEFAULTS-ONLY ON PURPOSE

- **The A-Frame tab's `index.html` is DERIVED FROM THE MODULE, and it is DEFAULTS-ONLY ON PURPOSE** (`engine/tslToAFrameHTML.ts`). Two independent rules, both easy to erode:
  **(a) The uniform rows are parsed out of the `export const schema = { … }` block `buildShaderModule` emits** (tslCodeProcessor.ts), never re-derived from the node graph. That block IS the loader's uniform contract — declared properties, colours and live-audio channels all land in it — so a page built from it cannot list a uniform the shader lacks or miss one it has. Consequences: those emitted schema lines are a PARSED FORMAT now (change their shape and `parseShaderModuleSchema` must move with it — `tslToAFrameHTML.test.ts` pins both ends); every value is re-normalized on the way in (`Number()` for floats, `#rrggbb`-or-black for colours, a file-name whitelist for `src:`) because property defaults and the shader name arrive from a `.fastshader`; the attribute is emitted MULTI-LINE, one uniform per row, which is safe because A-Frame's style parser trims each `;`-separated chunk (`utils/styleParser.js`); and a uniform named **`src` is DROPPED from the rows** — that parser is last-wins and the `shader` component's own key is `src`, so emitting it would replace the module path with a number and the page would load no shader at all. That guard is `RESERVED_ATTRIBUTE_KEYS` in `tslToShaderModule.ts` and it is SHARED with the module's own usage header, which writes the same `<a-entity …>` example and had the identical collision; `buildHeader` also computes its unique-property list BEFORE branching on it, so a shader whose only property is named `src` prints the no-property example instead of a dangling `shader="src: shader.js; "`.
  **(b) The page sets NOTHING A-Frame would set itself.** No comments, no `<a-light>` rig, no `background`, no camera entity, no `orbit-controls`, no `vr-mode-ui`/`loading-screen` overrides, no geometry/material attributes — a bare `<a-scene>` with one primitive at `0 1.6 -3`. It is a page meant to be ENTERED IN VR, so the default camera, the default light rig and the default Enter-VR button are the point, not an omission; the editor preview's own lighting/background/spin/subdivision are deliberately NOT mirrored (only the primitive follows it). A test pins the ABSENCE of each of those attributes, because "helpfully" adding one back is the obvious wrong move. **The ONE exception to (b) is tessellation for a displacement shader, and it is a correctness fix rather than a taste one**: `<a-plane>` and `<a-box>` default to a SINGLE segment per axis (`aframe/src/geometries/plane.js`, `box.js`), so a plane is four vertices sharing one normal — a `positionNode` has nothing to move and the relief the editor shows is *absent*, not coarser (measured: a 0.2-amplitude wave becomes a bilinear quad off by 0.26), while a box's 24 per-face-normal vertices slide apart into six floating squares. So a module matching `/positionNode\s*:/` — this file's own predicate; the loader answers the same question structurally, off the BUILT material — gets explicit `segments-*` attributes at 64, which A-Frame maps onto `geometry.segments*` for every primitive (`extras/primitives/primitives/meshPrimitives.js`; the schema's `max: 20` is inspector metadata nothing enforces, and the app's own preview already passes 64-256). A displaced `<a-box>` used to split at its 12 shared edges at ANY segment count (BoxGeometry duplicates those positions with per-face normals) and the fix could not be inlined without costing the page its reason to exist — **the loader (0.6 and 0.8) welds them itself now**, so this page gets it free, and the same move fixed podest and every exported module. **The SECOND exception is the SINGLE-GLB export.** While the effective format is `.glb` the page hangs `shader="src: model"` on `<a-entity gltf-model="url(<name>.glb)">` (the `modelFile` option) instead of a primitive, because the export IS the model: no segments, no radius, and the same scene, backend and scripts. It needs loader 0.8 — the tab's label says so, and 0.6 reads `src: model` as a path, logs a `shader-error` and leaves the model on its own materials. The Three.js tab stays on the primitive and the `.js`. **The page carries NO script of its own**: the VR backend is forced declaratively by `<a-scene renderer="backend: webgl">` (the bundle's aframe#5847 carry — see the vendoring bullet), which is what makes three r184 take its WebGL2 backend, the only one that can enter a WebXR session (the WebGPU one hard-throws in `XRManager.setSession`). The SPELLING is load-bearing: only the raw key `backend:` reaches the patched branch and only the exact value `webgl` forces, so a typo silently does nothing and Enter VR throws on a headset much later (`aframeBackendProperty.test.ts` guards the patch; `tslToAFrameHTML.test.ts` pins the attribute AND the absence of any inline script). This replaced an inline `navigator.gpu`-hiding script on 2026-08-31; pages exported before then still carry it and keep working, since hiding gpu and forcing WebGL reach the same backend. **The two install facts live in the tab's `index.html` LABEL, not on the page** (`CodeEditor.tsx` + `lv.json`): put the `.js` beside it, and serve the folder over http(s). The second one is not pedantry — the loader `fetch`es the module, so a double-clicked `file://` page renders a plain white default-material primitive with a full working scene around it and says nothing. If the page ever stops being comment-free, that is the sentence to move onto it.

### Plain Three.js is loader 0.8's FastShaders core, and two places say so

- **Plain Three.js is loader 0.8's FastShaders core, and two places say so**: README's "Using the shader module with plain Three.js" section and the usage header every export carries (`buildHeader` in `tslToShaderModule.ts`, which links to that section; it replaced the unqualified "Also usable directly with Three.js" line).
