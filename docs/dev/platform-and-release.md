### The supported browser floor is Chrome 111 / Safari 16.4 / Firefox 126, and each engine is held there by a DIFF…

- **The supported browser floor is Chrome 111 / Safari 16.4 / Firefox 126, and each engine is held there by a DIFFERENT feature** (measured 2026-09-08 against the built `dist/`, not inferred from caniuse). `build.target` is `esnext` with no polyfills and nothing transpiled down, so the floor is simply the newest thing actually used — which means it MOVES the first time someone reaches for a newer CSS function or JS syntax, silently, with a green build. The three that set it today: **`color-mix()`** (CostBar.css, Chrome 111 / Safari 16.2 / Firefox 113) — the newest CSS in the codebase and the ONLY thing holding Chrome that high, but it carries an explicit `rgba()` literal on the line above, so below 111 the app is whole and a drop-target tint is flat; **ES2022 class static blocks**, which `monaco-editor` 0.55 ships and Safari did not take until 16.4 — the one HARD break; and the non-standard **`zoom`** (NodePreviewCard.css / ContentBrowser.css / GraphsPage.css), which Firefox did not implement until 126, below which every asset tile renders at 1/0.67 and is clipped by the strip (that file's head comment explains why no `@supports` fallback was attempted). **The Safari case is the one to remember, because it does not look like a browser problem**: `static {}` appears ONLY in the `monaco` chunk and the editor worker — verified by grepping every built chunk — and CodeEditor is `lazy()`-imported (AppLayout.tsx), so nothing on the boot path needs ES2022. Safari 16.2 therefore boots the app, renders the canvas, and fails when the CODE PANEL is opened. index.html's boot watchdog cannot help there: it speaks only while `#root` is still empty, and React mounted. That watchdog (a bilingual "the browser is too old" note, shown after 15 s and taken back down if a slow boot arrives) is the ONLY enforcement anywhere — nothing feature-detects, deliberately, because every candidate test has browsers where the app boots and stays useful and blocking those would be a regression. The numbers are stated for READERS in three places and are a drift set: index.html's fallback text (bilingual, user-facing), README's Browser support table, and here. `public/eval/index.html` deliberately restates NONE of them — it `location.replace`s to the app, so a study participant on an old browser gets index.html's note by construction, and a fourth copy of the numbers would only rot.

### Offline/desktop

- **Offline/desktop**: the app must run with NO network. Monaco is bundled locally (`CodeEditor/monacoSetup.ts` — `loader.config({ monaco })` + Vite `?worker` workers; never reintroduce the jsdelivr CDN loader) and fonts are self-hosted (the `@fontsource/inter/*.css` + `@fontsource/jetbrains-mono/*.css` weights are imported directly in `main.tsx` AND `nodeEditor.tsx`, and the `fs-fontsource-woff2-only` vite plugin strips the legacy `.woff` fallback `src` from the vendored @fontsource CSS at build time so only the woff2 subsets ship — never reintroduce a jsdelivr/Google-Fonts CDN link). `FS_DESKTOP=1` — set automatically for `tauri dev`/`tauri build` via the CLI's `TAURI_ENV_*` env — switches vite to the desktop profile: base `/`, CSP meta suppressed, ShaderCarousel excluded from dist (it ships instead as a Tauri resource staged in `src-tauri/carousel-dist/`, served over LAN by the in-app bench server — see the src-tauri bullet under Subprojects), and the `__FS_DESKTOP__` define hides the "Download app" button + SC link and shows the "VR" bench popover. The desktop build also raises the size caps — 6M chars per image (the one figure still under the unchanged 8M per-image hard ceiling, which bounds every single payload on both builds), 32M per project and library, a 256 MiB zip read — through `utils/platformCaps.ts` and zipReader's `READ_*` constants. vitest always runs the WEB profile, so desktop values are tested only through the `DESKTOP_CAPS` table or an explicit parameter, and every web cap is pinned unchanged. Preview-iframe asset URLs resolve via `new URL(base + path, location.href)` (`resolveAssetUrl` in `tslToPreviewHTML.ts`) so they survive non-http schemes (tauri://) — don't revert to `location.origin` concatenation.

### Feedback ("!" toolbar button)

- **Feedback ("!" toolbar button)**: the red `!` in the toolbar's right cluster opens `Modals/FeedbackModal` — a composer that assembles a plain-text report and hands it to the user's own mail client via `mailto:`, with a clipboard fallback. **Nothing is uploaded, and that is a constraint rather than a preference**: the build CSP is `connect-src 'self' blob: <deploy origin>` + `form-action 'self'` (`vite.config.ts`), so a POST to Formspree / Google Forms / any hosted endpoint is blocked by the app's OWN policy; the desktop build must work with no network at all; and a third-party form would make someone else a data processor for grant-funded research feedback. A `mailto:` navigation is CSP-exempt (navigation, not a fetch) and works in every build. If a server-side endpoint is ever wanted, it needs a `connect-src` widening plus the mailto path kept underneath for the offline case — don't quietly swap one for the other. Report assembly is PURE and tested in `utils/feedbackReport.ts` (the DOM reads live in the modal): the opt-in technical block carries version/build, **graph counts (nodes, how many are connected, connections, groups, notes), cost points vs the selected headset profile, and the preview mesh (built-in geometry name, or a custom model's name + vertex count + size)**, then browser/platform/renderer/display. Counts only — no graph content leaves. Edges are counted on the UNWRAPPED graph (`unwrapCollapsedGroupEdges`), or the same project would report differently depending on which frames happened to be collapsed. `previewMesh.countMeshVertices` (and the compressed-glTF pre-check `inspectGltfCompression`, which reads only the two top-level extension-name arrays) is a **deliberate, narrow exception** to that module's "bytes are never parsed on the trusted side" rule: it counts OBJ `v` lines or reads integers out of a length-capped glTF JSON header — no geometry built, no URI resolved, no buffer touched, every path bounded, every failure returning null. The glTF MODEL reader (`utils/gltfReader.ts`) is the separate, larger documented exception, and the feedback report does not use it. It reports the AUTHORED vertex count, not what THREE ends up with (the OBJ loader emits non-indexed geometry and `fit-bounds` then welds duplicates), so don't reason about GPU cost from it. Also: `MAILTO_SAFE_CHARS` steers over-long reports to "Copy report" because Windows' shell truncates `mailto:` URLs around 2000 chars — a silently truncated bug report is worse than none, since the user believes they sent it. `previewBackend()` RESTATES the `__fsForceWebGL2` rule that `tslToPreviewHTML` emits as source text into the iframe (it can't be imported and called); `feedbackReport.test.ts` extracts that emitted function from the generated HTML, evaluates it, and fails if the two disagree — so a change to the WebKit-forcing rule can't silently make feedback reports lie about which renderer the user was on.

### Centralized vendoring (single source + sync)

- **Centralized vendoring (single source + sync)**: the A-Frame IIFE bundle (`a-frame-180-a-01.min.js`), the shaderloaders and orbit-controls live ONLY in `a-frame-shaderloader/js/`. The `fs-vendor-sync` vite plugin (`vite.config.ts`) copies **the bundle, loader 0.8 and orbit-controls** into `public/js/` (plus the bundle into `ShaderCarousel/components/three/`) at dev/build start; `src/vendorSync.test.ts` fails on drift in EITHER direction — a copy that diverges, and a `NOT_VENDORED` script that reappears. **0.4, 0.5 and 0.6 are deliberately NOT vendored** (0.4/0.5 since 2026-08-31, 0.6 since the loader switch): nothing resolves them same-origin — the preview and podest load 0.8, while older exports name them on the jsdelivr CDN, i.e. from the SUBMODULE — so a copy is dist nothing can load. They stay FROZEN in the submodule, because that is what already-exported shaders fetch. **A dropped copy leaves the hosts diverged**: the plugin only ever copies, GitHub Pages deploys with `force_orphan` and loses the file, while alvismisjuns and sferas upload with psftp `put -r`, which never deletes, and keep it — and an app tab opened before a Pages deploy fails its next preview rebuild against the removed file until it is reloaded. **Never hand-edit the copies** — edit the submodule source and re-run vite. Everything runs **Three.js r184**: the bundle (super-three 0.184), `node_modules/three` (`^0.184.0`), and the carousel's standalone ESM `ShaderCarousel/lib/three/*.min.js` (the official minified builds copied from `node_modules/three`, used by static/microplane benches via import map). The glTF decoders live in `a-frame-shaderloader/js/decoders/` — three r184's glTF Draco build and `meshopt_decoder.module.js` for MESHES, and `basis_transcoder.{js,wasm}` (the Basis Universal transcoder three's `KTX2Loader` runs) for KTX2 TEXTURES, plus a README carrying their provenance and the Apache-2.0 text Draco's and Basis's licences both require to travel with them. They are synced to `public/js/decoders/`, and `vendorSync.test.ts` also pins them byte-identical to `node_modules/three/examples/jsm/libs` and the README's size/sha256 table to the files. A three bump therefore fails until they are re-copied — which for the basis pair matters more than it looks, since a transcoder built for a different `KTX2Loader` worker protocol fails INSIDE a Worker, where nothing surfaces. Loader 0.8's `FastShaders.decoders` section (13b) is what installs them; exports fetch them by URL beside the loader, so push the submodule and purge all six files on jsdelivr, and never move them. The two committed Draco/meshopt test fixtures under `src/engine/fixtures/compressed/` are ENCODED by `scripts/gen-compressed-fixtures.mjs` from encoders already on disk (three's `draco_encoder.js`, and `meshoptimizer`, which is only a transitive dev dependency of `@types/three`), so the script is documentation-grade and CI never runs it.

### Push the `a-frame-shaderloader` submodule BEFORE the release tag, and PURGE jsdelivr when the pushed file is n…

- **Push the `a-frame-shaderloader` submodule BEFORE the release tag, and PURGE jsdelivr when the pushed file is new.** Exported `.js` reference the loader at `cdn.jsdelivr.net/gh/Alvis1/a-frame-shaderloader@master` (`CDN_BASE`, `tslToShaderModule.ts`) — as does the A-Frame tab's generated `index.html` (bundle + loader, the same two files the header names), while the app's own preview reads the same-origin `public/js/` copies (`resolveAssetUrl`) — so a loader pushed after the app deploys 404s for **every recipient of an exported shader while working perfectly for the author**, and jsdelivr caches branch refs (~12 h) AND caches the 404, so it does not self-heal on the next request. Force it: `https://purge.jsdelivr.net/gh/Alvis1/a-frame-shaderloader@master/js/<file>` — for the loader switch that is `js/a-frame-shaderloader-0.8.js` plus the five `js/decoders/` files (the Draco pair, meshopt, and the basis transcoder pair, whose sha256s must start `8478b5b6d6b74e7d` / `6cf17dc889352c42`), each checked with `curl -sL <cdn url> | shasum -a 256` against the local file. The full order: push the submodule → commit the parent's pointer bump and run `npm test` → purge → `npm version patch && git push --follow-tags` → `npm run deploy:alvismisjuns` → `npm run deploy:sferas` (held while a study cohort runs — the participant's preview changes loader). Push from the MAIN checkout's `a-frame-shaderloader/`, fast-forwarded from wherever the work was committed: a worktree's `--shared` submodule clone has the main checkout's submodule as its `origin`, whose checked-out `master` refuses the push. Order matters for a second, independent reason: `release.yml` checks the submodule out at the pointer RECORDED here (`submodules: recursive`) and `vendorSync.test.ts` compares it against the TRACKED `public/js/` copies, so an un-bumped pointer fails the release's own test gate before a single binary is built.
