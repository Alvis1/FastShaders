### Eval mode (`…/eval` — the user-study switch, `src/eval/` + `public/eval/index.html`)

- **Eval mode (`…/eval` — the user-study switch, `src/eval/` + `public/eval/index.html`)**: a research mode for the paper's SUS + telemetry study (design + references in `EVAL_MODE_PLAN.md`; deviations in its §7 are what shipped). The redirector arms a **sessionStorage** flag (`fs:evalArm`, sampled ONCE at module init — never localStorage, or the browser stays in eval mode forever) and drops the previous session record so every `/eval` visit re-runs consent; a mid-session reload of the APP url resumes instead. App-side: `EvalGate` (mounted in App.tsx behind `isEvalMode()`) shows the ConsentModal BEFORE any logging, and Agree adopts the participant code as the SHADER NAME (so the artifact inside the package is `shader/p01.js`, identifiable without opening the zip — and `newGraph()` inside a session resets to that code rather than the default — `evalShaderName()` in telemetry.ts — so a NEW pressed mid-session keeps it: J0302 of the 2026-10-20 sessions pressed NEW before their first node and their shader came back as `my-shader.js`; an empty code keeps the default) and runs `cleanSlateForStudy()` — `newGraph()` alone is NOT a clean slate: the preview mesh (store + IndexedDB), `fs:previewUniformValues`/`Bounds` (persist BY NAME; auto-names collide, and both ride `buildShaderBundle()` into the study zip) and the undo history (newGraph's own entry = one Cmd+Z from the previous user's document) must all be cleared; `fs:savedGroups` deliberately survives (owner's library — study-machine hygiene is a researcher step). **Telemetry**: `evalLog(type, payload)` — no-op outside a session — called from a REVIEWED chokepoint set pinned by `evalHooks.test.ts` (store graph actions; NodeEditor's `applyConnection`/keydown-delete/`placeTilePayload`; CodeEditor's two Apply gestures — deliberately NOT `requestCodeSync`, which projectImport also calls, so imports would count as Applies; `downloadShader`). telemetry.ts must never import the store (the store imports IT — EvalGate registers a bridge for snapshots and the 250 ms-debounced `preview-rebuild`, since raw `previewCode` advances per scrub frame). Events sit on ONE monotonic clock: the journal persists a wall anchor (first page's `performance.timeOrigin`) and recovery REBASES new timestamps — without it a reload mixes two `performance.now()` epochs and every duration is garbage; recovery also re-logs current visibility/focus (a page that loads visible fires no `visibilitychange`, so the flushed pre-reload `hidden` would otherwise close presence forever), and blur INTO the app's own preview iframe is tagged `target:'iframe'` = still present. The journal is **sessionStorage** (`fs:evalJournal`) — a consent decision: it survives the reload recovery exists for, dies with the tab (the promised withdrawal), and stays out of the fs:graph localStorage quota. **The single-GLB export is never offered in a study session**: EXPORT there opens the finish dialog, `exportFormatFor` answers the bundle for every surface, and the popover renders no smaller export button — only the "Export model" checkbox (the popover itself IS reachable there by right-click), `buildShaderExportChecked` returns the bundle path under `isEvalMode()` before any `.glb` call, the desktop Work folder neither lists nor opens a `.glb`, and SusModal keeps bare `buildShaderBundle()` — so the study zip is unchanged and `CONSENT_TEXT_VERSION` does not move. **EXPORT is the finish control and the action is SUBMIT** — in a study session it opens `EvalFinishModal` ("Are you finished?" → Continue working / Submit) rather than downloading a bare shader, because that is the button a participant reaches for when they think they are done; Submit opens the questionnaire and the ONE package is built at ITS submit, whose thank-you screen OFFERS the addressed email as a button, never opens it (sending from the participant's own client hands the researcher an identifying address, hence opt-in since consent-3; a mailto navigation is CSP-exempt, and the attachment is the one step mailto cannot do, hence the download first + the file named in the body) (the SUS answers belong inside it, and a second pre-questionnaire zip would give the researcher two files per participant that `eval-analysis.mjs` counts twice). **No study dialog closes on a click outside it** (2026-10-02, pinned by `evalDialogs.test.ts`): the consent never did, and now neither do its Details, the finish dialog, the questionnaire or the thank-you screen — they close only through their own buttons, plus Escape where it has a safe answer. The questionnaire is long and scrolls, so a scrollbar drag or a text selection released past the panel's edge delivers its `click` to the backdrop: with a close handler there the form vanished mid-answer, and on the thank-you screen the Download and email buttons went with it. **Every study dialog goes through ONE helper, `useStudyDialog` (`src/eval/studyDialog.ts`; same test), which makes the app behind it INERT and swallows every key but Tab in the window capture phase.** Inert first (`#root.inert`, ref-counted — the dialogs are portals on `document.body`, outside it): swallowing keys alone left focus free to LEAVE the panel, and Tab from the consent walked to EXPORT behind it, where Enter opened the questionnaire before Agree and produced a package with no consent record that was downloaded AND uploaded; Shift+Tab from the questionnaire reached Monaco, where typing changed the packaged shader with nothing logged; Tab reached the canvas nodes, where the arrows moved them. The consent also makes its own panel inert while its Details dialog is open (Details is a later portal, so Shift+Tab from it landed on the hidden "I agree", and Enter recorded consent), and Submit refuses outright without `isEvalSessionActive()`, so no path can package a session that never consented. Then the keys: the canvas and the code panel bind Delete/Backspace/X/A, ⌘Z and ⌘S on `window`, so a Backspace on a focused radio deleted the selected nodes behind the questionnaire, ⌘Z in the comment box undid a graph edit, ⌘S logged a code Apply, and — once a click outside stopped closing the dialog and left focus on the page — typing "a", "x" selected and deleted the whole graph. Each was logged after `sus-open`, so `no-edits-after-sus-open` failed and the package carried a different shader than the one rated. Typing, radio arrows and the textarea's own undo are default actions and keep working; ⌘S alone is prevented, because the code panel's handler that used to prevent it no longer sees it and the browser's Save Page dialog opened over the study instead. Telemetry's own window-capture activity listener is registered at Agree, so it still runs first; so is `useKeyboardNav`'s (it mounts with the canvas), which is why that hook ALSO stands down while any `aria-modal` dialog is open, not only when the key's target is inside one — a click outside a study dialog leaves focus on the page, where Alt+Arrow walked it to a pane and the arrows moved a node behind the questionnaire. From Submit to the thank-you screen the questionnaire is BUSY: Escape and "Back to the editor" do nothing, every answer control and its EN/LV button are disabled, and a "Packing…" line shows, because the preview capture can take 4 s with nothing changing on screen.
