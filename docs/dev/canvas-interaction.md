### Adding a node — one placement path

- **Adding a node — one placement path**: right-click canvas, **Shift+A** (opens AddNodeMenu at canvas centre; the search box autofocuses, so Arrow/Enter completes a keyboard-only add), dropping a wire on empty space, dragging a palette tile, or **clicking/Entering a palette tile**. Every tile route funnels through `tileDrag.ts` — `tileActivationProps` → `dropTileAtCanvasCenter` dispatches the SAME `fs-tile-drop` CustomEvent the touch-drag path uses, so `placeTilePayload` (including drop-on-edge splicing) stays the single implementation. Don't add a parallel placement path. **A click/Enter add is SCATTERED off the canvas centre** (`nextTileScatter`, 2026-09-09, owner request): it used to aim at the exact centre, so pressing a tile twice dropped the second node precisely on the first — indistinguishable from nothing having happened, which is how a repeated add reads as broken. Three things are load-bearing. The offset is in SCREEN px, applied before `screenToFlowPosition`, so the visible gap is the same at every zoom (a flow-space offset is invisible zoomed out and a shove zoomed in, and all that matters is that the cards do not sit on each other on screen). The angle steps by the GOLDEN angle plus bounded jitter rather than rolling free — a plain random angle repeats, and two of a handful of rolls landing a few degrees apart is exactly the stacked pair this prevents; the bounded step is always between a quarter and three quarters of a turn from the previous one, so `cos(Δ) <= 0` and two consecutive adds are at least `√2 · SCATTER_MIN_PX` (~34px) apart whatever the radii. And a DRAG is never scattered — the drop position is the user's aim, and nudging it would be the app arguing with a gesture (`tileScatter.test.ts` pins the single call site, since the vitest env is `node` and `dropTileAtCanvasCenter` reads a canvas rect). The AddNodeMenu is deliberately NOT covered: it places at the menu's own point, which for a right-click is where you pointed, and Shift+A's canvas-centre add costs a search and a keystroke per node rather than one repeatable press. **A SINGLETON type is not added twice — the gesture becomes "take me to it"** (`components/NodeEditor/singletonNodes.ts`; today the set is just `soundNode`, the Sound node — see its convention for why). Both add surfaces ask `findSingletonNode` and, on a hit, glide to the existing node through the same `focusNode` every other "take me there" gesture uses, instead of adding. In BOTH the check sits ABOVE the auto-connect that follows it, and for the same reason on each side: NodeEditor's tile path has already previewed a drag-connect plan against a PHANTOM id for a node that is now not going to exist (so it also clears the preview, or the highlight outlives the gesture), and AddNodeMenu may have been opened by dropping a WIRE, where connecting that wire into the pre-existing node would be a connection the user never aimed at. It is an ADD-SURFACE rule, not a graph invariant — a file from before the fold, or a hand-edited one, may still hold two, and nothing deletes one behind the user's back. **Several output nodes may coexist, and exactly ONE is ACTIVE** (2026-09-03; `utils/sdfPartition.ts` `activeSink` — see the several-outputs convention below). The Output's Add-menu row and palette tile simply ADD one (inactive unless it is the graph's first); paste/duplicate keeps Outputs in the clone set and strips the active flag off the clones; nothing redirects any more. (Until then the Output was a singleton and every add surface glided to the existing node; `outputFocus.ts` keeps only the framing helpers — `costFocusId` is the active sink — and `outputFocus.test.ts` now pins the OPPOSITE of the old redirects.) Related: the Output tile's preview socket reads `--node-cost-text` only under `.react-flow` — the token is published on `.node-editor`, which the asset bar also sits inside, so an unscoped read turned the TILE's socket white-on-white on a dark canvas (`outputTargetChip.test.ts`). **AddNodeMenu rows are ONE line — name + cost + category — and the description is the row's `title`**, picked up by the app-wide `TooltipLayer` (which delegates from `document` and borrows any `title`), so the menu is a list you scan and the explanation arrives on hover, in the same place the palette tiles put it. It used to render inline under each row: ~74 nodes each carrying a paragraph, and the widest description (Data Viz, 274 chars) is what forced `.context-menu--add-node`'s explicit width in the first place (now 280px, still explicit so the box doesn't resize itself around whatever the current search returns; `.fs-tooltip` wraps at its own 260px). The tail-stripping `displayDescription` is used here now — the inline line printed the `Also: …` search aliases. **Hover must NOT scroll the list**: `onMouseEnter` sets `focusedIndex` too, and the `scrollIntoView` that keyboard navigation needs fired a `scroll` event, which is one of TooltipLayer's dismiss triggers — it landed inside the 1 s dwell of the tooltip the same hover had just armed, and with the pointer then at rest no further `mouseover` re-armed it, so any row clipped by the list's bottom edge could never show its description at all (measured: scrollTop 47 → 66, tooltip never appeared). `scrollOnFocusRef` gates the scroll to keyboard moves and list swaps; `hoverFocus()` is the pointer path. Arrowing a row still shows no tooltip — arrow keys move `focusedIndex`, not DOM focus, so `focusin` never fires. `.context-menu__item--stacked` survives for DataRangeSettingsMenu's hint rows (the modifier exists because `.context-menu__item` is a shared single-row flex used by every submenu). **A press anywhere else CLOSES the menu** (`ContextMenu.tsx`, 2026-09-09, owner request). Until then the only closer was NodeEditor's `onPaneClick`, so the menu shut on bare canvas and stayed open for everything else — most obviously a click on a NODE, which is where a hand goes straight after opening that node's settings. It is **`pointerdown` in the CAPTURE phase**, for two independent reasons: React Flow's node handlers stop `click` propagation for their own gestures, so a bubble-phase click listener never hears the press that matters; and a press that becomes a DRAG produces no click at all while being unambiguously "I am doing something else now". It cannot eat its own opening press — the effect is armed only while `open`, and a right-click's pointerdown precedes the `contextmenu` that opens the menu. Two exemptions: the menu's own subtree (`ref.current.contains`), and `DISMISS_EXEMPT` — the popovers a settings menu itself opens (`.palette-pop`, `.mesh-picker__pop`), which portal to `document.body` and are therefore OUTSIDE the menu's subtree, so without the exemption picking a colour closed the menu the swatch belongs to. `onPaneClick` stays: closing twice is idempotent and it also clears the label peek, which this must not touch. Lives on the DISPATCHER beside the Escape handler, so every menu type gets both at once; `contextMenuDismiss.test.ts` pins the phase, the arming, both exemptions and that the two exempt classes are the ones those popovers really use.

### Double-click (or double-tap) a node and EVERY one of its socket labels stays up

- **Double-click (or double-tap) a node and EVERY one of its socket labels stays up** (`components/NodeEditor/labelPeek.ts`, pure + tested; the class goes on React Flow's node WRAPPER, the `fs-menu-active` idiom, and `.fs-labels-shown .typed-handle[data-tooltip]::after` in TypedHandle.css is the fourth trigger for the label the socket already has — same placement, never a second kind of bubble). A socket name is otherwise a one-at-a-time thing: you hover a dot and read one bubble, which is the wrong shape for the question people ask of an unfamiliar node — the whole port list — and unanswerable on touch, which has no hover. **It is built on CLICK, not `dblclick`**: a double TAP does not reliably synthesize a `dblclick`, which is exactly why the Color node carries a long-press beside its own `onDoubleClick`, so counting two clicks on the same id inside `DOUBLE_ACTIVATE_MS` (400) is what makes one implementation serve both pointers; clicks on two DIFFERENT nodes are never a pair however fast they arrive, and a backwards clock cannot pair an ancient click. Anything that already owns a double-click keeps it — `PEEK_EXEMPT_SELECTOR` (the number box's click-to-edit, a textarea's caret, `input`/`select`/`button`) and `PEEK_EXEMPT_NODE_TYPES` (the Color node, whose whole body IS its swatch and which has one socket to name). One node at a time, and three ways out: the same gesture again, Escape, or a click on empty canvas — the last two matter because touch has no Escape and on a dense graph the node you peeked may be under its own labels. **This is deliberately NOT the thing that was tried and rejected**: pinning every label while a node is SELECTED drowned the card in text (the note above `.typed-handle--tapped`), because selection happens constantly and as a side effect of dragging; a gesture that is asked for and put away is a different proposition. State is LOCAL to NodeEditor and applied imperatively — looking at a node's ports is not an edit, so it must never push through history, the autosave or a shared file.

### A socket's label has ONE placement, whatever made it appear

- **A socket's label has ONE placement, whatever made it appear** (`handles/TypedHandle.css`, audited 2026-09-03). The name-and-type label (`data-tooltip`, the instant light bubble) shows on four triggers — pointer hover, a touch tap, the drag-reveal while a wire hunts nearby (`reveal`), and the drag-connect preview (`.fs-connect-socket`) — and used to land in two places depending on which: hover and tap ABOVE the dot, the two drag states BESIDE it, so the same label jumped as the gesture changed and read as two tooltips. Placement is now a property of the SOCKET: beside it on its outer side — left of a left-edge input, right of a right-edge output, above/below the Color node's perimeter output when it rides the top or bottom — centred on the dot, outside the card, keyed on React Flow's `.react-flow__handle-{left,right,top,bottom}` classes. The triggers decide only WHEN it shows and its emphasis (connect adds the arrow and border). Every label is in FRONT: the reveal's old `z-index: -1` bought nothing (a label 6px off the dot never covers it, and the dragged wire lives in React Flow's connection layer, whose order against the nodes layer no z-index inside a handle can change). MEASURED in Chrome over Float/mul/Mic/Colormap/Output/Color sockets and a collapsed-group pill: hover, reveal and connect all report the label beside the dot, 4px gap, dy 0, no clipping ancestor. Two other tooltip classes stay deliberately distinct from this one: PROSE (`title` → the app-wide TooltipLayer's dark bubble, 200 ms dwell — node headers carry the var name this way, chips their explanation), and asset-tile hover cards. A `title` on a `pointer-events: none` element is DEAD (TooltipLayer resolves its host from `elementFromPoint`), and two were: the collapsed group pill's socket label (removed — the socket beside it already carries the name) and the Colormap ramp (removed — the rows region overlays the strip, so even a hit-testable strip never receives the pointer; the name is one right-click away in the node's settings). Related: hovering a socket after a drag or wire-drop works — an earlier probe that said otherwise had dragged the node under the bottom chrome — and React Flow's own auto-pan near the pane edge slides a drag-connect target away from the held node, which is why a ring can vanish at rest only near the canvas edge.

### F frames the selection

- **F frames the selection** (`focusNodes` in `outputFocus.ts`, bound beside Shift+A in NodeEditor): the "view selected" key of every node editor, through the SAME animated, zoom-capped glide (`OUTPUT_FOCUS_FIT`) the Output tile, the Add-node row and the cost pill use — `focusNode` is now its single-node case — so every "take me there" gesture lands identically. A selected member hidden in a collapsed group frames the pill standing in for it (`focusTargets` maps each id through `outputFocusTarget`, dedupes, drops stale ids). With NOTHING selected it frames the whole graph through `glideFitAll` — the SAME call the canvas bar's ⤢ button makes, so the two cannot land differently — because a key that silently does nothing reads as broken. **Every control that moves the view glides the same way** (2026-09-16, owner: "keep zooming style consistent"): `VIEW_GLIDE_MS` (500) in outputFocus.ts is the one duration for the cost pill, F, and the canvas bar's −/+/fit, which used to SNAP because React Flow's `zoomIn`/`zoomOut`/`fitView` take no duration by default; all of them then share d3's cubic-in-out. The −/+ buttons go through `glideZoom` → `zoomTo`, NOT `zoomIn({ duration })`: React Flow scales the CURRENT transform, so a second press mid-glide interrupts the first at its half-finished zoom and two quick presses land well short of two steps (and an interrupted d3 transition never resolves its promise, so that cannot be used to know when a glide ended). `zoomStepTarget` steps from the pending glide's TARGET instead — MEASURED, three presses 80 ms apart land on exactly 1.2³ — and the pending target is dropped whenever the user drives the view: React Flow's own wheel/drag through `onMoveStart`'s non-null event, and by hand on the three paths that call `setViewport` directly (trackpad wheel pan, double-tap drag, two-finger touch), which `outputFocus.test.ts` counts. A bare key, so it must never fire while typing: INPUT/TEXTAREA (Monaco's input is a textarea), SELECT (the Audio node's picker lives on the canvas) and contentEditable are skipped, and any modifier bails so Cmd/Ctrl+F stays the browser's find. `outputFocus.test.ts` covers the helper and source-pins the binding and its guards; MEASURED: F on a selected Output lands it at the canvas centre at zoom 1.5, F on nothing fits every node inside the canvas, F in the name box types an "f" and moves nothing. **A selects every visible node** (`selectAll.ts`, bound in the same handler under the same guards): Blender's key beside Shift+A and F. "Visible" excludes members hidden inside a collapsed group — the pill stands in for them, and selecting invisible nodes would let Delete remove what nobody could see was selected — but includes frames and notes (React Flow skips a child whose parent is also dragged, so frame plus members drag once). Pressed with everything already selected it DESELECTS all, the only modifier-free way back out (Cmd/Ctrl+A stays the browser's). It dispatches React Flow `select` changes through the store's `onNodesChange` — the marquee's own path — so it is a selection change, not an edit: no history entry, no autosave, no resync, and Cmd+Z after it undoes the previous real edit. MEASURED: 0/3 → A → 3/3 → A → 0/3, a partial 1/3 → A → 3/3, A in the name box types an "a", Cmd+A and Shift+A untouched.

### Floating chrome over the canvas must never move the canvas underneath — `nowheel`

- **Floating chrome over the canvas must never move the canvas underneath — `nowheel`** (2026-09-09, reported as "when I try to scroll in the properties window of a node, the node editor scrolls"). NodeEditor binds its wheel handler on `.node-editor__canvas` in the CAPTURE phase, and every panel that floats over the graph is a DESCENDANT of that element, so an ancestor listener beats the scroll container the wheel was actually aimed at: with trackpad scrolling on, a wheel over a settings menu panned the graph and the list did not move. The handler honours React Flow's `.nowheel` opt-out, so the escape is that class on the floating shell — `.context-menu` carries it now (ONE class on the shared shell, so no submenu can be added without it), beside the canvas bar's Panel and the note body. The other valid escape is portalling OUT of the canvas, which is what `MeshTargetPicker` does (`document.body`). `canvasWheel.test.ts` sweeps every stylesheet under `components/NodeEditor/` for `overflow-y: auto` and fails on a scroll container that is neither — so a new one cannot quietly reintroduce the bug.

### Canvas navigation — the ONE model, by input device.

- **Canvas navigation — the ONE model, by input device.** Everything below is an implementation detail of these four sentences; if a change makes one of them false on any platform, the change is wrong.
  - **Mouse (macOS and Windows alike): the WHEEL ZOOMS, the MIDDLE BUTTON PANS.** Wheel-to-zoom is React Flow's `zoomOnScroll`, which the custom wheel handler falls through to (see the next bullet for how a mouse wheel is told from a trackpad); middle-drag is `panOnDrag={DESKTOP_PAN_ON_DRAG}` = `[1, 2]`, i.e. middle AND right button — right is included because it costs nothing and some users reach for it, while LEFT stays free for marquee selection and node dragging.
  - **iPad and touchscreen: TWO FINGERS PAN, PINCH ZOOMS.** There are no wheel events on a real touch screen, so the gesture is re-created from raw pointers by the touch-nav effect: centroid drag = pan, finger distance = pinch-zoom anchored to the pinch centre. Unambiguous, because the raw pointers say how many fingers are down.
  - **Trackpad: the user SAYS so — `trackpadScroll`, right-click the toolbar → "Trackpad scrolling".** With it on, a two-finger vertical swipe pans (pinch still zooms, which is the trackpad's native zoom anyway); with it off, the mouse model above applies. Two-finger HORIZONTAL pans in both modes — `deltaX` on its own is unambiguous whatever the device — and pinch / `Ctrl`/`Cmd`+wheel pass straight through to React Flow in both, so **zoom is never unreachable**.
  - **Why a setting and not a device sniff.** A trackpad's two-finger swipe and a mouse's wheel notch arrive as the SAME event. A heuristic was built (`wheelKind.ts`: pixel-vs-line delta mode, then the legacy `wheelDelta` detent of 120), shipped, and REVERTED, because it read a real macOS mouse as a trackpad and took that user's zoom away — almost certainly because macOS accelerates mouse wheels too, so `wheelDelta` is rarely a clean multiple of 120, and the per-gesture latch let one such event poison a whole scroll. **Two properties make the class unsafe to guess at**: the failure is ASYMMETRIC (misreading a trackpad costs a pan you repeat; misreading a mouse removes a primary control), and it is UNTESTABLE from here — CDP's `Input.dispatchMouseEvent` hardcodes `wheelDeltaY` to ±120 whatever delta you request, and a constructed `WheelEvent` leaves it at 0, so neither reproduces the hardware the rule must be right about. `trackpadScroll.test.ts` fails on `wheelDeltaY`/`wheelDeltaX`/`deltaMode` reappearing in NodeEditor: do not reintroduce a sniff without ground truth measured on a real mouse AND a real trackpad. The flag DEFAULTS to the mouse model — historical behaviour, and a wrong default must cost the recoverable thing. It is read with `getState()` INSIDE the wheel handler, never closed over: the listener is bound once, so a captured value would freeze the setting at mount and the toggle would read as doing nothing until a reload.
  - The toolbar's right-click popup (`.toolbar__prefs-popover`) is that toggle's home, holds the two optional-category switches beside it (Textures, Distance fields — see that convention) and the GLB import's “Allow more than 10 materials” override (hidden in a study session; its hint is its OWN constant, since `optionalCategories.test.ts` counts `OPTIONAL_CATEGORY_HINTS`, and the popover's height is computed from the row count inside the component because that row comes and goes), and is the natural place for any later app-wide preference. It is a plain LIST with no heading (the "Input settings" title went on 2026-09-04 when the library rows arrived: a heading over three checkboxes was a row that did nothing — and its `aria-label` is "Settings" now, since a name that fits only the first row misnames the other two to a screen reader), ONE line per setting — the explanation is the row's `title`, raised by the app-wide `TooltipLayer`, the same "a list you scan, the detail on hover" rule the Add-node menu follows. The title sits on the LABEL, which wraps both the box and its text, so either half raises it (TooltipLayer resolves its host with `closest('[title]')`). It refuses to open on a text input — a field's context menu is the one place users genuinely rely on the OS one — and on the EXPORT / Download-app / ☰ controls, which own right-click for their own popovers; EXPORT's handler `preventDefault`s but does NOT `stopPropagation`, so without that guard both popovers opened at once. **It also opens on a touch LONG-PRESS anywhere on the bar** (`useLongPress(barRef, …)`, 2026-09-04 — iPadOS dispatches no `contextmenu` from a sustained touch, and the list is the ONLY way to switch the optional categories on), through the SAME guard (`prefsClaimedElsewhere`, module scope) so the two gestures cannot disagree about who owns a spot on the bar. Untested on a real iPad.
  - **One finger on touch never navigates** — it drags nodes and edges, draws, and marquee-selects, which is why `panOnDrag` and `selectionOnDrag` are both OFF on coarse pointers (`isCoarsePointer`). With React Flow's drag-to-pan on, the FIRST finger of a two-finger pan lands on the pane and opens a rubber band instead, so an empty-canvas two-finger pan came out as a selection box; dropping both leaves the touch-nav effect unopposed. The desktop model is untouched by any of this.
  - **Escape hatches that must keep working**: `Ctrl`/`Cmd`+wheel zooms on every device, and double-tap-and-drag pans on a trackpad, where the natural "grab" gesture is tap-tap-hold-drag and `panOnDrag={[1, 2]}` gives it no button.


### A canvas gesture takes the preview iframe out of hit-testing

- **A canvas gesture takes the preview iframe out of hit-testing** (`:root.fs-canvas-busy .shader-preview__iframe { pointer-events: none }`, armed by NodeEditor's `setCanvasBusy`). The preview is a SANDBOXED, opaque-origin document, so the instant the pointer crosses into it the parent stops receiving mouse events at all — including the `mouseup` d3-zoom listens for on the window. A middle-button pan dragged over the preview therefore **never ended**: release the button there and the canvas kept panning, because as far as the parent knew the button was still down (reproduced, and re-reproduced as a negative control by disabling just this rule). Node drags and connection drags cross the same boundary and hang the same way, so all three bracket it: `onMoveStart`/`onMoveEnd`, `onNodeDragStart`/`onNodeDragStop`, `onConnectStart`/`onConnectEnd`. The counter is REFCOUNTED because those overlap — React Flow fires `onMoveStart` for the pan under a selection drag — and a boolean would let whichever ended first re-arm the iframe under the one still running. Each release sits ABOVE the early returns in its handler (the drag-chrome rule), and NodeEditor's unmount clears the class outright: a stranded flag leaves the 3D view permanently unclickable. At rest the iframe keeps every event, so orbiting is untouched. **A CONNECTION drag also arms the app-wide selection chrome** (`setConnectChrome` beside it, over `beginDragChrome(null)` — utils/dragChrome.ts, the same refcounted `.fs-dragging` every seam grip uses; `null` because React Flow owns the pointer's look during a connect and a pinned `move` would fight the connection line). A wire drag sweeps the pointer across the whole window, and the engines disagree about whether the PRESSED element's `user-select: none` protects the gesture: MEASURED 2026-09-18, one wire dragged off a socket painted **38 selection rectangles** over the nodes and chrome in WebKit 26.5 and NONE in Chrome 152, while a grip drag — which already armed this — painted none in either. That was the owner's report ("when edges are dragged out the strange browser selections (partial) highlight appears"), from macOS, and Chrome's clean result is an accident of where the text happens to sit rather than a guarantee. A node drag and the marquee were measured CLEAN in both engines and are deliberately left alone. The token is MODULE scope beside `canvasBusy`, because the release has to be reachable from the pointer reaper AND from unmount, neither of which can see a ref; the reaper releases it ABOVE its `canvasBusy === 0` early return, since the two flags are cleared by different handlers and a stranded `.fs-dragging` makes the whole app unselectable. `connectionDragChrome.test.ts` pins all four sites.

### Edge interactions

- **Edge interactions** (`TypedEdge` + `bezierGeometry.ts` + `NodeEditor` handlers): edges are drag-to-disconnect, and support (1) **drop-on-edge insertion** — dragging a node/tile within `DROP_ON_EDGE_RADIUS` (screen px ÷ zoom) of an edge splices it in (`findNearestEdge`/`tryInsertOnEdge`), and (2) **routing waypoints** — double-click an edge or right-click → "Add routing point" drops a draggable point the wire curves through (Catmull-Rom spline); double-click a point removes it. Waypoints live on `edge.data.waypoints` (flow coords), are **visual-only** (graphToCode/cpuEvaluator never read them; persist via localStorage autosave + undo, and are carried across a code→graph resync by endpoint match in `useSyncEngine` — like groups. They also ROUND-TRIP through a `.js`/zip export→import: `buildProjectState` embeds whole edge objects (`exportShader.ts`) and `applyProjectToStore` restores them (`projectImport.ts`), so only a BARE-SCRIPT import — one with no FASTSHADERS_PROJECT_V1 block — loses them). **`edge.data` is sanitized as adversarial input on ALL THREE restore paths** (`utils/edgeExtras.ts` — `sanitizeEdgeExtras`, called from `loadGraph`, `applyProjectToStore`, and `loadSavedGroups` — the saved-group library is the same localStorage trust level and instantiating a group clones its edges straight into the graph): it is the one graph payload the engine never reads, which is exactly why it was unvalidated, while `TypedEdge` dereferences `w.x` during RENDER with no error boundary anywhere — `waypoints: [null]` (or a string, whose `.length` passes the `hasWaypoints` gate) threw out of render, blanked the page, and the 300 ms autosave then persisted the poison so every reload blanked again. The sanitizer drops non-object edge ELEMENTS, whitelists `data` to `dataType`/`waypoints`, clamps coords to ±1e6, caps at `MAX_WAYPOINTS_PER_EDGE` (64), and returns the SAME array when nothing needed changing — the autosave subscriber and `selectionOnlyGraphChange` compare edges by `data` reference. **The renderer and the drop-on-edge hit test share `bezierGeometry.ts`** so what highlights is exactly what snaps — a routed edge is measured against the SAME spline it draws (`distancePointToSpline`). `setEdgeWaypoints` pushes history once per gesture (add/remove/drag-start), never per drag-move frame. **A splice lands on the node's first FREE input, not always its first** (`edgeSplice.ts`, pure + tested): dragging an already-wired node onto a new edge used to delete whatever fed `inputs[0]`, so a half-built Multiply lost the operand you had just given it. Candidates come from `effectiveInputs(def, connected, /*trailing empty*/ true, valued)` — so a variadic fold GROWS a fresh socket instead of reporting itself full (`append` stops when its vec4 is full — CHANNELS, not sockets; see `utils/appendCapacity.ts`), and hidden `exposedPorts` params (Image's `uv`, Mic's `gain`) stay eligible in plain registry order with `tryInsertOnEdge` calling `exposeConnectedTarget` so the new edge can't point at a socket that never mounts. Only when EVERY socket is taken does it fall back to `inputs[0]` and replace that edge — the historical behaviour. Splice-time cycle risk is unchanged by this (reachability out of the node depends on its OUTGOING edges, and the port the splice picks is incoming).

### The edge menu's "Insert node" puts a node ON the wire

- **The edge menu's "Insert node" puts a node ON the wire** (`components/NodeEditor/edgeInsert.ts`; right-click an edge → Insert node → the search list opens at the same point and whatever is chosen is spliced in). It is the SAME splice a node or tile dropped near a wire performs — `spliceNodeIntoEdge` was extracted out of NodeEditor's `tryInsertOnEdge`, which is now only the SEARCH half (`findNearestEdge` then the shared splice), so a wire spliced by pointing at it and one spliced by picking from a list cannot land on different ports under different rules. Three things are load-bearing. The edge rides in the context menu's EXISTING `edgeId` field rather than a tenth positional argument to `openContextMenu` — the field already means "the edge this menu is about" — and AddNodeMenu reads it as `spliceEdgeId`. The splice runs INSIDE `handleAddNode`'s `asOneHistoryEntry`, so the node and both wires are one undo step (the rule the palette-tile path states: one Cmd+Z must not leave a node standing spliced-out mid-graph). And **a def with no outputs is refused by the splice itself**, not at the call site: both sinks declare `outputs: []`, so `def.outputs[0].id` is a TypeError on the node type a user is most likely to reach for while pointing at a wire — the drag paths happen to guard it in their callers (`def.inputs.length > 0 && def.outputs.length > 0`), which is exactly the kind of guard a new caller forgets. Refused means the node is still ADDED where the menu was opened, just not wired. `exposeConnectedTarget` moved into the same module (it is the store-touching half of landing a connection, and the splice needs it); `edgeSplice.ts` keeps the pure port CHOICE. `edgeInsert.test.ts` drives the real store for the rewiring, the first-free-input rule and both refusals, and source-pins all three surfaces.

### A wire dropped on empty canvas connects from EITHER end

- **A wire dropped on empty canvas connects from EITHER end** (`components/NodeEditor/edgeInsert.ts` — `DroppedPin`, `connectDroppedWire`). Releasing a connection over nothing opens the AddNodeMenu with the pin that started it, and picking a node wires the two: pull from an OUTPUT and the new node is fed by that pin (its `inputs[0]`), pull from an INPUT and the new node feeds it (its `outputs[0]`). Only the output half worked, and the input half was not merely unimplemented — `onConnectStart` discarded the pin outright for a `target` handle, three functions before anything could have used it, so half the gesture opened a menu and then added a loose unwired node. **The side rides in the menu state as `sourceHandleType`, React Flow's own `handleType` vocabulary carried verbatim** so there is nothing to translate; it is not derived from the registry, because a collapsed group's synthetic boundary sockets match no registry port. Getting the direction wrong is the failure to fear here: an edge authored OUT of an input renders as NOTHING while the store keeps it and codegen still reads it. `ConnectionStub` takes the same field — React Flow keeps the two sides in separate `handleBounds` buckets and each side has its own port list for the wire's colour, so reading `source` for an input pin finds nothing and the stub silently does not draw — and mirrors its control points, or a wire dropped left of an input doubles back through its own node. **The menu's connect also stopped being a fourth connect path**: `connectNodes` is `applyConnection`'s core (single-input replacement + `exposeConnectedTarget`) extracted so both obey one rule — the menu restated neither, so it could double-feed an occupied input and point an edge at a hidden parameter socket that never mounts. The telemetry and the image→normal colour-space flip stay with `applyConnection`: they need its node scan, and the flip is unreachable from the menu today (an Image node added from the menu is EMPTY since GLB Phase 4; the texture picker can now fill one, so a wire dropped from the Output's Normal onto a menu-added Image node that is later filled connects through `connectNodes` WITHOUT the colour-space flip — a known follow-up). Known gap, deliberate: a connect made from the menu logs no `edge-connect` telemetry event, so a study session under-counts connects made this way — closing it means adding a chokepoint to `evalHooks.test.ts`'s reviewed list, which changes what a running study records. `edgeInsert.test.ts` drives the real store for both directions, both refusals and the shared rule, and source-pins the tracking.

### Drag-connect

- **Drag-connect** (`dragConnect.ts` + NodeEditor drag handlers): dragging a node so its CENTER lands on another node's body proposes a connection — the hovered node rings (`fs-connect-target`), the chosen input socket rings, and its name label is forced visible in the ONE place a socket's label ever appears (see the socket-label convention below) — beside the socket, outside the card, on the node the preview lifts to the front — and gains a focus border plus a thick arrow between label and socket pointing at the socket (`.fs-connect-socket` in TypedHandle.css: the arrow is the handle's otherwise-unused `::before`, a clip-path polygon in `--border-focus` so ring, arrow and node outline read as one system; every input handle in the app is a left-edge handle, so the arrow only needs left-side geometry. The label sat INSIDE the card first and was flipped by owner request — there it covered the row's own value widget); releasing commits exactly what the tooltip showed (even on a sub-`DRAG_HISTORY_THRESHOLD` drop — a shown preview must not lie; the plan's endpoints are re-validated at drop against mid-drag mutations like held-pointer Cmd+Z). Direction follows the side (dragged left of the hover's center → dragged.out feeds hover.in; right → hover.out feeds dragged.in; impossible/cyclic directions fall back to the other before giving up), vertical alignment picks the best (output, input) PAIR — so multi-output sources like Data-node columns choose their column by alignment too — with FREE inputs beating occupied (occupied only replaced when nothing is free; the gesture counterpart's own existing edge doesn't count as occupying, so re-docking a feeder re-recognizes its connection instead of double-feeding a second input), and cycles are never offered. **Every mounted input must be REACHABLE, and physical alignment alone cannot promise it** (measured 2026-09-02 over every dragged/hover/side combination of the 76 editor node types: 246 of 9540 left a socket unreachable). The gate sweeps only the HOVER box's height, so a dragged node TALLER than the hover node (remap, smoothstep, clamp, mix, the Output node dropped onto a Float — its `position` row was unreachable) or one whose OUTPUT socket sits far from its centre (`uv`'s is 46px above it, `select`'s 35px below — `uv` onto `add` could never ring `b`) never brings the far sockets level with anything. The planner therefore takes `draggedCenterY`/`hoverTop`/`hoverHeight` and first SWEEPS the dragged node across the hover box to check that physical alignment gives every distinct socket height a band of at least `MIN_BAND_PX` (8 flow px — `select` onto `mul` technically reached `a` in a 2px band, which reads as unreachable); when it does, physical alignment is used unchanged — the common case, and the one where a Float aimed level with the Output's `color` row must get `color` rather than a proportional share of the box. When it does not, the sweep is STRETCHED: the dragged centre's fraction down the hover box is mapped across the candidate sockets' span, each end socket owning a full half-pitch cell, in the direction physical alignment would move (feed-dragged reverses — moving the dragged node DOWN brings its UPPER inputs level with the hover's output). The output side keeps physical pairing in both modes (the output nearest the chosen input), which is what still lets a Data node pick its column by alignment. After the change the same matrix reads 0 of 9540, and real drags of every example above ring every socket; `dragConnect.test.ts` sweeps the measured shapes. Cycle/occupancy checks run on the UNWRAPPED logical graph (`unwrapCollapsedGroupEdges`) — raw collapsed-group boundary edges would contract members into one vertex and fabricate cycles. Hit boxes follow the VISIBLE card (cost-scaled types multiply the measured box by `getCostScale` of the number THE CARD scales by — the live `nodeCostPoints` for ShaderNode, which is override-aware and grows with a variadic fold's operand count, and the `data.cost` snapshot for PreviewNode/ClockNode/MathPreviewNode, which is what those three read — so a measured cost profile cannot leave a band of a card outside its box. Surveyed 2026-09-02 against the painted DOM: the box matches the card for every one of the 76 editor types, and the only paint outside it is the cost badge above the card, which is deliberate. A first pass that unioned descendant ELEMENT rects reported 4–25px of "spill" on eleven types, but that was the glyph's SVG box and the clipped sin/cos waveform path — measured by INK (`getBBox()` through `getScreenCTM()`), every glyph's vector art sits inside its card, so neither is a cause of an unreachable socket). The drop snaps the node beside its new peer (handles aligned, `CONNECT_SNAP_GAP` apart) and then MAKES ROOM (`overlapCascade.ts`): the connected pair stays fixed and overlapped nodes escape along the cheapest single axis (+10px gap) that clears ALL current offenders AND the whole settled set — the full-set check is load-bearing: a greedy per-box push ping-pongs a wide mover in the corridor between the two anchors (the exact geometry every snap creates) — with knock-on pushes rippling outward (BFS, settle-once — deterministic, terminates; a cascade beats a grid here because node footprints vary ~10× and minimal displacement preserves the user's layout). Deltas are absolute-space applied to local positions (parent-invariant), and every shifted node (plus the tile-snapped node) gets the SAME position→membership reconciliation a user drag gets (`reparentedNode` + parent-before-children reorder) — a member pushed out of its group frame detaches instead of invisibly vanishing on collapse. The plain single-pass anti-overlap nudge remains for NON-connect drops. Connect + snap + cascade + reparent ride the gesture's single `pushHistory`. Node-body hover WINS over the drop-on-edge preview AND suppresses splice-on-drop (what wasn't previewed is never committed); wire-connects and drop-connects share one `applyConnection` (single-input enforcement, hidden-socket exposure, image→normal colorSpace flip). The decision logic is pure and tested (`dragConnect.test.ts`); NodeEditor only adapts React Flow internals (measured boxes, MOUNTED handle bounds — hidden `exposedPorts` params and unmounted grow-sockets, i.e. the arithmetic folds + the variadic `append`, don't participate) and paints the preview imperatively like the edge highlight. **Palette tiles drag-connect too**: HTML5 dragover previews via the payload record tileDrag keeps from dragstart (the DnD spec hides `dataTransfer` data until drop) and the touch path streams `fs-tile-drag-move`/`-end` events (which also gave touch drags the drop-on-edge highlight); the not-yet-created node plans as a PHANTOM (`TILE_PHANTOM_ID` — def-derived ports all at the cursor, so vertical tile movement picks the hover node's socket and the tile side offers its first free port; a fresh id can't cycle or occupy), the drop swaps in the real id, connects via the same `applyConnection`, and snaps beside the peer two rAFs later (post-measure) — all under `addNode`'s single history entry. Click/Enter palette adds never preview, so they never connect (`activate` flag on the drop detail) and keep their historical unconditional splice at canvas centre. Hardening: the drop commits ONLY plans referencing `TILE_PHANTOM_ID` (a live node-drag preview can't be hijacked), stale HTML5 payload records are healed on OS-file drops (`endHtml5TileDrag`), only one touch tile drag runs at a time, the edge highlight is withheld from payloads that can't splice (saved groups, textures, input-less nodes), and the canvas `onDragLeave` falls back to a coordinate check when `relatedTarget` is null (Safari) so child-boundary crossings don't flicker the preview.

### PREVIEW MODE — look at ONE node's output on the 3D view

- **PREVIEW MODE — look at ONE node's output on the 3D view** (2026-09-10, owner request; `utils/nodePreview.ts` is the pure half, `components/NodeEditor/PreviewRoute.tsx` the line). Right-click a node → **Preview** (one row for a one-output node, one row per socket for `toHsl`/Split/a Data node's columns, "Stop preview" on the active one — in `menuShared`'s shared `NodeActions` footer, so every per-node menu offers it and the sinks, which have no output, get no row), or **⌘/Ctrl+click** the node (first output; the same click on the previewed node toggles it off, on another node switches). While it lasts the 3D preview renders THAT socket on the Output's Color with EVERY other input of the Output disabled, everything but the previewed node and the Output dims to 0.25 (nodes, wires, frames, notes — the symbolic Output→3D link is deliberately NOT dimmed, the Output still feeds the view), the previewed node takes the selected lift + border, and a STRAIGHT solid `--border-focus` line runs from its socket to the Output's Color socket (straight so it can never be mistaken for a wire that exists). It ends on a press anywhere else, on Escape, or when the graph is replaced (import / NEW). Six rules. (1) **Nothing is an edit.** The state is `nodePreview` in the store, session-only like `hoveredNodeId` — never persisted, never in history, never in a shared file — and the reroute happens in a DERIVED graph only the sync engine's `previewCode` pass sees (`previewGraph`: unwrap, drop every edge into any sink, replace the target Output — `findDefaultOutput`, deliberately NOT `defaultOutput`, since the point of the rewrite is to STRIP that node's binding and materials and a TARGETED one has to be reached too — with a CLEAN one at the same id carrying only its `materialSettings` and the active flag (so that node's mesh targets, `gltfMaterialIndex`, `modelSignature` and `modelMeshes` are all dropped ON PURPOSE: the previewed socket is shown on everything that node shades), strip every other sink's flag so a Raymarch Output cannot outrank it, synthesize an Output under `PREVIEW_OUTPUT_ID` when the graph has none, add ONE edge socket→`color`); `graphToCode` needs no preview branch, and codegen's own Color rules widen a scalar/vec2 and coerce a logic node exactly as a hand-wired socket would. **KNOWN LIMIT since the per-material Output split, not fixed**: `previewGraph` replaces exactly ONE node, so on a document with several Output nodes — which every GLB import produces — the other TARGETED ones still contribute their own `parts` / `materialParts` entries and go on painting their meshes. Preview mode is whole-model only on a single-Output document; elsewhere the previewed socket lands on whatever the replaced node shades, and nothing says so on screen. `code`, the export and the panel keep the real graph: `setCode(code, 'graph', previewCode?)` grew the third argument so the two land in ONE write, and the graph→code effect threads `previewChanged` through both of its guards the way `revalidated` is. (2) **A code→graph pass ENDS it** (`doCodeSync`'s first line): `requestCodeSync` has already put the panel's text on the preview and with `syncSource` at 'code' nothing emits the reroute, so a mode left set would read as on while showing the applied code, then snap back on the first scrub. The sync engine also clears a target whose node or socket is gone (`resolveNodePreview`), and NodeEditor clears on `fs:graph-imported`/`fs:graph-new` because a re-import keeps the same ids. (3) **The outside press is CAPTURE-phase `pointerdown`** (ContextMenu's closer reasoning: React Flow stops click propagation, and a press that becomes a drag never clicks), exempting the node itself (scrubbing its own number boxes is part of looking at it), `PREVIEW_KEEP_SELECTOR` — the menus a right-click on it opens with their portalled popovers, and the WHOLE 3D pane, since orbiting the model is looking at the preview — and the middle button, since panning is not a click. A press on another node ends this preview BEFORE that node's own click/row starts its own. (4) **The two node marks are ATTRIBUTES (`data-fs-preview="src"|"dst"`), not classes — measured, not taste.** React Flow's wrapper renders its `className` from `selected`/`dragging`, React writes the WHOLE string when that prop changes, and a hand-added class goes with it: ⌘/Ctrl+click both selects and previews, and the `selected` write landed AFTER the effect's `classList.add` (MutationObserver, old value carrying the class, new value without) — the previewed node dimmed with the rest. `fs-menu-active` and `fs-labels-shown` are classes and carry the same latent weakness; they survive only because a menu closes on any press. (5) **The line is DOM-tracked per rAF** like PreviewLink — the source's `.react-flow__handle.source[data-handleid]`, the Output's Color input, each falling back to the card's edge midpoint when unmounted — but sits ABOVE the node layer (z 5, mounted before the panels so the canvas bar still wins), and is not drawn at all when the graph has no plain Output on the canvas (the module then feeds the synthesized one). (6) **PROBE TRAPS**: the preview iframe's `srcdoc` does NOT change on a shader edit — the hot-swap path posts the module as an `fs:shader` message, so verify by listening inside the frame, not by grepping `srcdoc`; and under `vite dev` the live store module is `useAppStore.ts?t=<hmr>`, so `import('/FastShaders/src/store/useAppStore.ts')` from the page yields a SECOND, empty instance — take the URL from `performance.getEntriesByType('resource')`. MEASURED in Chrome: menu and ⌘+click both enter, the iframe receives `return { colorNode: vec3(sub1) }` and gets the real module back on Escape, the code panel never changes, the undo button stays disabled, and a click in the 3D pane keeps the mode. Not logged to eval telemetry (display-only; adding it means a new chokepoint in `evalHooks.test.ts`'s reviewed list). `nodePreview.test.ts` pins the derived graph against the real codegen and source-pins the wiring.

### Groups

- **Groups**: selection groups are first-class React Flow nodes (`type: 'group'`) created via Ctrl+G or right-click → Group Selection. **A new group takes a random colour from the DIMMED colour-node palette** (`GROUP_COLOR_PALETTE` = `NEW_COLOR_PALETTE.map(c => dimColor(c, 0.45))`, 2026-09-09, owner request) rather than the one indigo every group used to arrive in — a graph of frames otherwise read as one repeated colour until each was opened and recoloured by hand. Three rules. It is DERIVED from the colour-node palette, never a second hand-picked table: "the same palette, dimmer" is the whole rule, so `newNodeValues.test.ts` pins the RELATIONSHIP (one entry per hue, lower chroma, same channel order — mixing toward a NEUTRAL is what keeps the hue) instead of the hexes. It is dimmed IN WHAT IS STORED, not in the renderer: `getGroupFrameColors` already mixes 0.18 into the node body for the fill, but the SELECTED border is the stored colour at full strength, and dimming there would restyle every group saved before this. And it follows the colour node's spread rule — prefer a hue no group on the canvas is wearing (`pickSpreadColor`, shared by both, compared lower-cased), because with five entries a uniform roll repeats about one time in five, which is the sameness it exists to fix. **Only `groupSelection` rolls one**: `instantiateSavedGroup` restores the colour the group was saved with, `codeGroupBuilder` carries each built-in's own, and a group with no colour at all still falls back to `GROUP_DEFAULT_COLOR`, so every existing group keeps its indigo. **A new group is also NUMBERED** — `Group 1`, `Group 2`, … (`nextGroupLabel`, same day and the same reason: a canvas of frames all called "Group" names nothing). `max + 1` over the groups already matching `Group <n>` exactly, the `nextPropertyName` convention — the number is a label, not an identity, so a gap left by a deleted group is not reused and a RENAMED group ("Fresnel") neither counts nor blocks. Not retroactive: a group already on the canvas keeps its bare "Group", since renaming it would be an edit nobody asked for, and `GroupNode` still falls back to "Group" for an empty label. They have no registry entry and no shader semantics — `graphToCode`/`cpuEvaluator` ignore the *node*, but call `unwrapCollapsedGroupEdges()` from `edgeUtils.ts` at their entry to translate visually-rewritten boundary edges back to their real child endpoints, so collapse state never affects compiled output. Groups can be recolored, renamed, collapsed (members hidden via `display: none` className — *not* React Flow's `hidden: true`, which would unmount rAF loops; the toggle anchors at the frame's TOP-RIGHT corner — the pill appears at the old top-right and expanding grows leftward from the pill's top-right, `groupCollapse.test.ts` pins the round-trip). **A group frame's size has ONE home: top-level `width`/`height` plus the `data.width`/`data.height` mirror** — and `groupFrameSize` is the shared reader, because there used to be two. `groupSelection` wrote the canonical pair while `codeGroupBuilder` (EVERY built-in preset and texture) wrote `style: { width, height }` and nothing else. React Flow renders both identically — `node.width ?? node.style?.width` — so the divergence was invisible until something ASKED the node how big it was, and `toggleGroupCollapsed` asks: it read `node.width ?? data.width ?? 200`, found neither, and recorded 200x120 as the remembered expanded size. MEASURED in Chromium: a dropped preset rendered 300x428, collapsed to the pill, and **expanded to a 200x120 stub with its whole graph outside the frame** — unrecoverable by mouse, since the corner grip only exists on an expanded frame and React Flow's resizer refuses to shrink a parent below its children. The builder emits the canonical shape now; `groupFrameSize` still reads `style` (and `measured`) so every group already saved that way is repaired without a migration; and the expand DROPS `style`, so a group is normalized to one shape the first time it is touched. Two further guards on the expand, both because falling back to `currentWidth` there means falling back to THE PILL: a remembered dimension is honoured only if it is a finite number ≥ the resize grip's own minimum (`MIN_GROUP_W`/`MIN_GROUP_H`, shared with `GroupNode`'s `NodeResizeControl` so the two cannot drift), otherwise the frame is rebuilt around its members; and a remembered size is floored at "the frame contains its members" — UNPADDED, because a member flush against the edge is a real layout and a padded floor would grow every tight frame by 24px per expand, and skipped entirely when any member is UNMEASURED (right after a load, or in the node test env, where the 160x60 guess overestimates a real node enough to inflate a correct frame). A group ALREADY collapsed by the old code is repaired by an exact signature — a `style` size beside precisely `200x120`, which no other path can produce, since resizing first would have given the collapse a real `width` to read, saved to a per-browser library (`fs:savedGroups`), and dragged out of containers. Members never get `extent: 'parent'` — `onNodeDragStop` reconciles `parentId` after every drag instead. **Notes are ordinary members**: Ctrl+G sweeps a selected note in, dragging one into a frame adopts it, and it then rides the group's drags/collapse/ungroup/save-to-library like any node (a note is usually the LABEL for the cluster being grouped, so leaving it outside stranded the annotation). Notes stay exempt only from the placement rules that would fight their purpose — anti-overlap nudging (it would fling a note off the nodes it was deliberately dropped over) and drop-on-edge splicing — both guarded by `isNote` in NodeEditor's drag handlers, not by bailing out of membership. `addNote` PREPENDS, so ordering matters: a note is born parentless and both adoption paths re-sort it after its parent (`groupSelection` front-inserts the container; the drag handlers run the parent-before-children lift). `groupNotes.test.ts` pins all of it. `organizeSelection` still skips notes — auto-layout has no meaningful slot for a free-floating annotation. **A MARQUEE drawn inside a frame selects the frame only once it has selected EVERY member** (`components/NodeEditor/groupMarqueeSelection.ts`, 2026-09-09, owner request "in groups allow to do selections"). The canvas runs `SelectionMode.Partial`, so React Flow selects anything the band merely TOUCHES — right for a card, wrong for a frame, which is a big transparent backdrop that a band drawn anywhere inside it overlaps by construction: rubber-banding two nodes inside a group also grabbed the group, and dragging that moved the whole group with every member instead of the two nodes picked. Three things are load-bearing. The rule reads the MEMBERS, not the rectangle, and that is what makes it work at all: React Flow only re-proposes a selection when its own node SET changes (`areSetsEqual` in the Pane's `onPointerMove`), so a band grown to cover a frame without sweeping in a new node would never re-select it — deriving from members means the last member's own change carries the frame. It is gated on **`userSelectionRect`**, not `userSelectionActive`: the rect is set on the pane's pointerdown while the active flag is only set AFTER the first batch of select changes has been dispatched, so gating on the latter lets the opening sweep through. And it lives in NodeEditor's `onNodesChange` WRAPPER rather than the store's action, because the marquee lives in React Flow's store, which the app store cannot see — which is also what keeps `selectAll` (the A key, dispatching straight to the store action) taking frames along with everything else, as it is meant to. Two consequences are deliberate: an EMPTY frame is never marquee-selected (nothing to have taken; its header and the A key still select it), and a COLLAPSED pill is exempt entirely, since a pill stands in for a node and selects like one. **An expanded frame's only interactive surface is its HEADER** (drag, select, and the right-click GroupSettingsMenu): the body is `pointer-events: none` so the area inside a frame behaves like bare canvas — right-click opens the Add-node menu, drags rubber-band/pan, clicks don't select the group. This relies on React Flow already marking `.react-flow__viewport`/`.react-flow__nodes` pointer-events-none, so a pass-through frame leaves `.react-flow__pane` as the event target — which is what the Pane's `wrapHandler` guard requires before firing `onPaneContextMenu` (and it's why the touch long-press path, which dispatches a synthetic `contextmenu` on the pointerdown target, routes identically). Collapsed pills opt back in and stay fully interactive — a pill stands in for a node. The resize control opts back in too; see the pass-through block in `GroupNode.css`. **Groups resize exactly like notes**: a single `NodeResizeControl` at the BOTTOM-RIGHT with the notes' enlarged 15×15 grab box, rendered only while expanded AND selected — not React Flow's full `NodeResizer`, whose eight edge/corner handles ringed the frame and turned every near-miss along an edge into an accidental resize. So both surfaces now follow one rule: drag by the header, scale by the one corner. (Notes get that drag rule from `dragHandle: '.note-node__header'`; groups get it from the pointer-events pass-through above — different mechanism, same behaviour.)

### Board drawings

- **Board drawings**: freehand ink annotations (DrawingLayer + DrawToolbar) are VISUAL-ONLY like notes/waypoints — invisible to graphToCode/cpuEvaluator/the sync engine.
