Loading an entry ADOPTS that file's identity as the shader name (`adoptShaderName`: the authored name is kept when `toKebabCase` says it denotes the same file, so `my-shader.js` stays "My Shader"; the DISK name wins when they diverge, so `waves.js` whose graph is called "Untitled" becomes "waves"). **Opening a `.glb` adopts its FORMAT with its name** (`setExportAsGlb(true)` in `loadEntry`'s glb branch; `effectiveExportFormat` still falls back to the bundle if the restored mesh cannot be packed): the session flag decides `bundleKind`, so without it the next Save wrote a `waves.js`/`.zip` sibling — silently, the folder holding no such name to confirm over — and left `waves.glb` on the pre-edit shader for the next open to load. Save then writes back to the file it was opened from — the tracked name VERBATIM, preserving the on-disk casing that makes the write land on it rather than spawn a lowercase sibling — and the name box is the save-as control: rename the shader and Save forks a new file, which is the only way to make a copy. Save runs the export pre-flight (N1) BEFORE it derives that target, because answering "Export without the 3D model" can turn a `.zip` into a `.js`; cancelling reports "Save cancelled — nothing was written." the way a declined replace does. That "did the user rename it?" test is `toKebabCase` on both sides, never raw strings (`exportShader.shaderBaseName` is the shared derivation, so a predicted name can't drift from the written one): a file name is what identity MEANS here, so "My Shader" → "My  Shader" is not a rename, while re-typing a prettier spelling of an adopted stem would otherwise take the save-as branch back to the file it was already on. The flip side is inherent to deriving names by kebab and cannot be fixed in the rules — `toKebabCase` is many-to-one, so **"Zīle" and "Zāle" are one file** (`z-le.js`) — which is why a save that would land somewhere OTHER than the tracked file lists the folder first and `window.confirm`s when that name already exists. **The provenance of the document on screen is therefore THREE states, not a nullable file name** (`DocOrigin`), because two of them are indistinguishable if you only track a name: `file` (loaded from / last written to it — writing back is the point and stays silent), `new` (NEW built a blank document, which resolves to `my-shader.js` via `DEFAULT_SHADER_NAME` often enough that Save must look before replacing), and `null` — unknown provenance, a session restored from the autosave or an import from another surface — which writes the derived name SILENTLY, exactly as it did before any of this existed. That last one is a deliberate limit rather than an oversight: the app cannot tell the user's own file from a stranger's there, so prompting would fire on the first save of every launch, which is noise, not safety. The listing is fetched only on the asking branches, so ordinary re-saves pay nothing for it; on confirm the write uses the spelling already on disk. Four things ride on this. The origin is COMPONENT state, not a store field (one reader, one writer, the control never unmounts on desktop, and the web build never mounts it at all). It is dropped on `fs:graph-imported` and set to `new` on **`fs:graph-new`** — a dedicated event `newGraph()` dispatches, deliberately NOT a reuse of `fs:graph-imported`, which would arm NodeEditor's import auto-fit on top of the one `startNewShader` already schedules. Both listeners are guarded by a `loadingRef`, because `announceGraphImport` runs SYNCHRONOUSLY inside `importShaderText` and would otherwise clear the very origin the load is about to set. Re-tracking happens ONLY in the write's success path AND only if an `originEpoch` counter is unchanged across the awaited write: claiming a file that was never written — or one belonging to a shader some other surface imported during the await — would aim the next Save at whatever really is at that name. And `newGraph()` also resets `shaderName` (see the NodeEditor bullet); the reset alone is NOT what severs the tracking, and assuming it was is the trap — a document already AT the default name kebabs to the same file, so the tracked target survives the reset and only the event breaks the link. **A kind flip forks the pair**: adding an image turns `waves.js` into `waves.zip`, and switching the EXPORT popover's Format to one `.glb` makes it `waves.glb`; there is no delete command in the IPC surface, so the stale sibling stays; the Save tooltip names the exact target so at least the flip is visible before it happens. Rust hashes every image it stores and re-verifies the hash on every read; the webview never names a file, only a closed slot vocabulary (`graph`/`savedGroups`, the `x-fs-slot` header on a RAW write body) and 64-hex digests. GC keeps the broad `"fsimg-` scan, where a false positive only keeps a file. **Every write stages under its own name** (`<name>.<pid>-<seq>.tmp-fastshaders`, `staging_path`): async commands run concurrently and the graph and the library can put the SAME new image at once — with one shared staging name one call removed or renamed the other's file (measured: one of two concurrent puts failed with `E_IO` in 40 of 40 rounds, and the loser's rename fallback could delete the image the winner had just committed). `store_image` also takes a destination that already hashes to the digest as success and never removes it. GC keeps every image any `.json` in the directory names — the backup and a quarantined file included — and a `.json` it cannot read aborts the pass before anything is deleted. **It also keeps every digest THIS PROCESS has stored** (`StoredImages`), and that is not belt-and-braces: GC reads the documents in one loop and deletes in a SECOND, the two commands run on separate async workers, and the webview's gate cannot serialize them because `desktopAutosaveBoot.ts` BOUNDS its `gc()` call and a pass that merely takes too long opens the gate exactly as a finished one does. A put committing between the loops named an image no document mentioned yet, GC deleted the file, `autosave_write`'s `E_MISSING_IMAGE` check had already passed, and the document committed a ref whose pixels were gone — a dangling ref at the next boot and nothing else said so. `store_image` CLAIMS its digest before it touches a file and `gc_dir` consults the set INSIDE the same critical section as its `remove_file`, so the two serialize. The staging sweep is deliberately NOT claim-guarded: a live `<digest>.txt.<pid>-<seq>` swept mid-`stage` fails the rename with `E_IO`, which surfaces as the `autosave-file-failed` notice and rewrites on the next edit — loud and recoverable, where collecting a committed image was silent and permanent. main.rs intercepts `CloseRequested` on the MAIN window and a user-initiated `ExitRequested { code: None }` (Cmd+Q, the last window closing), emits `fs:autosave-flush`, and waits up to 3 s for `autosave_close_ready` before it destroys the window or exits (`request_flush`/`finish_close`; programmatic exits carry `Some` and pass).
