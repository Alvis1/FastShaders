### The Image node's sockets ride the BORDER, centred, with no text

- **The Image node's sockets ride the card's BORDER, spread evenly and centred on the picture, with no text** (2026-09-19, owner request; it replaces the LABELLED ROWS decision of 2026-09-11, research §8 decision 3, which held for eight days). The node has five outputs — Color (`out`, vec3, still `outputs[0]`), then **R, G, B and Alpha** (float swizzles of ONE sample; see the Image node bullet) — and up to six opt-in inputs, and every one of them is placed by `nodes/edgePorts.ts`: `edgePortOffset(i, n)` returns px from the port region's centre, in the SAME units and the same `calc(50% ± Npx)` idiom an authored designer offset uses, so `sockOv[id] ?? edgePortOffset(...)` lets a Node Designer override simply replace a computed slot. The pitch is `EDGE_PORT_PITCH` = 14 px, which is `.node-base__row`'s `min-height`: the column is exactly as dense as the rows it replaced. `edgePortRailHeight` is a FLOOR on the region, not a height — a real picture is taller and the floor does nothing; the 48 px empty slot is what it exists for. Inputs are indexed against the node's FULL input list, so exposing a parameter (or a drag-reveal mounting the hidden ones, which now happens IN the rail rather than as floating `RevealSockets` — two placements of the same six sockets is how they end up on top of each other) never slides a socket out from under the wire aiming at it. `visibleRows` is EMPTIED rather than the body being branched around, so `.node-base__body` collapses; the filename and the thumbnail moved INSIDE `.shader-node__region` on both surfaces, because the sockets are centred on that region and the picture has to be part of what they are centred on. **`.shader-node__edge-region` sets `align-items: center`** — the cross axis of a column is horizontal, and the default `stretch` pulls the thumbnail to the card's width and distorts every picture. **The re-measure key gained the picture** (`imageGeomKey` folds the payload's length and tail, the stored and source dimensions, and the file-name length; the `<img>` also calls `updateNodeInternals` `onLoad`): the offsets are from the region's CENTRE, so the region changing height moves every socket, and React Flow measures handles once per `updateNodeInternals` — without it the edges draw to where the sockets used to be and a reload "fixes" it.

  **The names live in the socket's own tooltip.** Hover, a touch tap, and the double-click label pin (`fs-labels-shown`) all read `TypedHandle`'s `data-tooltip`, which is built from the `label` prop every rail handle passes — so nothing was added to make this work, and a socket's label keeps its ONE placement (beside the dot, outer side). This RESTORES NODE_DESIGN_REQUIREMENTS #8 ("output sockets show no text/label") rather than bending it: `LABELLED_OUTPUT_TYPES` is now EMPTY and is kept as the NEGATIVE guard (`imageEdgePorts.test.ts` fails the moment a type joins it), and `.shader-node__in-label` — the one on-card INPUT label in the app — is retired outright. Exception 8a survives and is not expressible in that set: the Data node's outputs carry their CSV column headers, which are USER DATA and the only thing telling N identical float sockets apart, so it is recognised by its per-instance `dynamicOutputs` and keeps printing them verbatim.

  **The channel order after `out` is R, G, B, Alpha** — the order every format the user already reads writes them in (RGBA, `#rrggbbaa`, an ORM map's r/g/b). It was Alpha-second. The move is SAFE and was measured: emission is handle-keyed throughout (`graphToCode` reads `IMAGE_CHANNEL_COMPONENTS.get(edge.sourceHandle)` and never walks `def.outputs`), edge ids are built from handle STRINGS, and the node is one-way through `codeToGraph` — so no emitted byte and no saved `.fastshader` moves. `IMAGE_CHANNEL_COMPONENTS` moved with the registry to keep the lockstep pin (`imageNodeAddable.test.ts`, `imageChannelSockets.test.ts`) meaningful; nothing in production iterates that Map. `out` staying `outputs[0]` is the one line that cannot be relaxed — drop-on-edge insertion, a dropped wire, ⌘-click Preview, `cpuEvaluator`'s shape fallback and dragConnect's phantom-tile tie-break all mean it.

  Three things stayed load-bearing through the change. **One filter for both surfaces**: the opt-in param filter is `effectiveNodeDef` (utils/exposedPorts.ts — the ramp filter, then `effectiveImageDef`), and ShaderNode (with the node's exposed set) and NodeVisual (with nothing exposed, a replica being a fresh node) both draw from it. **One empty slot**: a node without a valid payload shows ONE element, `ImageThumbEmpty` ('No image', its `title` the hint): a node added empty from the palette, one whose payload a restore path stripped, and every NodeVisual surface. It is NOT `pointer-events: none`, because its title is the hint (TooltipLayer resolves hosts through `elementFromPoint`), and it is inert rather than a button, or every palette tile would gain a keyboard tab stop. The hint (`imageEmptyHint()`) names the settings menu's Texture row, the ONE control that fills THIS node (a dropped file makes a NEW node, so the hint does not suggest it), and shares the row's own `'Texture'` key so the two read as one thing in either language — except where no such menu is reachable: a study session (the picker is hidden) and every NodeVisual replica (it has no menu at all, and the Node Designer stage draws it hit-testable, so a right-click there opens only the browser's own) keep the plain 'No image in this node.' (`IMAGE_EMPTY_HINT_EVAL`, which NodeVisual passes through `ImageThumbEmpty`'s `hint` prop); `imagePicker.test.ts` pins all three. **Glyphless, not art**: the node is glyphless on purpose (`glyphCoverage.test.ts`), the thumbnail being its identity; it is NOT movable art, so the designer's dx/dy/scale never touch the thumbnail and `ART_NODE_TYPES` stays colormap-only. The Node Designer can author only `outputs[0]`'s offset on this node, which the rail honours; the four channel sockets are not authorable there and never were.

  **The settings menu moved with it.** Preview mode for this node is a "Preview Channel" label plus one short button per socket (Color · R · G · B · A) at the TOP of the menu — `menus/PreviewChannelRow.tsx` — where the generic menu prints the node's own name. It writes the same `setNodePreview` field the shared footer rows write, cleared by pressing the lit button, so there is no second route into preview mode and no second way out; ⌘/Ctrl+click on the node still previews `outputs[0]`. `NodeActions` gained a `preview` prop DEFAULTING to today's behaviour, passed `false` from exactly one call site: it is rendered by six menus, and a predicate like "hide the rows when there are several outputs" would silently strip Preview from toHsl, Split and every Data node column. Two lines that read "Image" went: the generic menu's node-name line (the card beside the menu already says it, twice when the node has a filename) and `ImageNodeSettings`' own `context-menu__category` heading — the divider stays, and the orphaned `"Image"` entry was deleted from `lv.json` with its call site. A third sticky `.context-menu__category` in one scrolling list also overlapped the two above it, which is how the duplicate got noticed.

### Drop-time image conversion is ASKED, not assumed

- **Drop-time image conversion is ASKED, not assumed** (`Modals/ImageImportModal`): dropping image(s) opens one dialog per drop — a single line, "Convert image to optimized format?", **Yes** (green) / **No**, plus "Don't ask again" persisting to `fs:imageConvert` (`imageConvertMode: 'ask'|'always'|'never'`). **That preference MUST stay reversible from the UI** — it is offered in the Image node's settings menu ("Optimize on import": Ask each time / Always / Never) and in the "?" panel, and a remembered `never` announces itself on every drop via the one-liner. Without those, ticking the box next to "No" silently pins every future drop with no way back and no signal, which reads exactly like the feature being broken. **No is not Cancel** — the image imports either way, so Escape and the backdrop mean No; the explanation lives in the node's settings menu (Format / Resolution / Size / Original) rather than in a dialog standing between a drag and the canvas. It is a question because the conversion is lossy in a way the app cannot judge: a normal map wants "keep", a photo wants "convert", and at drop time the app does not know which it has (the Data-map flag is only set afterwards). "Keep as-is" still runs the canvas round-trip — EXIF/GPS strip, device texture cap, payload budget are not preferences — it only turns off the FORMAT change (`chooseFormat`'s `allowWebp: false` keeps the image in its own family) and the power-of-two snap. When the user asked to convert and **this browser cannot encode WebP** — MEASURED on this machine 2026-08-02: Safari 26.5.2 *decodes* WebP fine (`<img>` and `createImageBitmap`) but `toBlob`/`toDataURL('image/webp')` still return `image/png`, while Chrome 150 encodes it and q=1 really is lossless — the canvas shows a top-centre ONE-LINER ("Not optimized — stored as JPEG") with a **?** opening `Modals/ImageConvertInfoModal` and a dismiss; it self-clears after 12s and can be turned off for good from that panel (`hideImageConvertNotice`, `fs:hideImageConvertNotice`). The one-liner is STORE state (`importNote` + `showImportNote`/`dismissImportNote`, holding LINES that `utils/importNote.ts` renders; session-only — never history, the autosave or localStorage) so that any surface can post to it, not only the canvas drop; a later note REPLACES the earlier one, and the timer and ✕ dismiss BY ID so an older note's timer cannot clear a newer note. That is also what lets the store's "Add anyway" re-encode report. A drop's note carries the per-image budget lines (N5) above the WebP line; `hideImageConvertNotice` silences only the WebP-capability line and its "?" (which renders only beside it), because a budget line is a cap and caps are not hideable. Not a modal, deliberately: it reports a browser capability, not a decision, so it must not stand between a drag and the canvas — but a capability limit the user can't see at all is worse than the fallback itself, which is how a dropped `.png` silently became a JPEG (PNG blew the 600 K budget at 1024×2048, leaving JPEG as the only candidate). The Image node's card label also shows the **stored** extension, not the dropped file's (`displayImageFileName`, pure + tested) — a re-encode routinely leaves `.png` on WebP bytes, and the card must not assert a format the node doesn't hold; the `title` keeps the name as dropped. **The GLB import builder is the recorded EXCEPTION to this question** (`engine/gltfImport.ts` + `utils/gltfTextureEncode.ts`, GLB Phase 5 Step 8): textures extracted from a dropped model are optimised automatically, without the dialog, and a remembered `never` does not apply — the answer is made by SLOT (`slotEncodeClass` over `glbSlotPolicy`, owner rule Q12): base colour and emissive lossy at up to 1024 px even from a PNG; a normal or metallic-roughness map at up to 512 px, lossless-ONLY from a lossless source (`chooseFormat`'s `losslessOnly`: it halves instead of going lossy) and lossy from a JPEG. It goes through `encodeImageFile`'s options argument, which is absent on every drop, so drops are unchanged (pinned to goldens). The pre-snap originals are stashed under the existing rule only (a snap fired), so a 16-material import (up to ~48 textures) can still churn the 32-record origin LRU and evict an earlier "Revert to original" record — accepted, the cache being a device-local convenience.

### What the conversion does (WebP + power of two)

- **What the conversion does (WebP + power of two)**: a dropped image is re-encoded to **WebP as far as the running browser will go** — lossless WebP for sources that must stay exact (PNG, and `.webp` re-drops whose container says VP8L), lossy WebP q0.85 for photographic sources, with a quality ladder (0.85→0.75→0.65) tried before any dimension is thrown away. Support AND losslessness are **probed at runtime** on an 8×8 gradient (`probeEncodeCaps`), never inferred: WebKit silently returns PNG from a WebP request (still true in 2026, and it covers the Tauri WKWebView build, not just Safari), and the HTML spec leaves `quality` UA-defined for WebP, so Chromium's "q=1 means lossless" is an implementation detail. `chooseFormat` is a FALL-THROUGH, not a preference — making the lossless branch absolute would hand every over-budget PNG to the halving retry and land a 2048² screenshot at 256-512px. **Alpha never yields JPEG** on any capability combination (pinned by test). Dimensions are then snapped to a power of two **ALWAYS**, under "convert" (`imageCodec.ts`, owner rule 2026-09-10: "use power of two always; jump up if it is near 80 percent"): per axis INDEPENDENTLY, an axis at or above `POT_ROUND_UP_RATIO` (0.8) of the next power of two rounds UP to it (1920 → 2048, 1700 → 2048) unless that exceeds the device cap, anything else rounds DOWN (1080 → 1024, 1280 → 1024, 1600 → 1024) — so 1920×1080 lands on 2048×1024 (+1 % pixels), never on a square, the largest growth on an axis is 1.25× and the largest shrink just under 1.6×. A rounded-UP target that blows the payload budget falls back to the rounded-DOWN one (`potFloorTarget`, never larger than the base that already fit). **The snap never trades losslessness for a round-up**: when the base encode is lossless, the power-of-two pass tries only the lossless candidates, so a lossless PNG whose round-up does not fit losslessly lands on the floor target instead of silently going lossy — and when the floor does not fit losslessly either, the NPOT base ships. That is not rare: a dithered or pixel-pattern PNG resamples into anti-aliased pixels that no longer compress (measured: a dithered 1700² PNG, 288 K lossless at its own size, fits the 1024 floor only lossy). It REPLACED a conservative snap — nearest POT only within 1.25× up / 1.15× down (1280×720 stayed NPOT), skipped entirely for binary-alpha cutouts and low-colour sources — and those skips are GONE with "always": pixel art, UI sprites, masks and hard cutouts are now resampled too, which blurs hard pixels and frays a cutout's edge against `alphaTest`. The escape hatches are what keep that acceptable: "Revert to original" restores the exact pre-snap encode, and answering **No** in the import dialog still stores an image untouched (no format change, no snap) — the right answer for a normal map or pixel art. `PixelStats` is `{ alpha }` now; the colour count and binary-alpha flag existed only for the skips. **nothing in this stack needs POT** — three r184 has no `makePowerOfTwo`/`textureNeedsPowerOfTwo` path left (that was WebGL1/ES2) and both WebGL2 and WebGPU sample NPOT with RepeatWrapping and full mipmaps — so it is a deliberate hygiene choice rather than a correctness fix, and the resample goes through a **wrapped border** (`POT_WRAP_MARGIN`): plain `drawImage` clamps at the edges, so a seamless tile would come back with a seam on every boundary, in a node whose Repeat setting defaults ON. The pre-snap encode is ALWAYS produced first and kept as the node's "original", and the snap is declined outright when that stash can't be made — a destructive step never ships without its escape hatch. Conversion is automatic at drop with an in-flight ghost at the drop point (transform/opacity only, so the compositor keeps it animating while the encoder blocks) and multi-file drops are **serialized** (N concurrent encoders compounded into one freeze). Honest progress is impossible — `toBlob`/`toDataURL` are single opaque calls with no callback and no cancel.

### The Image node's RESOLUTION is a choice

- **The Image node's RESOLUTION is a choice** (`resolutionLadder` in imageCodec.ts + `resizeEncodedImage` in imageImport.ts, 2026-09-09): the settings menu's Resolution row is a dropdown offering POWER-OF-TWO sizes derived from the ORIGINAL — the one lever that turns "this shader is too expensive" into something actionable, since a 4 K photo on a blurred backdrop costs the same bandwidth as one that matters. Six rules. It re-encodes from the ORIGINAL (`imageOriginCache`), never from what is stored — 2048 → 1024 → 512 through the current payload would stack three lossy passes and could never go back UP — which is also why the ladder is ANCHORED to the original's dimensions rather than to the current ones: an anchor that moved with each pick could only ever descend. **Every rung is a POWER OF TWO** (2026-09-10): the top rung is the original snapped by the drop's own 80 % rule and capped at the device (`potTarget`), each further rung halves both axes — so a freshly converted image sits ON the top rung, and a 1920×1080 photo's ladder reads 2048×1024 / 1024×512 / 512×256 / 256×128. A rung whose size IS the source's (a source that was already POT within the cap) is marked `original` and routed through `revert()` rather than re-encoded, since re-encoding would spend a lossy pass to reach a worse copy of a file already in hand; any other source's exact size is not a rung, and Revert is the way back to it. Rungs are keyed `${w}x${h}`, never by divisor — with a POT anchor "divisor 1" means the snapped original, which is usually NOT the original, and `imageResolution.test.ts` fails on `divisor === 1` reappearing. An NPOT payload — stored before the snap became unconditional, or declined at drop — sits on no rung, so its size is shown as its own `current` option rather than leaving the box reading someone else's number. The floor is a SHORT-side rule (`RESOLUTION_MIN_DIM` **8**, owner 2026-09-10: "allow to go as low as 8px" — it was 64 behind a fixed four-rung list; the ladder now halves until the short side would drop below 8, so a 2048×1024 original offers eight rungs down to 16×8, and every rung at or below 256 px pays the cost floor, ×0.5) so a panorama is not cut off early, and no rung exceeds the device cap: the anchor lands ON the cap (a POT-floored one — `clampPotCap`) and halvings only shrink. **A large step down goes through a 2:1 PYRAMID first** (`resizeEncodedImage`): one `drawImage` from 2048 to 8 is a bilinear sample of a few dozen of four million pixels, i.e. aliased noise rather than an average of the picture; an exact halving averages each 2×2 block and never samples past the edge (every destination pixel maps between four source texels), so it is seam-safe for a tile and leaves the wrapped resample only the final step of less than 2×. MEASURED on a period-3 stripe pattern (true mean red 170): single-step pixels spanned 128–255 in Chrome 152, WebKit 26.5 and Firefox 153, the pyramid 169–171 in all three — and a 1px red/blue pattern is the WRONG probe for this (at a power-of-two ratio every bilinear tap lands exactly between two columns and averages by accident, which is how the first check reported single-step as fine). `resizeEncodedImage` deliberately repeats `encodeImageFile`'s TAIL rather than calling it: that function's job is the DROP decision (source-pixel guard, EXIF orientation, device cap, POT snap, and the halving retry — which here would hand back a resolution other than the one picked), while what is genuinely shared is the wrapped resample (Repeat defaults ON, so a plain resample seams every tile), `chooseFormat`, the quality ladder and the payload budget. And this path may AWAIT where Revert and the Data-map flip may not: those await a READ and then write TWO things, which is what would split them into two undo entries, whereas here the whole await precedes a SINGLE `updateNodeData` — the node is re-read after it (the menu can outlive its node), the project-wide budget is re-checked only when the new encode GROWS the payload — a pick that shrinks it is never refused, even in a project already over budget (it used to be, with the Revert notice's wording) — and a refusal raises its OWN `image-resolution-cap` notice (N6) rather than borrowing `image-revert-cap`. The refusal is on BYTES, and a step DOWN can grow the bytes (a lossless source that fits a lower rung only lossy comes back longer), so the notice says "Raising" only when the pick adds pixels (`resize.raising`) and "Resizing" otherwise; like every image notice it names the file by its STORED extension (`displayImageFileName`), as the card does, a failed encode leaves the node untouched, and `srcWidth`/`srcHeight` are set to the ORIGINAL's dimensions, which is what those keys have always meant. **The ladder's SOURCE is the stashed original when there is one, else the payload ITSELF while it has never been resized** (`ladderSource`, 2026-09-10) — the origin cache is written only by a drop-time snap or by a resize, so for the ordinary unsnapped drop there is no record and none is needed until the first pick, which STASHES the exact payload it is about to replace (`stashImageOrigin` inside `applyResolution`, `originId` + `srcWidth`/`srcHeight` written in the same `updateNodeData`). That is what puts the control on every image node, with no IndexedDB round trip to appear. Stashing on EVERY drop was tried first (2026-09-09) and reverted the same day, on an audit: every drop then competed for the cache's 32 slots, so an ordinary drop could evict the ONE record that undoes a destructive snap (`potTarget` is conservative, so snaps are a minority of drops), every drop paid a `getAll` + sort, and the study clean slate became responsible for bytes it never had to hold. `canKeepOriginal` gates that first pick — `canStashPayload`, the same rule `payloadToRecord` applies, asked up front: a payload the cache would refuse (>600 K, i.e. placed under ignore-limits) is never resized, or the resize ships with no way back, and the read-only row names THAT reason rather than blaming device-local storage. The `original` rung on a payload-sourced ladder is a no-op (it already is the original); on a stashed one it is `revert()`. **The Original row + Revert button LATCH for the menu session** (`receiptRef`, keyed on `nodeId|originId` — the node AND its payload lineage: a second right-click MOVES the menu without remounting it, and a later lineage change on the same node, such as a texture pick, must not keep a stale "not on this device" row up): their gate is "the payload differs from the original", which is false on the very frame a revert lands, so without the latch the block unmounted under the cursor and the documented receipt — the button dropping to "already the original" — could never render. A revert keeps `originId`, so the receipt survives it. **And the original the menu READ belongs to ONE `originId`** (`menus/imageOriginView.ts`, pure + tested, 2026-09-12): the cache read is async and the menu's state outlives the node it was read for, so it is held as `{ id, payload }` and `origin`/`pending` are DERIVED from it — no original and `pending` until the read for the id the node carries NOW answers. Before that the menu kept "the last payload read": moved from node A to node B, it showed A's original with Revert LIVE, and a click wrote A's picture into B (the ladder would have re-encoded from A's original too); and an id going to '' mid-read left `pending` stuck at true, which disabled B's Resolution select for the rest of the menu session. A menu moved onto a CLONE reuses the read — correct, the cache is content-keyed — while the receipt, per node, does not carry. `imageOriginView.test.ts` runs the moved-menu sequence through a model of the component (tied to it by source pins) AND through a transcription of the old menu, so each scenario is shown to fail the old code rather than pass vacuously. `resized` (was `wasSnapped`) is the pair `srcWidth`/`srcHeight`, written by the snap AND by a resize, deleted by a revert; it is the truthful name now that a resolution pick is the common way those keys appear on a never-snapped node. The control still disables itself with the device-local explanation when a RESIZED image's original has left this device (shared project, another browser, aged out of the LRU). **The loop is closed**: `imageNodeCost` prices the node by its stored resolution (see the `complexity.json` entry above), so a rung down is a visibly cheaper badge.

### "Revert to original" (Image node settings)

- **"Revert to original" (Image node settings)**: restores the ORIGINAL payload — the pre-snap encode for a drop the power-of-two snap fired on, or the pre-resize payload once a Resolution was picked (the cache is written at exactly those two moments and no other; `clearImageOrigins()` empties it for the study clean slate, since a participant's dropped source images must not stay recoverable from the study machine and the consent text covers neither cache). For the snap that means the payload the import WOULD have produced without the POT snap — same EXIF strip, same device texture cap, same 600 K budget; NEVER the raw source file (that would re-embed the GPS the canvas round-trip exists to strip, and blow every cap). Bytes live in `utils/imageOriginCache.ts` (IndexedDB, `previewMeshCache`'s throw-safe shape), **not** on `values`: `totalImageChars`/`sanitizeImageNodes` inspect only `imageB64`, so a second payload key would be invisible to the 600 K per-image cap, the 3 M project cap, the 8 M hard ceiling and the whitelist — a tampered `.fastshader` could smuggle an unbounded blob past the trust boundary — and it would ride ~101 history clones, the autosave, the clipboard and the project embed. Only `originId` (+ `srcWidth`/`srcHeight`) ride the node, all three whitelisted in `sanitizeImageNodes`. The record is **content-keyed** (a digest of the stashed payload): it survives Ctrl+D/paste, which mint fresh node ids while cloning `data`, and a re-drop under a different headset texture cap becomes a DIFFERENT record instead of silently rewriting what an existing node reverts to. Reads are re-validated as adversarial (`recordToPayload`: version, key-matches-digest, whitelist, dimensions). Device-local by design, so the row disables with an explanatory tooltip after sharing a project, in another browser, or once it ages out (32 records / 24 MB LRU on the web; 64 records / 256M chars on desktop, `utils/platformCaps.ts`, where each record may reach the 6M per-image cap so the character bound binds first, and the WKWebView/WebView2 IndexedDB quota at that size is unverified). Ticking **"Data map (linear, no mipmaps)" also restores the original** — that checkbox is the only moment the app learns an image is a normal/height map (the drop cannot know), and a resampled normal map has wrong normals; both changes ride ONE `updateNodeData` so it stays a single undo entry, which is why the record is prefetched when the menu opens, and re-read whenever the node's `originId` changes (`ImageNodeSettings` is its own component precisely because it needs that hook — an awaited read inside the handler would split one click into two undo steps).

### Image node

- **Image node**: drag-dropped images become an `imageNode` (mirrors the Data node pipeline; since GLB Phase 4 the node can also be added EMPTY from the palette/Add-node menu, and since 2026-09-18 it is OFFERED there — see the Texture-node bullet; the file-drop path is not an add surface and is never gated). Payload = whitelisted `data:` URL on `values.imageB64` — **adversarial**: codegen re-encodes the decoded bytes (`decodeImageNode` → `bytesToBase64`, never the stored string), the ShaderNode thumbnail renders only `validImageDataUrl()`, malformed payloads degrade to an inert `vec3(0,0,0)`. **The payload does NOT sit in the editor's code**: graphToCode emits `img.src = "fs-asset:<node>-<hash>"; // name, WxH, size` and `utils`-style pure helpers in `engine/imageAssets.ts` splice the real `data:` URL back in at the surfaces that run or export the module as a standalone document (XR popup, A-Frame tab, Download Shader) — the sandboxed preview instead receives each payload ONCE per document and resolves the placeholders in the iframe (`engine/previewAssetFeed.ts`, see the preview-rebuild convention) — a word-wrapped 600K-char literal otherwise buried the shader under ~8,500 rows in Monaco and re-tokenized megabytes per graph edit. Safe because image nodes are already one-way through codeToGraph, so nothing ever read that payload back; the placeholder carries a payload hash so changing an image's BYTES still changes `code` and invalidates the code-keyed preview memos. An unknown placeholder key is left verbatim and degrades via the existing decode() fallback. Emission = FLAT module-scope statements with top-level await (never an async IIFE — codeToGraph's ReturnStatement visitor would hijack the output): `new Image()` → `try { await decode() } catch` → 1×1 fallback → `THREE.Texture` with RepeatWrapping, `flipY` written explicitly from the texture spec (true; false under the glTF orientation), sRGB or linear data-map per `values.colorSpace` ('color' | 'data'); the Fn body samples `texture(tex, uvExpr).rgb` (vec3 out; `uv` input falls back to `uv()`). **Channel sockets (the Texture node, GLB Phase 4).** Besides `out` (Color, vec3, still `outputs[0]`), the node offers R, G, B and Alpha (float, always mounted; ids `r`/`g`/`b`/`alpha`, ONE Map-only table in `utils/imageChannels.ts`). The registry declares them after `out` in the table's order (pinned in `imageChannelSockets.test.ts` and `imageNodeAddable.test.ts`), rendered as unlabelled sockets on the card's border (see the edge-ports bullet); they are `float`, so `portShapeForHandle` reports 1 and a channel wired into Color or Environment is widened to `vec3(imageN.a)` like any scalar. All four are SWIZZLES OF ONE SAMPLE, the toHsl shape. While no channel socket is wired the emission is byte-identical — `texture(…).rgb`, consumers read the bare var (`registry/imageOutOnlyByteStability.test.ts`, tampered handles included). Wiring any of them (`imageSampleIsWide` in graphToCode, the ONE predicate the emitter and `resolveEdgeRef` share) emits `texture(…).rgba` once, and `resolveEdgeRef` hands out `.rgb` for `out` (also for a null or tampered handle) and `.a`/`.r`/`.g`/`.b` for the channels; the invalid-payload fallback is then `vec4(0, 0, 0, 1)`, because a vec3 cannot carry `.a`.
