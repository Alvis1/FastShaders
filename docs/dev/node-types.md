### Noise nodes

- **Noise nodes**: 8 MaterialX-backed nodes (`perlin`, `perlinVec3`, `fbm`, `fbmVec3`, `cellNoise`, `voronoi`, `voronoiVec2`, `voronoiVec3`) all use the same `pos`/`scale` parameter convention. graphToCode emits them via the `def.category === 'noise'` branch; codeToGraph parses them via `processNoiseCall`; CPU thumbnails come from `noisePreview.ts`; live GPU previews run the generated TSL through the preview iframe (`graphToCode` → `tslToPreviewHTML` → `buildShaderModule`). `tsl-textures` was removed in favour of three.js's built-in MaterialX noise; the `texture` category backs the content-browser Textures tab (`builtinTextures.ts`) and holds NO node definition since GLB Phase 4 moved the Image node to `input`: a def in an OPTIONAL category is unofferable until the user finds the switch, and the Image node must be addable whatever that switch says (`registry/imageNodeAddable.test.ts`).

### The Perlin family is SIGNED, and the four signed types carry a per-node range flag.

- **The Perlin family is SIGNED, and the four signed types carry a per-node range flag.** `perlin`/`perlinVec3` (`mx_noise_*`) and `fbm`/`fbmVec3` (`mx_fractal_noise_*`, which sums Perlin octaves) emit MaterialX's raw ~[-1,1]; `cellNoise` and the three `voronoi` types are already [0,1] and must NEVER carry the flag — a remap there would halve a range that was already correct. That signedness surprises people in two specific ways: `round(noise)` returns −1/0/+1 rather than 0/1, and the Output node's Discard culls on ANY non-zero so BOTH tails cull. Nodes the user ADDS now therefore default to a 0–1 remap. The whole scope rule is one storage decision: **the flag lives in `values.signed` as 0/1 and an ABSENT key means SIGNED**, so every graph saved before this, every noise member of the built-in textures/presets, and every re-imported `.js` keep emitting byte-identically (pinned by `graphToCode.test.ts`'s junk-value sweep and `registry/noiseRangeCorpus.test.ts`). `utils/noiseRange.ts` is the ONE coercion point (`SIGNED_NOISE_TYPES` + `isUnsignedNoise`), and its read is an EXACT `=== 0 || === '0'` — deliberately NOT `Number(v) < 0.5`, which maps `null`/`false`/`''`/`[]`/`0.4` all to "unsigned", and `null` is what the `fs:graph` autosave turns a non-finite into, so a coercing read would change a shader's appearance across a reload. The flag is deliberately NOT in `def.defaultValues`: on a noise node that map is the SOCKET list (`PreviewNode` builds a param handle per key), so a key there becomes a wireable dead socket with an "expose as input socket" checkbox beside it, and flips `isAtDefaultValues` to false on every legacy node — which is also why the "booleans get no expose toggle" rule is structural here rather than a special case. `resetNodeValues`' `PRESERVED_KEYS` carries `signed` so a Reset restores pos/scale without silently flipping the range back. Emission wraps the FINISHED call (`mx_noise_float(pos.mul(4)).mul(0.5).add(0.5)` — method chain, no new import), never `posExpr`, and gates on the def TYPE as well as the stored value: a tampered `.fastshader` putting `signed:0` on a voronoi node would otherwise emit a remap `codeToGraph` is required to refuse, and the round trip would grow junk nodes on every Apply. `matchNoiseUnsignedRemap` collapses that exact shape back into ONE node and is MANDATORY, not tidiness — `useSyncEngine`'s `mergeMatch` carries no `data.values` across a resync, so without it every code-panel Apply would reset the node to signed AND grow a Multiply/Add pair. The matcher is narrow on purpose: bare-Identifier callee (keeps it off dataRange's symlog `.mul(0.5).add(0.5)` tail), exactly ONE noise argument (`mx_noise_float(p, 2)` would otherwise collapse with the amplitude silently dropped), and an inline call receiver never a variable (a variable can have several consumers, so one flag couldn't mean "raw here, remapped there"). Unlike the Time-speed collapse it is SEMANTICS-PRESERVING, so it can only change how many nodes a shader is drawn with, never what it renders. **fBm is only APPROXIMATELY 0–1** — three's `mx_fractal_noise_float` sums 3 octaves from amplitude 1.0, so the remap lands ≈[-0.375, 1.375]; deliberately NOT clamped, because a clamp is a third chain link that breaks round-trip stability and flat-tops the peaks (wire a real Clamp node if you want one). A signed node shows a `±1` chip on its card (`ClockNode`'s `×speed` precedent — the SURPRISING state is the one marked). `cpuEvaluator` follows the flag for both the value and the range: that block used to assert [0,1] for the whole noise category, which is exactly why the signed GPU output was a surprise — the editor's own edge cards had been reporting 0…1 for a shader emitting −1…1. `edgeValueLabel` prefers the inferred RANGE over the probe value for anything with a noise node upstream (see the sampled-field bullet below), because the fixed sample UV lands on an integer lattice where Perlin is exactly 0, which on a card reads as a dead wire. The CPU thumbnail deliberately still renders 0–1 for legibility (raw signed values would clamp half of every legacy card to black, which is ambiguous as a mode signal in a way the chip is not).

### Scientific colormaps (`colormap` node + `colormaps.ts`)

- **Scientific colormaps (`colormap` node + `colormaps.ts`)**: the catalogue is the perceptually uniform / colour-vision-safe families the scivis community actually uses (viridis · magma · inferno · plasma · cividis · batlow · lajolla · L*-linear grey; cool-warm · vik · roma; two CET isoluminant maps; turbo as the one rainbow option), stored as sRGB hex ANCHORS in the GENERATED `colormapData.ts` and reconstructed piecewise-linearly. Three things are load-bearing. (1) **The LUT is baked in LINEAR light.** The catalogue is sRGB-encoded — that is what matplotlib/Crameri/CET publish — but the texture carries no colour-space tag and the renderer's working space is linear, so `buildColormapLut` converts. Interpolating sRGB values as if they were linear is the exact error that destroys the uniformity these maps exist to provide, and it is invisible: the picture merely looks "a bit washed". The SAME bug was live in Stripes/Data Viz, whose ramp endpoints went out as `vec3(hex/255, …)` while a Color node's identical hex went out as `color(0x…)` (which THREE.Color decodes); both now emit `color(0x…)`, so one hex means one colour app-wide. (2) **The half-texel inset is not cosmetic**: `t → t·(N−1)/N + 0.5/N` is what puts t=0 and t=1 on the ramp's true endpoints, and the endpoints are what people recognise a map by (`#440154`…`#fde725` IS viridis). (3) **The isoluminant entries are there for the 3D case specifically.** On a lit, spinning mesh a strong lightness ramp competes with shape-from-shading and flattens the geometry; an isoluminant map leaves luminance to the lighting and carries value in hue alone (Kindlmann et al. 2002; Kovesi, arXiv:1509.03700). It buys that by giving up fidelity — vision resolves luminance far better than hue — so both families ship and the picker labels the trade-off rather than choosing for the user. `colormaps.test.ts` pins the published endpoints AND the properties (sequential = monotone lightness, diverging = lightest centre with equally dark arms, isoluminant = flat lightness), so a regenerated table that quietly stops being perceptual fails.

### Data Stripes / Data Viz ramp ends are WIREABLE colour sockets

- **Data Stripes / Data Viz ramp ends are WIREABLE colour sockets** (`RAMP_COLOR_NODES` / `RAMP_COLOR_PORTS` / `effectiveRampDef` in `utils/exposedPorts.ts`). `lowColor`/`highColor` are REAL `def.inputs` (dataType `color`) that KEEP their `defaultValues` entries — the documented micNode trap: a param living only in `defaultValues` can be ticked "expose as input socket" and still render nothing, because ShaderNode builds sockets from `def.inputs`; the retained default is what still draws the inline swatch. They follow the opt-in `exposedPorts` rules, but through the two nodes' BESPOKE settings menus (the generic `NodeSettingsMenu` never opens for them), which mount the shared `menus/RampColorPorts.tsx` — deliberately NOT a copy per menu, and deliberately offering only the ramp ports, since `baseFrequency`/`density` have no `def.inputs` entry and ticking them would author a socket that never renders. `effectiveRampDef` is the ONE filter, shared by ShaderNode and the card replica, so a palette tile cannot advertise a socket a freshly dropped node lacks. Emission goes through `colorRefOf`, the deliberate INVERSE of `scalarRefOf`: a 1-channel source is WIDENED with `vec3()` rather than narrowed with `.x` (three's `MathNode.getInputType` picks the longest operand and pads/truncates silently, so a scalar endpoint would make the whole ramp a scalar with no error, which the Output node then splats into alpha). `resolveExposedParam` is unusable here — its unwired fallback is `Number(raw)` and `Number('#1b2a4a')` is NaN. An unwired node emits the identical `color(0x…)` as before, so every already-exported shader is byte-stable.

### The dataviz family is emitted by hand and is ONE-WAY through codeToGraph

- **The dataviz family is emitted by hand and is ONE-WAY through codeToGraph** (`stripes`, `dataviz`, `colormap`, `dataRange`, `isolines` — same standing as `imageNode`). Each has an empty `tslFunction` and a `CUSTOM_EMISSION_BASENAMES` entry; without that entry the var name falls through to the empty-string base and every instance collides. Two rules they all follow. **Inputs are scalars, so a non-scalar source is coerced with `.x`** (`scalarRefOf` → `shapeOfEdgeSource`): nothing in the editor validates connection types, and `vec2(<vec3>, 0.5)` is a compile error rather than a wrong picture. **Stored numbers are re-emitted through `num(Number(…))`, never `String()`** — `resolveExposedParam` interpolates the stored value verbatim, and these modules are executed by the XR popup at the app's REAL origin, so a value out of a `.fastshader` file must be a number or nothing (`numericParam` is the safe local equivalent).

### `dataRange` decides its DOMAIN on the CPU, not per fragment

- **`dataRange` decides its DOMAIN on the CPU, not per fragment** (`planNormalize` in `dataViz.ts`): min/max, robust 2–98%, zero-centred, ±3σ, log, symlog, manual. Choosing a domain is a judgement about the data and needs the whole column, which only code-gen can see — the shader then evaluates a plain affine/log/symlog chain with baked constants. The tracing is deliberately ONE HOP from a Data node's `colN` handle (`columnForHandle`, shared with the settings menus so the numbers on screen are the numbers baked in); anything else means "no statistics" and falls back to the manual domain rather than guessing. Every degenerate case resolves to something that still renders: a flat column widens to a unit domain instead of dividing by zero, and `log` over data touching zero floors the low end instead of taking log of a non-positive. The menu prints the column's statistics for the same reason the Data node's own menu lists per-column ranges: every tone control downstream is in normalized units, so without them the user tunes against numbers they cannot see. **The settings menu is three stacked parts** — *From/To* (the resolved domain, always visible and always editable: an automatic mode is otherwise invisible, since "robust 2–98%" produces a number the user never sees, and editing either box switches to `manual` seeded with the numbers currently on screen, in ONE `updateNodeData` so it is one undo entry). Then *Method*, a `<select>` over the seven modes with the selected one's hint beneath it (they were seven tall stacked buttons; the hints are the feature and survive the collapse). Then *Formula* — see the next bullet.

### The Data Range formula box is PARSE-THEN-RE-EMIT, and that is the whole design

- **The Data Range formula box is PARSE-THEN-RE-EMIT, and that is the whole design** (`utils/dataRangeFormula.ts`). A user can type an expression like `(v - lo) / (hi - lo)` and the shader evaluates it. That string travels inside a shared `.fastshader`, and the generated module is EXECUTED at the app's real origin by the XR popup and shipped inside every downloaded `.js` — so it must never become code. The `unknown` node's `rawExpression` precedent (`isSafeUnknownExpression`) is validate-**then-pass-through**, which is defensible for a string this app's own parser produced but is the wrong shape for one a human types and shares. So the input is tokenized into a closed AST **carrying no free-form strings at all** — identifiers resolve to `VarId` union members at parse time, function names to `FuncId` — and the emitter writes TSL from its own literal tables. **Emission closure**: every character emitted comes from a finite statically-known alphabet (the `FUNCS` TSL names, the fixed method names, `( ) , .`, `num()`-formatted finite numbers, and the `scalarRefOf` upstream reference); the user's string contributes ZERO characters, so injection is *unrepresentable* rather than filtered, and `dataRangeFormula.test.ts` asserts it mechanically by Babel-parsing the output and checking every identifier against the allowed set. Consequences that are load-bearing: **an absent (or unusable) `values.formula` emits byte-identically to what this node emitted before the feature existed** — the built-in chain is *wrapped*, never edited, and a formula equal to its method's default is not stored — so every saved graph and exported `.js` is unchanged (pinned by a 7-mode × 22-junk-value sweep in `dataVizNodes.test.ts`); the language is ASCII **by explicit code-unit range** and `normalize()` is never called (normalizing would MAP homoglyphs onto real names, manufacturing the vulnerability it looks like it prevents, and `Number('٥') === 5` is why digit detection is never delegated to `Number()`); `VARS`/`FUNCS` are `Map`s, not `Record`s (the `VALID_SWIZZLE`/`TOHSL_*` prototype-chain class — a bare object resolves `constructor`/`__proto__`/`toString` to truthy values); **every rejection falls back to the built-in chain**, so a hostile file still compiles (`dataVizExecution.test.ts` executes both the accepted and the rejected paths); depth/token/node budgets are EXPLICIT counters, so 500 unary minuses — which never pass through `parseExpr` — cannot reach the JS stack; and `mod`/`%`, two-arg `atan`, comparisons and vector constructors are deliberately absent (floor-vs-truncated modulo disagree across backends; scalar-ness is a grammar invariant because the node's output port is declared `float`). `sanitizeDataRangeNodes` at the three store boundaries is a **resource** bound (the string rides ~50 history clones, every autosave and every export), NOT the security control — that lives at the emitter, which every import path reaches by construction. **A refused formula announces itself in the GENERATED CODE**, as a `// Data Range: custom formula ignored (<reason>) — using the <mode> formula.` line beside the fallback chain — the code panel, the A-Frame tab and the downloaded `.js` all carry it, so the recipient of a shared file sees it too. That is deliberately not the canvas's job: half the rejections are `non-finite` (a divisor folding to zero), which depends on the wired column's STATISTICS, and reaching those from a node component costs a whole-graph subscription per node. The canvas chip is therefore scoped to what it can cheaply know and its meaning is exact — `ƒ` = carries a grammar-valid formula, `ƒ!` = carries one the GRAMMAR rejects (wrong everywhere it is opened); it never claims the shader is running the formula. `hasCustomFormula` is the ONE predicate all three surfaces ask, so a whitespace-only string (which `parseFormula` trims to `absent`, meaning the shader is already emitting the plain chain) cannot red-flag a node on one surface and read as normal on another. The chip is NOT `pointer-events: none` — it carries `title={formula}`, and TooltipLayer resolves its host via `closest('[title]')` from `elementFromPoint`, so a non-interactive chip's tooltip silently never fires (the neighbouring `.shader-node__colormap-strip` carried exactly that dead `title` until 2026-09-03; it is gone now — see the socket-label convention). Not mirrored into `NodeVisual`: `formula` is not a `defaultValues` key, so the replica can never be handed one. **And `sanitizeDataRangeNodes` reads `values.formula` by plain property access, NEVER `'formula' in values`** — `getNodeValues` is `data.values ?? {}`, which guards nullish and nothing else, so a tampered `values: 5` arrives as a primitive and `in` THROWS: inside `loadGraph` that throw hits the outer catch, returns null, and the 300 ms autosave then overwrites the user's ENTIRE saved graph with the demo one; on the import path it escapes after `pushHistory` + `setShaderName` have already run, which is the mid-apply failure `extractProjectState`'s shape gate exists to prevent. `sanitizeDataNodes` has the correct shape. (`sanitizeOriginKeys` in `utils/imageNode.ts` had the same defect and is FIXED. The sentence above is also now history for a different reason: `getNodeValues` routes through `rawNodeValues`, which COERCES a non-object to `{}` — but it hard-returns `{}` for `output`/`group`/`note`, so an Output node's own `values` had no coercing accessor at all and every reader wrote `?? {}` by hand. **`outputNodeValues(data)`** (types/node.types.ts) is that accessor, sharing `isValuesObject` with `rawNodeValues` so the two can never disagree about what a values object IS; ShaderSettingsMenu's `'opacity' in values` and OutputNode's `channel in current` both went through it on 2026-09-18, and `types/outputNodeValues.test.ts` pins that neither keeps the nullish-only guard. `chainOperands.ts`'s `in` is safe twice over — its values come from `getNodeValues`, and no Output def grows operands.)

### `isolines` reuses the Stripes AA construction, and the ordering is the whole trick

- **`isolines` reuses the Stripes AA construction, and the ordering is the whole trick**: the derivative is taken of the CONTINUOUS phase, never of `fract(phase)` — `fract` is discontinuous once per level, so `dFdx(fract(p))` spikes exactly at each contour and draws a spurious line through the one it is meant to smooth. The derivative is floored (`.max(0.00001)`) so a flat region cannot collapse the smoothstep's two edges onto each other, and contours packed tighter than a pixel fade to their average coverage instead of aliasing into moiré. `dataVizTslContract.test.ts` builds these chains against the REAL `three/tsl` — every other test compares generated source to expected source, which cannot catch a method that does not exist (`.sign()`, `.oneMinus()`): that produces perfect-looking source and a blank preview pane.

### Sound (`soundNode`) — live audio driving a shader, from a microphone, another input device, or the machine's o…

- **Sound (`soundNode`) — live audio driving a shader, from a microphone, another input device, or the machine's own output.** **The NAME is "Sound"; `soundNode`, the React Flow type `sound` and the emitted `sound<n>_<channel>` uniform base all say "sound"** — the rename went all the way down on 2026-09-08 because nothing had been exported yet, so no saved `.fastshader` carried the old registry type and no shipped module carried the old `mic1_*` property names. A graph saved between the fold and the rename carries the interim flow type, which `loadGraph` re-derives from `registryType` like any other. **The separate Audio Input node was FOLDED IN on 2026-09-08**: the two nodes differed only in which capture API they opened, and a microphone is simply a `device` source, so one node with a source picker covers both. That picker spent a day on the node FACE (inherited from the absorbed node, where it answered "what is this listening to?" at a glance) and moved into the right-click menu the same day by owner decision: it cost 22px of node height and 20px of width on a control most graphs set once, and the question that changes minute to minute — is capture live? — is still answered on the face by the arm light. `registry/legacyNodeTypes.ts` migrates `audioInput` → `soundNode` (with `flow: 'sound'`, since the fold also changes which COMPONENT draws it — `node.type` is persisted, and without it a migrated node renders as React Flow's default bare white box) on every restore path, the ports and defaults were identical so every edge and stored value survives, and because these nodes are one-way through `codeToGraph` no graph can emit the old `aud` base again. **It is a SINGLETON on the canvas** (`components/NodeEditor/singletonNodes.ts`; see the placement-path convention for how the two add surfaces glide to the existing node instead of adding): there is exactly ONE capture session and ONE analyser, so a second node would emit a second set of uniforms driven by the very same sound and carry a second source picker pointed at the same session — two controls for one scope, which is how the two end up disagreeing. Nothing downstream would break; it would just be a node that lies about being its own input. **Emission**: four ORDINARY NUMERIC UNIFORMS — `const sound1_bass = uniform(0);`, one per CONSUMED channel (`level`/`bass`/`mid`/`treble`, the Data node's `usedCols` rule). That shape is the entire design: the value rides the `fs:uniform` postMessage channel that already exists, so **nothing new crosses the preview sandbox boundary except numbers**, and `buildShaderModule`'s `uniformLineRe` pass turns the same line into `params.sound1_bass` plus a `{type:'number'}` schema entry with NO change to `PropertyInfo`/`collectShaderProperties` — so a downloaded `.js` has four real properties an embedding page can drive (the module header prints the six-line driver snippet and the secure-context caveat, because an undriven download is permanent silence with no error). Emitted BY HAND with an empty `tslFunction`. It claims its variable base through a dedicated ALIAS branch in graphToCode (like `dataNode`, NOT via `CUSTOM_EMISSION_BASENAMES`) — it emits `<var>_<channel>` identifiers, so each emitted channel is reserved as a `claimName` alias; without that a user property NAMED `sound1_bass` takes the name first and the emitted `const sound1_bass` becomes a duplicate declaration, a SyntaxError that fails the whole module. One-way through codeToGraph (an Apply demotes it to plain `property_float` nodes — pinned as a known shape in `engine/soundNode.test.ts`), and its branch must stay BEFORE the generic `inputs.length === 0 && defaultValues` branch, which would emit `(0.8)` from the analyser settings — the same trap the Time node avoids. `soundChannelForHandle` is shared by the emitter and `resolveEdgeRef` so a hand-edited handle in a `.fastshader` can never reference an undeclared variable. **The variable base still goes through `soundAnalysis`'s indirection even though there is only one of them** (`SOUND_VAR_BASE`, `SOUND_NODE_BASES`, `isSoundNodeType`, `soundVarBase`): codegen's name claim, its emission branch, `resolveEdgeRef`, the preview pump and podest must never disagree about that string, which three bare literals cannot guarantee. `SOUND_NODE_BASES` is a **Map**, not a plain object, because `registryType` arrives from `.fastshader` files (the documented `constructor`/`__proto__` trap). What the fold DID retire is routing: a uniform no longer has to be matched to a capture by its prefix, because there is one analyser to route to. **The node is its own React Flow component** (`SoundNode.tsx`, flow type `sound`), NOT a ShaderNode. That is the whole layout story: ShaderNode derives socket positions from in-flow ROWS, so this node fought it endlessly (settings paired with outputs by index; filtering inputs to the exposed set re-flowed the card). Every node that looks deliberate — Time, the noise family — is a component that places each handle ABSOLUTELY at a chosen offset, and this one does the same. **Its geometry lives in `nodes/soundGeometry.ts`** — a pure, import-free module read by SoundNode.tsx, `SoundCardContent` (the tile) AND `layoutEngine`'s footprint, so no surface can hold a stale hand-copied twin of the numbers (the tile used to, and drifted). Layout: the two parameter chips stacked FULL-WIDTH at the top of the body (param sockets on the left edge aligned with them, `title` on each row naming the param), then the LIVE LEVEL METER, then the arm light centred below it with the four outputs spread down the right edge beside it. The card is `SOUND_W` = 68px wide (border-box) over a **103px** body (shortened from 118 on 2026-09-09: slimmer value chips, 18 → 14, still comfortably over the 12px compact `DragNumberInput` inside them, plus the gap above the arm light closed from 10.5px to 4.5px). It cannot go much below that, and the floor is the SOCKET COLUMN rather than anything visual — four outputs 18px apart span 54px and the last needs ~8px of body under its centre so its disc stays inside the card at the coarse-pointer size. `soundGeometry.test.ts` pins those RELATIONSHIPS rather than the literals, since the numbers are a judgement that is expected to move while a collision is a silent break on three surfaces at once — it grew to 88x140 for the day the source picker sat on the face and shrank back when that moved to the settings menu, which is the whole reason those numbers are worth stating. **The meter has ONE markup definition** (`.shader-node__level-meter` in ShaderNode.css beside `.shader-node__sound-btn`, the arm light — it lives there rather than in SoundNode.css because it was shared with the absorbed node, and it still is with the tile replica; each surface supplies only the PLACEMENT inline from `soundGeometry.ts`), and the fill is driven imperatively from an rAF loop reading `readSoundLevels()` straight off the SESSION rather than the preview's pump — so it answers "is this hearing anything?" with the preview panel shut and while the shader is mid-rebuild, and never re-renders a canvas node 60×/s. Every placement rule in SoundNode.css is scoped to `.sound-node__body`, NOT `.sound-node` — the tile renders the same body inside CardShell's frame with no `.sound-node` ancestor, which is exactly how the arm light once fell back to in-flow margins and sat on top of the chips there; the light's PLACEMENT rides a `.sound-node__btn-wrap` div (inline `top` from `SOUND_BTN_TOP`) while its size/colour/blink stay in ShaderNode.css. **The light lifts — shadow and size — under its OWN pointer, not the node's** (2026-09-10; it re-publishes `--fs-node-lift`/`--fs-node-scale` on itself; the keyframe and transition rules are in the node-selection bullet). `CardShell` takes `hideOutput` for content that places its own per-port handles — without it the shell's generic centre dot rendered as a fifth, phantom output on the tile. **Sockets are pinned to `z-index: 2`, above the arm light's `1`, and that is not cosmetic tidying**: React Flow positions every handle with a `transform`, a transform CREATES a stacking context, so a socket tooltip's own `z-index: 10` (TypedHandle.css) is SEALED INSIDE its handle and can only compete with siblings at the handle's own level — `auto`. The arm light's wrapper is likewise a transform-made stacking context at `z-index: 1`, so it out-painted every tooltip reaching over it and the lower outputs' labels were simply clipped away mid-word. The rule is a DESCENDANT selector (the param handles are nested one level deeper, inside SoundNode's per-input wrapper, and their tooltips can be covered by the value chip above them) while the positioning pair beside it stays a CHILD selector, governing outputs only — the params keep React Flow's own centring. Any future node that puts a z-indexed transformed element beside handles inherits this same trap. Offsets are px from the BODY, not the card, so a wrapping header cannot drag the sockets with it. Consequences of living off ShaderNode: it is OUT of the Node Designer's designable set (`ndData.designerNodes()` derives exactly the ShaderNode-rendered registry), it has no `customGlyphs` entry, `layoutEngine` needs its fixed footprint, `loadGraph` re-derives `type` for graphs saved while it was still a ShaderNode, and **every extra React Flow surface must REGISTER `sound` in its `nodeTypes`** — `GraphModal` (node-editor.html) didn't, so it rendered there as React Flow's DEFAULT node, a bare white box with top/bottom handles; both surfaces share `flowTypes.ts` now, which is also where the retired `audio` entry is recorded. **A param carrying an edge shows the VALUE ARRIVING, not the word "wired"**: it reuses ShaderNode's exported `edgeValueLabel` (live value, inferred `min…max` range, or `…` when underivable) through the same two-step selector — subscribe to a cheap string key so a position-only graph notify bails on `Object.is`, then rebuild the map from `getState()`. It renders as PLAIN TEXT with no plate, blue when live, because on a node a fill means "you can edit this" and plain text means "this is derived"; the stored number is dead once an edge overrides it, so offering an editable box would be a lie. **Two capture APIs behind ONE picker, because no single one covers what users mean by "the audio playing on this machine"** (`utils/soundSource.ts`, pure + tested): `system` = `getDisplayMedia`, `device` = `getUserMedia` with an exact id — and a LOOPBACK driver (BlackHole, VB-Cable, VoiceMeeter) shows up in that same device list, which is how the device path hears system sound where the display path cannot. Measured against shipping browsers: Chromium gets TAB audio on every platform, whole-SYSTEM audio on Windows/ChromeOS and on macOS only with **Chrome 141+ on macOS 14.2+** (Apple exposed no third-party system-audio API before that); **Safari and Firefox implement `getDisplayMedia` and IGNORE the audio constraint entirely** — the share succeeds carrying video only. That is why `no-audio-track` is its own status rather than a failure: the user did nothing wrong, "try again" would just repeat it, and the fix differs (a missed checkbox is retryable; a browser that cannot share audio needs a loopback device). It is also the single likeliest FIRST-RUN outcome, so its wording names both causes. Consequence for the desktop shell: macOS Tauri is WKWebView and gets nothing from the display path, while **Windows Tauri is WebView2 (Chromium) and does** — so the option is never gated on `__FS_DESKTOP__`, only on runtime feature-detection plus the honest `no-audio-track` report. **`getDisplayMedia({ video: false })` REJECTS** — the spec requires a video track — so `systemAudioCapture.ts` asks for video and then never consumes it: `enabled = false`, no sink. It deliberately does NOT `stop()` that track, because a display session hangs off its video track and stopping it can tear the whole share down, taking the audio with it. **The `device` DEFAULT is the default input, i.e. the microphone** (`DEFAULT_SOUND_SOURCE = DEFAULT_DEVICE_SOURCE`), deliberately not the absorbed node's `system`: every `.fastshader` saved before the fold holds a `soundNode` whose author meant the microphone and arming one must still open it, and `system` cannot be armed without a share sheet and comes back with no audio track at all on two of three browsers. **An EMPTY `deviceId` is VALID and means that default input** — not a hole in the model: `startDeviceCapture` already treats a falsy id as "add no `deviceId` constraint", and before the page holds ANY media permission `enumerateDevices()` returns a placeholder whose `deviceId` is the empty string TOO (not just the label), so without this entry the device half of the picker is unusable until the user grants a permission they can only reach through the picker; MEASURED in Chromium, selecting the only device on offer silently reverted to `system`. `selectableInputDevices` drops that placeholder so it cannot render as a nameless twin of "Default input", and `decodeSoundSource` returns **null** for anything unrecognised rather than falling back — silently resolving junk to `system` would put a screen-share picker in front of the user. **Source selection is SESSION-only and never reaches `node.data.values`**: a `deviceId` is origin-scoped and rotates when site data is cleared, so it is meaningless in a shared `.fastshader`, and storing one would ride the autosave, undo history and project embed while adding fingerprinting surface for nothing. Keeping only the portable half (`system`) would leave the node half-remembered, which is harder to explain than either consistent answer. **Capture is parent-side only and gated on a click.** `getUserMedia` is denied to the preview iframe's sandbox-issued opaque origin *below* the Permissions-Policy layer, so `allow="camera *"` would not help and `allow-same-origin` would hand adversarial shader code `fs:graph`/`fs:savedGroups`/the IndexedDB caches. Since a node's presence in a graph IS its execution here (`fs:graph` restores with no gesture), `deviceCapture.ts` is the ONE `getUserMedia` call site, `systemAudioCapture.ts` the ONE `getDisplayMedia` one, and `soundSession.armSound` is the ONE path to either — reachable from exactly TWO real clicks (`SoundNodeButton`, the arm light on the node, and the preview's `SoundControl`), never from an effect, a message handler, a store subscription, or anything a loaded `.fastshader` can reach. **CHOOSING A SOURCE CAN NEVER START A CAPTURE**: `setSoundSource` only REDIRECTS one that is already running (by disarming and re-arming with the settings it kept), so the dropdown is not a third path in. That is what made it safe to put the picker on the node face while it lived there, and it is why the picker is not a third path in now that it lives in the settings menu; on the `system` path the platform also requires transient activation and shows its own share sheet, but that is not licence to relax the rule. **There is deliberately no persisted grant and no "remember this"**: `projectImport`'s `writeLs` block copies preview prefs straight out of an imported file, so a consent key would be one line of attacker-supplied JSON from being pre-granted; not having the key makes that unreachable. Arm/disarm carry a monotonic generation token written synchronously: the permission prompt and the share sheet are both non-modal and can sit open for 30s, so arm→cancel→arm leaves two starts in flight, and without the token the loser's MediaStream is never stopped (OS indicator lit for the life of the tab); the same token guards the `ended` callback, so a device unplugged, a revoked permission or Chrome's own "Stop sharing" disarms the session instead of leaving it at `on` with every band decaying silently to zero. `audioCaptureCore.ts` owns the AudioContext/AnalyserNode/`readLevels`/teardown BOTH paths use, so the fftSize-realloc rule, the never-connect-to-`destination` rule and the gain-is-applied-in-the-SHADER rule cannot drift between them, and it listens for `ended` on EVERY track (a display session's may arrive on the video track alone). **The palette tile is inert twice over**: `NodePreviewCard` replicates the arm light as a `<div>`, never a `<button>` — a tile must not become another way to open a capture — with the explicit `--inert` class, since a `<div>` can never match `:disabled` and it would otherwise show enabled-green beside a grey unwired canvas node; and it renders NO picker at all. While the picker sat on the face the tile needed a DISABLED `<select>` twin, because a card's `pointer-events: none` stops the pointer but not the keyboard and a live one would have made every tile a tab stop that enumerates the machine's audio devices — the picker moving into the settings menu removed that replica, and with it a drift site. **`gain` is an exposed input socket applied SHADER-side as a SEPARATE statement** (`const _sound1_bass = sound1_bass.mul(g);`) — never folded into `uniform(0).mul(g)`, which would stop `uniformLineRe` matching and silently drop both the export schema property and the live uniform binding; gain 1 + unwired emits byte-identically to the ungained form, and the analyser therefore does NOT apply gain (it would scale twice). `smoothing` is ALSO an exposed socket but resolves differently: it sets the AnalyserNode's `smoothingTimeConstant` on the CPU, so ShaderPreview's `micSettingsKey` selector resolves a wired edge with **`evaluateNodeOutput`** (the node-card evaluator) instead of emitting anything — it follows constants/sliders/arithmetic and reads 0 for GPU-only sources, and codegen must stay out of it entirely. `readSoundSettings` is the ONE coercion point, and the clamp is load-bearing because Web Audio THROWS on an out-of-range `fftSize`/`smoothingTimeConstant`. **the Sound node and imageNode are the two nodes that DRAG-REVEAL their hidden param sockets (`revealHidden`) — not keyed off `usesExposedPorts`, since the Output node is in that set and deliberately does not. Without the Sound node there, its smoothing/gain were unreachable by wire: you had to know to tick them in the settings menu first. Both params are declared as real `def.inputs`, not just `defaultValues` keys** — ShaderNode builds sockets from `def.inputs`, so a param that lives only in `defaultValues` can be ticked "expose as input socket" and still render nothing at all (the noise nodes and Time get away with it only because they render through PreviewNode/ClockNode, which have their own socket handling). They keep their `defaultValues` entries too, so an unexposed param still shows its inline number widget, and ShaderNode filters `def.inputs` down to the exposed set exactly like `imageNode`. **The right-click menu is where the source is chosen** (`SoundNodeSettings`), and it is the ONLY such control — the node face carries no second copy, because two controls for one session is how the two end up disagreeing. Label and picker sit on their own rows with the `<select>` at half width: stretched across the panel it was as wide as the longest device name the machine reported, which made it the widest row in a fixed-width menu and dragged the box out with it. Truncation is covered because `SoundSourceSelect` names the current source on the FIRST line of its tooltip, which is why that tooltip is built by hand. Below it sits a HINT rendered only while it applies: device LABELS are empty strings until the page holds a media permission (the spec's anti-fingerprinting rule, not a bug), so on first run the picker falls back to positional names, which reads as the list being broken. **In ShaderPreview, these uniforms are split out of `uniforms` BEFORE anything reads it**, which in one move keeps them out of the overlay, out of `handleReset` (which would otherwise write capture-derived values to disk via `usePersistedState`, contradicting "nothing is recorded"), out of the `fs:preview-ready` re-push, and out of "Set as default". The rAF pump posts `fs:uniform` DIRECTLY and must never call `handleUniformChange`/`handleReset`; the meter is written imperatively; and disarming POSTS ZEROS, or the shader freezes on whatever the last captured frame happened to be. The auto-disarm on "no live-audio uniforms left" gates on INTENT, not on `captureRef.current` — during the prompt no capture exists yet AND `SoundControl` unmounts, so a capture-gated check would let the answer install a live capture with no button anywhere to stop it. Targets come from the GENERATED CODE (avoiding an `s.nodes` subscription) but are GATED on the graph really containing a Sound node: an emitted `const sound1_bass = uniform(0);` is textually identical to a user property that happens to be named `sound1_bass`, so without the gate such a property would vanish from the Uniforms overlay in a graph with no Sound node in it. ONE analyser serves the whole graph, so if a graph does arrive holding two (a pre-fold file migrating both onto `soundNode`, or a hand-edited one — the singleton rule governs the ADD surfaces only), the second one's settings are ignored, `find` making that deterministic (first in node order) rather than arbitrary. **podest CAN hear a microphone, and is deaf to system audio ON PURPOSE** (`public/podest.html`): capture lives in the TOP document — the stage iframe is the same opaque-origin sandbox and could never call `getUserMedia` — and values cross as ordinary `fs:uniform` messages, the same in-place `_propertyUniforms` write the sliders use, so a parent-held capture survives every stage restart (device loss, stall watchdog, time fold). Its `SOUND_RE` matches the same `sound<n>_<channel>` names the editor emits, so a Sound node's uniforms are driven there whatever source the shader was authored against — but podest makes no `getDisplayMedia` call at all, because a share sheet needs a click and a picked window, and podest's whole point is running unattended for weeks. Mic names are split OUT of the reported uniform map **before `onUniforms`**, which in one move keeps them out of the slider list, out of `state.values` and therefore out of the IndexedDB tuning record — reaching `onUniforms` would replay a frozen room-noise level at every boot (value/bounds seeding happens before the row is appended, so filtering later is too late). The arm light is bottom-left, deliberately **NOT** in the `:root.is-present` hide rule: everything else is hidden in presentation mode, but the blinking red light IS the privacy indicator and a pedestal has no visible tab strip. **A drop never arms; a drop always disarms** (both `loadShaderText` and the `fs:uniforms` branch, so a shader that fails to apply cannot leave a live capture driving names from the previous one). **Auto-arm is deliberately NOT implemented**: permission is keyed to ORIGIN, podest shares the editor's, `getUserMedia` needs no transient activation, and podest auto-replays its last drop at boot — so an auto-arm would let a shared `.js` open the microphone silently at every boot for weeks on an unattended machine. An unattended sound-reactive exhibit therefore needs a REMEMBERED-DECISION gate (a flag plus a digest of the exact shader it was granted for), which is a separate design decision, not a gap to quietly fill. The band maths is a hand-written twin of `soundAnalysis.ts` (podest is a standalone vanilla page and cannot import the app's modules) — keep the floor/floor band partition in sync. **The XR popup and the LAN bench server are still deaf** (backgrounded rAF throttling; same sandbox with no parent; plain HTTP is not a secure context, which is also the reachable case `micSupported()`'s `navigator.mediaDevices` check answers) — and fixing XR by capturing at the real origin would let an imported `.fastshader` open the mic using a grant given for the user's own shader, which is the one line this must not cross. **The DESKTOP build needs `src-tauri/Info.plist`, which is not optional garnish**: macOS TCC refuses a microphone request outright — no prompt, no grant, just a `NotAllowedError` — when the requesting process's `Info.plist` carries no `NSMicrophoneUsageDescription`, so without that file the Sound node works in every browser and is permanently dead in the `.dmg`. tauri-bundler picks the file up automatically because it sits beside `tauri.conf.json`. Nothing else was blocking it: wry 0.55.1's `webView:requestMediaCapturePermissionForOrigin:` handler grants unconditionally, `tauri://localhost` and `http://tauri.localhost` are both secure contexts, `csp: null` injects no policy, and the capabilities ACL governs IPC commands, not web APIs. Two consequences worth remembering — `tauri dev` runs the bare binary with NO `.app` bundle and therefore no `Info.plist` at all, so capture can only ever be tested from a real `tauri build`; and under today's ad-hoc signing TCC identifies the app by cdhash, so a grant will not survive an update until the build is properly signed (and if hardened runtime is ever enabled, `bundle.macOS.entitlements` must additionally grant `com.apple.security.device.audio-input`). **Failure wording is shared by the two arm surfaces through `utils/soundStatusMessage.ts`** for one specific reason: they used to hold byte-identical copies of the switch, which is how the desktop build ended up telling users to fix a permission in an address bar it does not have — `denied` on the `device` path is the one status that branches on `__FS_DESKTOP__`. That table is itself the merge of two, and most cases now branch on the SOURCE, because the two paths still fail differently inside one node: `system` gets the share-sheet vocabulary and `no-audio-track`, `device` keeps the MICROPHONE wording even for a loopback driver (it is `getUserMedia` either way, so the setting the user has to find really is the one their OS labels "Microphone" — naming it is the whole point of these sentences), and a NAMED device reports differently from the default one, since `getUserMedia` really does answer OverconstrainedError on an exact `deviceId` where it answers NotFoundError with no constraint.

### Time node's `speed`

- **Time node's `speed`**: the Time node's multiplier follows the SAME opt-in `exposedPorts` rules as the noise params — hidden until ticked in Node Settings, drag-revealed dimmed, auto-exposed when an edge lands, and a wired edge overrides the stored number. It lives in `defaultValues`, NOT `def.inputs`, and must stay there: `ensureBareInputNode` refuses to auto-create a node whose def declares registry inputs, so adding one would silently drop the Time node (and its edge) from `sin(time)`. graphToCode emits `time.mul(<literal|var>)` (method chain — no `mul` import, same convention as the noise `scale`); `tryParseTimeSpeed` collapses BOTH forms back into one Time node, wiring the variable form to the `speed` port. The collapse is deliberately narrow — bare `time` receiver, unshadowed, exactly one argument, and a variable that resolves to a real node — so the fixtures' `const t = time; mul(t, x)` idiom stays a genuine Multiply.

### Time node speed

- **Time node speed**: the Time node carries a `speed` multiplier in `defaultValues`, shown ON the node as an always-visible editable `× <n>` row (`.clock-node__speed-row`) and, when the `speed` socket is wired, as the value ARRIVING through the shared `edgeValueLabel` — plain text, no plate, exactly like the Sound node's wired params. It was previously a read-only red chip in the bottom-right corner that rendered ONLY when `speed !== 1`, so at the default the node carried no sign it had a multiplier at all, which reads as the control having gone missing rather than as "it is at 1". Also settings-editable through the generic `NodeSettingsMenu` defaultValues loop. **Its sockets live INSIDE `.clock-node__canvas-wrap`** so they centre on the clock FACE: positioned against the whole node they sat exactly half a header-height too high, and moved again whenever a long varName wrapped the title to a second line. The left/right insets must always be overridden as a PAIR — only `-right` was, so the shared `transform: translateY(-50%)` override (which also strips React Flow's own `translateX(-50%)`) left the speed socket floating ~6px INSIDE the card while the output sat on the edge. `graphToCode` has a dedicated `def.type === 'time'` branch placed BEFORE the generic `inputs.length === 0 && defaultValues` branch (which would emit the invalid `time(1)` — `time` is a uniform node OBJECT, not a callable): `speed === 1`, a missing key, or any non-finite value emits the historical bare `const time1 = time;` BYTE-FOR-BYTE, so no already-exported shader changes; otherwise it emits the method chain `const time1 = time.mul(k);` (no extra import, same convention as the noise `scale` param). `codeToGraph`'s `tryParseTimeSpeed` collapses that shape back — but ONLY when the receiver is the bare `time` identifier, `time` is unshadowed, there is exactly one argument, and it folds to a numeric constant. It deliberately does NOT collapse `mul(time, k)`, `mul(time1, k)` (the human idiom — ~51 occurrences across the `Tests/` corpus, usually two muls sharing one Time node) or a non-literal multiplier (`mul(t, speed)` in builtinTextures/builtinPresets). **`ensureBareInputNode` needs its `def.defaultValues` bail-out to except `time`** — without it, adding defaultValues silently drops the Time node AND its edge from `sin(time)`/`add(pos, time, normal)` with no error. `values.speed` is adversarial at all three read sites (graphToCode, cpuEvaluator, ClockNode): `Number()` then `Number.isFinite() ? … : 1`, never `String()` and never `resolveExposedParam`. ClockNode integrates `dt * speed` into a phase accumulator (never `Date.now() * speed`, which teleports the hand on every scrub frame) with the rAF deps kept `[]`. `complexity.json` keeps `"time": 0` — `nodeCostPoints` can only express value-dependent cost for `chainable` defs, and `node.data.cost` is a creation-time snapshot frozen into saved graphs.
