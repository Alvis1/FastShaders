### `fs:graph` and `fs:savedGroups` are stored as pure ASCII

- **`fs:graph` and `fs:savedGroups` are stored as pure ASCII** (`utils/asciiStorage.ts` — `toAsciiStorageJson`, the ONE writer path for both keys). WebKit (Safari, and the macOS desktop's WKWebView) charges localStorage by the stored string's in-memory width: 1 byte per character while it is 8-bit, 2 once any character above U+00FF is in it. Every Latvian diacritic is above U+00FF, so one "ā" in a note doubled the cost of a multi-megabyte autosave, and the app's own 3M-char image budget could no longer be saved. MEASURED in WebKit 26.5 (Playwright webkit-2336): the quota is 5,242,880 bytes per origin counting key + value, so `fs:graph` holds at most 5,242,872 8-bit characters. A 3.5M-char value with one "ā" throws QuotaExceededError; the same value through `toAsciiStorageJson` saves and reads back identical. Three things are load-bearing. (a) Everything above U+007F is escaped as `\uXXXX` AFTER the stringify. That is always legal: a non-ASCII code unit can only sit inside a JSON string literal, and no JSON escape contains one. Surrogate halves are escaped one at a time and the parse reassembles them. (b) The escaped text is then RE-ENCODED through `TextEncoder`→`TextDecoder`, and that step is not optional: `String.prototype.replace` on a 16-bit subject returns a 16-bit string even when every character is ASCII, and WebKit refuses it exactly like the unescaped one (measured). Never re-encode by decoding as `latin1`: that label is windows-1252 and garbles U+0080–U+00FF. (c) A payload with nothing to escape is written unchanged, since pure-ASCII stringify output measured 8-bit. The common case therefore costs one regex scan (~1 ms per 5M chars) and stores the bytes it always did. The readers need nothing: the parse decodes `\uXXXX` before the reviver sees a key. The other readers are fine too: `viewportMemory` checks `fs:graph` for presence only, and ShaderCarousel's `bench-registry.js` parses `fs:savedGroups` plainly. An older build also reads the escaped text correctly. Chromium and Firefox pay for it, because they charge by UTF-16 length regardless: each escaped character costs 6 there instead of 1 (an emoji 12). That is negligible beside base64 image payloads, the only term that reaches megabytes. The node suite can only pin the round trip (`asciiStorage.test.ts`, `store/storagePersistence.test.ts`); `scripts/verify-webkit-storage.mjs` is the proof against real WebKit, with a control write that must FAIL, or the run proves nothing. The payload refs are applied to the OBJECT first (`imagePayloadsForStorage` / `libraryPayloadsForStorage`); `toAsciiStorageJson` stays the only writer.

### An image payload is STORED once per localStorage document

- **An image payload is STORED once per localStorage document** (`utils/imagePayloadRefs.ts`, pure + tested). In memory nothing changed: every Image node holds its full `imageB64`, identical payloads are interned on load, and paste / Ctrl+C / Ctrl+D / the clipboard shift / the menu's Duplicate Node / saved groups share the string through `cloneNodesSharingPayloads` as history always did, so graphToCode, imageAssets, cost, thumbnails and the export never see a reference. At the two writers, the first node of a document holding a payload keeps it inline, and every later holder of the byte-identical payload is written `imageB64: ''` (same key position) + `imageRef: 'img1-<FNV-1a hex>-<length base36>'`. `fs:savedGroups` refs may cross groups, and the reader harvests every group's payloads BEFORE the per-group catch, so a dropped group still vouches for the others. There is deliberately NO table object: `fs:savedGroups` must stay a bare array (0.3.33 returns `[]` for anything else, and its next save overwrites the library); an `fs:graph` top-level table would be DROPPED by an older build's first autosave; and a third shared key would need cross-key garbage collection over non-transactional, eventually consistent localStorage. What 0.3.33 sees on a new autosave: no crash, first copies with pixels, duplicates as cards without thumbnails that render black; its autosave keeps `imageRef`, so this build restores them. A document without duplicates is written byte-identically (the writers return the same array). **Identity is decided by CONTENT, never by the hash**: a ref resolves only to the first VALID inline payload in the document whose re-derived key matches, and a later different payload with the same key is always written inline. FNV collides for real: `data:image/png;base64,L8zt5mTG` / `…E6b4siKM` share 61a5fde1 and are the test fixture. `MAX_REF_RESOLVED_IMAGE_CHARS` (16M) bounds what a small document may expand to in consumers that work per instance; the writer applies the same guard in the same order, so the reader never strips what the writer wrote (a seeded property test pins it). A ref that cannot be resolved empties the node and is counted by N8 (the existing notice keys). `imageRef` never survives into the store (resolve, then `sanitizeImageNodes` strips strays), and `applyProjectToStore` resolves too, so a 0.3.33 export carrying refs recovers against the file's own copies (after the project block's own `imageRefs` pass, on the same per-document budget). `WRITE_IMAGE_REFS` (in imageNode.ts) is the rollback lever: false writes every copy inline again and puts the library budget back on instances, while the readers keep resolving. The EXPORT is unchanged (one copy per node), which is why the PROJECT budget still counts instances (`PROJECT_IMAGE_BUDGET_COUNT`); `sanitizeImageNodes`' soft running total is 0.3.33's per-instance total, plus one rule on top: a repeat of a payload that is already kept is free — so everything 0.3.33 keeps is kept (counting DISTINCT payloads instead is not a superset: the kept duplicates leave room for later payloads 0.3.33 strips, which then fill the total and strip a small late image 0.3.33 keeps). The autosave's quota backoff (`uniqueImageChars`) counts distinct payloads.

### `fs:viewport` — the canvas remembers where you were looking

- **`fs:viewport` — the canvas remembers where you were looking** (`utils/viewportMemory.ts`, pure + tested). Everything else about a session already survives a refresh (the graph, both split ratios, the asset bar's height, the open tab), so coming back to a canvas re-framed by `fitView` read as the app having lost your place. Stored as `"<x>,<y>,<zoom>"` — three numbers need no `JSON.parse`, so the read needs neither a reviver nor the shared `safeJson` deny-list, the same reasoning `fs:nodeEditorScroll` gives — and **validated, never coerced**: `Number(' 1 ')` is 1, `Number('١٢')` is 12 and `Number('0x10')` is 16, and localStorage is writable by anything at this origin. A zoom outside React Flow's own `minZoom`/`maxZoom` is rejected up front rather than restored and then clamped on the first interaction, which would visibly jump. Four things are load-bearing. **The read happens ONCE, in a lazy `useState` initializer** — `useRef(readStoredViewport())` looks equivalent and hits localStorage on every one of NodeEditor's many renders. **The write is trailing-debounced (300 ms, the graph autosave's window)**: `onMoveEnd` fires once per gesture for React Flow's own pan/zoom, but the custom trackpad and two-finger paths drive the canvas by calling `setViewport` imperatively per pointermove and each of those is a complete d3-zoom start/zoom/end cycle. Programmatic moves report through the same handler, which is deliberate — a `fitView` after an import, NEW or a Work-folder load re-aims the memory at the graph now on screen, so nothing has to remember to clear it. **The decisive line is in `App.tsx`, not in NodeEditor**: the graph is seeded in App's mount effect, i.e. AFTER React Flow's init, so the `fitView` prop only ever fitted an empty canvas and App dispatches `fs:graph-imported` to frame the seeded graph. That boot arm fits straight over a restored viewport (measured — the restore looked like it had simply not been implemented), so it is now skipped when `saved && readStoredViewport()`. Gated on `saved` rather than on the stored viewport alone: a corrupt or missing autosave lands the DEMO graph on screen instead, and that must still be framed. `defaultViewport`/`fitView` on the `<ReactFlow>` element still carry the first paint, so the canvas never flashes at 0,0,1 on the way. **And `cleanSlateForStudy` clears the key** — an eval participant must not inherit the previous user's pan.

### `fs:nodeEditorScroll` — the node-editor.html overview's scroll offset

- **`fs:nodeEditorScroll` — the node-editor.html overview's scroll offset** (`components/Graphs/scrollMemory.ts`, pure + tested; the DOM half lives in `GraphsPage`, which vitest's `node` env cannot cover). Both axes of the page's ONE scrollport (`.gp__tablewrap`) as `"<top>,<left>"` — two integers need no JSON, so the read needs neither a reviver nor the `safeJson` deny-list. It exists because the normal way to LEAVE that page is a reload: Save writes `nodeRegistry.ts` / `citations.json` / `editorVisibility.json` through `/__nd`, all of which are in the page's own module graph, so HMR reloads it and the user landed back at row 1 after every edit. Four rules, each closing a way the offset silently goes wrong. It is **validated, never coerced** (`parseScrollPos`: length-capped before splitting, then digits-only per field — `Number('')` is 0 and `Number('١٢')` is 12, and localStorage is writable by anything at this origin, the same trust level `sanitizeDrawings`/`sanitizeEdgeExtras` reason about; a scroll position that is quietly wrong reads as the feature not working rather than as a bug anyone reports). It is **clamped to the port's live extents** (`clampScrollPos`) on every frame of the restore, and to a floor of 0 — the browser would clamp a `scrollTop` write anyway, but computing the target explicitly is what lets the restore tell a clamp from an arrival while the table is still growing (and `scrollHeight - clientHeight` goes NEGATIVE mid-mount, which as a target is indistinguishable from having landed). The restore is **mount-only** (one `useLayoutEffect`, one key read per component instance) and deliberately does NOT re-run when a filter or sort rewrites the row set — an offset only means anything against the table that produced it, so re-applying it after 82 rows became 8 is a jump to the bottom of a list nobody scrolled; the in-flight chase abandons itself the moment `rowSetKey` (count + filter/sort state, the free-form fields length-prefixed) stops matching. And it is **never SEEDED**: the save gate opens only on evidence (`shouldOpenSaveGate` — nothing was stored, the restore never wrote, or the port moved somewhere neither the restore nor a browser clamp put it), because every Graph cell is zero-height until `FitNodeHeading` measures its replica, so the restore chases the final height across ~20 frames and MOST of the ways that chase ends leave the port on a clamp; writing that clamp back aims the next restore lower again and the remembered row walks to the top one save-edit-reload cycle at a time. The browser's two unbidden moves are handled differently on purpose: the clamp that follows the table getting SHORTER is identified by EXTENT (`isForcedClamp` — a smaller offset on an axis whose maximum has fallen below what we wrote) and then FOLLOWED, so the user's next scroll is measured from where the port really is; scroll ANCHORING cannot be identified at all (it raises the offset, which is exactly the shape of a user scrolling down) and is turned off in CSS instead — `overflow-anchor: none` on `.gp__tablewrap`, one declaration with no visible effect, pinned by `scrollMemory.test.ts` because MEASURED without it the offset walked 6000 → 9683 over 8 reloads with no input at all.

### Uniform values persist by name, are never SEEDED, and any disagreement with the graph is announced

- **Uniform values persist by name, are never SEEDED, and any disagreement with the graph is announced** (`utils/uniformOverride.ts`, pure + tested — ShaderPreview itself has no coverage, the vitest env is `node`). Removing a property node keeps its stored value (the iframe ignores `fs:uniform` messages for unknown names), so delete + undo — and re-adding a property with the same name and the same number — restores the user's last tuning. What no longer happens is the trap that made this read as broken: the map used to be filled from the authored default the first time a uniform was **seen**, so an entry existed for users who had never opened the overlay, the `fs:preview-ready` re-push then decided the value, and editing the number on the property node had NO visible effect — on a binary channel like Discard that reads as the app being broken. An entry now exists only because the user tuned a slider or imported a file, so "no entry" means "the graph decides". A stored value that differs from the authored default is an **override**, computed by DERIVATION (`stored ≠ authored`, compared at the same 9 significant digits `uniformDefaults` bakes at, so a re-bake can't strand a badge beside a button `planUniformDefaults` refuses to act on) and never from a persisted baseline: a baseline would need a second key plus a migration, and it would still be wrong, because "the literal for this NAME moved" is not "the user edited this number" — which of two same-named properties owns the bare identifier follows the nodes ARRAY order, so a group drag can fake it. **Editing the number on a property node clears that uniform's entry outright**: `updateNodeData` is the authoring chokepoint (import, undo/redo, the code→graph sync and "Set as default" all go through `setNodes` and stay silent) and it dispatches `fs:uniform-authored` carrying the node id's emitted name — an event, not a store subscription, so the panel doesn't re-render per pointermove, and the hot `fs:uniform` post drives the preview at pointer rate instead of waiting out the 200 ms rebuild debounce. `handleReset` (the red ✕) now DELETES the current shader's entries rather than writing the defaults back — writing them back re-armed the trap for every uniform, and the old whole-map replace pruned every remembered name outside the current shader, contradicting the never-prune rule. `fs:previewUniformBounds` is validated per entry like its sibling (it was a bare cast, and `projectImport` writes it straight out of a project block) and both maps are count-capped. `projectImport` also CLEARS both keys when the imported file carries no tuning block — without the else-branch a shader inherited the previous one's tuning for every same-named property, and `property1`/`color1` are the auto-generated names, so a collision is the norm.

### VR cost budgeting

- **VR cost budgeting**: `VR_HEADSETS` ships ONLY measured devices (just Quest 3 since 2026-08-14 — an unmeasured budget certifies shaders for hardware nobody ran; every resolver falls back to `VR_HEADSETS[0]`, so persisted removed ids degrade to Quest 3). A device earns a row by running ShaderCarousel and importing the result: the CostBar accepts EVERY JSON the bench saves (raw results `{metadata, shaders}`, suggestion, patch/profile — `parseCostFile`; the raw branch mirrors bench-stats' `buildSuggestion` and a drift test pins the two against the committed benchData pair) via drag-drop, the device dropdown's "Import result JSON…" picker, AND the same-browser handoff: a finished driver-bench run stores its ~1 KB profile under **`fs:benchResult`** (`bench-stats.storeBenchResult` — never from InOut, which cannot price) and the CostBar offers it as a one-click Add/✕ chip (`utils/benchResult.ts`, pure + tested — length-capped and re-validated through `parseCostFile` since localStorage is untrusted whoever wrote it; re-checked on the cross-tab `storage` event, so the chip appears live while the bench tab is still open, and content-hash dedup makes an already-imported run read as consumed). The bench's primary download is the profile alone (`…-profile-….json`, `exportProfile`) — one file, no multi-download browser prompt; raw+CSV+suggestion moved to a secondary "Research data" button (`exportResults`), which is what `benchData/` commits and `fit-calibration.mjs` needs; cost gradient visualization in CostBar. Points price per-pixel TIME only. Texture MEMORY is the second currency they leave unpriced, and it is reported, not budgeted, by `utils/textureMemory.ts` beside the total. A PMREM-prefiltered environment image can outweigh the image itself about 4.5× (48 MiB beside 10.7 MiB for a 2048×1024 equirect), and the preview model's own textures are not in it.

### Profiles can also be AUTHORED by hand

- **Profiles can also be AUTHORED by hand** — the device dropdown's "Profiles" group holds `New profile…` / `Edit profile…` / `Export profiles…` beside the import row (`Modals/CostProfileModal.tsx`, one dialog with a `new`/`export` mode, PORTALLED to `document.body` because the CostBar sits in a React Flow panel where a `position: fixed` backdrop would resolve against a transformed ancestor; its name field is a real input, never `window.prompt`, which WKWebView need not implement). **The editing medium is the FILE**: Edit downloads the active profile as `{ meta, costs }` — deliberately the shape `parseCostFile` already accepts, so a download re-enters through every existing entrance (drop, picker, bundle) with no second format — you retype numbers and drop it back. That loop only works because the file carries its own `meta.id`: without it the content-hashed id changes with the numbers and every save FORKS a near-duplicate row. `readIdentity` validates the claim (`PROFILE_ID_RE`, label trim + 60 cap, budget/cap clamps) and `profileFromParsed` applies three rules — a claimed `maxTextureDim` may only TIGHTEN the active cap (the store's "never loosening it" invariant, which is a safety limit on image downscaling); a claimed `maxPoints` wins (unlike a bench export, which has none and inherits the active budget so the bar's scale can't jump); and **a claimed id may never take over a MEASURED row** — benchmark numbers cost a device run to reproduce, so such a file lands beside it under its derived id instead. `PROFILE_ID_RE` is permissive INSIDE the `cp:` namespace (`[^\p{C}]`, length-capped) on purpose: a derived id embeds the device string verbatim (`cp:Quest 3|microplane|…`, GPU names reach `qualcomm / adreno-7xx`), so an alphanumeric charset rejected the ids this module itself mints and silently disabled identity for every measured profile. **Provenance is the whole point of the split**: `CostOverrideMeta.manual` (absent = measured, so profiles persisted before it existed are unaffected) keeps typed numbers out of the "● measured" badge and the `Measured` optgroup — they get `✎ custom` and their own group — and it rides `buildMergedComplexity`'s `calibratedFrom`, so a hand-authored table says so in the committed `complexity.json`. Editing a MEASURED profile's download is the one case that crosses over: the id is refused, so the copy is demoted to `manual` and relabelled `<name> (edited)` rather than inheriting a run's provenance with retyped numbers (a byte-faithful copy derives back to the same id and stays measured, which is what makes restoring a backup honest). `New profile…` seeds from the AUTHORED table rather than an empty map — empty is rejected by `parseCostFile`, dropped by the store's boot loader, and gives the user no node keys to fill in — so creating one reprices nothing until it is edited. Export writes one profile or a `{ fastShadersCostProfiles, profiles: [...] }` bundle whose entries are single-profile files, so `parseCostProfileBundle` reuses the same parser (bounded at 100 entries, junk entries dropped rather than failing the import); `importBenchFile` tries the bundle first, since a bundle has no top-level `costs` for the single parser to find. Every entrance reports through ONE transient `cost-bar__notice` strip (`Added`/`Updated "<name>"`, 12 s, dismissible) — a download is otherwise silent and the drop-back leg of the loop used to end with the previous "Saved <file>" notice still on screen, which reads as nothing having happened. Four more rules hold the panel together. **The invalid-run consent gate covers the bundle entrances too** (CostBar AND the code panel's `.json` drop, which also learned to try `parseCostProfileBundle` first — the app's own multi-profile export was otherwise rejected by the one surface that accepts its single-profile sibling): one prompt listing the flagged entries, and declining imports the VALID ones rather than losing the file. **A bundle keeps the active device** (`importCostProfiles(list, { select: 'current' })`, while a single import still auto-selects): restoring a backup must not reprice the open shader against whichever entry the file happened to end with — but it still re-selects that device, since an entry may BE it with new numbers and the applied table has to catch up. **The badge counts what a hand-authored table actually MOVED** (`editedCostCount`, `✎ custom · N edited`): `meta.count` is the table's size, so a freshly seeded profile read `78 nodes` beside a real run's `2 nodes` — inviting exactly the wrong comparison when nothing had been typed yet. And **deleting a hand-authored profile confirms** while a measured one still doesn't: a benchmark row is a drag away from being re-imported, typed prices exist nowhere else and this panel has no undo. One trap worth keeping: `arrowNavRef` (which stops a Windows CLOSED select from firing an action row as bare ArrowDown browsing commits each step) is set only on keydown, so it LATCHED — consumed per `change` now AND cleared on `pointerdown`, because MEASURED on macOS ArrowDown opens the popup without committing, so no change event follows to consume it and every later mouse click on an action row silently did nothing


### A `values` entry is adversarial, and coercing one can THROW

- **`values` is typed `Record<string, string | number>` and that type is a runtime LIE** (2026-09-19). The map arrives verbatim from a `.fastshader`, `fs:graph` or `fs:savedGroups`; `rawNodeValues` only ever checked that it was an OBJECT, and no sanitizer coerces its entries — `sanitizeImageNodes` deliberately leaves a non-string payload in place (its test is `typeof url === 'string'`, so anything else falls through untouched) and `width`/`height` are seen by no sanitizer at all. `String(v)` and `Number(v)` run ToPrimitive, which **throws** when neither `valueOf` nor `toString` yields a primitive: `String({toString:1})` and `Number(Symbol())` are both a `TypeError`. There are ~45 such coercions across codegen, the CPU evaluator, the export paths and the node components.
- **The consequence is not a degraded node, it is a dead app.** There is no error boundary anywhere in this app (`grep componentDidCatch|getDerivedStateFromError` returns nothing), so a throw from `graphToCode` — which the sync engine runs inside a render — unmounts the root and the screen goes blank. The graph is already in the store by then, and the 300 ms autosave is a `useAppStore.subscribe` OUTSIDE React, so it writes the poisoned graph back to `fs:graph` and the app blanks again on **every reload**, until localStorage is cleared by hand. Four characters of JSON in a shared shader (`{"speed":{"toString":1}}`) are enough.
- **MEASURED 2026-09-19: 38 fatal single-key graphs across 17 node types.** The sweep seeds `fs:graph` through Playwright's `addInitScript`, one poisoned key per page, and reads `e.stack` filtered to `/src/` in `page.on('pageerror')` — which is also what separates a newly introduced site from a pre-existing one.
- **Guarding the call sites one at a time DID NOT CONVERGE** — every node family has its own reads (`numVal` in the image branch, a second `paramExpr` in another, the property/colour emitters, `colormaps`, `soundSettings`…). Three rounds of patching took it from 38 to 20 to 3. So it is closed where every reader already comes through: **`rawNodeValues` drops uncoercible entries**, returning the map **BY IDENTITY** when there are none — which is every real graph, so no allocation and no memo invalidation (the identity contract that accessor already documents).
- **`utils/valueCoerce.ts` is the guard for readers that take a `values` map as a PARAMETER** (`decodeImageNode`, `imageAssetFor`, `readImageTextureSpec`, …), which the accessor cannot reach. `valueStr`/`valueNum` are **drop-ins**: they differ from `String()`/`Number()` only where those would throw. `plainStr` is the strict one — strings and numbers only — for the Image node's per-render re-measure key, where a million-element array would coerce WITHOUT throwing and build a multi-megabyte string twice a frame.
- **Both are permissive on purpose, and this is the trap.** Anything that coerces without throwing is kept EXACTLY as it was, booleans and arrays included, because those coercions are load-bearing and pinned: the Image node's `repeat` reads `false`, `null` and `''` as CLAMP — i.e. the `Number()` zero — against a `historicalReads` reference in `imageTextureSpec.test.ts`. The first cut of `valueNum` returned NaN for `null`/`''` and silently flipped every such node from clamp to repeat. A guard that turns junk into a legal value is a guard that hides the junk; a guard that turns a legal value into junk is a regression.
- **Three sites bypass the accessor and need their own guard**: `utils/colormaps.ts` (`String(id)`, `String(def.stops)`), `utils/soundSettings.ts`, and `nodes/SoundNode.tsx` — a bespoke component that reads `data.values` raw rather than through `getNodeValues`. A new component that does the same must guard too.
- `types/nodeValuesAdversarial.test.ts` pins both halves (nothing uncoercible reaches a caller; everything else is returned by identity, value for value), and `utils/valueCoerce.test.ts` pins that the drop-ins agree with `String`/`Number` on every input that does not throw.
