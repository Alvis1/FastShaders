### `fs:graph` and `fs:savedGroups` are stored as pure ASCII

- **`fs:graph` and `fs:savedGroups` are stored as pure ASCII** (`utils/asciiStorage.ts` — `toAsciiStorageJson`, the ONE writer path for both keys). WebKit (Safari, and the macOS desktop's WKWebView) charges localStorage by the stored string's in-memory width: 1 byte per character while it is 8-bit, 2 once any character above U+00FF is in it. Every Latvian diacritic is above U+00FF, so one "ā" in a note doubled the cost of a multi-megabyte autosave, and the app's own 3M-char image budget could no longer be saved. MEASURED in WebKit 26.5 (Playwright webkit-2336): the quota is 5,242,880 bytes per origin counting key + value, so `fs:graph` holds at most 5,242,872 8-bit characters. A 3.5M-char value with one "ā" throws QuotaExceededError; the same value through `toAsciiStorageJson` saves and reads back identical. Three things are load-bearing. (a) Everything above U+007F is escaped as `\uXXXX` AFTER the stringify. That is always legal: a non-ASCII code unit can only sit inside a JSON string literal, and no JSON escape contains one. Surrogate halves are escaped one at a time and the parse reassembles them. (b) The escaped text is then RE-ENCODED through `TextEncoder`→`TextDecoder`, and that step is not optional: `String.prototype.replace` on a 16-bit subject returns a 16-bit string even when every character is ASCII, and WebKit refuses it exactly like the unescaped one (measured). Never re-encode by decoding as `latin1`: that label is windows-1252 and garbles U+0080–U+00FF. (c) A payload with nothing to escape is written unchanged, since pure-ASCII stringify output measured 8-bit. The common case therefore costs one regex scan (~1 ms per 5M chars) and stores the bytes it always did. The readers need nothing: the parse decodes `\uXXXX` before the reviver sees a key. The other readers are fine too: `viewportMemory` checks `fs:graph` for presence only, and ShaderCarousel's `bench-registry.js` parses `fs:savedGroups` plainly. An older build also reads the escaped text correctly. Chromium and Firefox pay for it, because they charge by UTF-16 length regardless: each escaped character costs 6 there instead of 1 (an emoji 12). That is negligible beside base64 image payloads, the only term that reaches megabytes. The node suite can only pin the round trip (`asciiStorage.test.ts`, `store/storagePersistence.test.ts`); `scripts/verify-webkit-storage.mjs` is the proof against real WebKit, with a control write that must FAIL, or the run proves nothing. The payload refs are applied to the OBJECT first (`imagePayloadsForStorage` / `libraryPayloadsForStorage`); `toAsciiStorageJson` stays the only writer.

### An image payload is STORED once per localStorage document

- **An image payload is STORED once per localStorage document** (`utils/imagePayloadRefs.ts`, pure + tested). In memory nothing changed: every Image node holds its full `imageB64`, identical payloads are interned on load, and paste / Ctrl+C / Ctrl+D / the clipboard shift / the menu's Duplicate Node / saved groups share the string through `cloneNodesSharingPayloads` as history always did, so graphToCode, imageAssets, cost, thumbnails and the export never see a reference. At the two writers, the first node of a document holding a payload keeps it inline, and every later holder of the byte-identical payload is written `imageB64: ''` (same key position) + `imageRef: 'img1-<FNV-1a hex>-<length base36>'`. `fs:savedGroups` refs may cross groups, and the reader harvests every group's payloads BEFORE the per-group catch, so a dropped group still vouches for the others. There is deliberately NO table object: `fs:savedGroups` must stay a bare array (0.3.33 returns `[]` for anything else, and its next save overwrites the library); an `fs:graph` top-level table would be DROPPED by an older build's first autosave; and a third shared key would need cross-key garbage collection over non-transactional, eventually consistent localStorage. What 0.3.33 sees on a new autosave: no crash, first copies with pixels, duplicates as cards without thumbnails that render black; its autosave keeps `imageRef`, so this build restores them. A document without duplicates is written byte-identically (the writers return the same array). **Identity is decided by CONTENT, never by the hash**: a ref resolves only to the first VALID inline payload in the document whose re-derived key matches, and a later different payload with the same key is always written inline. FNV collides for real: `data:image/png;base64,L8zt5mTG` / `…E6b4siKM` share 61a5fde1 and are the test fixture. `MAX_REF_RESOLVED_IMAGE_CHARS` (16M) bounds what a small document may expand to in consumers that work per instance; the writer applies the same guard in the same order, so the reader never strips what the writer wrote (a seeded property test pins it). A ref that cannot be resolved empties the node and is counted by N8 (the existing notice keys). `imageRef` never survives into the store (resolve, then `sanitizeImageNodes` strips strays), and `applyProjectToStore` resolves too, so a 0.3.33 export carrying refs recovers against the file's own copies (after the project block's own `imageRefs` pass, on the same per-document budget). `WRITE_IMAGE_REFS` (in imageNode.ts) is the rollback lever: false writes every copy inline again and puts the library budget back on instances, while the readers keep resolving. The EXPORT is unchanged (one copy per node), which is why the PROJECT budget still counts instances (`PROJECT_IMAGE_BUDGET_COUNT`); `sanitizeImageNodes`' soft running total is 0.3.33's per-instance total, plus one rule on top: a repeat of a payload that is already kept is free — so everything 0.3.33 keeps is kept (counting DISTINCT payloads instead is not a superset: the kept duplicates leave room for later payloads 0.3.33 strips, which then fill the total and strip a small late image 0.3.33 keeps). The autosave's quota backoff (`uniqueImageChars`) counts distinct payloads.

### Payload caps bound what re-materializes a payload, not undo depth

- **Payload caps bound what re-materializes a payload, not undo depth** (`MAX_IMAGE_ENCODED_CHARS` in `utils/imageNode.ts`, `MAX_DATA_ENCODED_CHARS` in `utils/dataNode.ts`). History carries `values.imageB64` and `values.dataB64` BY REFERENCE (`cloneNodesSharingPayloads`: strings are immutable and every edit path replaces `values` wholesale); every other key on a node is still deep-copied per history entry. What the caps bound is the 300 ms autosave's `JSON.stringify` against the origin's localStorage budget, the per-node re-embed in every export, and the `atob` decode.
- **`MAX_DATA_ENCODED_CHARS` is a CONSTRUCTION bound, not a policy number**: 16 columns (`MAX_COLUMNS`) × 8192 rows (`MAX_TEXTURE_WIDTH`) × 4 bytes = 524,288 bytes = 699,052 base64 chars, computed from those two constants so it moves with either. `decodeDataNode` checks three O(1) ceilings before the linear decode (length, `MAX_COLUMNS`, `MAX_TEXTURE_WIDTH`), and the column ceiling is not redundant: a legal-size blob declared `rowCount: 1, columnCount: 131072` measured 13.5 ms against 0.1 ms. There is deliberately no soft/hard split, because nothing above the construction bound can be legitimate.

### `fs:viewport` — the canvas remembers where you were looking

- **`fs:viewport` — the canvas remembers where you were looking** (`utils/viewportMemory.ts`, pure + tested). Everything else about a session already survives a refresh (the graph, both split ratios, the asset bar's height, the open tab), so coming back to a canvas re-framed by `fitView` read as the app having lost your place. Stored as `"<x>,<y>,<zoom>"` — three numbers need no `JSON.parse`, so the read needs neither a reviver nor the shared `safeJson` deny-list, the same reasoning `fs:nodeEditorScroll` gives — and **validated, never coerced**: `Number(' 1 ')` is 1, `Number('١٢')` is 12 and `Number('0x10')` is 16, and localStorage is writable by anything at this origin. A zoom outside React Flow's own `minZoom`/`maxZoom` is rejected up front rather than restored and then clamped on the first interaction, which would visibly jump. **`readStoredViewport` is itself gated on a stored graph** (`fs:graph` present, or `fs:desktopAutosave` = `'1'`): a stored viewport with no stored graph means the graph key was cleared or this is a first visit, and restoring a pan measured against a document that no longer exists would open the demo on empty canvas. Deliberately nothing finer than that — no per-shader viewports, no graph digest — because every path that REPLACES the graph already runs `fitView` (see the programmatic-move rule below). Four things are load-bearing. **The read happens ONCE, in a lazy `useState` initializer** — `useRef(readStoredViewport())` looks equivalent and hits localStorage on every one of NodeEditor's many renders. **The write is trailing-debounced (300 ms, the graph autosave's window)**: `onMoveEnd` fires once per gesture for React Flow's own pan/zoom, but the custom trackpad and two-finger paths drive the canvas by calling `setViewport` imperatively per pointermove and each of those is a complete d3-zoom start/zoom/end cycle. Programmatic moves report through the same handler, which is deliberate — a `fitView` after an import, NEW or a Work-folder load re-aims the memory at the graph now on screen, so nothing has to remember to clear it. **The decisive line is in `App.tsx`, not in NodeEditor**: the graph is seeded in App's mount effect, i.e. AFTER React Flow's init, so the `fitView` prop only ever fitted an empty canvas and App dispatches `fs:graph-imported` to frame the seeded graph. That boot arm fits straight over a restored viewport (measured — the restore looked like it had simply not been implemented), so it is now skipped when `saved && readStoredViewport()`. Gated on `saved` rather than on the stored viewport alone: a corrupt or missing autosave lands the DEMO graph on screen instead, and that must still be framed. `defaultViewport`/`fitView` on the `<ReactFlow>` element still carry the first paint, so the canvas never flashes at 0,0,1 on the way. **And `cleanSlateForStudy` clears the key** — an eval participant must not inherit the previous user's pan. **The preview's camera keys are validated the same way**: `fs:previewCameraPos` and `fs:previewRotation` are read through `finiteVec3` (`components/Preview/finiteVec3.ts`, 2026-10-11): all three axes must be finite numbers, so a stored `{"x":1e999}` (Infinity after `JSON.parse`) is refused, and the camera also keeps the radius < 1 rejection (`cameraTooClose`; orbit `minDistance` is 2). The live `fs:camera` and `fs:rotation` reports from the sandbox use the same guard, because a forged NaN rotation was baked into the next cold rebuild and made the model vanish until Play or a reload. The orbit TARGET (the controls pan) is deliberately NOT persisted: it lives in ShaderPreview for the session only (preview-and-runtime.md, the budget section), there is no localStorage key for it, and it needs no inventory row.

### `fs:nodeEditorScroll` — the node-editor.html overview's scroll offset

- **`fs:nodeEditorScroll` — the node-editor.html overview's scroll offset** (`components/Graphs/scrollMemory.ts`, pure + tested; the DOM half lives in `GraphsPage`, which vitest's `node` env cannot cover). Both axes of the page's ONE scrollport (`.gp__tablewrap`) as `"<top>,<left>"` — two integers need no JSON, so the read needs neither a reviver nor the `safeJson` deny-list. It exists because the normal way to LEAVE that page is a reload: Save writes `nodeRegistry.ts` / `citations.json` / `editorVisibility.json` through `/__nd`, all of which are in the page's own module graph, so HMR reloads it and the user landed back at row 1 after every edit. Four rules, each closing a way the offset silently goes wrong. It is **validated, never coerced** (`parseScrollPos`: length-capped before splitting, then digits-only per field — `Number('')` is 0 and `Number('١٢')` is 12, and localStorage is writable by anything at this origin, the same trust level `sanitizeDrawings`/`sanitizeEdgeExtras` reason about; a scroll position that is quietly wrong reads as the feature not working rather than as a bug anyone reports). It is **clamped to the port's live extents** (`clampScrollPos`) on every frame of the restore, and to a floor of 0 — the browser would clamp a `scrollTop` write anyway, but computing the target explicitly is what lets the restore tell a clamp from an arrival while the table is still growing (and `scrollHeight - clientHeight` goes NEGATIVE mid-mount, which as a target is indistinguishable from having landed). The restore is **mount-only** (one `useLayoutEffect`, one key read per component instance) and deliberately does NOT re-run when a filter or sort rewrites the row set — an offset only means anything against the table that produced it, so re-applying it after 82 rows became 8 is a jump to the bottom of a list nobody scrolled; the in-flight chase abandons itself the moment `rowSetKey` (count + filter/sort state, the free-form fields length-prefixed) stops matching. And it is **never SEEDED**: the save gate opens only on evidence (`shouldOpenSaveGate` — nothing was stored, the restore never wrote, or the port moved somewhere neither the restore nor a browser clamp put it), because every Graph cell is zero-height until `FitNodeHeading` measures its replica, so the restore chases the final height across ~20 frames and MOST of the ways that chase ends leave the port on a clamp; writing that clamp back aims the next restore lower again and the remembered row walks to the top one save-edit-reload cycle at a time. The browser's two unbidden moves are handled differently on purpose: the clamp that follows the table getting SHORTER is identified by EXTENT (`isForcedClamp` — a smaller offset on an axis whose maximum has fallen below what we wrote) and then FOLLOWED, so the user's next scroll is measured from where the port really is; scroll ANCHORING cannot be identified at all (it raises the offset, which is exactly the shape of a user scrolling down) and is turned off in CSS instead — `overflow-anchor: none` on `.gp__tablewrap`, one declaration with no visible effect, pinned by `scrollMemory.test.ts` because MEASURED without it the offset walked 6000 → 9683 over 8 reloads with no input at all. The walk was 6000 → 6376 → 6772 → 7201 → 7657 → 8153 → 8663 → 9173 → 9683, the first nudge at t=190 ms as `scrollHeight` went 11349 → 11954; a bottom-parked port never showed it (clamped at its maximum, anchoring has nowhere to push). `isForcedClamp` tests `max < wrote`, never `now.top === max.top`: the extent read one tick after the clamp measured 105px TALLER than the offset the clamp produced. It exists because of a MEASURED loss (built page, headless Chrome 1500x900, no input): parked at 10992, reloaded, the restore lands, the late webfont swap shortens the table, the port is clamped to 6143 and that was written over the good offset (`scrollMemory.test.ts` holds the figures). A shrink the USER caused (a category chip, the search box) is suppressed by the same rule, so the stored offset survives the filter; their next scroll is measured from the clamped position and saves normally. Requiring `chaseOver` costs nothing: every gesture that can scroll fires one of the restore's document-level abort events FIRST. `wantScrollRef` is read ONCE per component instance, because StrictMode runs mount → cleanup → mount in dev and a second read would pick up a clamp the first pass wrote. And it is localStorage, not sessionStorage: the page is routinely opened in a FRESH TAB.

### Uniform values persist by name, are never SEEDED, and any disagreement with the graph is announced

- **Uniform values persist by name, are never SEEDED, and any disagreement with the graph is announced** (`utils/uniformOverride.ts`, pure + tested — ShaderPreview itself has no coverage, the vitest env is `node`). Removing a property node keeps its stored value (the iframe ignores `fs:uniform` messages for unknown names), so delete + undo — and re-adding a property with the same name and the same number — restores the user's last tuning. What no longer happens is the trap that made this read as broken: the map used to be filled from the authored default the first time a uniform was **seen**, so an entry existed for users who had never opened the overlay, the `fs:preview-ready` re-push then decided the value, and editing the number on the property node had NO visible effect — on a binary channel like Discard that reads as the app being broken. An entry now exists only because the user tuned a slider or imported a file, so "no entry" means "the graph decides". A stored value that differs from the authored default is an **override**, computed by DERIVATION (`stored ≠ authored`, compared at the same 9 significant digits `uniformDefaults` bakes at, so a re-bake can't strand a badge beside a button `planUniformDefaults` refuses to act on) and never from a persisted baseline: a baseline would need a second key plus a migration, and it would still be wrong, because "the literal for this NAME moved" is not "the user edited this number" — which of two same-named properties owns the bare identifier follows the nodes ARRAY order, so a group drag can fake it. **Editing the number on a property node clears that uniform's entry outright**: `updateNodeData` is the authoring chokepoint (import, undo/redo, the code→graph sync and "Set as default" all go through `setNodes` and stay silent) and it dispatches `fs:uniform-authored` carrying the node id's emitted name — an event, not a store subscription, so the panel doesn't re-render per pointermove, and the hot `fs:uniform` post drives the preview at pointer rate instead of waiting out the 200 ms rebuild debounce. `handleReset` (the red ✕) now DELETES the current shader's entries rather than writing the defaults back — writing them back re-armed the trap for every uniform, and the old whole-map replace pruned every remembered name outside the current shader, contradicting the never-prune rule. `fs:previewUniformBounds` is validated per entry like its sibling (it was a bare cast, and `projectImport` writes it straight out of a project block) and both maps are count-capped. `projectImport` also CLEARS both keys when the imported file carries no tuning block — without the else-branch a shader inherited the previous one's tuning for every same-named property, and `property1`/`color1` are the auto-generated names, so a collision is the norm.

### VR cost budgeting

- **VR cost budgeting**: `VR_HEADSETS` ships ONLY measured devices (an unmeasured budget certifies shaders for hardware nobody ran, so the paper-spec rows went 2026-08-14; every resolver falls back to `VR_HEADSETS[0]`, so persisted removed ids degrade to Quest 3). Two rows today: Quest 3, whose run IS the table, and Steam Frame (2026-10-21, `benchData/steamframe-20261021`), the first built-in row carrying its own `costs` — applied through the ONE lookup `deviceCostOverrides` (a profile's costs, else the row's), at boot and on every selection, so the cost bar tags it "measured" and a study package records it as `measured` with the run in `source`. Its prices are RATIO-BRIDGED (table × SteamFrame-MicroPlane ÷ Quest3-MicroPlane), never the profile's raw points: the table is Quest 3 STATIC, and on Quest 3 MicroPlane reads the cheap noises well under Static (Perlin 27 vs 36), so raw MicroPlane points over a Static table would mix two currencies. Only the noise family was run, so only it is repriced; a node both MicroPlane runs read as 0 (Cell Noise, under the timer floor) keeps the table. `steamFrameHeadset.test.ts` re-derives every number from the committed files. Budget 200 like Quest 3 (in TABLE points: the divisor its node points are printed against — like every budget it prints as 100, next section): the device's speed lives in the prices, and its eye-buffer size is unknown, so no pixel ratio is measured. A device earns a row by running ShaderCarousel and importing the result: the CostBar accepts EVERY JSON the bench saves (raw results `{metadata, shaders}`, suggestion, patch/profile — `parseCostFile`; the raw branch mirrors bench-stats' `buildSuggestion` and a drift test pins the two against the committed benchData pair) via drag-drop, the device dropdown's "Import result JSON…" picker, AND the same-browser handoff: a finished driver-bench run stores its ~1 KB profile under **`fs:benchResult`** (`bench-stats.storeBenchResult` — never from InOut, which cannot price) and the CostBar offers it as a one-click Add/✕ chip (`utils/benchResult.ts`, pure + tested — length-capped and re-validated through `parseCostFile` since localStorage is untrusted whoever wrote it; re-checked on the cross-tab `storage` event, so the chip appears live while the bench tab is still open, and content-hash dedup makes an already-imported run read as consumed). The bench's primary download is the profile alone (`…-profile-….json`, `exportProfile`) — one file, no multi-download browser prompt; raw+CSV+suggestion moved to a secondary "Research data" button (`exportResults`), which is what `benchData/` commits and `fit-calibration.mjs` needs; cost gradient visualization in CostBar. Points price per-pixel TIME only. Texture MEMORY is the second currency they leave unpriced, and it is reported, not budgeted, by `utils/textureMemory.ts` beside the total. A PMREM-prefiltered environment image can outweigh the image itself about 4.5× (48 MiB beside 10.7 MiB for a 2048×1024 equirect), and the preview model's own textures are not in it.

### Every device's budget PRINTS as 100, and only the display divides

- **Every device's budget PRINTS as 100** (owner, 2026-10-23: "all that changes are the node points"; `utils/budgetPoints.ts`, `POINT_BUDGET`). The cost TABLE keeps its own currency — table points, calibrated on a Quest 3 whose frame is 200 of them — and so does everything stored, exported or recorded: complexity.json, a profile's `costs` and `maxPoints`, the store's `totalCost`, every `data.cost` snapshot, a study's snapshots, `budget-crossed` events and package figures (eval-mode.md), and the bench (ShaderCarousel's own "100 points ≡ 8.33 ms" is that table currency, not the printed 100). Only the DISPLAY divides: a surface prints `raw × 100 / budget` (`toBudgetPoints`) — the share of the selected device's frame a node or a shader takes — where `budget` is that device's `maxPoints` in table points. It is a module singleton beside the active price table (`setDeviceBudget`, called by the store at boot and in `setSelectedHeadsetId`, which also bumps `costVersion`): components read it through `useDeviceBudget`/`useBudgetPoints` (`hooks/useDeviceBudget.ts`, re-rendered on `costVersion`, so a card never divides by one device's budget while pricing under another device's table), non-React code (the layout engine, NodeEditor's hit boxes, the Designer) through `budgetPointsOf`. Two devices therefore differ in their node PRICES alone: the device dropdown prints no budget beside a name (`deviceOptionText` takes the device alone — owner: "Do not show points behind device profiles, because all is 100"), and the select's tooltip says every device's budget is 100. On both shipped headsets (budget 200) a printed figure is half its table figure.
- **Summed first, rounded only for print.** A total — the cost bar's, a sink's badge, a collapsed group's pill, a ready-made tile's — is summed in table points and divided ONCE, then `formatPoints` rounds it to 0.01 with trailing zeros dropped (`17.5`, `23.33`, `4`) and a dot whatever the locale (the number fields' `formatFieldNumber`). A non-finite junk figure prints `0`, never NaN, and a junk budget (non-positive or non-finite) leaves a figure in table points rather than dividing by it. Adding PRINTED figures would drift: three nodes of ⅓ point each print `0.33`, and their total prints `1`, never `0.99` (`budgetPoints.test.ts`).
- **A rounded figure is MARKED, and its exact value is one hover away** (`components/Points/Points.tsx`, the ONE printer; `<Points value={…}>` takes BUDGET points, already divided). When the 0.01 rounding dropped digits — beyond a 1e-9 relative slack, so float noise like `0.1 + 0.2` does not earn it — a small CENTRED dot follows the figure, raised to the digits' middle and tucked against the last digit so it cannot read as a decimal point or as a separator from whatever follows (the owner's choice of mark), and the span's `title` carries the value to six decimals for the app-wide TooltipLayer. The span takes the pointer back (`.fs-points--tip { pointer-events: auto }`): every badge it sits in is `pointer-events: none`, and a title on an element the pointer passes through never shows. An exact figure is bare text, with nothing to mark or hover. `tip={false}` where the host's own title already states the exact figure — the cost bar's total, whose tooltip fills `{total}` with `formatPoints(points).exact` — because one hover cannot show two. node-editor.html's overview turns the tip back off over its inert tiles (`.gp__preview .fs-points--tip { pointer-events: none }`, GraphsPage.css), or the span revives the tile's drag, click-to-add and description tooltip over the badge. On touch the dot still marks a rounded figure, but a tap does not reveal the exact value (TooltipLayer opens on hover or keyboard focus).
- **The cost bar** (`CostMeter`, shared with the intro's budget slide, which converts with the same `useBudgetPoints`) reads `<total> / 100 pts`, with end labels 0 and 100, the marker at min(points / 100, 1), and red past 100 — the same test as the summed table total passing the device's table budget, the comparison a sink badge (`useSinkBadgeClass`, over that sink's own total) and the study's `budget-crossed` watcher make in table points. **Its right-click point-cap editor is GONE** (2026-10-23), with `fs:costBudgets`: a typed cap layered over a device's measured budget made the scale a per-machine setting (it reached the study as an inherited condition — see localStorage above), and with every budget printed as 100 there is no budget left to type. A right-click on the bar gets the browser's own menu, `resolveDeviceBudget(id, profiles)` lost its override argument, and the store REMOVES the key at every boot (`deviceBudget.test.ts` pins the removal and that nothing reads or writes it), so a cap typed before the change cannot linger.
- **Colour and size scale on budget points too**: `COST_GRADIENT_SPAN` is 40 BUDGET points (`utils/colorUtils.ts`; it was 80 table points when the budget printed as 200), and `getCostColor`/`getCostTextColor`/`getCostScale` take budget points. Under both shipped headsets every colour and every card size is therefore what it was; a device with another budget moves them all (a stricter device grows its cards, since each node is a larger share of its frame). `useCostChrome(cost)` takes TABLE points and returns the badge's `points` with the chrome judged in budget points (node-visuals-and-designer.md).
- **Every price follows the SELECTED device's table**: `freshNodeCost` (`utils/typeCost.ts`) — the palette tile, the Add-node row, the Designer, the node-editor overview, the palette strip's sort and every creation snapshot — prices under the active table since 2026-10-23. It read the SHIPPED table before, so under a device carrying its own prices (the Steam Frame row, a measured profile) a noise tile and the card dropped from it printed the shipped price while the cost bar charged the measured one. A ready-made tile prices through `assetCostPoints` (discovery-and-i18n.md, Asset-browser ordering) and every canvas card prices LIVE (node-visuals-and-designer.md). A device change bumps `costVersion`, which re-renders every reader and re-sorts every strip.

### Profiles can also be AUTHORED by hand

- **Profiles can also be AUTHORED by hand** — the device dropdown's "Profiles" group holds `New profile…` / `Edit profile…` / `Export profiles…` beside the import row (`Modals/CostProfileModal.tsx`, one dialog with a `new`/`export` mode, PORTALLED to `document.body` because the CostBar sits in a React Flow panel where a `position: fixed` backdrop would resolve against a transformed ancestor; its name field is a real input, never `window.prompt`, which WKWebView need not implement). The group ends with `Compare devices…` (2026-10-23): it opens `<base>compare/` in a NEW tab (`window.open(url, '_blank', 'noopener')`, so the canvas stays where it is), it is a sentinel in `ACTION_OPTIONS`, so the arrow-nav guard below covers it, and it is never offered in a study session, where what the editor offers is part of the condition, nor in the desktop build, whose webview has no tab to open it in (`OFFERS_COMPARE`; the page itself: platform-and-release.md). **The editing medium is the FILE**: Edit downloads the active profile as `{ meta, costs }` — deliberately the shape `parseCostFile` already accepts, so a download re-enters through every existing entrance (drop, picker, bundle) with no second format — you retype numbers and drop it back. That loop only works because the file carries its own `meta.id`: without it the content-hashed id changes with the numbers and every save FORKS a near-duplicate row. `readIdentity` validates the claim (`PROFILE_ID_RE`, label trim + 60 cap, budget/cap clamps) and `profileFromParsed` applies three rules — a claimed `maxTextureDim` may only TIGHTEN the active cap (the store's "never loosening it" invariant, which is a safety limit on image downscaling); a claimed `maxPoints` wins (unlike a bench export, which has none and inherits the active budget, so importing one moves only the prices it measured: the budget is the divisor every printed point goes through, and inheriting it keeps every other node's printed share where it was); and **a claimed id may never take over a MEASURED row** — benchmark numbers cost a device run to reproduce, so such a file lands beside it under its derived id instead. `PROFILE_ID_RE` is permissive INSIDE the `cp:` namespace (`[^\p{C}]`, length-capped) on purpose: a derived id embeds the device string verbatim (`cp:Quest 3|microplane|…`, GPU names reach `qualcomm / adreno-7xx`), so an alphanumeric charset rejected the ids this module itself mints and silently disabled identity for every measured profile. **Provenance is the whole point of the split**: `CostOverrideMeta.manual` (absent = measured, so profiles persisted before it existed are unaffected) keeps typed numbers out of the "● measured" badge and the `Measured` optgroup — they get `✎ custom` and their own group — and it rides `buildMergedComplexity`'s `calibratedFrom`, so a hand-authored table says so in the committed `complexity.json`. Editing a MEASURED profile's download is the one case that crosses over: the id is refused, so the copy is demoted to `manual` and relabelled `<name> (edited)` rather than inheriting a run's provenance with retyped numbers (a byte-faithful copy derives back to the same id and stays measured, which is what makes restoring a backup honest). `New profile…` seeds from the AUTHORED table rather than an empty map — empty is rejected by `parseCostFile`, dropped by the store's boot loader, and gives the user no node keys to fill in — so creating one from a device on the shipped table (Quest 3) reprices nothing until it is edited. From a device carrying its own prices (the Steam Frame row, a measured profile) the new profile sets those nodes back to their shipped prices, which the dialog's "so nothing changes until you edit it" does not say. The profile inherits the selected device's budget into its record and its file — the divisor its points print against — but since 2026-10-23 the dialog never mentions one ("Starts from the shipped node prices, so nothing changes until you edit it…", where it used to add "and this device's budget"): every budget reads 100. Export writes one profile or a `{ fastShadersCostProfiles, profiles: [...] }` bundle whose entries are single-profile files, so `parseCostProfileBundle` reuses the same parser (bounded at 100 entries, junk entries dropped rather than failing the import); `importBenchFile` tries the bundle first, since a bundle has no top-level `costs` for the single parser to find. Every entrance reports through ONE transient `cost-bar__notice` strip (`Added`/`Updated "<name>"`, 12 s, dismissible) — a download is otherwise silent and the drop-back leg of the loop used to end with the previous "Saved <file>" notice still on screen, which reads as nothing having happened. Four more rules hold the panel together. **The invalid-run consent gate covers the bundle entrances too** (CostBar AND the code panel's `.json` drop, which also learned to try `parseCostProfileBundle` first — the app's own multi-profile export was otherwise rejected by the one surface that accepts its single-profile sibling): one prompt listing the flagged entries, and declining imports the VALID ones rather than losing the file. **A bundle keeps the active device** (`importCostProfiles(list, { select: 'current' })`, while a single import still auto-selects): restoring a backup must not reprice the open shader against whichever entry the file happened to end with — but it still re-selects that device, since an entry may BE it with new numbers and the applied table has to catch up. **The badge counts what a hand-authored table actually MOVED** (`editedCostCount`, `✎ custom · N edited`): `meta.count` is the table's size, so a freshly seeded profile read `78 nodes` beside a real run's `2 nodes` — inviting exactly the wrong comparison when nothing had been typed yet. And **deleting a hand-authored profile confirms** while a measured one still doesn't: a benchmark row is a drag away from being re-imported, typed prices exist nowhere else and this panel has no undo. One trap worth keeping: `arrowNavRef` (which stops a Windows CLOSED select from firing an action row as bare ArrowDown browsing commits each step) is set only on keydown, so it LATCHED — consumed per `change` now AND cleared on `pointerdown`, because MEASURED on macOS ArrowDown opens the popup without committing, so no change event follows to consume it and every later mouse click on an action row silently did nothing


### A `values` entry is adversarial, and coercing one can THROW

- **`values` is typed `Record<string, string | number>` and that type is a runtime LIE** (2026-09-19). The map arrives verbatim from a `.fastshader`, `fs:graph` or `fs:savedGroups`; `rawNodeValues` only ever checked that it was an OBJECT, and no sanitizer coerces its entries — `sanitizeImageNodes` deliberately leaves a non-string payload in place (its test is `typeof url === 'string'`, so anything else falls through untouched) and `width`/`height` are seen by no sanitizer at all. `String(v)` and `Number(v)` run ToPrimitive, which **throws** when neither `valueOf` nor `toString` yields a primitive: `String({toString:1})` and `Number(Symbol())` are both a `TypeError`. There are ~45 such coercions across codegen, the CPU evaluator, the export paths and the node components.
- **The consequence is not a degraded node, it is a dead app.** There is no error boundary anywhere in this app (`grep componentDidCatch|getDerivedStateFromError` returns nothing), so a throw from `graphToCode` — which the sync engine runs inside a render — unmounts the root and the screen goes blank. The graph is already in the store by then, and the 300 ms autosave is a `useAppStore.subscribe` OUTSIDE React, so it writes the poisoned graph back to `fs:graph` and the app blanks again on **every reload**, until localStorage is cleared by hand. Four characters of JSON in a shared shader (`{"speed":{"toString":1}}`) are enough.
- **MEASURED 2026-09-19: 38 fatal single-key graphs across 17 node types.** The sweep seeds `fs:graph` through Playwright's `addInitScript`, one poisoned key per page, and reads `e.stack` filtered to `/src/` in `page.on('pageerror')` — which is also what separates a newly introduced site from a pre-existing one.
- **Guarding the call sites one at a time DID NOT CONVERGE** — every node family has its own reads (`numVal` in the image branch, `numericParam` beside it and in the march and dataviz branches, the property/colour emitters, `colormaps`, `soundSettings`…). Three rounds of patching took it from 38 to 20 to 3. So it is closed where every reader already comes through: **`rawNodeValues` drops uncoercible entries**, returning the map **BY IDENTITY** when there are none — which is every real graph, so no allocation and no memo invalidation (the identity contract that accessor already documents).
- **`utils/valueCoerce.ts` is the guard for readers that take a `values` map as a PARAMETER** (`decodeImageNode`, `imageAssetFor`, `readImageTextureSpec`, …), which the accessor cannot reach. `valueStr`/`valueNum` are **drop-ins**: they differ from `String()`/`Number()` only where those would throw. `plainStr` is the strict one — strings and numbers only — for the Image node's per-render re-measure key, where a million-element array would coerce WITHOUT throwing and build a multi-megabyte string twice a frame.
- **Both are permissive on purpose, and this is the trap.** Anything that coerces without throwing is kept EXACTLY as it was, booleans and arrays included, because those coercions are load-bearing and pinned: the Image node's `repeat` reads `false`, `null` and `''` as CLAMP — i.e. the `Number()` zero — against a `historicalReads` reference in `imageTextureSpec.test.ts`. The first cut of `valueNum` returned NaN for `null`/`''` and silently flipped every such node from clamp to repeat. A guard that turns junk into a legal value is a guard that hides the junk; a guard that turns a legal value into junk is a regression.
- **Three sites bypass the accessor and need their own guard**: `utils/colormaps.ts` (`String(id)`, `String(def.stops)`), `utils/soundSettings.ts`, and `nodes/SoundNode.tsx` — a bespoke component that reads `data.values` raw rather than through `getNodeValues`. A new component that does the same must guard too.
- **The whole `values` FIELD can be a primitive, and `in` THROWS on one.** `outputNodeValues(data)` (`types/node.types.ts`, pinned by `types/outputNodeValues.test.ts`) is the Output's shape-guarded read: `getNodeValues` hard-returns `{}` for an Output, and no restore path coerces the field — `sanitizeOutputMaterialsReport` cleans MATERIALS entries only, and `unfoldOutputMaterials`' material-0 branch is a shallow spread. A tampered `values: 5` reached ShaderSettingsMenu's `'opacity' in values` and the node's own `channel in current` inside a React event handler, which showed as a checkbox and a clear-swatch that silently did nothing. The same class as `sanitizeDataRangeNodes` and `sanitizeOriginKeys` (the Data Range formula bullet of node-types.md holds the `loadGraph` half).
- `types/nodeValuesAdversarial.test.ts` pins both halves (nothing uncoercible reaches a caller; everything else is returned by identity, value for value), and `utils/valueCoerce.test.ts` pins that the drop-ins agree with `String`/`Number` on every input that does not throw.

### A node's ID, TYPE and data-borne SOCKET LISTS are adversarial too

- **The shape gate (`utils/graphShape.ts`) refuses what blanked the app from a RESTORED node rather than from its values** (2026-10-11). Each was measured in Chrome blanking the app for good through `fs:graph`, because the autosave keeps the graph and there is no error boundary. (1) **Ids**: a node id, an edge endpoint or a string handle holding `"`, `\`, CR, LF, FF or NUL (`isSelectorSafeId`). React Flow builds UNESCAPED attribute selectors from them — `useUpdateNodeInternals` on every node's mount (`.react-flow__node[data-id="${id}"]`), `isValidHandle` during a connection drag — and inside a double-quoted CSS string `"`/CR/LF/FF THROW a SyntaxError; from a mount effect that unmounted the whole app, both through `fs:graph` and through a shared project opened with Open. A `"` is also how an id smuggles in a selector LIST. Backslash and NUL silently MISS (React Flow never re-measures that node's handles; NUL misses even through `CSS.escape`, which turns it into U+FFFD, so `nodeEl` cannot find it either). U+2028/U+2029 match like any other character and are allowed. No id or handle the app mints holds one. (2) **A node or edge `type` naming an `Object.prototype` member** (`isUsableFlowType`): React Flow falls back from our map to its OWN builtin map, a plain object, so `constructor`, `valueOf` or `__proto__` resolves to a non-component and rendering it throws. (3) **Socket lists carried in node DATA** (`hasUsableDataSockets`): a Data node's `dynamicOutputs` and a collapsed group's `collapsedInputs`/`collapsedOutputs` must be arrays of records with selector-safe string ids and text display fields; `5`, `"abc"` or `[null]` threw from TypedEdge's selector (`portShapeForHandle`) or GroupNode's render. (4) **`data.label` must be text**, because React Flow's fallback node renders it as a child. None is repairable without guessing what was meant, so restores DROP the node and its wires (`loadGraph` counts them in its console warning; a saved group loses only the bad node and its bad-handle edges), and `extractProjectState` REJECTS the block, so the file opens as a plain script. Our own selectors still go through `nodeEl`/`handleEl`. Drift-guarded in `graphShape.test.ts`: every registered flow type, every built-in preset and texture graph, and a group the store itself collapses pass the gate. `glbRepackHostile.test.ts` now asserts that an import refuses a block carrying a `"` id (the repack still carries it byte-exactly).
- **A restored node POSITION is only required to be FINITE** (`hasUsablePosition`), never bounded, while waypoints and drawings clamp to ±1e6. Anything whose work scales with a wire's or a node's distance must therefore cap its own output. `arrowMarks`' `ARROW_MAX` (63 chevrons per wire, node-visuals-and-designer.md) is the first such cap: uncapped, a node at x = 1e12 asked one render for about 8e9 chevrons, a hang that the autosave brought back on every reload, and 64 waypoints inside the sanitized box already gave 1.39M marks. Capped, the same graph renders in 31 ms with 63 chevrons (review 2026-10-11).
