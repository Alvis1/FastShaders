### Sync engine

- **Sync engine**: `syncSource` field in zustand (`'graph'` | `'code'`) prevents infinite sync loops. `useSyncEngine` hook manages bidirectional sync with `lastSyncedCodeRef` to skip no-op updates

### Node values

- **Node values**: always use `getNodeValues(node)` from `@/types` — never cast `node.data as ...`

### Edge IDs

- **Edge IDs**: always use `generateEdgeId(source, sourceHandle, target, targetHandle)` from `@/utils/idGenerator`

### Single ShaderNode

- **Single ShaderNode**: one component handles all TSL node types dynamically via registry

### rAF ref pattern

- **rAF ref pattern**: PreviewNode/MathPreviewNode/EdgeInfoCard overwrite refs for animation — this is correct (avoids stale closures)

### Canvases inside the React Flow viewport MUST be CPU-backed

- **Canvases inside the React Flow viewport MUST be CPU-backed**: the `getContext('2d', { willReadFrequently: true })` in PreviewNode is deliberate — an ACCELERATED canvas becomes its own compositing layer in Safari, WebKit's overlap compositing then promotes the surrounding nodes into layers rasterized at 1×, and the whole zoomed canvas goes blurry (empirically bisected 2026-07-11 via the `?fsdbg=nocanvas` switch in `main.tsx`, which stays available for renderer triage). Never add a plain-context or WebGL canvas to anything rendered inside `.react-flow__viewport` — and prefer SVG outright for VECTOR content: the sin/cos waveform is `nodes/WaveformSvg.tsx` and the Time node's face is `nodes/ClockFaceSvg.tsx` (each the ONE renderer behind its live node AND its asset-card tile; `utils/waveform.ts` / `utils/clockFace.ts` are the pure tested models), because a fixed-resolution canvas bitmap blurs under the viewport zoom no matter how it's backed, while the per-frame work drops from a full repaint to one or two transform writes. Only raster content (the noise previews) still earns a canvas — PreviewNode is the last one in the viewport.

### Animated editor surfaces read ONE clock

- **Animated editor surfaces read ONE clock** (`utils/appClock.ts` — `appTime(rafTimestamp)`): the rAF loops in MathPreviewNode, PreviewNode and EdgeInfoCard used to mint a private epoch at first frame, so `t` meant "seconds since THIS loop started" — a sin card showed sin(48.3) while the freshly-hovered edge chip evaluated the same wire at t≈0.15, and no two surfaces could agree except by coincidence. All loops now derive t from the shared module epoch; rAF callbacks within one frame share a timestamp, so every surface evaluates the identical t and cpuEvaluator's per-time cache buckets coalesce (one per frame, not one per surface). **On-node connected-input labels tick too**: `edgeValueLabel` returns an `animated` flag (time-driven on the UNWRAPPED graph, and not a noise source — a ticking probe of a noise field would still be one arbitrary sample, so noise keeps its range) and all four label surfaces (ShaderNode rows, Output channel cells, Mic params, the Time node's wired speed) render through `nodes/LiveEdgeValue.tsx`, which overwrites textContent from a rAF on the shared clock — imperative writes, NOT per-frame React re-renders, with `utils/edgeValueText.ts` as the shared pure formatter so the ticking path can't format differently from the resting one. The `animated` bit must ride each surface's cheap string key (wiring Time into an existing upstream chain can leave text/live unchanged — sin(0) is 0 either way — and a stale flag keeps the label frozen). Two deliberate exceptions: the ClockNode HAND integrates `dt × speed` instead of reading appTime (wall-clock × speed lands on an unrelated `% 60` residue every speed-scrub pointermove — the hand would teleport; it shows RATE, not absolute time, and after a speed change its angle intentionally diverges from the shader's `time.mul(speed)`), and the 3D preview stays on three's own clock (sandboxed iframe, rebuilt on edit). Never reintroduce a per-loop `startTime = timestamp` epoch.

### An import auto-frames the canvas

- **An import auto-frames the canvas**: importing a shader replaces the nodes but NOT the viewport, so a project whose nodes sit anywhere but where the user is looking lands off-screen and reads as a failed import (an empty canvas). Every import surface funnels through `projectImport.ts`, which dispatches **`fs:graph-imported`** whenever the graph is actually replaced — deliberately NOT `fs:project-imported`, which also fires for a model-only zip where the graph never changed and re-framing would throw away the user's viewport. NodeEditor **ARMS** a fit on that event rather than fitting on it: a project block writes its nodes in the same tick the event fires (React hasn't rendered them), and a bare script has NO graph at all until `useSyncEngine`'s code→graph pass finishes a commit or two later — so the fit runs from the `[nodes]` effect, on the next graph the editor actually renders, behind the same double-rAF measurement guard `startNewShader` uses (`fitView` frames the MEASURED box; unmeasured nodes fit as zero-size points at maxZoom). Two details are load-bearing: the pending rAF is held in a REF torn down only on unmount, never by the effect's own cleanup — the cost pass writes the Output node's new total straight back into `nodes`, so an imported graph re-renders inside the two-frame window and a cleanup-owned rAF would be cancelled by exactly the change proving the import landed — and the arm carries a `IMPORT_FIT_TIMEOUT_MS` disarm, so an import that never yields a graph (parse errors, a byte-identical re-import that the sync engine skips) can't leave a fit primed to hijack a later unrelated edit. Desktop Work-folder loads get the FRAMING for free — same `importShaderText`/`importShaderZip` — but they do two things on top of the shared path (adopt the file's name, track it as the Save target), so "for free" is a claim about the fit only.

### A dropped shader ASKS: Open or Add

- **A dropped shader ASKS, and the second answer is what makes the question worth asking** (`Modals/ShaderImportModal.tsx`, raised through the store queue `pendingShaderImports` by the ONE gate `utils/shaderDropRequest.ts`; the two answers live in `engine/projectImport.ts` as `openDroppedShader` / `addDroppedShader`, the additive plan in `engine/shaderGroupImport.ts`, the names in `utils/shaderDropName.ts`). Until 2026-09-19 dropping a `.js`/`.mjs`/`.tsl`/`.zip` on the canvas, the 3D preview or the code panel REPLACED the whole project with no warning — the most destructive thing a drag can do in this app, reachable by accident, recoverable only by noticing in time. A bare confirm would have been a speed bump; **ADD** is the feature: the dropped shader's chain is parked beside the graph already on the canvas, in one group frame named after the file, so "open someone else's shader next to mine and take a piece of it" stops being a two-window clipboard exercise. Nine rules. (1) **The gate is one function and it is skipped in a study session** — `isEvalMode()` returns false from `requestShaderImport`, so `/eval`, `/evalpro` and `/evalp` keep today's drop byte for byte (the GLB dialog's rule, and it also keeps `fs:graph-imported` firing where the telemetry chokepoints expect it). The three surfaces each RETURN when the gate took the file; falling through would run the old import as well and overwrite the answer the user gave. (2) **"Load Script…" and the desktop Work folder do NOT ask** — they are already explicit instructions to open a file. Only a DROP asks, which is why `importScriptFile` in the code panel takes a `fromDrop` flag rather than the two callers sharing one behaviour. (3) **The forwarded-shader `window.confirm` stays on the surface**, ahead of the gate: sandboxed shader code can forge `fs:preview-drop`, and a dialog it forged is one the user might answer. (4) **OPEN is today's import plus the NAME.** The authored name inside the file still wins; the file's STEM is the fallback, and that is new — a bare shaderloader script, and a project block shipping no name, used to leave the PREVIOUS shader's name on a graph that has nothing to do with it, which is the name the next export would then have been written under. `nameFallback` is threaded through `importShaderZip` → `importShaderText` → `applyProjectToStore` and defaults to absent, so every other caller is byte-identical. The Work folder answers the same question the OTHER way on purpose (`adoptShaderName` lets the name on DISK win, because there the file is the document's identity and Save must find its way back to it). (5) **ADD drops every sink.** Plain Outputs and Raymarch Outputs alike (`isSinkNode`) leave with the edges that fed them — that is what "not attached to output" means, and it is not tidiness: among untargeted plain Outputs exactly one contributes and a DRIVING Raymarch Output suppresses every plain one, so an arriving sink can silently take over the render of the shader it was added to. Because no Output arrives, the unfold/active-sink repairs `instantiateSavedGroup` must re-run over the COMBINED list have nothing to do, and the planner never reads or rewrites a live node. A file that is nothing but an Output is REFUSED (`nothing-to-add`) rather than dropping an empty frame. (6) **Every id is re-minted.** A `.fastshader` carries the ids it was saved with and the live graph usually holds the very same ones — it is typically an export of a shader this one descends from. (7) **A singleton is redirected, not duplicated**: a Sound node already on the canvas keeps its place and the arriving copy's wires are re-pointed onto it (`SINGLETON_NODE_TYPES`, the same "glide to the node that is already there" rule both add surfaces follow); a fold that would leave a self-edge drops it. (8) **NESTING survives** — groups and notes the dropped file carried keep their `parentId` links, only ROOT-level nodes become members of the new frame, and the result is emitted parents-first because React Flow requires a parent before its children. A child whose parent was a dropped sink, or whose `parentId` names nothing in the file, is re-rooted into the frame; a parent CYCLE in a hand-edited file does not hang the walk. (9) **ADD announces `fs:graph-merged`, never `fs:graph-imported`** — the document did not change, so the desktop Work folder must not forget the open file and turn the next Save into a Save-as, and the study telemetry must not log an import. It is ONE undo entry, the image budget is counted against the LIVE graph plus the arrivals and checked BEFORE `pushHistory` (so a refusal leaves none), the preview mesh is untouched (an Add is not a new document, so a zip's `models/` entry is not installed), and the arriving nodes go through the same sanitizers every other ingestion path runs. The frame parks clear to the RIGHT of everything on the canvas rather than at the pointer — two of the three surfaces have no canvas coordinates to offer, and `fs:graph-merged` frames the result anyway. The dialog itself is the model-drop dialog's shape (file name, one warning line only when there is work to lose, two EQUAL plates, red text Cancel), remembers nothing, and focuses ADD so Enter is the answer that cannot throw work away. Verified in Chrome 2026-09-19: the dialog, Add (6 → 16 nodes, one Output, the import note), Open (the graph replaced and the name adopted), Cancel, Escape, the code-panel drop, and the picker NOT asking.

### History

- **History**: circular buffer (50 entries) with undo/redo via `structuredClone`, Cmd+Z/Cmd+Shift+Z shortcuts, plus visible Undo/Redo buttons in the canvas's bottom-LEFT bar (`.fs-canvas-bar` — one pill also holding the Draw tools and the zoom −/+ / fit / canvas-bg controls that replaced the React Flow Controls stack; the buttons call `undo()`/`redo()` directly — equivalent to the keyboard path, since the graph→code effect re-runs on any nodes/edges identity change regardless). **Continuous gestures must be bracketed**: `beginInteraction()`/`endInteraction()` snapshot ONCE up front and suppress `pushHistory` until the gesture ends, so a DragNumberInput scrub is one undo entry instead of one per pointermove frame — and, just as importantly, the whole graph isn't `structuredClone`d 60×/s (megabytes once images are embedded). `beginInteraction` deliberately ignores `isUndoRedo` (that flag guards the sync engine's post-undo reconciliation; a pointer gesture is always a real mutation, and honouring a stale flag would silently swallow the gesture's history). DragNumberInput brackets on first move — not pointerdown, since a press that becomes a click-to-edit would push a no-op entry — and closes the bracket on pointerup, pointercancel, and unmount.

### `setCode(code, 'code')` — the user typing in the TSL panel — writes `code` ONLY; `previewCode` advances on a g…

- **`setCode(code, 'code')` — the user typing in the TSL panel — writes `code` ONLY; `previewCode` advances on a graph→code sync or on Apply (`requestCodeSync`).** ShaderPreview subscribes to `previewCode`, so half-typed TSL never swaps `srcDoc`: without the split every keystroke would re-fetch and re-parse the ~1 MB A-Frame bundle under a fresh opaque origin — the same cost the 200 ms rebuild debounce exists to collapse. It is also the reason the preview looks frozen while you edit code until Apply; collapsing `setCode`'s two branches into one write is the accidental way to lose it.

### Deleting a node SPLICES the chain, it does not cut it

- **Deleting a node SPLICES the chain, it does not cut it** (`utils/edgeUtils.ts` → `bridgeEdgesAcrossDeletedNodes`): each outgoing edge of a deleted node re-parents onto the live source reached by walking its first incoming edge upstream, crossing whole runs of deleted nodes — `X → A → B → C` with A+B selected becomes `X → C`. Single-input-per-port is preserved (first bridge to a `(target, targetHandle)` wins, later ones drop), an edge whose TARGET is deleted is dropped, and a chain that dead-ends upstream is dropped. React Flow's own delete is disabled (`deleteKeyCode={null}`) precisely so that every user-facing deletion path goes through that ONE helper — NodeEditor's keydown handler, `store.removeNode`, and the group-delete run. A fourth deletion path that skips it silently redefines what Delete means: the graph disconnects, the generated code changes, and nothing errors.

### A node component that mounts or unmounts handles at runtime MUST call `useUpdateNodeInternals(id)` in an effec…

- **A node component that mounts or unmounts handles at runtime MUST call `useUpdateNodeInternals(id)` in an effect keyed on the handle SET** — `exposedPorts.join('|')`, the collapsed group's boundary-socket ids, the grown-operand count. React Flow never refreshes its handle-bounds map on its own, so an edge to a freshly mounted handle stays in the store and still emits correct code but simply never DRAWS, and existing edges snap to stale anchors when a socket count shifts. The symptom actively misleads: a page reload fixes it (every handle is measured on first mount), so it reads as a React Flow rendering glitch rather than a missing effect. All eight dynamic-handle components already do it — ShaderNode, OutputNode, RaymarchOutputNode, PreviewNode, GroupNode, SoundNode, ClockNode, ColorNode — so a NINTH node type is the only way to reintroduce the bug.
