## Testing

- Framework: **vitest** (configured in `vite.config.ts` so `@/*` alias + TS setup are inherited from the build config). Test files match `src/**/*.test.ts`; environment is `node` (no jsdom — tests target pure logic only).
- **The suite runs with `isolate: false`** (vite.config.ts), so every file in a worker SHARES that worker's module registry and globals. That halves the wall clock — a per-file worker re-imports the heavy engine graph (store → builtin textures/presets → codeToGraph → Babel) at ~350 ms a file — and it is what the costTable import-cycle flake below was really about. The contract a new test must honour is therefore NOT "no global mocking" (vite.config.ts's comment still says that, and it was never true of the whole suite): **every file that calls `vi.stubGlobal` (`grep -rl 'vi.stubGlobal(' src`) must restore it** (`src/stubGlobalRestore.test.ts` fails on one that does not) — `vi.unstubAllGlobals()` in an `afterEach`/`afterAll`, since a leaked stub lands on whatever file the worker runs next, and `unstubGlobals: true` in the vitest config would make that enforceable rather than aspirational. The second shared thing is the module registry: `registry/editorVisibility.test.ts` is the ONE file that calls `vi.doMock`/`vi.resetModules` (it has to — the shipped visibility JSON is EMPTY again since the Image node was unhidden on 2026-09-18, so every direct assertion would be vacuous), and a `resetModules` clears the registry the setting exists to share. Keep store-mutating suites self-resetting in `beforeEach`. The third shared thing is the store's HISTORY FLAGS: `pushHistory` silently does nothing while `isUndoRedo` or `coalescingHistory` is up, the app's sync engine is what clears `isUndoRedo` after an undo (tests have none), and a gesture test can leave a bracket open — so a suite that undoes hands a silenced history to whichever file the worker runs next, and that file's "one undo entry" assertion fails at random (measured 2026-09-24 in `glbImportCommit.test.ts`: 1 run in ~6). Every suite that touches the undo history therefore spreads **`HISTORY_IDLE`** from `src/test-utils.ts` into its reset; `src/historyIdleReset.test.ts` fails on one that does not (a text check — it catches the forgotten reset, not every way around it) and pins that the object really does un-silence `pushHistory`.
- Shared test factories live in `src/test-utils.ts` (`makeNode`, `makeEdge`). Always import these instead of redefining stub builders in each test file — the helpers cast through `unknown as AppNode/AppEdge` to skip React Flow's full Node generic constraints. It also holds the KTX2 harness: `installInProcessWorker()` runs three's blob Workers (KTX2Loader, DRACOLoader) in `node:vm` — it stubs `Worker`, so its caller must `vi.unstubAllGlobals()`, and `stubGlobalRestore.test.ts` holds callers to that — plus `fakeRenderer()` (r184's `hasFeature` throws until `init()` resolves) and `makeKtx2Glb()`. It holds the ONE glTF/GLB fixture set, too (Phase 5): `makeGlb(doc | { jsonText }, bin?)` (the research doc's section 11 recipe: JSON padded 0x20, BIN padded 0x00; `{ jsonText }` goes in verbatim for fuzzing), `TRIANGLE_POSITIONS` + `gltfPrimitiveDoc(extra)` (asset, buffer 0, view 0, accessor 0; `extra` keys REPLACE the base's), the header-only image fixtures `pngHeaderBytes`/`jpegHeaderBytes` (an `app1Bytes` run can push the SOF past a scan window)/`webpHeaderBytes` (`VP8 `/`VP8L`/`VP8X`)/`ktx2HeaderBytes`, and `makeRealPng(w, h, rgba)`, a real decodable PNG (zlib `deflateSync` + `crc32`). `makeKtx2Glb` and `gltfTestFixtures.packGlb` build their containers through `makeGlb`, so the tree has one GLB layout; `glbFixtures.test.ts` proves every builder writes what it claims. Use these rather than a local `glb()` helper (the two in previewMesh.test.ts and projectImportZipLimits.test.ts predate them). Three r184's KTX2 test textures are committed under `src/engine/fixtures/ktx2/` (MIT, never edit) beside two GLBs from `scripts/gen-ktx2-fixture-glbs.mjs`; `ktx2Transcode.test.ts` runs the real basis transcoder over them, not a stub.
- **Every shaderloader suite gets its loader from `src/shaderloaderHarness.ts`** (a non-test module, imported only by tests). `ACTIVE_LOADERS` is `['0.6', '0.8']`: 0.6 is read from the SUBMODULE (the frozen file exports fetch; `loaderAvailable` skips it on a non-recursive checkout), 0.8 from its served `public/js` copy (vendorSync pins it to the submodule). The weld, per-mesh dispatch, schema, mesh-edge and transform suites run the SAME assertions against both, through `evalLoader` (the vm sandbox 0.6's suites always built, plus options for `AFRAME.components` / `AFRAME.THREE` stubs; by default the AFRAME stub carries a FRESH inert `gltf-model` from `inertGltfModelEntry`, because 0.8 warns when it cannot hook one and its agent-wide `Symbol.for` flag would leave a stub shared between sandboxes hookable only once) and `transformsOf` (0.6's top-level functions, or 0.8's `FastShaders.transforms`). `PINS` holds the few source anchors that necessarily moved between 0.6's object-literal component and 0.8's core functions (the dispatch slice, syncWeld→unbary, weld-before-bary); every other pinned literal is spelled identically in both files by construction, so do not add a row for one — make the 0.8 spelling match instead. Never read a loader at a suite's module top level: a copy that stops being vendored makes that read THROW, not skip. `shaderloader08Core.test.ts` covers what only 0.8 has — the core without A-Frame, against real three/webgpu inside vm, including the first end-to-end run of the component through the injectable `FastShaders.fetch`/`.importSource` (the default Blob-URL import cannot run in vm and is only source-pinned; it needs a browser).
