### One node, one look — the CANVAS is the reference.

- **One node, one look — the CANVAS is the reference.** A node is drawn on four surfaces: the graph canvas (`nodes/*`, the live implementation and the thing every other surface must match), the asset-browser tiles (`NodePreviewCard`), the node-editor.html overview (the same cards, plus a `GraphModal` that renders the REAL canvas components), and the Node Designer's stage (`NodeVisual` via `nodeDesigner/bridge`). Only the `shader` flow type gets there through the shared `NodeVisual` replica; `color`/`preview`/`mathPreview`/`clock`/`mic`/`output`/`raymarchOutput` each need a hand-written card, and **every hand-written card is a drift site**. The rules that keep them honest: (1) **a node's styling must never depend on which page draws it** — the `.react-flow .drag-num` opaque number plate was the live instance (identical widget, crisp on the canvas and washed-out on every tile; the designer only escaped by hand-mirroring the rule in `node-designer.html`), so the on-node look now sits on `.drag-num--compact` itself, which IS the on-node variant. Same shape as the `.mic-node`-scoped arm light. `.react-flow .node-base__cost-badge` is the one DELIBERATE exception (documented in NodeBase.css: the asset bar is outside the canvas and keeps the cost-gradient colour). (2) **Shared geometry/drawing beats a copied replica**: `soundGeometry.ts` (mic box + socket rows), `utils/clockFace.ts` (the Time face — the card used to hold a second copy that seeded its hand from `Date.now()`, so the tile pointed somewhere a freshly dropped node never does; it draws phase 0 now), `COLOR_NODE_SIZE` + `LABEL_MAX/MIN_PX` (the colour swatch, which had an 84/2/15px twin of the canvas's 56/1.5/10px, reverse-engineered against the strip's `zoom: 0.67` — the card now renders the REAL `.color-node` classes counter-scaled by `CARD_COLOR_SCALE`, which also got it the long-name wrap/clip/fit-text rules its twin silently lacked). (3) **A `<div>` replica cannot match `:disabled`** — the inert mic light needs the explicit `--inert` class or a tile shows enabled-green beside a grey unwired canvas node. (4) **Fake handles read the real tokens** (`--handle-size`/`--handle-border`): hardcoded 10px went wrong on touch, where tokens.css bumps the real socket to 12px. (5) **Every flow type needs a dispatch branch** — `output` had none and fell through to the generic shader card, which turned a 7-input def into seven editable number boxes; the overview showed that beside a `GraphModal` rendering the real Output node. Deleting a replica is the best fix available: the slider tile's hand-built track/thumb/labels are gone, and it renders the same `<input type="range">` the canvas and designer do. (6) **A node title is capped at TWO rows, it wraps at ONE balanced seam, and the node stays at its designed width.** Three rules do that together (2026-09-03, owner request with a mock: "wrap names to max 2 lines if necessary, making the nodes slimmer"). `.node-base__title` is `overflow-wrap: normal` (never split a word) plus a 2-line clamp; the authored designer width is applied as the PREFERRED width with `min-width: min-content` as the floor on EVERY surface (ShaderNode and NodeVisual alike — the cards' old floor-only branch and NodeVisual's `exactWidth` prop are gone); and `nodes/NodeTitle.tsx` is the ONE renderer of `.node-base__title`, giving the name exactly one break opportunity at the most balanced seam `titleSplit.ts` finds — a space, the character after `_`/`-`, or a camelCase boundary (Unicode-aware) — with every other space made non-breaking. The canvas header is the GENERATED VAR NAME, a single unbreakable run, so before this `cameraPosition1` forced a 47px design out to ~95px to sit on one line (and with break-word it had shattered into `camera`/`Position`/`1`); now it wraps as "camera / Position1" and the floor is the longer half. MEASURED: cameraPosition1 49px/2 rows, positionWorldDirection1 73px/2 rows ("positionWorld / Direction1"), mul1 47px/1 row; tiles agree (Camera Position 47px/2 rows, Cross Product 48px/2, Greater Than 45px/2). Digits stay on the fragment before them, so a lone `1` can never be a row. Every header keeps its `title` so a clamped name stays readable on hover; `titleSplit.test.ts` pins the seam rule and greps that no node component renders the title span by hand. TRAP: the pure module is `titleSplit.ts`, not `nodeTitle.ts` — on this case-insensitive filesystem a file differing from `NodeTitle.tsx` only by case fails `tsc` AND makes Vite resolve the extensionless `./NodeTitle` import to the `.ts` file, a 404 on every importer's cached transform after the rename until each importer is touched. (7) **The asset-card layer may SCALE a node, never RESTYLE one** — and this is the rule the hand-written cards actually broke. `NodePreviewCard.css` used to carry `.node-preview-card .node-base:not(--exact) { min-width: 100px }` plus header/badge/row overrides, to draw those cards "larger"; once `FitNodeHeading` normalized heading size that was pure distortion, and on a FIXED-geometry node it was a lie: the Sound node is exactly `MIC_W` wide (80px then, 88 since it grew the source picker), so a 100px card frame left its 77px body 20px short of the right edge — all four output sockets floated INSIDE the frame and the arm light sat off centre, beside a canvas node whose sockets are on the border (Time and Sine were widened past their own content the same way). Two mechanisms replace it. Each card passes the LIVE node's class to `CardShell` (`nodeClassName="clock-node"` …) so the node's own stylesheet reaches the card, and it renders the node's REAL structural classes (`.preview-node__canvas`, `.math-preview-node__port-row`, `.clock-node__canvas-wrap`) instead of the retired `__canvas--clock/--math/--noise` twins. And every card socket is `CardSocket` — NodeVisual's `StaticHandle` element, i.e. the live handle classes placed in the live wrapper — so `.clock-node__canvas-wrap > .react-flow__handle` centres the tile's socket on the clock FACE exactly as it does on the canvas; the old `--right-abs`/`--left-abs` twins hardcoded `top: 50%` of the whole card, which is why the Time tile's socket sat half a header-height below the node's. `assetCardGeometry.test.ts` pins all of it from source (no browser needed): no geometry declaration in the card stylesheet may reach a node-internal class, no `<CardShell>` may omit `nodeClassName`, the card-local handle classes may not come back, and every non-`shader` flow type must still have a dispatch branch. Measured after the fix (Chrome, card vs canvas node, frame-normalized): mic/Time/Perlin/Sine/Color all agree on aspect ratio and socket placement to within a rounding pixel. (8) **A surface may scale a card only from a WRAPPER around it** — node-editor.html's overview draws these same tiles at roughly canvas size with `zoom: var(--gp-preview-zoom)` on `.gp__preview`, which MULTIPLIES `.node-preview-card`'s own `zoom: 0.67` (1.5 × 0.67 ≈ 1) instead of replacing it. Overriding that 0.67 is what breaks, and it breaks one tile only: `CARD_COLOR_SCALE` is a RATIO against the card's zoom, not an absolute swatch size, so it rides an ancestor factor exactly like every other tile and is stranded compensating for a zoom that no longer applies — the Color / Property Color tiles end up the one pair in the set at the wrong size, with nothing in CSS to say why (re-deriving the constant per surface makes it worse: it would pin the swatch at 56px while its neighbours grew). `assetCardGeometry.test.ts` fails on a `zoom` declaration aimed at `.node-preview-card`/`.saved-group-card` from `GraphsPage.css`, and its node-internal geometry sweep now runs over that stylesheet too — SCALING a card is allowed from anywhere, reaching INTO one is the same defect wherever it is written.

### Surface parity is MEASURED, not assumed

- **Surface parity is MEASURED, not assumed** (`nodes/nodeVisualParity.test.ts`; the sweep script drops every designable type on node-editor.html and selects it on node-designer.html, then diffs sockets, widgets, rows, sizes and glyph markup — 2026-09-03, owner: "in node-designer some nodes look different than in the node overview, for example Data Stripes"). 15 of 67 designable types differed, in four classes, each a way a replica came to depend on the page drawing it. (1) **The opt-in ramp filter was applied by the CARD, not by the replica** — the designer's bridge passed the raw definition, so Data Stripes / Data Viz showed `lowColor`/`highColor` there as NUMBER rows. `effectiveRampDef(def, [])` now runs INSIDE NodeVisual (a replica is a fresh node: nothing exposed) and NodePreviewCard's copy is gone. (2) **The CANVAS was wrong too, worse**: ShaderNode's rows layout filtered through `effDef` but its operator branch (`effectiveInputs(def…)`, `opSocketCount`) and the rows layout's DETACHED-socket loop (`def.inputs.map` for designer-moved sockets — Data Stripes' designer moved every socket, so this is the loop that drew it) read the raw `def`, so a freshly dropped Data Stripes carried all three input sockets with the two colours drawn as number boxes (NaN for a hex). Both read `effDef` now, and a COLOUR operand in either place gets the swatch the colour row gets (the interactive picker only on the designer stage, the inert span elsewhere — `colorPickerHistory.test.ts` pins three sites per file). Measured after: fresh canvas = card = designer at `signal` only; ticking Low Color in the settings menu mounts the socket with a real #1b2a4a swatch and no extra number box. (3) **The card inherited the PAGE's font size** — canvas 14px (app body), overview card 10px, designer 13px (its own body rule) — and the number widgets, sized from their container, came out 30px on a card and 32px on the stage for the same node; `.node-base` now sets `font-size: var(--font-size-md)` itself. (4) **The Slider's range input kept its UA 2px margin** on the designer page (no reset.css there), 4px bigger than the canvas; `.shader-node__slider` zeroes it. Also aligned: the designer previewed an input with no registry default as `0.1` where the canvas and card show `0` (2px wider Vec nodes) — `previewFor` seeds `0` now. What legitimately still differs: the designer wraps BUILT-IN art (nodes with no saved svg — sqrt, exp, log2, round, fract, clamp, greaterThan, lessThan, equal) in one extra empty `<g>`, which paints identically; and the canvas header is the var name (one row) where cards and the designer show the label (`Data Stripes`, two rows), so a card can be a header-row taller than its canvas node by design. PROBE TRAPS worth keeping: `getBoundingClientRect` on a card is scaled by the strip's `zoom` and FitNodeHeading's transform — compare `offsetWidth`/`offsetHeight`; and the overview keys rows by `.gp__type`, the designer's `#nodeSel` options by value.

### Renaming a node in the Node Designer

- **Renaming a node in the Node Designer** (the inspector's **Name** / **Name (LV)** fields): a node's DISPLAY LABEL is editable; its `type` is not, and the Type row carries a `locked` chip saying why — `type` is the registry key, the `registryType` stored in every saved `.fastshader`, and what `codeToGraph` matches on, so renaming it would orphan every existing graph. The label is safe precisely because it is display-only: no engine module reads `def.label` (pinned by `nodeLabelRename.test.ts`, which greps the ten engine files), it reaches no generated code and no persisted payload, and the Latvian overlay is keyed by TYPE so an English rename can't orphan a translation. **Names are registry SOURCE, so they do NOT ride `customGlyphs.ts`** — English lives in `nodeRegistry.ts`'s `label`, Latvian in `node-i18n.json`'s `nodes` map, and they travel their own patch path: `locateRegistryLabels` (the `label` half of `descriptionSplice.ts`, sharing its two-form locator — property + the unary-math `[type, label, description]` tuple, label at index 1) plus `POST /__nd/labels`, which splices by BYTE RANGE so a rename is a one-line diff in a hand-formatted file. **Label and description slots are both keyed by node type and must never be merged into one `slots` array** — `spliceDescriptions` indexes them into a `Map`, so a merged list would collapse each pair and let a label patch rewrite a description's bytes (`nodeLabelRename.test.ts` asserts the ranges never overlap). Save tiers differ from the glyph file's: dev endpoint → linked folder (the same pure splice run in the browser behind a dynamic `import()`, so `@babel/parser` stays out of the designer's initial load) → **no download tier**, because a built page holds `nodeRegistry.ts` only as a compiled module and has no source text to splice; the fields disable themselves and say so. `assertValidNodeLabels` validates the map the registry would hold AFTER the patch, not the patch alone — uniqueness is a whole-file property (`nodeMatchRank` tiers an exact name hit above everything, so two nodes sharing a label make that tier ambiguous), compared case-insensitively because the ranker lowercases. Two known consequences, both narrow and both deliberate: a rename moves the node in SEARCH (label is the first entry in `nodeMatchRank`'s name tiers — the designer warns inline when the new name appears in another node's prose, mirroring `nodeSearch.test.ts`'s collision sweep, and those tests' hardcoded labels are pins meant to fail loudly on a rename); and it is NOT retroactive to `data.label`, the creation-time snapshot in already-saved graphs. That snapshot is invisible almost everywhere (canvas headers show the generated varName; every menu, tile and preview reads the live `def.label`) but it IS what `varName ?? data.label` falls back to, which is permanent for `split` (graphToCode never names it) and for cycle members, and it is re-frozen into `BoundarySocket.name` when a group collapses. Refreshing it on load is NOT a safe fix: `useSyncEngine` keys its pass-1 match on `registryType + data.label`, and for code-parsed nodes that string is deliberately the var name.

### What the Node Designer can and cannot edit

- **What the Node Designer can and cannot edit**: `ndData.designerNodes()` is `getAllDefinitions().filter(d => getFlowNodeType(d) === 'shader')` — the designer authors a `customGlyphs.ts` entry (glyph SVG, justify/scale/dx/dy, width/height, text scale, socket offsets) plus the node's display name (see the renaming bullet above), and previews it through `NodeVisual`, so a node is designable exactly when NodeVisual draws it. The **16 excluded types have no glyph to author and are not drawn by NodeVisual at all**: `output`, `raymarchOutput`, `time`, `soundNode`, `color`/`property_color`, the 8 noise nodes, `sin`/`cos` — each renders through its own component with its own hardcoded geometry (`soundGeometry.ts`, `CLOCK_SIZE`, `COLOR_NODE_SIZE`, the preview canvases). Opening one in the designer would show a stage with nothing the model can change. Making any of them designable is therefore not a filter tweak: it needs the node's geometry moved into the designer's model (and, for the mic, its absolutely-placed sockets expressed in `customGlyphs`' center-relative `sockets` vocabulary) — a real feature, not a gap. **The Image node IS designable since GLB Phase 4** (it joined `getAllDefinitions()` as a ShaderNode-rendered def): the stage draws its empty slot with its five channel sockets spread along the right border — the EDGE-PORT layout (`nodes/edgePorts.ts`, 2026-09-19), no rows and no port text — and the designer can author width, height, text scale and the `out` socket, never the thumbnail. An authored `out` offset still WINS: the rail reads `sockets[id] ?? edgePortOffset(i, n)`, both in px from the region centre, so the two vocabularies are the same one. It inherits the designer's existing multi-output gaps, shared with `split`/`toHsl`: the output-edge stub toggle draws a stub on EVERY out handle, R/G/B/Alpha are not authorable, and `ndData`'s input list names all six raw params although the replica draws none (the designer binds only rendered `data-port` elements).

### Node visuals

- **Node visuals**: per-node designer overrides live in `glyphs/customGlyphs.ts` — `{ svg, justify, scale (glyph-only; spacing fixed), dx/dy (glyph nudge), width (exact, ≥24), height (exact in both layouts, ≥28; shorter than content overflows; independent of glyph scale), text (0.4–2.5× header/value/label fonts via --node-text-scale), sockets (center-relative offsets, 4px snap; op layout natively, rows layout detaches the socket from its row — values follow) }`; frame radius/border are **fixed app-wide**. **The designer's CORNER DRAG rescales socket offsets proportionally with the height** (`nodeDesigner/socketScale.ts`, pure + tested; sign-symmetric snap, because `Math.round` is asymmetric on `.5` and would make the twelve shipped `±n` operator pairs lopsided on their first resize) so the ports travel with the frame instead of staying knotted around the body centre; the **W/H number fields deliberately do NOT** — that is the "taller frame, same sockets" escape hatch. RENDERER semantics are unchanged (plain px from the body centre), which is exactly what keeps all ~55 saved designs byte-identical until an author grabs that node's own corner — a renderer-side reinterpretation of the stored px was MEASURED to shift ~48 of them (Multiply's ±12 → ±14.9). Non-first outputs (`split` y/z/w, `toHsl` h/s/l, `dataviz` `value`, the Image node's Alpha/R/G/B) are not authorable and so do not scale — a known gap. Connected inputs show edge values (`min…max` ranges, bare `…` when underivable; geometry attributes have analytical ranges). Multi-channel data **arriving on a connected input** stacks the node into N cards (sibling layers behind the card, staggered negative z, single group shadow from the deepest layer). **A row the design has emptied is not rendered at all** (`visiblePortRows`, shared by ShaderNode and NodeVisual, pinned by `rowPorts.test.ts`): a socket override takes the socket, its label and its value OUT of the row, so a row whose input is moved draws an empty left half and one carrying the moved `out` draws an empty right half — and when both are empty the row is a bare 14px strip that, because `.shader-node__region` carries the authored height EXACTLY, has nowhere to go but past the card's own bottom border. MEASURED in Chromium: **26 ShaderNode-rendered types hung 5–39px of empty row outside their frame** (`cameraNear` worst), on the canvas AND on every asset tile and overview card. Nothing failed, because the row is transparent — it shows only as a ragged bottom edge, and worst on a multi-channel node where the offset stack layers give the spill something to sit against, which is how it was finally noticed. Filtering the rows rather than growing the region is what keeps the authored designs intact: the region's height is untouched, so the 25 affected types whose sockets are placed against its centre do not move a pixel. **Still open**: on 7 types (`cameraNear` 25px, `cameraFar` 23px, `screenUV` 11px, `abs`/`sqrt` 7px, `normalLocal` 6px, `tangentLocal` 4px) the GLYPH ART itself is taller than the authored height and still spills — that is authored DATA, not renderer logic, and correcting it moves those nodes' sockets, so it needs a design decision rather than a sweep. (2026-09-02: those numbers are the glyph's SVG ELEMENT box, which paints nothing — measured by ink, `getBBox()` mapped through `getScreenCTM()`, the vector art on all seven sits 5–23px INSIDE the card's bottom edge and well inside its sides, so nothing visible spills; what is oversized is the box the designer's model reasons about, which matters to the Node Designer's stage and to nothing the user sees.) Sockets are **static** — never set `transform` on handle `:hover` (React Flow positions handles via transform) — and never stack. **Every node PREVIEW surface renders through ONE component** — `nodes/NodeVisual.tsx` (asset cards, node-editor overview, the Node Designer's stage) — so a preview can no longer drift from the editor; ShaderNode stays the live implementation NodeVisual mirrors (change them together). **Movable node art**: for glyph-less art nodes (the Colormap ramp) the same `dx`/`dy`/`scale` fields transform the art element via `nodeArtStyle` (CSS px, purely visual — sockets/rows never move); the designer drags the ramp like a glyph. The Node Designer (`node-designer.html`, a Vite entry backed by `src/nodeDesigner/`) saves via the dev-server endpoint `/__nd` (any browser), the File System Access API (Chromium), or download; see `NODE_DESIGN_REQUIREMENTS.md`

### The glyph modal's point editor

- **The glyph modal's point editor** (marquee, multi-move, corner-grip scale, Delete, arrow nudge — `designerApp.ts`): **the selection is a set of INDICES into `glyphPoints()`**, because nothing else survives a frame — `renderGlyphPts()` destroys and rebuilds the whole handle layer on every pointermove and `collectGlyphPoints` mints fresh point defs each pass, so neither a DOM node nor an object identity can hold it. An index is meaningful exactly as long as the art's STRUCTURE is, which is what `ptsSig()` measures: it folds tag + delete-kind + anchor/control and deliberately NOT coordinates, so a gesture that only MOVES points keeps its selection while adding or removing a shape or a path segment drops it — and the renderer re-checks the sig every pass as the backstop for the invalidation sites an explicit `clearGlyphSel()` misses (a delete re-indexes every point it did not remove). The `PT_CAP` truncation therefore belongs to `glyphPoints()` and NOT to the renderer: a point past the cap gets no handle, so a selection able to reach it would be invisible, un-clickable and un-deletable. **`mApply` is the SOLE commit path** — every gesture writes only `#mPreview`'s DOM and `#mSvg`, and nothing in the modal calls `stash()` — so **Cancel is the session-level undo** (which is why closing a dirty modal confirms first: a whole session of moves, scales, nudges and deletes lives in that textarea and nowhere else). The 20-entry `glyphUndo` stack is a SEPARATE, coarser thing: whole `#mSvg` strings, one per gesture, one per HELD arrow run (keyed on `e.repeat` — auto-repeat fires ~30 keydowns/s and a snapshot each would evict the ⌘A+Delete entry the stack exists for), and one per whole-document replacement, which is why Clear / Built-in / Load / Upload / .svg-drop all route through `replaceGlyphSource` — assigning `.value` by hand fires no `input` event, so ⌘Z after a replacement restored the document from before it. Typing in the textarea clears BOTH the stack and the selection: those snapshots describe a document the user has since rewritten, and the textarea has the browser's own undo. **Hit order is the handle layer's contract** (SVG hit-testing is topmost-wins, i.e. last-appended wins): the full-canvas marquee backdrop is appended FIRST so everything after it still gets the pointerdown, the selection bbox and its corner grips next, and the point handles LAST — grips appended after the handles swallowed the pointerdown of any UNSELECTED point within ~15px of a padded bbox corner, and the only escape was clearing the very selection being extended. Traps a future gesture would re-introduce: (a) every mutating gesture gates on `el('mApply').disabled` FIRST, above the selection bookkeeping and the listeners — `refreshMPreview` injects the raw text whether or not it parses, so a gesture on the HTML parser's RECONSTRUCTION of half-typed markup writes that reconstruction back into `#mSvg`, which then parses, clears the red error and enables Apply, reading as the typo having been accepted; (b) the gestures focus `#mPrevBox` with `preventScroll: true`, since `.modal` is `max-height: 92vh` and a plain `focus()` scrolls the layer between the browser's hit test and the gesture's own `viewPtOf` read (measured: 139px of scroll = 27.8 of the canvas's 56 view units, so the first drag after focus was elsewhere teleported the point half the canvas — intermittent, because a repeat focus on an already-focused element does not re-scroll); (c) pointer capture goes on `#mPtsLay`, never on the pressed handle, which the next frame's re-render deletes; (d) every multi-point write runs TWO ASCENDING passes over a snapshot taken up front, never a read-back — relative path args rebase on the segments before them, and a setter can clamp against a sibling on its own element that the same gesture is moving (a rect's top-left reads the live bottom-right); (e) `pruneEmptyGroups` runs before the `innerHTML` commit, because 26 of the 34 shipped glyphs are wrapped in a `<g transform>` and an emptied wrapper is a TRUTHY `innerHTML` — "delete everything" would save a glyph that draws nothing while `glyphCoverage.test.ts`'s balanced-tag/no-URL checks all stay green, which is precisely the bare-titled-box failure that test exists to catch; (f) the modal's keydown gate is `activeElement === #mSvg`, NOT the page's `INPUT|TEXTAREA|SELECT` `typing` regex — the modal's other controls are two checkboxes and the load `<select>`, none of which take a character, so gating on `typing` silently killed Del/⌘A/the arrows while the selection stayed drawn, with no click able to return focus without destroying that selection; and the keys bail outright while a gesture owns the pointer, since they replace the `<svg>` that gesture still holds a reference to.

### The glyph modal's TOOLS, rotation, source link and paint bar

- **The glyph modal's TOOLS, rotation, source link and paint bar** (the same file; `glyphEditorGuards.test.ts` greps source for the invariants below, because none of them fails loudly). A tool row (Select · Pen · Draw · Line · Rect · Ellipse · Add point · Rotate) re-routes the marquee backdrop's pointerdown by mode; nothing about the existing marquee/move/scale code changed, it simply is not reached while another tool is armed. Five things are load-bearing. (1) **`renderGlyphPts` is now a WRAPPER** — `renderGlyphPtsInner()` then `syncGlyphHl()` then `renderPaintBar()` — because the renderer returns early three times (no layer, "drag points" unticked, no parsed root) and both new surfaces must refresh past all of them: hooked inside, unticking the checkbox left `<mark>` rectangles painted behind a textarea with no selection to explain them, and the paint bar reading "5 shapes" against an empty one. For the same reason the **Format** button is gated in `refreshMPreview` (the TEXT funnel) and not in the renderer, or it stays disabled with a tooltip blaming an SVG error the user has already fixed. (2) **Every new overlay element carries `.pt-dec`** — `#mPtsLay circle{pointer-events:all}` is an ELEMENT rule written when every circle in the layer was a draggable handle, so a decorative one is hittable by default and swallows the exact press it invites: the pen could not be finished by clicking its own first anchor, and the Add-point marker, drawn under the cursor by construction, ate every insert click. `.pt-off` is the same mechanism for the opposite reason — outside Select the handles are a read-only picture and a press belongs to the armed tool. (3) **A shape is created into the group that owns the SELECTION** (then the document's single top-level `<g>`, then the root), and both drag corners are converted through the inverse CTM before `width`/`height`/`rx` are measured — transforming an EXTENT would be silently right on the 24 `translate(28 28)` glyphs and 12.5% wrong on the one `scale(0.875)` wrapper. A rotated or sheared container makes an axis-aligned `<rect>`/`<ellipse>` unauthorable, so those two tools fall back to the root — decided inside `resolveDrawTarget`, which is also what draws the "· into `<g …>`" label, so the label cannot promise a container the tool will refuse. **⇧ on a box tool means SQUARE, not the point-drag angle lock**: `angleLockVec` snaps the drag VECTOR to the 30/45 families, which on a rect is a different thing entirely (a 35° drag locks to 30° and comes out 1.73:1, not square). (4) **Rotation has two mechanisms and the split is not cosmetic**: point coordinates rotate for lines, polylines, text/circle centres and path anchors/controls, but a `<rect>` is axis-aligned by construction and an `<ellipse>`'s rx/ry ARE its axes — rotating their points just drags the corners, which reads as the shape being resized and skewed — so `rect`/`ellipse`/`text` (and any element carrying its own transform, whose numbers already live in a turned frame) get a `rotate()` folded into their own `transform` instead, composed in the PARENT's space from the ORIGINAL attribute every frame (never from the last frame's output, which would accumulate a rotate() per pointermove), negated under a mirroring parent, and refused outright under a non-similarity one. The pivot comes from `getBBox()` for any element whose handles do not describe its extent — a rect's two handles are a top-left ANCHOR and a bottom-right SIZE handle, and size handles are excluded from the writes, so a pivot built from writable handles alone swung the shape around its own corner. The gesture accumulates an UNWRAPPED per-frame delta; measuring against the gesture's first angle folds at half a turn and spins the art backwards. **The KEYBOARD path (⌥←/→) is a RUN, not a series of presses**, and that is not an optimisation: applying a per-press delta to the art the previous press produced re-derives the pivot from already-rotated geometry, and the AABB centre of a rotated point set is not the rotated AABB centre — MEASURED on the shipped `dataviz` polyline, six ⇧⌥→ presses land the whole shape 1.38 view units from where one 90° drag puts it, as a pure translation (an L-shaped selection spanning the canvas goes 9.3), and it stacked one `rotate()` per keypress into the saved art. So `rotRun` keeps the run's ORIGINAL source text plus the accumulated total, restores that source and RE-PLANS against it each press — the plan cannot be cached, because `refreshMPreview` replaces `#mPreview`'s innerHTML and every element reference in it goes with the old tree. The run is validated by comparing the SOURCE TEXT (plus `selSig`) rather than by enumerating invalidation sites: typing, an undo, a paint change and a tool gesture all move it, so one comparison covers every way it can stop being valid. `rotateTransform` also FOLDS a leading same-pivot `rotate()` rather than prepending another, which is what keeps the attribute one call long. The undo snapshot stays THIS press's pre-state, so ⌘Z steps back one tap. Rotation is a TOOL and not a grip on the selection frame because a grip has to live outside that frame, and on art that fills the canvas there is ~1.6 units of room out there — it would be drawn on top of the very handles that (correctly) win an ambiguous press, i.e. visible and unclickable in exactly the select-all case people reach for first. (5) **The source link joins two halves by DOCUMENT ORDER and VERIFIES it** — the Nth drawable in the text is the Nth in the DOM, checked with `tagsAlign` on every pass rather than assumed, because the preview is built by the HTML parser and foreign-content rules can close the `<svg>` early on a breakout tag and shift every index by one; a mismatch shows a note and no highlight, never a wrong one. The highlight is a mirror div behind a transparent textarea (a textarea cannot style its own content) whose wrap-deciding metrics — `white-space`, `overflow-wrap`, `word-break`, the border widths — are COPIED at runtime, not hardcoded, and which never measures while the modal is hidden (`clientWidth` is 0 there, and the width would be cached negative) — which is exactly why `openGlyph` adds `.show` BEFORE its first `refreshMPreview`: refreshing first left the mirror holding the PREVIOUS glyph's text and that session's `<mark>` spans, i.e. blue blocks over unrelated lines of a different document, cleared only by the next real gesture. **Format** is a button and never automatic: a "reformat if it already looks formatted" heuristic false-positives on any newline inside an attribute, which is ordinary Illustrator output, so pasted art would silently reflow on the first drag. It calls `focusPtCanvas()` for the reason `replaceGlyphSource` documents — WebKit does not focus a `<button>` on click, so the caret stays in `#mSvg`, the keydown bails above the ⌘Z branch, and the undo entry it just pushed would be unreachable. **Escape's `!caret` term is gone**: clicking a line of markup selects that shape and deliberately leaves the caret where the user is reading, so a selection held with the caret in the box went from rare to ordinary — and from there Escape discarded the whole session. It still closes on the second press. The paint bar reads EFFECTIVE values through `getComputedStyle` (the only thing that resolves a presentation attribute, an inline `style` and inheritance from a `<g fill="none">` alike) and converts the `rgb()` it answers in back to hex, or a shape painted the palette's own colour matches no swatch; it writes presentation ATTRIBUTES to match the shipped art, skips what the container already supplies, and commits on `change` rather than `input` so typing a width is one undo entry and not three. With nothing selected the swatches set what the next drawn shape uses — session-only, deliberately not persisted.

### Node selection is an ELEVATION change, not a band

- **Node selection is an ELEVATION change, not a band**: every node shell (`.node-base`, `.output-node`, `.note-node`, `.color-node`, and the collapsed group pill) rests on `--shadow-node` (a hard `2px 2px 0` contact shadow) and marks selection by swapping the WHOLE property for `--shadow-node-selected` (`8px 8px 0`) — the same card, lifted toward the viewer under the app's fixed top-left light. Nothing else changes. The coloured `box-shadow: 0 0 0 <n>px` band this replaces (and `--node-selection-width`, and `.node-base__stack-frame`, and the `--node-cat` custom property six node components published solely to feed it) are all GONE — a band drawn in the node's own category colour sat directly on top of the node's 1.5px category BORDER, so a selected node read as one fat mis-drawn border rather than as a highlight, and the 4× offset jump is legible on one node among fifty in a way a ring is not. Consequences to respect: box-shadow REPLACES rather than adds, which is now the point — each selected rule is ONE token and must not re-state `--shadow-node` beside it; neither token is redefined in the dark block, since graph nodes render identically in both themes; and a STACKED (multi-channel) node still suppresses the card's own shadow entirely (`box-shadow: none`, set inline by ShaderNode and mirrored in CSS) because the DEEPEST stack layer carries the group shadow — so it is that layer, not the card, whose inline `boxShadow` switches to `--shadow-node-selected`, lifting the whole stack as one object. Two shells are deliberately outside the rule: an EXPANDED group frame keeps a faint band (it is a transparent frame with no fill and no resting shadow, so it has no elevation to raise — and `getGroupFrameColors` gives it a full-strength border when selected as the second channel), and `.fs-connect-target`'s drag-connect ring stays an `outline`, which is now the ONLY outline-style node indicator on the canvas and therefore unmistakably not selection. `NodeVisual` (the inert replica behind asset cards, the node-editor overview and the Node Designer stage) has no `selected` concept at all and hardcodes the resting token — a documented divergence from ShaderNode, not drift. `cssTokens.test.ts` is the guard that makes retiring a token safe: a `var()` naming a property nothing declares is invalid at computed-value time, so CSS drops the ENTIRE declaration — which is exactly how the first cut of this change left a selected Color node with no shadow at all while every one of the then-152 test files stayed green. **HOVER uses the same lift**, and both are driven by ONE inherited custom property, `--fs-node-lift`, published on React Flow's node WRAPPER (`.react-flow__node`, rising on `:hover` and `.selected`) and read by every shell as `box-shadow: var(--fs-node-lift, var(--shadow-node))`. The wrapper is the one element the card AND its multi-channel stack layers both descend from, which is what lets a stacked node rise as a single object instead of highlighting its top card; the fallback in that `var()` is what every NON-React-Flow surface renders at (asset cards, the node-editor.html overview, the Node Designer stage), and each shell ALSO sets the property on its own `--selected` modifier so selection still draws where React Flow's class is absent. Every shell carries `transition: box-shadow var(--transition-fast)`, so hover and box-selection both ease rather than snap — selection differs from hover in exactly one way, it STAYS. Asset tiles join the same system rather than copying it: `.node-preview-card:hover` publishes the same variable (plus a `transform` of its own), which keeps the card layer scaling a node instead of RESTYLING one — the rule `assetCardGeometry.test.ts` enforces. **The lift does NOT move the node — it deepens the shadow and GROWS the card slightly** (`--fs-node-grow`, 1.02; corrected 2026-09-09). **Written as the standalone `scale` PROPERTY, never `transform: scale()`**, and that is load-bearing: `.node-base` is not only ShaderNode's card — PreviewNode, MathPreviewNode and ClockNode render it too and each sets `transform: scale(<cost scale>)` INLINE on that same element, which beats any stylesheet rule. Written as `transform` the lift left the 8 noise nodes, sin/cos and Time as the only nodes on the canvas that did not respond to hover, silently, since every other node did. The used transform is translate → rotate → scale → transform, so the standalone property composes with the inline one and both scales apply — the same reason the retired movement used `translate`. `nodeLift.test.ts` pins the property AND that the set of shells taking the lift SHADOW is the set taking the lift SCALE, so a node can never deepen its shadow without growing. It used to travel `--fs-node-rise` (−3px on both axes) as well, on the reasoning that a shadow stepping out without the object rising reads as having grown a shadow rather than as having come forward. That movement is GONE from every canvas shell, and the defect it could not avoid is why. React Flow computes wire endpoints from stored positions and knows nothing about a CSS translate, so every wire on a lifted node had to be offset by the same rise to stay on its socket — a PREDICTION that holds only while React Flow measured the sockets with the card AT REST. Selecting a node also thickens its border (`--fs-node-border-scale`), which changes the node's SIZE, which fires React Flow's per-node ResizeObserver and re-measures the handles — at a moment when the card is already displaced and mid-`transition`. The displacement was then baked into the stored bounds AND added again by the edge, so every wire on a selected node sat ~3px above its socket and STAYED there after deselecting, because the correcting re-measure caught the card mid-transition too. Reported from the canvas as "hover follows correctly, click adds the same offset again"; hover is exempt precisely because hover does not thicken the border and so triggers no re-measure. Removing the movement closes the class outright: nothing is displaced by 3px, so no measurement can be wrong and no prediction is needed. The GROWTH that replaced it is not a smaller version of the same bug, and the size is the reason: a transform changes no layout so it fires no observer of its own, and although it does move the sockets (`getBoundingClientRect` includes transforms), at 1.02 on a 50px node the extreme socket moves 0.5px against the 3px that was reported — with nothing predicting it in JS, the worst case is a stale sub-pixel offset rather than a doubled visible one. Raising the scale materially brings the defect back at a size people can see; a bigger cue belongs on the SHADOW, which costs no geometry at all. `nodeLift.test.ts` pins the bound. Gone with it: `nodeRisePx`, TypedEdge's endpoint offset and its two per-edge store subscriptions, the `.node-base::before` hit-area shim (which existed only because the moved card painted outside React Flow's stationary wrapper, so hover was driven by the very element that moved and could oscillate — 47 flips across a slow creep along a noise node's edge), and the `--fs-node-rise` term in the selection rectangle's inset. **The ASSET TILES take the same lift** (NodePreviewCard.css / ContentBrowser.css publish `--fs-node-lift` and scale by `--fs-node-grow` on hover; the saved-group tiles too). They never had the measurement problem — nothing measures them and they carry no wires — but a tile that lifted differently from the node it depicts is exactly the drift `assetCardGeometry.test.ts` exists to stop, so they follow. The scale also suits that surface better than the move did: the strip is drawn through a computed `zoom` (~0.5–0.7×), so a translate had to be sized to survive being multiplied by it — at 0.5× a 1px rise is sub-pixel and the tile 'did not animate' as far as anyone could see — where a scale is scale-INVARIANT and reads as 2% at every zoom the bar can produce. `--fs-node-rise` is retired outright rather than left declared, since a dead token invites the next reader to wire it back up. **The Sound node's ARM LIGHT lifts under its OWN pointer, not the node's** (`.shader-node__sound-btn` in ShaderNode.css; owner request 2026-09-09 "make the sound node's button drop a shadow; make the button react the same way when a node is hovered over (shadow and size)", clarified 2026-09-10: "the shadow and the size only when the mouse is over the button, not the node"). It rests on `--shadow-node` and, hovered or keyboard-focused, grows as a hovered node grows (`--fs-node-grow`) but casts HALF a lifted node's shadow — `--shadow-node-control-hover`, 4px against 8px (owner, 2026-09-10: "make the shadow fall closer 2x"): the light sits on a card that is already raised off the canvas, so the full 8px read as it floating far above that card; `nodeLift.test.ts` pins the ratio, not the literal. The first cut read `--fs-node-lift`/`--fs-node-scale` off the node WRAPPER instead, so hovering ANYWHERE on the node deepened the light to 8px and grew it 1.02 on top of the card's 1.02 — the card rose off the canvas and the light rose off the card by the same distance again, which read as the light sticking out; a session spent measuring that as "working" in three browsers, because it was working as built. Four things are load-bearing. (1) **The light RE-PUBLISHES the two properties on itself** (`--fs-node-lift: var(--shadow-node); --fs-node-scale: 1` at rest, raised by `:hover:not(:disabled):not(--inert)` / `:focus-visible`) — a custom property declared on an element beats the one its parent hands down, so that one move cuts the inheritance from the wrapper without touching the node's own lift, and every rule that reads them keeps working unchanged. It still grows WITH its card on node hover, since it is inside it; it just adds nothing of its own. A disabled light (grey, unwired — it cannot be armed) does not lift: a lift says "press me". A `.fs-connecting` rule flattens it while a wire is dragged, mirroring the node rule. (2) **The LIVE blink's keyframes must carry the lift** — declarations inside a running animation sit in the ANIMATION origin and outrank the author rule for as long as it runs, so a keyframe naming `box-shadow` REPLACES the drop shadow rather than adding to it; both halves of `fs-mic-blink`, and the reduced-motion rule that replaces the base the same way, compose `var(--fs-node-lift, var(--shadow-node))` beside the glow (now the light's own value) — the dark half's old `box-shadow: none` would have blinked a recording light's shadow away twice a second. `var()` inside `@keyframes` re-resolving per element is verified in Chrome 152 only; it is the first `var()` in any keyframes under `src/`, and the Safari 16.4 / Firefox 126 floor is unverified. While the blink runs, `transition: box-shadow` on the light is inert (a running animation on a property beats a transition on it), so a LIVE light eases only its `scale` — accepted, since the blink is a step function anyway. (3) The standalone `scale` property is mandatory for a second reason here: `.shader-node__arm-wrap` carries `transform: translate(-50%, -50%)`. (4) **The tile needs nothing**: the card publishes `--fs-node-lift` to everything inside it, and the light's own declaration now shadows it, so a hovered tile lifts as one object with its light at rest — the canvas composition. The scoped `.node-preview-card:hover .shader-node__sound-btn` publish the first cut needed is gone. `nodeLift.test.ts` pins the re-publish, the own-hover rule and its disabled/inert/wire-drag exclusions, the keyframe and reduced-motion composition, and that no surface hands the light a node-level hover. **Known leftover**: `hoveredNodeId` in the store now has no reader — TypedEdge was the only one — so it is written on every hover for nothing; removing it is a separate cleanup, and the `fs-connecting` CSS suppression beside it still earns its place (it now governs the shadow alone). A node's settings menu holds the same lift for its own node: NodeEditor puts `fs-menu-active` on the wrapper for the life of the menu, keyed on the `contextMenu.nodeId` the store already carries, so the panel you are editing never sits beside a graph that has forgotten which node it belongs to. Imperative (the `clearConnectPreview` idiom, `CSS.escape` included — node ids come from `.fastshader` files) rather than a className on the node OBJECT, because node data changes push through history and the autosave and opening a menu is not an edit; the effect's cleanup covers every way a menu ends WITHOUT enumerating them, including a second right-click MOVING the menu to another node, which only re-renders and would otherwise leave the class behind. **The cost-badge numbers cast the same hard shadow as everything else** — `1px 1px 0`, replacing a `0 1px 2px` blur: dark `rgba(0,0,0,0.45)` on an asset tile (the number is drawn in the user's cost-gradient colour there, and a white halo did nothing against the near-white bar and vanished into the dark one), and `--node-cost-text-shadow` on the canvas, which is already the contrast-flipped companion of the colour the number itself takes. **The marquee itself is BOUNDARY ONLY** — a 1px dotted `--border-focus` outline with no fill, because the translucent blue wash it replaces tinted every node it swept over, and on a canvas whose whole job is colour a selection must not change what the shader looks like. It is an `outline` rather than a `border` so the line can sit outside the box without touching the rect React Flow sizes inline: the LIVE band stays at `outline-offset: 0` (its edge has to mean exactly "what is inside this"), while the box that REMAINS after the pointer is released — `.react-flow__nodesselection-rect` — stands off at **5px**, clearing the 8px shadow and 3px rise its selected nodes now carry. `outline-offset` moves only the line, so dragging the selection still grabs where it always did. Both need `!important` on the outline: React Flow ships `.react-flow__nodesselection-rect:focus { outline: none }` to suppress the UA focus ring, that rect really IS focused after a marquee (it is focusable so the selection can be nudged by keyboard), and without the override the released box drew no line at all while its offset still applied — a silent failure that looks like the rule never matched. **Clicking also THICKENS the node's border** — `--fs-node-border-scale` 1 → 1.5 on `.selected` and `fs-menu-active` (NodeBase.css), read by every shell: the canvas components set their frame INLINE (the colour is the node's category and is only known in JS), so the width rides `NODE_BORDER_WIDTH` from `nodes/nodeFrame.ts` — one place holds the 1.5px the node spec fixes, and its `var(…, 1)` fallback is what keeps asset tiles, the node-editor overview and the Designer stage at rest. A SCALE and not a width, so each shell scales ITS OWN base (1.5px card, 1px note, 2px group frame) rather than all snapping to one number. Hover deliberately does NOT thicken: the lift alone made hovering and selecting render identically, so sweeping the pointer across the canvas looked like it was selecting everything it passed — a committed state gets weight, a passing one only gets height. **A lifted node's WIRES move with it.** The card's sockets travel with the card, but React Flow computes edge endpoints from node POSITIONS and knows nothing about a CSS `translate`, so every wire on a lifted node hung a few px off its port and read as unplugged. `TypedEdge` therefore offsets each endpoint by `nodeRisePx()` (which READS `--fs-node-rise` off the DOM rather than duplicating the literal, so geometry and CSS cannot drift) when THAT end's node is lifted — only that end, since the other node has not moved. It costs two subscriptions per edge, both folding to a small NUMBER (`selected` from React Flow's `nodeLookup`; hover + open-menu from the app store's `hoveredNodeId`/`contextMenu` in ONE selector), so the value is 0 for every edge that does not touch the node and a hover re-renders only the one or two wires that actually moved — MEASURED: hovering a node moved exactly 2 of 6 paths, by exactly −3,−3. **Dragging a WIRE suppresses hover entirely** (`fs-connecting` on the canvas root + NodeEditor pausing `hoveredNodeId`): a connection drag sweeps the pointer across every node between the socket and the target, and lifting each in turn is noise on top of a gesture that already has its own target affordance. The CSS and JS halves must stay in step — if one suppresses and the other does not, the card lifts while its wires stay put, which is the very defect the offset exists to fix. Selected nodes and the menu-active node keep their lift throughout, so the suppression rule carries `:not(.selected):not(.fs-menu-active)`.

### A hovered edge thickens; a SELECTED one thickens more and opens its data card

- **A hovered edge thickens; a SELECTED one thickens more and opens its data card** (`HOVER_EDGE_BOOST` 1.35 / `SELECTED_EDGE_BOOST` 1.8 in `TypedEdge.tsx`; hover added 2026-09-09). The gap between the two is the point, and it is the same passing-vs-committed distinction the nodes draw: hover says "this is the wire under your pointer", selection says "this is the one you are working on", and matching them would make sweeping the canvas look like it was selecting every wire it passed. Hover state is LOCAL to the edge component — a hovered-edge id in the store would re-render every edge on every hover to tell all but one of them nothing — and is cleared when the wire is dragged off its port, where the hit path it was hovering is replaced by the connection line. Neither boost may be expressed as a CSS `:hover` stroke-width, for the reason below. No shadow, no glow, no colour change either: a wire is a line, not a plate, so an offset copy of it is only another line — at any offset big enough to see, it stops reading as that wire's shadow and starts reading as a second wire beside it; weight is the property a line actually has to spend. The boost scales the WHOLE ribbon, both `strokeWidth` and the per-channel perpendicular `offsets`, never the stroke alone: multi-channel lines sit `GAP` (1.167px) apart and are already up to 1.2px wide, so thickening strokes on their own would close those gaps and fuse a 4-channel ribbon into one solid band — the highlight would destroy the channel count it is highlighting. It also fixed a gap: only the 1-channel case used to thicken, so a selected multi-channel edge was marked by nothing but an opacity nudge. NB `.fs-edge-drop-target`'s `stroke-width: 4 !important` reaches EVERY path TypedEdge renders (it means "any path that is not the hit area"), so anything added there inherits it mid-gesture.

### Light theme by default, app-wide dark mode

- **Light theme by default, app-wide dark mode**: flat design in a TECHNICAL style — every corner is square (`--border-radius-*` are all 0; only true circles like sockets, the colour swatch, the clock face keep `50%`), and every elevation shadow is a HARD down-right offset with zero blur whose distance encodes height (`--shadow-sm` 2px chips → `--shadow-md` 4px cards/tooltips → `--shadow-lg` 8px modals/popovers over ORDINARY content → **`--shadow-float` 6px, every panel floating over the NODE CANVAS**; graph nodes rest at 2px via `--shadow-node` and rise to 8px via `--shadow-node-selected`, which is how selection is drawn — see the node-selection bullet; wires get the same treatment at half the offset). **`--shadow-float` exists for the ONE far more than for the number**: that set used to span three different shadows (menus at 8px, canvas bar and draw cluster at 4px, cost pill and NEW at 2px), so the app's own controls sat at three apparent heights over one canvas. It now covers the whole set (context/settings menus incl. Add-node, cost pill, NEW, canvas bar, draw cluster, EdgeInfoCard, the mesh-target picker, both drop hints). The ALPHA deliberately does not change from `--shadow-lg` — distance is what encodes elevation here, and a second variable would make two panels at the same height look different. NOT used for modals, toolbar popovers or asset tiles, which float over content that tops out at 4px. **The toolbar's top-edge strip restates it** (`.app-layout__left::before`: 6px tall, 6px left inset, `--shadow-float-color`) — the app's topmost plate was otherwise casting its shallowest shadow. **The DEPTH is authored and 6px is a second pass**: the first cut was 12px, picked to clear a selected node's 8px so a menu could never cast the same shadow as the node it was opened from, and that read as too heavy — the chrome looked like it was peeling off the canvas. Halving it leaves a KNOWN INVERSION: at 6px a SELECTED node (8px) casts a longer shadow than the panel over it. Accepted, because the comparison that matters on screen is against a node at REST (2px), which is what every node but the selected one or two is doing; the alternatives are lowering `--shadow-node-selected` (it IS the selection affordance, and the 4x jump from 2px is what makes it unmissable) or going back to a depth already rejected by eye. `cssTokens.test.ts`'s ramp suite guards the parts that are NOT judgement calls, since none of this fails loudly: the sm<md<lg chrome ordering, that float is its own value and has not collapsed onto one of them, that it clears a resting node, that the hand-drawn strip's height and left inset still equal the token's offset, and that every floating canvas panel resolves to ONE token. It deliberately does NOT assert float vs `--shadow-node-selected` in either direction — pinning that would freeze a judgement call that belongs to whoever is looking at the screen — never reintroduce a blur radius or a nonzero radius literal (tiny `text-shadow` legibility halos and the mic light's glow are the deliberate exceptions). Standalone chrome buttons all share ONE height (`--ctl-size`, inline-flex, horizontal-only padding — compact in-row widgets like palette swatches, CostBar chips and node-internal controls are exempt) and chrome button/header text shares ONE size (`--font-size-sm`; headers differ by weight, never size — glyph-only buttons may size their glyph freely). CSS tokens in `tokens.css`. The toolbar sun/moon button (`codeEditorTheme`, persisted to `fs:codeEditorTheme` — the store field keeps its historical name) is the ONE dark-mode control: it themes Monaco AND stamps `data-theme="dark"` on `<html>` (via `setCodeEditorTheme` + an inline FOUC guard in `index.html`), which flips the CHROME tokens redefined in `tokens.css`'s `:root[data-theme="dark"]` block (backgrounds, text, borders, chrome shadows, `color-scheme`). **Graph nodes FLIP with the theme** (2026-09-09, owner request), but only their SURFACE does. Three tokens carry it — `--node-bg` (the body), `--node-ink-rgb` (everything drawn ON it) and `--node-plate` (the inner fields: a number box, the mesh picker) — and all three are redefined in the dark block. `--node-ink-rgb` is an `r, g, b` TRIPLE rather than a colour because ~39 declarations each pick their own alpha (`rgba(var(--node-ink-rgb), 0.55)`); writing them as finished colours would have meant a second literal per site and a second chance to miss one, and a missed site is unreadable text on a dark card rather than anything that fails loudly. **The MEANINGFUL colours still do not flip**: `--type-*`, `--cost-*` and `--cat-*` stay out of the dark block, so a socket's data type, a node's price and its category read the same for everyone; shadows stay dark in both themes (an elevation shadow is a shadow), and the two `text-shadow` halos stay black because they sit under WHITE text on a coloured header. Until this change nodes were deliberately theme-INVARIANT, and the reasoning is worth keeping in view rather than lost: a node carries category colour, cost colour and live shader values, none of which have a dark counterpart, so holding the body fixed guaranteed those read identically — what replaced it is the narrower, checkable rule above. **The GLYPH art inverts** in dark mode — `:root[data-theme="dark"] .node-glyph { filter: invert(1) hue-rotate(180deg) }` — rather than being re-authored: its ink is `#2B2B2B` across ~236 colour literals in 77 saved designs plus the built-in `renderArt` set, and a sweep would change the file the Node Designer round-trips and make every future glyph an exercise in picking two colours. The pairing is the standard one: the invert flips lightness (dark ink becomes light, a white knockout becomes dark, so figure and ground keep their relationship) and the hue-rotate undoes the invert's hue flip, so the family's accents come back as themselves instead of their opposites. It is scoped to `.node-glyph` and must stay so: the colormap strip is real data colour, the image thumbnail is the user's own picture, and the noise previews, waveform and clock face are READINGS — inverting any of them would be a lie rather than a restyle. **The node HEADER mixes into the card, not always into white** (`getCostColor`'s `dark` flag, 2026-09-09): 45% cost colour against 55% of the body, which lightens on a light node and darkens on a dark one. Blending toward white in both themes made a dark node's header the brightest thing on it — a pastel band over a near-black card, louder than the glyph it labels. The mix RATIO is unchanged, so a header keeps the same colour strength either way (a cheap node still reads green, an expensive one orange, which is the whole point of colouring it); only what it mixes into moves. Header TEXT needs no parallel change — every caller picks it with `getContrastColor(costColor)`, which flips on its own once the fill darkens. **The canvas ink eases at the white end** (`canvasInkColor`, used for cost badges and 1-channel wires): pure white on a dark backdrop glares and reads as brighter than the nodes it connects, so the white end comes down for the reason `--node-bg` is an off-white; the BLACK end is untouched, since a softened black on a light canvas just looks washed out. `getContrastColor` stays binary for text ON a swatch, where the ground is a saturated cost or note colour and every bit of contrast counts. Two further consequences to respect. The dark chrome ramp is a MID-grey and its stated reason ("nodes are a fixed off-white, so a near-black chrome put a card at 16.5:1") is now history; the ramp is kept because the rest of the app was tuned against it, and re-darkening it is a separate judgement about the whole interface. And `getGroupFrameColors` takes a `dark` flag: a group frame is the backdrop panel BEHIND its member cards, so mixing it from the light base on a dark canvas puts a pale sheet under dark cards and inverts the depth ordering the mix exists to preserve — `NODE_DARK` beside `NODE_WHITE` in colorUtils duplicates the token for the same reason (pure, node-tested, no CSSOM), so the two MUST track each other. Per-surface dark tweaks (hardcoded light-assuming literals that tokens can't reach) live as `:root[data-theme="dark"]` blocks in each component's own CSS; the React Flow grid color is a prop flipped in `NodeEditor.tsx`. The canvas background is user-pickable AND remembered PER THEME (`nodeEditorBgColorLight`/`Dark`; `nodeEditorBgColor` is the effective active-theme value; dark default `#41454d`); cost badges and 1-channel edges auto-flip via `getContrastColor(nodeEditorBgColor)` so they invert to light on the dark canvas automatically. `projectImport` applies theme BEFORE canvas color so the color lands in the right per-theme slot.

### The colour picker is app-wide, and lives OUTSIDE the NodeEditor tree

- **The colour picker is app-wide, and lives OUTSIDE the NodeEditor tree** (`components/inputs/PaletteColorPicker.tsx` + the pure `colorPickerModel.ts`; it has no React-Flow dependency, so CostBar / ShaderPreview / Toolbar can import it). It draws the shader's OWN palettes first, `BUILTIN_PALETTES` below them, and two bottom rows of globally-recent colours (`utils/recentColors`, which COLLAPSE when empty — placeholder cells read as a rendering bug). Seven rules are load-bearing. (1) **`history` is a REQUIRED prop with no default** (`'bracket' | 'none'`): `bracket()` opens `beginInteraction`, which snapshots the graph AND clears `future`, so bracketing a PREFERENCE site (canvas bg, draw ink, cost poles, preview bg, a live uniform) would push an undo entry that restores nothing and wipe the user's redo stack on every pick. The gate covers the CLEAR path too — `onClear` used to call `bracket()` directly. (2) **Live-apply and commit are different paths.** A native `<input type="color">` fires ~60 events/s while its wheel is dragged, so `applyLive` calls `onPick` per frame and records NOTHING; `createColorCommitStager` stages the value and one flush — on idle (600 ms, the `useHistoryBracket` window), blur, close, or unmount — records exactly ONE recent. The native `change` event is deliberately not the commit signal: browsers disagree about whether it fires during a drag, so a design keyed to it floods on one engine. A swatch click is neither: `pickSwatch` applies WITHOUT staging, so a palette or recent colour is never recorded. "Recent" is for colours the user MIXED — a palette colour is permanently one click away in the rows above, so recording it spends an MRU slot duplicating something already on screen and evicts a mixed colour that exists nowhere else, and re-recording a RECENT reorders the row under the pointer mid-click. It still flushes first, or a custom colour just dragged to would be dropped by the swatch click that follows it. (3) **Every effect is keyed on `open`** — the popover and its custom input only exist inside the portal, so an effect without it attaches to nothing; the custom input therefore uses React props (React treats `type="color"` as a text-like input, so `onChange` already covers native `input` AND `change`, deduped by its value tracker). (4) **A click inside an IFRAME closes it via window `blur`, not via the outside-pointerdown listener** — such a click never reaches this document, and the 3D preview is an iframe filling most of the right column, so "click elsewhere to dismiss" simply stopped working over the largest target on screen. Focus is the only signal that crosses: the browser focuses the `<iframe>` and blurs this window. Gated on `document.activeElement instanceof HTMLIFrameElement` and read on a macrotask (at blur time it is still the old element), because a bare close-on-blur also fires on an app/tab switch and, on macOS, when the "Custom" row opens the OS colour dialog — where it would kill the picker mid-pick. (5) **Escape `stopPropagation()`s** in its capture-phase listener: `ContextMenu.tsx` closes the whole settings menu on a bubbled Escape and skips only INPUT/TEXTAREA/SELECT/contentEditable — the swatches are `<button>`, so once a picker lives in a context menu a leaked Escape would take the menu with it. (6) **The portal host is RESOLVED, not `document.body`**: ShaderPreview fullscreens its own root and the top layer renders only that subtree, so a body portal would be invisible on exactly the controls kept usable in fullscreen — `pickPortalHost` adopts `fullscreenElement`/`webkitFullscreenElement` when it CONTAINS the anchor, and a `fullscreenchange` closes the popover so it can't be left in a torn-down host. (7) **Placement is measured** (`placePopover` + `useLayoutEffect` + `getBoundingClientRect`, the ContextMenu precedent) — the height is now variable, so the old `+130`/`-134` literals described a layout that no longer exists. Rows are a `grid-template-columns: repeat(5, 20px)`, NOT a flex row: every built-in is exactly 5 colours, which is why a bare `display: flex` never visibly failed, but user palettes run to 64 and spilled straight through the border; the 146px width is derived (5×20 + 4×4 = 116 content + 14 chrome + ~15 for a classic scrollbar) and the popover is `max-height`-bounded and scrolls. **`ColorPickerPopover` is exported separately** — anchor + `open` + `onClose`, no trigger — because the Color node IS the swatch (a 56px circle whose perimeter carries the output socket) and has nowhere to put one; it renders the popover anchored to itself, opened by the same double-click / long-press that used to click a hidden input. The canvas bar's background button does the same for the opposite reason: it is a `.fs-canvas-bar__btn` in a row of bar buttons with a small swatch inside, and a full-bleed colour chip there would break the bar's rhythm. **The rollout is complete and pinned**: `colorPickerHistory.test.ts` carries the reviewed `history` value for EVERY call site together with the writer that justifies it, fails on a picker in a file the table doesn't list, and fails on an `<input type="color">` rendered anywhere but the popover's own "Custom" escape hatch and `PalettesModal` (the palette EDITOR — it authors the very swatches the picker offers, so a picker there would be circular, and its rows run a bespoke draft-then-commit-on-blur model built around the native input's blur). TypeScript already catches a MISSING `history`; only a source pin catches a wrong one. Two consequences for the CSS: every site's size rule is written with TWO classes (`.shader-node__left .shader-node__input-color`, `.context-menu .context-menu__color`, …) because a single class ties with `.palette-swatch` and the winner would fall to whichever stylesheet the bundler emits last; and no site rule may set a `background` — the fill arrives as an inline `background` SHORTHAND, which also resets `background-clip`, so an inset (the preview's backdrop swatch) has to be drawn with an inset `box-shadow` instead. **`NodeVisual` is the one surface that does NOT get the picker**: it is the inert replica behind asset tiles and the node-editor overview, and the cards' `pointer-events: none` stops the pointer but not the keyboard — a real picker there would make every colour row a tab stop that opens a popover from a static replica. It renders `PaletteColorPicker` only under `interactive` (the Node Designer's stage, whose `onValueChange` writes a session-only preview model, hence `history="none"`) and otherwise an inert `<span>` carrying the SAME `.palette-swatch` classes — the OutputCardContent precedent, and the reason the old `<input readOnly>` had to go (`readOnly` is not honoured on a colour input, and a UA swatch and a `background` do not paint identically).
