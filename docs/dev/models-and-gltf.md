### Custom preview mesh

- **Custom preview mesh**: dropping a `.obj`/`.glb`/`.gltf` on the 3D preview — or on the node canvas or the code panel, which both hand it to the preview's own `loadMeshFile` through `fs:preview-model-file` (utils/previewModelDrop.ts; a model dropped with a project follows the import, as on the preview) — (or importing a zip carrying one) loads it as the `custom` preview geometry. The mesh lives in the store's `previewMesh` slice — never history, the localStorage autosave, or the project embed (bytes can be tens of MB) — but IS mirrored to an **IndexedDB cache** (`utils/previewMeshCache.ts`) so it survives a reload; localStorage is the wrong store here (strings only, ~5-10 MB origin budget the graph autosave already fills). `setPreviewMesh` is the single persist chokepoint (fire-and-forget, resolves on every failure path so a quota error can't break a drop); the boot restore passes `{ persist: false }` since those bytes came out of the cache. Restore ordering is the subtle part, and it is why **the stored preference is kept VERBATIM and the no-mesh fallback is DERIVED at render** (`components/Preview/previewGeometryPref.ts`: `validateGeometry` accepts `'custom'` whether or not a mesh is loaded, `shownGeometry(stored, hasMesh)` is what the document, the Model `<select>` and the Subd gate all read — the `effectiveTab` rule for `fs:assetTab`, for the same reason). The read is async, so there is a window on every boot in which the preference is valid and the mesh has not arrived; the old code closed it by DOWNGRADING `'custom'` to `'sphere'` in the validator (an imperative store read) plus an effect that called `setGeometry('sphere')` whenever the mesh was absent — and `usePersistedState` writes its value straight back, so every boot overwrote the stored `'custom'` for ~250 ms (MEASURED in Chrome: `'sphere'` at t=188 ms, `'custom'` again at t=442 ms; the effect's own write at t=219 ms). A reload, a vite dev full-reload or a crash inside that window destroyed the preference for good: the mesh still came back from IndexedDB — so the Model entry sat in the dropdown named after the user's file — while the viewport rendered a sphere, on that boot and every boot after it (the owner's "the model disappears and there is a sphere, although the top selection shows that it is the mesh", 2026-09-18). `bootGeometryWasCustom()` (the module-init snapshot, sampled before React mounts) and its `setGeometry('custom')` on restore stay as the belt-and-braces half; with the preference intact they are a no-op write. A synchronous drop or zip import always wins over the cache read. `previewGeometryPref.test.ts` pins the validator, the derivation and all three readers, and fails if a `setGeometry('sphere')` ever returns. Cached bytes are re-validated as adversarial input (`recordToMesh` → the same `createPreviewMesh` constructor: extension whitelist, 64 MB cap, GLB magic, name sanitize) and get a FRESH session id so the iframe rebuilds. The sandboxed iframe receives models via the generalized `fs:obj-model` feed (glb rides as bytes, obj/gltf as text pre-decoded ONCE at load, and a compressed model's decoder bytes in an optional `decoders` field — see the decoders convention; keyed `custom:<id>` so a stale feed can't cross documents — every mesh change forces an iframe rebuild, and the per-rebuild structured-clone copy is the accepted price of a fresh document). Drops over the iframe are forwarded to ShaderPreview via `fs:preview-drag`/`fs:preview-drop` (podest's forwarder pattern — the iframe swallows drag events over the whole 3D view; the parent root handles chrome-area drops, and `.js`/`.zip` drops route through the shared `projectImport` path). `fit-bounds` takes an EXPLICIT `regen` flag at every attach: true rebuilds normals/UVs (OBJ — non-indexed loader output), false preserves authored GLB data (spherical UVs only when missing); podest's twin component defaults the OPPOSITE way, so never rely on either default. SECURITY: model files are adversarial — bytes cross only via postMessage + iframe-minted blob URLs, and BOTH sandboxed stages (editor preview + podest) install a `THREE.DefaultLoadingManager.setURLModifier` allowlisting `blob:`/`data:` so a hostile `.gltf`'s absolute-URL buffers/textures can't phone home (CSP is absent in dev, desktop, and podest — the modifier is the real control, not CSP); the XR popup runs at the app's REAL origin, so it installs an origin-widened variant (`blob:`/`data:`/same-origin — built-in models load by real URL there). Iframe-forwarded SHADER drops (`.js`/`.zip`) require a `window.confirm` — sandboxed code can forge `fs:preview-drop`, and a project import replaces the whole graph (model files only swap the session mesh, so they stay immediate — the one model exception is RESTORING the shader stored in a forwarded `.glb`, which needs the same confirm; see the GLB-restore convention); a combined shader+model drop is sequenced shader-first so the dropped model deterministically wins. Export: with a mesh loaded, "Download Shader" emits a zip with `models/<sanitized-name>` (`exportBundle.ts`, pure + tested); import: `importShaderZip` restores the first model entry and forces `custom` geometry — a refused model entry (empty, bad GLB magic, compressed, or over `MESH_MAX_BYTES`, which is reachable inside a zip only since the reader cap became 96 MiB) no longer vanishes: the shader still loads and the canvas import note says the model was skipped and why (podest pairing semantics; a model-ONLY zip returns `'model'` and just loads the mesh), while model-LESS text imports CLEAR the stale mesh so it can't contaminate the next export. **Compressed glTF is PRE-CHECKED before loading** (`inspectGltfCompression`, called inside `createPreviewMesh`, so drop, canvas, zip import and cache restore agree). **A glTF's structure may now be READ on the trusted side** (`utils/gltfReader.ts`, the second documented exception to this module's no-parse rule; see its utils tree entry). At runtime it is called ONLY through its `gltfPreviewFacts` adapter, inside `createPreviewMesh` (Step 6: every glb/gltf load carries `PreviewMesh.gltf`, which index-section dormancy reads). Its two partners exist: the pre-read size gate (`preReadModelGate`, which `loadMeshFile` calls with its OFFER predicate (`!isEvalMode()`, not paired with a shader, a glTF) as the third argument — so only an offered `.glb` gets the 96 MiB build-path cap, and everything else is exactly the old 64 MiB test) and the writer `gltfStrip.ts`, which produces the texture-stripped copy that becomes the preview mesh. Phase 5 wires the reader into two places: the build-from-materials path (the composer `engine/gltfImport.ts` behind the Step 9 dialog, which passes the OFFER predicate — `!isEvalMode()`, not paired with a shader, a glTF — to the gate, which then lets a `.glb` of up to `GLB_READ_MAX_BYTES` be read, so its textures are extracted before the stripped copy meets the 64 MiB model gate through the unchanged `createPreviewMesh`; the IndexedDB cache and the zip export then carry the stripped model, never a further copy of the textures), and `createPreviewMesh`'s model facts (`gltfPreviewFacts`, landed in Step 6). It is stricter than GLTFLoader, and a refusal only withdraws the build: the model-only drop stays today's path.
  - Draco and meshopt are DECODED, not refused (see the decoders bullet). `inspectGltfCompression(json, support = BUNDLED_DECODERS)` reports `needs: { draco, meshopt }`, and `createPreviewMesh` stores it as `PreviewMesh.decoders` — present only when a need is true, derived, and never persisted (the IndexedDB restore re-runs `createPreviewMesh`). Three r184 still never reads a Draco primitive's uncompressed fallback, so a Draco model works only because the decoder is installed, and the pre-check keeps the older refusals reachable for any caller that passes `{ draco: false, meshopt: false }` (Draco whenever listed, meshopt when required).
  - KHR_texture_basisu is transcoded, not refused: `BUNDLED_DECODERS.ktx2` sets `needs.ktx2`. The drop-time "shown with their fallback images" line fires only for a caller passing `{ ktx2: false }`. In the app the same line now arrives from the sandbox's `fs:model-ktx2` count, when a transcode really fell back.
  - The check is FAIL-OPEN: JSON over 8 MiB or unparseable JSON is not inspected, and the iframe's late overlay stays the backstop.
  - Refusals are structured (`MeshRefusal`, with a `reason` a caller can branch on) and translated; sizes are MiB rounded up.
  - The preview drop notice stays 12 s and has a ✕ (the notice itself stays `pointer-events: none`; the button opts back in).

### A FastShaders single-GLB export is RESTORED only by an explicit choice, and its payload never survives into a …

- **A FastShaders single-GLB export is RESTORED only by an explicit choice, and its payload never survives into a preview copy** (`utils/glbShaderExtras.ts`, `importShaderGlb` in engine/projectImport.ts; GLB Phase 7 Step 6). A GLB carrying a module is a `.js` in a model's clothing. Six rules. (1) **The gate.** Restore is a button of the GLB import dialog, Phase 5's one gate, which every model drop reaches through `ShaderPreview.loadMeshFile` (preview, canvas, code panel, iframe). It is offered even when nothing can be built (`planGlbImportDialog`'s third argument, `restoreFactOf`), it is never the focused default and nothing is remembered, it is unreachable under `isEvalMode()` and for a model dropped WITH a shader (`offerBuild: false`, the shader wins), and an iframe-forwarded drop (`loadMeshFile`'s `source`) also needs the forwarded-`.js` `window.confirm`, since the sandbox can forge the drop. A stored shader the reader refuses is announced (`fsRefusalNotice`) whether or not the dialog opens. (2) **The PROJECT wins in the editor.** Its block goes through `extractProjectState` + `applyProjectToStore` exactly like a `.js` block (every sanitizer, the payload refs under one `RefBudget`, one undo entry, one `fs:graph-imported`), with the GLB's own images offered as scan-only `data:` literals (`assetLiteralText`); the module is not parsed at all then, and `module.fnv1a` only adds a dialog warning when it no longer matches (an accidental-edit detector, not a control). With no usable project the MODULE, placeholders inlined, takes the bare-script path, images not recoverable, as a `.js` without a block. Podest, A-Frame pages and plain three run the module: that asymmetry is the rule. (3) **Every refusal happens before the store is touched**, and the abort signal is checked after every await; the commit is `importShaderZip`'s model-plus-script tail (`showCustomMesh`, hoisted and shared). The mesh swap is not undoable (the zip and NEW precedent). (4) **No preview copy keeps the payload** (layer L1). `createPreviewMesh` — drop, zip import, IndexedDB restore, build, restore — prefers the COMPACTING drop: the Phase 5 strip with no built materials, which reclaims the module/project views and the images only the module used (`'kept'` mode zeroes the payload instead). Zeroing alone left the payload's size in every later copy and made a re-export cycle grow (integration §3 C10). A model the strict reader refuses gets the in-place drop; a payload sniffed in a container that will not parse is a bad GLB (fail closed); a file whose JSON never spells `"fastshaders"` is the same bytes, unread. **That sniff answers `\u00` as well as the literal key** (`fsJsonMayCarry`, and its byte form inside `sniffBytes`), because a JSON key is delimited by literal quotes and the only escape that can spell a letter is `\uXXXX`, every character of `fastshaders` being U+0061..U+0074 — so `{"extras":{"fastshaders":…}}` parses to the same document while a literal-only gate reads it as `none`, hands the bytes back undropped, and walks a stranger's module into the IndexedDB mirror, the XR blob and every zip `models/` entry. The `00` keeps it tight: a bare `\u` matches almost any multi-megabyte BIN. The restore's own preview mesh is the strip for the materials the restored project's index sections claim. So the XR popup (real origin), the IndexedDB record and every `models/` export entry never carry a module — which changes a zip's `models/` bytes for such a GLB, intentionally. (5) **The opt-in is never spelled** where the app runs a shader (layer L2), and every run document closes the loader's latch (L3); see the XR popup bullet. (6) **Structural errors refuse the whole restore** (`damaged` / `too-large` / `unsupported-version` / `inconsistent`); the file loads as a model with a notice. Per-image failures stay per image (`images-missing` on the project side). Podest twins the reader (`fsReadGlb`/`fsDropPayload`/`fsJsonReviver`), asks before running a GLB's module, and strips every `.glb` in `loadModelBuffer`; `podestGlbReader.test.ts` runs the twin beside the editor's reader, verdict for verdict and drop bytes for drop bytes. NOT run in a browser yet: the restore round trip, the forwarded-drop confirm, podest's confirm and replay.

### A dropped PBR model is OFFERED as a shader — the GLB import dialog

- **A dropped PBR model is OFFERED as a shader — the GLB import dialog** (GLB Phase 5 Step 9; `Modals/GlbImportModal.tsx` + `Preview/useGlbImport.tsx`; decisions pure and tested in `utils/glbImportGate.ts`, words in `utils/glbImportCopy.ts`, the report in `utils/glbImportReport.ts`, the builder in `engine/gltfImport.ts`). Every model drop ends in ShaderPreview's `loadMeshFile` (preview DOM and iframe-forwarded drops, the canvas and the code panel through `fs:preview-model-file`), which is the ONE interception point. A `.glb`/`.gltf` in which the trusted-side reader finds a buildable material AND an extractable texture opens ONE dialog, and the dialog IS the confirm gate: “Build a shader from this model's materials (replaces the current shader)” / Model only / **Restore the stored shader** (offered only for a FastShaders single-GLB export, and never the focused default — see the GLB-restore convention) / Cancel. There is deliberately no “don't ask again” — replacing a shader is never remembered. Eight rules. (1) It is not offered in a study session (`isEvalMode()` keeps today's drop byte for byte, the 64 MiB pre-read gate included — `offer` is the third argument of `preReadModelGate`, so only an OFFERED `.glb` gets the 96 MiB build-path cap), nor for a model dropped WITH a shader (`pairedWithShader` on the event from the canvas's project branch, `offerBuild: false` on the preview's own combined drop) — that model pairs with the shader just imported. (2) Model only IS today's model drop (`applyModelBytes`, over the bytes already read) and fires nothing; Cancel changes nothing, the model included; Escape and the backdrop mean Cancel, and focus starts on Model only so Enter keeps the historical outcome. A model the reader REFUSES (it is stricter than GLTFLoader) is loaded model-only with an info line saying why the build was withdrawn. (3) Build commits through `commitGlbImport(project, mesh)` in projectImport.ts — the texture-stripped mesh FIRST (importShaderZip's order; the geometry no longer DEPENDS on it — `shownGeometry` derives the fallback from the live mesh — but a commit that sets the model before the project keeps the prefs re-read describing the document it is about), then the module-private `applyProjectToStore`: ONE `pushHistory`, the same restore-path sanitizers as any shared file, `fs:project-imported`, then `fs:graph-imported` (auto-fit, Preview mode cleared, Work-folder origin dropped). Undo restores the graph but never the previous model (the mesh is session-only), and the dialog says so when a model is loaded. (4) N11: more than `GLB_IMPORT_MATERIAL_LIMIT` (10) BUILDABLE glTF materials (used by a default-scene triangle primitive — `buildableMaterialIndices`, never `json.materials.length`) is blocked (Model only / Cancel) unless the toolbar's right-click setting “Allow more than 10 materials” (`fs:allowManyMaterials`, exact `'1'`) is on, in which case the dialog itself carries the confirmation; past the editor's section ceiling (`MAX_INDEX_MATERIALS`, 16) the lowest-index materials are built and the rest keep their authored materials, said in the dialog AND the report. The setting is hidden in a study session and reset by `cleanSlateForStudy`. (5) N9 is an ESTIMATE from header-read dimensions and the shared slot table, never an encode: the build REPLACES the project, so the whole 3M budget counts as free; over it the primary becomes “Import at {res} px” (the largest ladder rung under the largest planned side that fits) or disappears, and Ignore limits skips it. The builder enforces the real budget and reports what it did, and `applyProjectToStore`'s soft-cap sanitizer is the backstop. (6) N12 is `textureMemory` over the planned stored sizes, with one/other keys. (7) ONE report per build, in the canvas import note (30 s instead of 12): summary, over-max, 64 MP decode downscales, “Not imported” (occlusion — the Output has no AO channel — and the closed `GltfFeatureId` labels, never a name out of the file), and at most six per-texture outcomes (downscaled and why / skipped and why — the project's image budget and the per-image size limit are two different reasons) plus a count. Every file-supplied name is sanitised and filled through `fillTemplate`. The build is an import, so the drop-time “Convert image?” question is never asked and a remembered `never` does not apply — the recorded exception to that bullet. (8) A second drop while the dialog is open is refused with a notice rather than swapping the file under the user's cursor — EVERY model drop (an `.obj` and a model paired with a shader included, checked in `loadMeshFile` before the offer) and every shader `.js`/`.zip` on the preview (`handleDroppedFiles`, before the iframe confirm): the sandboxed preview can forge a drop and so open a dialog, but it can never answer one. The dialog is portalled through `pickPortalHost`, so it stays visible in the preview's fullscreen. The facts' `embeddedShader` stays `null`: the stored-shader fact reaches the dialog as `planGlbImportDialog`'s THIRD argument (`restoreFactOf`), not through the facts — see the GLB-restore convention. NOT run in a browser yet — see the Step 9 report's browser checks.

### Compressed glTF is decoded by three r184's own decoders, delivered as BYTES into the sandbox

- **Compressed glTF is decoded by three r184's own decoders, delivered as BYTES into the sandbox** (`utils/meshDecoders.ts` + the `FastShaders.decoders` section of loader 0.8). The files are the glTF Draco build (`draco_wasm_wrapper.js` + `draco_decoder.wasm`, 250 KB), `meshopt_decoder.module.js` (29 KB) and the Basis Universal KTX2 transcoder (`basis_transcoder.js` + `.wasm`, 585 KB), vendored under `a-frame-shaderloader/js/decoders/`. The sandbox's URL allowlist admits only blob:/data:, and its opaque origin could not fetch from the app anyway, so the TRUSTED parent pushes the decoder bytes inside the model message it already sends once per document (`handleIframeLoad` → `loadDecoderPayload(mesh.decoders, decoderAssetUrl)`; podest's parent does the same from `modelDecoderFiles`, a substring scan of the glTF JSON, never a parse). It does this only when the model needs them: primitive, teapot and march documents carry no decoder code at all (byte-identical), and decoders never ride a shader hot-swap. Each model document runs a static configure right after the loader's `<script src>`, whose resolver reads a null-prototype `window.__fsDecoderUrls`; the feed script (`fillDecoders`; podest's stage `fillDec`) mints blob: URLs into it from the pushed bytes BEFORE `setAttribute("gltf-model")`, accepting only the names `DECODER_FILES` lists (generated, never retyped), text for a `.js` and an ArrayBuffer for a `.wasm` — the SUFFIX decides — at most 1 MiB each (both twins are executed by their tests). Five rules are load-bearing.
  (1) **Draco loads through a DEDICATED LoadingManager, which is its own allowlist.** It maps `fs-decoder:/<one of three constant names>` to host-supplied URLs and everything else to an unfetchable `blob:fs-decoder-missing`, and it never touches `DefaultLoadingManager`'s modifier, which stays blob:/data:-only. The worker never fetches: DRACOLoader hands it the wasm as `decoderConfig.wasmBinary`.
  (2) **A missing decoder must fail, never hang.** In manage mode `install` sets `setDRACOLoader(null)` rather than leaving A-Frame's own loader. A-Frame's gltf-model system builds a DRACOLoader aimed at gstatic on EVERY scene, and in the sandbox its fetch lands on the allowlist's empty data: URL: the worker then never answers. With null, `GLTFLoader.parse` throws synchronously and A-Frame's `load()` try/catch turns that into `model-error` (measured 39–45 ms in Chrome, WebKit and Firefox). For the same reason a decoder is never mapped to a data: URL. A MESH decoder (Draco, meshopt) the editor's parent cannot fetch posts `fs:obj-model-error` (the translated `decoderLoadMessage`, whose `{reason}` is translated too when the app wrote it — an empty or over-1-MiB file, `DecoderLoadError.kind` — and inserted as it came for an HTTP status or the engine's own fetch error) instead of the model; podest's parent shows its own banner and posts the model WITHOUT the decoders, so the stage fails fast — and the stage's generic model-error banner then replaces the parent's more specific one (known, not fixed). **The KTX2 transcoder is the exception, and the editor's parent posts the model anyway**: it decodes TEXTURES, so a model needing only it parses fine and the loader's plugin falls back to each texture's PNG/JPEG source — suppressing it would hide a model that renders, and that DID render before 8.4 wired the transcoder in. So `!needs.draco && !needs.meshopt` takes the same `decoderLoadMessage` as an INFO line (`showDropNotice`) and then posts, podest's own behaviour; a basisu-REQUIRED model then reports the stage's own model-error, as it does on podest. `meshDecoders.test.ts` pins both branches from source.
  (3) **It installs from a wrap of the `gltf-model` COMPONENT's `init`,** not from the shader component. Podest shows models with no shader component, and its XR popup attaches the shader after the markup-baked model began loading; GLTFLoader reads `dracoLoader`/`meshoptDecoder` at parse time, which the init wrap precedes.
  (4) **TRAP: `window.THREE` is the bare three NAMESPACE.** The submodule's `build/entry.js` assigns it after A-Frame built its enriched global, so `THREE.DRACOLoader` and `THREE.GLTFLoader` are undefined on every page using this bundle. Take loaders from `AFRAME.THREE`.
  (5) **meshopt is a lazy shim, a fresh one per PARSE.** It imports the ES module (it ends in `export`, so a classic `<script>` — A-Frame's `meshoptDecoderPath` route — cannot load it) on the first decode, and it caps the decoded bytes per model at 256 MiB before allocating. Per parse is load-bearing: A-Frame's gltf-model builds its GLTFLoader once and reuses it for every `src`, so a total kept per LOADER was a lifetime budget that refused the third 100 MiB model with a message blaming it. `install` therefore wraps the loader's `parse` to swap in a new shim, and only a shim it tagged, never a decoder the page set itself. Draco's output is bounded only by the decoder's 2 GiB wasm heap (one worker).
  **KTX2 (KHR_texture_basisu) rides the same path.** The files are `basis_transcoder.js` + `basis_transcoder.wasm` (585 KB, three r184's own, Apache-2.0), pushed by the parent only when `PreviewMesh.decoders.ktx2` says the model uses basisu. Four rules are load-bearing.
  - (1) **`detectSupport` needs an INITIALISED renderer, and nothing at install time has one.** r184's `hasFeature` throws before `renderer.init()` resolves. A-Frame's own route, the gltf-model SYSTEM's `basisTranscoderPath`, calls `detectSupport` synchronously in its `update`, so it throws, and the loader must never write it. `renderstart` is no signal either, because A-Frame emits it right after calling the ASYNC `setAnimationLoop`. `install()` therefore sets a LAZY shim as `loader.ktx2Loader`. On the first KTX2 texture the shim awaits `renderer.init()`, which is memoized, so the renderer is never re-initialised, then runs `detectSupport` and then `parse`.
  - (2) **The transcode target is baked into the worker when it is created** (`KTX2Loader.js:315-321`; measured: later config changes are ignored). There is ONE KTX2Loader per document, `configure()` disposes it, and tests build a fresh loader per configuration.
  - (3) **Stock three LOSES the fallback when a transcode fails** (measured). The builtin basisu extension has already committed to the KTX2 source, so a basisu-USED model with a perfectly good PNG shows nothing. The loader therefore registers its own plugin named `KHR_texture_basisu`, which REPLACES the builtin because GLTFLoader keys plugins by name. On any failure it falls back to the core `source`, and it counts `fallbacks`/`missing`. The preview reports those counts through the forgeable `fs:model-ktx2` message (the model document's `model-loaded` listener, once per document), which raises ONE info line naming both counts — `MESH_KTX2_FALLBACK_KEY` and `MESH_KTX2_MISSING_KEY`, joined — for the model the CURRENT document was built for, once per model. One line and not two because `showDropNotice` REPLACES the notice and re-arms its single timer, so a second call from that same handler dropped the first sentence unseen while the model was already marked reported, i.e. the fallback line could never be read on a model reporting both. That fallback is the PNG/JPEG core source, never the EXT_texture_webp one.
  - (4) **The KTX2 manager CHAINS `DefaultLoadingManager.resolveURL` for every URL except the two transcoder names.** Unlike Draco's loader, KTX2Loader also fetches the IMAGE through its own manager, and without the chain a hostile `uri` would bypass the sandbox allowlist.

  The shim caps the header before transcoding: one face, one layer, ≤ 14 levels, ≤ 64 MiB, and ≤ 8192 px per side — 4096 whenever the file cannot reach a compressed target and would land uncompressed at 4+ bytes a texel, which is THREE cases read out of the same 80 bytes: the GPU has no compressed format at all; the file is ETC1S (`supercompressionScheme` 1, the u32 at offset 44) on a GPU whose only format is ASTC, which r184's FORMAT_OPTIONS can never give it (`basisFormat: [UASTC]`, `priorityETC1S: Infinity`); or the file is RAW (`vkFormat` non-zero, the u32 at offset 12), which three sends to `createRawTexture` with no transcoder, so the GPU's formats do not enter into it. UASTC_HDR narrows the same way (bptc or nothing) but its marker is in the DFD, not the header, so it is deliberately out of reach. A one-shot `console.info('FastShaders KTX2: transcoding for …')` names the chosen format, and it is how the Quest check reads ASTC.

  The XR popups (the editor's and podest's) configure explicit same-origin URLs; export pages — and a plain three.js page that configures only `DRACOLoader` — locate `decoders/` beside the loader on jsdelivr, and leave a page-configured `dracoDecoderPath` alone. Every cap reports through `FastShaders.decoders.lastError` into the model-error overlay. None of this has run in WKWebView (the `.dmg`), WebView2 or on a Quest.

### A zip the reader refuses says WHY, on every surface

- **A zip the reader refuses says WHY, on every surface** (`utils/zipReader.ts`, `engine/projectImport.ts`, `utils/zipImportNotices.ts`). Until 2026-09 `importShaderZip` swallowed every reader error, so an archive over a cap read as "no shader" on all five import surfaces. The reader now throws a typed `ZipLimitError` and `importShaderZip` rethrows it; each surface's catch calls `reportZipImportError` FIRST, which queues LimitModal's `zip-limit` notice — a refusal with NO Ignore-limits checkbox, because that checkbox cannot lift a reader cap. Only non-zip errors fall through to the surface's own (now translated) text. Four rules are load-bearing. (a) The invariant is "the reader opens anything the writer emits", which is why the SUM cap is `MESH_MAX_BYTES` + 32 MiB: an image rides a bundle three times (the inlined module, the project block and `images/`), so a legal soft-capped bundle is ~72 MiB and 64 MiB refused the app's own exports (`zipLargestBundle.test.ts` round-trips it). With Ignore-limits a bundle is unbounded — that is the export pre-flight's job, not the reader's. (b) The cap is also a literal in podest.html, and `zipReader.test.ts` fails when the two differ, so they move in one commit. (c) The pre-read gate (`MAX_ARCHIVE_BYTES`) refuses a huge file before `file.arrayBuffer()` allocates it; the deflate-bomb defence is still the streamed counter, not the number. (d) A refused MODEL inside an otherwise good zip is information, not a refusal: the shader loads and the canvas import note gets a `zip-model-skipped` line whose `{reason}` is the model's own `meshRefusalMessage`, so a model over `MESH_MAX_BYTES`, or one whose container `validateMeshBytes` rejects, gets the advice a preview drop gets (Draco, meshopt AND KTX2 models all load — the decoders ship); a model-ONLY zip whose model is refused throws `ZipModelSkippedError`, reported as that line. `isZipLimitError`/`isZipModelSkippedError` check `name` as well as `instanceof`, because the suite runs `isolate: false` and one file resets modules. The code panel no longer refuses a model file either: `importScriptFile` hands it to the preview through `requestPreviewModelLoad`, as the canvas does.

### An export FastShaders could not open again asks first (N1, `utils/exportPreflight.ts` + `Modals/ExportPrefligh…

- **An export FastShaders could not open again asks first (N1, `utils/exportPreflight.ts` + `Modals/ExportPreflightModal.tsx`).** The invariant is that the reader must open what the writer emits, and nothing checked it: an export whose entries summed past `zipReader`'s `MAX_TOTAL_UNCOMPRESSED`, or that held more than its `MAX_ENTRIES`, downloaded fine and then failed on every import surface and in Podest. EXPORT, NEW's save-first and the desktop Work-folder Save therefore build the export through `buildShaderExportChecked(asks)` (which delegates to `buildShaderBundleChecked` for the bundle format), which compares `bundle.unpackedBytes` and `bundle.entryCount` with the reader's size and entry caps and, only when one is crossed, shows one dialog: "Export without the 3D model ({model} MB)" / "Export anyway" / "Cancel". Six rules are load-bearing. (a) **The size is what the READER counts**: the sum of the entries' data (STORE, no directory entries) or the bare `.js` length, computed by `buildExportBundle` from the same entry list it writes, so the prediction cannot drift from the file. `<=` fits, because readZip's three cap checks are all strict `>`; `exportBundle.test.ts` and `exportPreflight.test.ts` pin both. (b) **The model button appears only when a model is in the bundle AND dropping it brings the bundle within BOTH caps**; otherwise the dialog offers just Export anyway / Cancel. The answer is ONE build (`buildShaderBundle({ includeMesh: false })`, the same expression the EXPORT right-click checkbox drives). It never writes the session `exportIncludeMesh` flag, so the next export asks again. (c) **Cancel on NEW's save-first abandons NEW** (the user asked to save first), and the pre-flight must finish before `newGraph()`, which removes the preview model. On the Work folder, Cancel reports "Save cancelled — nothing was written.", and the pre-flight runs BEFORE the target name is derived, since dropping the model can flip zip→js. (d) **The study never sees it.** EXPORT branches to EvalFinishModal first, SusModal builds the package with bare `buildShaderBundle()`, and the wrapper skips the dialog under `isEvalMode()`, because NEW's save-first is the one study-reachable download (research doc §8) — the one `isEvalMode()` gate in Phase 1's notices. (e) Sizes print through `formatMiB` (`utils/formatSize.ts`; rounded UP, so 96 MiB + 1 byte reads "96.1"/"96,1" and never equals the limit). Inside the soft image budget the SIZE cap cannot fire: a model is ≤ `MESH_MAX_BYTES` by construction and 3M chars of images add about 8.3 MB (each DISTINCT image rides the bundle about three times — inlined in the module, in the project block, and as its `images/` file; a Ctrl+D copy shares the module's inlined payload and the `images/` file, and adds only its own project-block copy). It is reachable only PAST that budget: by ticking Ignore image size limits, or by answering "Add anyway" on the project image-budget notice (`image-total-cap`, `canProceed: true` — drop, paste, Ctrl+D and saved-group instantiate all raise it, and its "Add anyway" needs no checkbox), plus the Phase 6 desktop caps. A manual size test therefore needs one of those two, a model, and enough large images to pass 96 MiB (a 64 MiB model plus at least 21 DISTINCT 600K-char images, about 1.65 MB each; duplicates would take far more). (f) **The ENTRY cap is reachable with default limits, at any size**: `collectImageFiles` writes one `images/` entry per DISTINCT image (MIME + decoded bytes), so more than 510 distinct images (more than 509 with a model riding along) cross readZip's 512 `MAX_ENTRIES` — small images stay far inside the 3M budget. Ctrl+D and paste copies carry byte-identical payloads and add no entry, so a manual test needs distinct images, not duplicates. `ExportBundleSize.entryCount`/`entryCountWithoutMesh` are counted from the same entry list the zip is written from, the dialog then names the count in FILES rather than MB (and adds a second sentence when both caps are crossed), and `exportPreflight.test.ts` proves the 510/511 boundary against the real builder and the real reader. The one reader cap the pre-flight does NOT check is the 512-byte entry NAME. Image and model stems are capped at 64 characters, but the `.js` entry is named after the shader (`shaderBaseName`), whose name is uncapped, so a shader name of about 510 characters or more makes every ZIP export unreadable (reproduced: `readZip` throws `name`); a bare `.js` export never goes through the zip reader, so none of the three caps applies to it. Every `await` between the click and `downloadShader(bundle)` must stay a microtask or the dialog's own click — a timer or awaited I/O there would cost the anchor download its transient activation in Safari. **The desktop variant is non-blocking** (Phase 6). The desktop build reads up to `DESKTOP_MAX_TOTAL_UNCOMPRESSED` (256 MiB), so `planExportPreflight`'s default limit is `READ_MAX_TOTAL_UNCOMPRESSED` and the blocking dialog applies only above 256 MiB there. An export between the web cap (96 MiB) and the desktop cap is delivered and THEN announced by the import-note line `export-desktop-only` ("Saved (… MB). Only the desktop editor can open it again — Podest and the web editor open up to 96 MB."). `announceExportDelivered(bundle)` posts it from `downloadShader`'s tail (it takes the delivered `ShaderExport`, so a `.glb`'s own report lines ride the same note), after the anchor click (so EXPORT and NEW's save-first both get it, and neither calls it itself), and from the Work folder's write success path — never before delivery, so a cancelled or failed save cannot claim one. It takes a BYTE COUNT (`planDesktopOnlyExport(sizeBytes, readLimit, webLimit)`), so a later single-file export can pass its own size and get the same line. It is a no-op on the web build (read cap = web cap) and in a study session. `importNote.test.ts` pins the after-delivery order on all three surfaces. **On the web the dialog points at the desktop app** (DesktopAppNote) when `exportLiftedByDesktop` holds — the refusal is the SIZE cap alone and the export fits 256 MiB; the entry cap is 512 on both builds, so it never earns the pointer. **The single-GLB export has its OWN variant** (`planSingleGlbPreflight`), because a `.glb` reopens through a different path than a zip: the re-import applies `GLB_READ_MAX_BYTES` to the FILE, and nothing is "unpacked", so the zip wording does not apply. Crossing it opens GlbExportModal's too-large view — Cancel / Export anyway / Export WebP only (offered only when dropping the PNG-JPEG copies fits) / **Export without KTX2 copies** (only when dropping THOSE alone fits — `sizes.noKtx2`, the same file measured without them) / Export as .zip instead (only when THAT bundle passes `planExportPreflight`). The repacker's own caps (64 embedded images, 16 MiB each, 64 MiB together) are HARD refusals in the build, never an "Export anyway", and they surface in the failed view. The GLB build awaits image encodes, so it cannot keep the microtask-only rule above: when `navigator.userActivation.isActive` is false after the build (a missing API counts as lapsed) the modal's 'ready' view supplies a fresh click — the Safari anchor-download rule — while `prepared.build(mode)` stays SYNCHRONOUS after the last answer. The Work-folder Save (`delivery: 'write'`) never needs it. **The KTX2 copies are an OPT-IN of that same export** (Phase 8): the popover's row writes the session-only `exportKtx2`, `buildShaderExportChecked` passes `{ encoder }` into `prepareSingleGlb` only when that flag AND a registered encoder are both there, and no build registers one — so today the row does not render (`hasKtx2Encoder()`) and every `.glb` is exactly the file Phase 7 wrote. When they ARE asked for, the composer decodes each written texture's payload to RGBA8 (`utils/ktx2Pixels.ts`, DOM-only, injected in tests) and encodes it SERIALLY through `encodeKtx2Checked`, keyed by the texture index the FIRST measure assigned. **The SIZE gate runs before the decode, never after**: `ktx2Eligible` is asked with the node's stored `plan.payloadSizes` dims — the same ones `encodeGlbFallback` measures against — and a refusal is pushed to `ktx2Skipped` with no `pixelReader` call, because `encodeKtx2Checked` would refuse an over-4096 texture only once the whole bitmap was RGBA8 in memory (~0.75 GB at 8192², retained in `pixelsFor` for the rest of the loop, and `values.width`/`height` reach 8192 with no restore path validating them). Those dims are passed INTO the reader too, which refuses a bitmap of any other size, so a payload free to lie about its dimensions is refused before `getImageData`; every failure is collected as a report line and never fails the export, so the worst case is the file without copies. The repacker writes each as an EXTRA `KHR_texture_basisu` source beside the texture's own image, `extensionsUsed` only — never REQUIRED, never replacing the core `source`, and never an `assets` target (the Image-node decision) — so a viewer without a transcoder is unaffected. An absent or empty `ktx2Sources` map writes byte-identically to before (pinned), which is what keeps every Phase 7 digest valid.

### Model animation (`gltf-anim`)

- **Model animation (`gltf-anim`)**: a dropped `.glb`/`.gltf` carrying clips PLAYS, in the editor preview AND on podest. A-Frame core ships no animation-mixer (that component lives in `aframe-extras`, deliberately not bundled), so `gltf-model` parsed the clips, hung them off the object3D as `model.animations`, and nothing ever read them — an animated model loaded as a static rest-pose mesh. `GLTF_ANIM_SCRIPT` in `tslToPreviewHTML.ts` registers the mixer component on `#preview-entity` for every MODEL geometry (an OBJ simply reports no clips); `public/podest.html` carries a hand-minified twin (`pushGltfAnim`, beside `pushFitBounds`, pushed into both its stage doc and its VR popup) and `previewGltfAnim.test.ts` runs BOTH through the same assertions — the `fit-bounds` drift-guard pattern, and the only thing keeping the copies honest. The contract is `fs:anim-set {playing, inPlace, clip, time}` / `fs:anim-seek` down, `fs:anim {has, duration, canInPlace, name, clip, clips}` / `fs:anim-time` up. **Controls**: a second bottom-left pill (▶ play/pause, ◎ in-place, ☰ clips) plus the scrubber running to the display cluster, present only while `fs:anim` reports a clip. **The ☰ is a plain visible button and the clip list has NO minimum-clip gate** — both are corrections of the same mistake. It shipped first as a right-click-only context menu on the ▶, suppressed below two clips; a user reported it simply "does not work", and both halves of that gate explain it: on a single-clip file right-click did nothing and fell through to the browser's own menu, and the handler sat on the 28px ▶ alone so a near-miss did the same. A control that exists on some models and not others, reached by a gesture that silently no-ops, is indistinguishable from a broken feature. Right-click now works anywhere on the PILL and long-press is bound to the pill too, but they are shortcuts — the button is the affordance. On a single-clip file the list still answers a real question (what is this clip called). `Preview/AnimClipMenu.tsx` for the editor; podest builds its own `#anim-clips`. **Six things are load-bearing.** (1) **`fit-bounds` must NOT bake an animated model** — the bake moves each node's world matrix into its vertex data and then flattens every local matrix to identity, which is exactly the state an AnimationMixer overwrites, so a node-TRS clip applies its keyframes a SECOND time and the model tears itself apart; morph clips break by a different route, since `applyMatrix4` transforms `position` and `normal` but NOT `morphAttributes`. Animated models therefore take the Object3D fallback a SkinnedMesh already takes, with the same documented cost: `positionGeometry` stays in the model's AUTHORED units, so position-driven presets/textures/noise defaults — all tuned for the ±0.8 the pre-normalized built-ins deliver — are mis-scaled on it. (2) **That fallback measures with `Box3.setFromObject`, and swapping it for an entity-frame union of the meshes' own boxes was TRIED and REVERTED.** setFromObject is world-axis-aligned, so it folds in `#preview-entity`'s resting tilt and `#spin-parent`'s live rotation and can frame an animated model up to ~1.7× small depending on the angle it loaded at — a real flaw, and the obvious fix makes things worse: a local AABB is never larger than the world one, so EVERY animated model grows, and the shortfall is not bounded by the rotation, because setFromObject also expands by `Points`/`Line` primitives and by an InstancedMesh's per-instance spread, none of which a mesh-geometry union sees. A model carrying any of those measures far too small and scales up hard (reported from the field as "the model is super large"). Slightly small beats blown up; `previewFitBounds.test.ts` pins the flaw, including the √2 case, so the trade is deliberate rather than forgotten. (3) **In place = FREEZE the root track, never delete it.** The root-motion track is the `.position` track of the TOP-MOST animated node — depth-from-root over the nodes the clip actually targets, resolved with `THREE.PropertyBinding.findNode` (the mixer's own lookup, so it can't disagree, and it handles the `.bones[x]`/`parent/child` name forms a plain string match would miss) — not "a direct child of the scene root": in a rigged glTF the translation lives on the hips, several levels inside an Armature carrying no tracks of its own. Every keyframe takes frame 0's value, on all three axes; DELETING the track would leave the node wherever the last mixer write put it, so toggling mid-playback would strand the model at an arbitrary offset instead of returning it to where the clip starts — which is the pose `fit-bounds` measured its framing from. Both clips are held at once and the toggle swaps between them, so `__inPlaceClip` must not mutate the authored one (`clip.clone()` deep-copies times+values). A clip with NO root translation returns null → `canInPlace: false` → the toggle renders disabled, because a live button that does nothing reads as broken. (4) **A clip change re-reports, it does not just move an index** — duration and `canInPlace` are properties of the CLIP (an Idle usually has no root translation where a Walk does), so `selectClip` re-derives both and re-reports, which is what resizes the scrubber and disables the toggle; it restarts at 0, because a playhead is a position in THIS clip and carrying 3.2 s into a 1 s idle lands on a clamp that reads as the picker having chosen the end. An out-of-range index CLAMPS to 0 rather than disabling playback — the parent replays a remembered index onto a fresh stage and the model may have changed under it. `update()`'s clip check needs `typeof oldData.clip === 'number'`: A-Frame's first `update()` gets an EMPTY oldData, and a bare `!==` reads `undefined !== 0` as a clip change and resets the playhead on every unrelated play/pause push. (5) **`seek()` is the one place a time reaches the action, so the non-finite guard belongs there** — the clamp is two comparisons and NaN fails BOTH, so it would sail through and poison the mixer clock for every later `update()`. (6) **The playhead survives a stage rebuild.** Every shader edit swaps the editor's `srcDoc`, and podest rebuilds its stage on device loss / the stall watchdog / the ~4.4 h time fold; both parents keep the last reported time (and clip, and both toggles) and replay them on `fs:anim`, clip FIRST since a clip change rebinds at 0. Time reports are throttled to ~30Hz and painted IMPERATIVELY onto the thumb, never through React state. **Presentation mode**: podest's controls ARE in the `:root.is-present` hide rule (entering ⛶ sets `presenting()`, so one rule covers fullscreen and the remembered mode) — unlike the mic light, which stays because it is a privacy indicator, playback chrome over the artwork is exactly what presentation mode exists to remove. The EDITOR's controls deliberately stay up in its own fullscreen, like the rest of its floating clusters. **Known limits, all deliberate**: the exported `.js`/zip does not animate (the zip carries the model bytes, so the data is there — only the mixer is missing); the XR popup gets the component and autoplays the baked defaults, with `post()` short-circuiting on `window.parent === window` so a top-level document doesn't message itself 30×/s; and **wiring the Output node's Displacement channel displaces in BIND/REST space** — which is a narrower caveat than it looks, and the reverse of what this line used to claim. The old claim was that because `NodeMaterial.setupPosition` ASSIGNS `positionNode` over `positionLocal` AFTER stacking `skinning()`/`morphReference()` (`NodeMaterial.js:779`/`:785`/`:813`), displacement DISCARDS skinning and morph animation. That was read from the source call order and never run; the source order is not the emission order. `skinning()`/`morphReference()` are void nodes that append their `positionLocal` writes to the stack DURING their own setup, and `StackNode.build` builds a snapshot first and the nodes appended during that pass second, so the skin/morph writes generate LAST. MEASURED against r184's real `GLSLNodeBuilder`: with `positionNode = positionLocal.add(...)` the vertex shader emits `positionLocal = position;` → the displacement → then `bindMatrix * vec4(positionLocal, 1)` and the bone-weighted skin write (or, for morphs, `positionLocal *= baseInfluence; positionLocal += delta * influence`). Skinning and morph CONSUME the displaced position; nothing is discarded. What IS true: the displacement expression sees the RAW `position` attribute and the REST-pose `normalLocal` (skinning reassigns `normalLocal` only after the displacement has read it), so the offset is baked into the rest pose and then carried by the skeleton rather than computed on the deformed surface — and a morph's `*= morphBaseInfluence` scales that offset too. Node-TRS animation is unaffected either way (it happens on the Object3D, not in the shader). This ordering is an implementation detail of `StackNode`'s two-pass build, NOT a documented three contract, so it wants a regression pin rather than an assumption.
