### Distance fields (`sdf` category, 2026-09-02, widened and consolidated 2026-09-03)

- **Distance fields (`sdf` category, 2026-09-02, widened and consolidated 2026-09-03)** — Inigo Quilez's canonical forms as module helpers, with `cpuEvaluator` carrying the same maths for the on-node labels (value for every node; ranges only where an honest cheap interval exists — `sdCircle`, `sdCombine` union/intersect/subtract, `sdfMask`, `sdfModify` — the rest report `…` rather than a wrong bound). Negative inside, zero on the edge, positive outside; the 2D ones take a CENTRED position (wire `uv` through `sub(0.5)`), box extents are HALF-sizes, everything axial stands along Y (turn it with a Transform upstream). PRIMITIVES: `sdCircle` (a sphere for a vec3), `sdBox` (ONE def for 2D and 3D — the helper is chosen by the wired position's WIDTH at emission, `sdBox2`/`sdBox3`, both parsing back to the one def; `round` inflates the corners. **Half-extents are ONE vec3 socket** since 2026-09-09, so the dispatch now changes only WHICH COMPONENTS the helper reads and not the call's arity — both variants take (position, half size, rounding) and the flat case ignores `.z`, where before it carried a Half depth socket that meant nothing), `sdTorus`, `sdCylinder` (rounded, capped), `sdCapsule` (vertical), `sdCone` (capped, two radii), `sdPlane` (half-space, normal + offset; the normal is **one vec3 socket** since 2026-09-09, and it is the node whose default could NOT be broadcast from a scalar — a normal must point somewhere and (0,1,0) is not uniform — so the DEGENERATE case carries it: an unwired socket emits the bare 0 and the helper reads a zero-length normal as "up", which also stops a wired zero vector normalizing to NaN), `sdOctahedron` (exact), `sdStar` (n points, sharpness m — m = n is a regular polygon; uses TSL's two-argument `atan`). OPERATORS over the DOMAIN (p → p′): `sdfTransform` (**ONE vec3 socket per group** since 2026-09-09 — Move, Turn in degrees, Scale — where each was three floats; wire a Vec3 node, since an unwired group emits its scalar identity and there is no vec3 editor widget. **Scale is NON-UNIFORM** as of the same change: it divides p per axis, so the field is a BOUND rather than a true distance whenever the components differ — multiply back with Modify: scale using the SMALLEST component, and expect to lower the Raymarch node's Step scale on a strongly anisotropic shape), `sdfRepeat` (grid, ROUND form — the mod form disagrees between GLSL and WGSL for negative inputs; **vec3 Spacing and Limit**, same consolidation as Transform — spacing 0 on an axis still leaves that axis alone and limit 0 is still endless, per component), `sdfRepeatPolar` (n copies about Y, single evaluation — the sector seam on asymmetric shapes is documented), `sdfMirror` (**one vec3 socket** of 0..1 fold weights since 2026-09-09 — and its unwired DEFAULT changed with it, from (1,0,0) to (1,1,1). Unlike Plane there is no degenerate value to hang the old default on, because 0 is a meaningful weight (fold nothing) and so cannot double as a sentinel; folding all three axes beat folding none because a freshly dropped node that visibly does nothing reads as broken), `sdfDeform` (MODES twist / bend / elongate; `amount` stays a scalar — it drives twist and bend and is genuinely one number — while elongate's three stretch axes became **one vec3 socket**). Over the DISTANCE (d → d): `sdCombine` (MODES union / subtract [a minus b] / intersect / xor — IQ's k-NORMALISED quadratic smin, k the fillet thickness in distance units, floored at 1e-6 so k = 0 is the HARD op and never a division by zero; xor is exact and takes no k), `sdfModify` (MODES round / shell / scale). BRIDGES: `sdfExtrude` (2D distance + position → 3D, along Z), `sdfRevolve` (position → the 2D profile plane, about Y), `sdfMask` (distance → 0–1 coverage with a linear edge; deliberately not `smoothstep`, whose equal edges are a WGSL error at width 0). **Two folds carry a migration**: `sdBox2`/`sdBox3` → `sdBox` and `smoothUnion`/`sdSubtract` → `sdCombine` — `registry/legacyNodeTypes.ts` migrates the old REGISTRY TYPES on every restore path (values kept, ports were kept so every edge survives), while their old CALL NAMES in an already-exported `.js` parse back through `HELPER_ALIASES` (the 2013 mix-form `smoothUnion(a, b, k)` lands on Combine's union with the same k — a slightly different fillet, accepted). The whole family was rendered end to end in one shader on the real WebGL2 backend (2026-09-03) — expect bound-only-field cracks on deformed / scaled / smooth-combined surfaces, which is what the Raymarch Output's Step scale is for.

### A vec3 INPUT SOCKET emits its unwired default as a BARE NUMBER, and the helper broadcasts it

- **A vec3 INPUT SOCKET emits its unwired default as a BARE NUMBER, and the helper broadcasts it** (`sdfTransform`, `sdfRepeat`, `sdBox`, `sdfDeform`, `sdPlane`, `sdfMirror`, 2026-09-09). The obvious form — having codegen emit `vec3(0)` for an unwired vec3 port — is the trap: `codeToGraph` reads that as a real Vec3 CONSTRUCTOR and mints a node for it, so the graph grows by one node on every Apply (MEASURED: sdfExtrude's round trip went from 3 nodes to 4, with `errors: []` and a correct picture throughout — the `unwrapScalarWiden` class of defect). So emission is unchanged — an unwired port still emits its scalar default, and `unwiredDefaults.test.ts`'s whole-registry snapshot moved by exactly the two lines whose arity changed — and the broadcast happens inside the helper body, where `vec3(t)` fills from a float and is the identity on a vec3. That last fact is the one everything rests on and it is the kind that yields perfect-looking source and a blank preview, so `sdfVecSockets.test.ts` builds it against the REAL `three/tsl` rather than asserting on text. `cpuEvaluator` carries its own copy of these formulas, so it has a matching `vec3Input` that broadcasts an unwired scalar the same way — without it the card's live numbers disagree with the picture for every unwired group, reading Box's 0.5 into x alone as a flat sheet where the shader draws a 1x1x1 box. The UX consequence is deliberate: there is no vec3 editor widget, so a consolidated group has no inline number boxes and a translation costs a wired Vec3 node. **A group whose unwired default is NON-UNIFORM cannot use this shape as-is** — one scalar broadcasts uniformly, and emitting a `vec3(a, b, c)` literal is the graph-growing trap above. Two of the six hit that: Plane carries its (0,1,0) in the helper's degenerate branch, and Mirror simply changed default. A third case would want stored values that can hold a vector, which is a real feature (it is also what a vec3 editor widget needs) rather than a tweak.

### Helper VARIANTS — one def, several emitted helpers, chosen by `values.mode`

- **Helper VARIANTS — one def, several emitted helpers, chosen by `values.mode`** (2026-09-03; `sdCombine`, `sdfModify`, `sdfDeform`). A def with `modes: { values, default, labels, symbols? }` keeps its DEFAULT mode's helper as its `tslFunction` and registers the others as table entries carrying `alias: { type, ports?, values: { mode } }` (a variant may take FEWER arguments — `sdXor` has no smoothness, the default `sdfTwist` has no stretch — so `helperCallPorts` is what both engines map arguments by). The mode lives in `values.mode` and NEVER in `defaultValues` (on a ShaderNode that map is the socket list, and `unwiredDefaults.test.ts` refuses a string there); `modeOf` reads it through the closed vocabulary with the default as the fallback, so junk from a `.fastshader` can only ever select a real helper and an ABSENT key is the default — which is what keeps a graph saved before a mode existed emitting byte-identically. `helperNameFor` is the ONE place the callee is chosen; the variable is named after the DEF (`sdCombine1` whatever the mode), never after the helper. The settings menu (`NodeSettingsMenu`) offers a Mode `<select>` for any def with `modes`, and ShaderNode draws the mode's symbol as a chip (bottom-left, the formula chip's mirror) so a Combine set to subtract is distinguishable from one set to union on the canvas — the header shows the var name and the rows the operands, so nothing else would tell them apart. Not mirrored into NodeVisual: `mode` is not a `defaultValues` key, so the replica can never be handed one (the formula-chip rule). `sdfModes.test.ts` round-trips every mode of every multi-mode def byte-identically and pins that helper names are reserved from the namer.

### Raymarch Output (`raymarchOutput`, 2026-09-03) — surface AND volume marcher in ONE node

- **Raymarch Output (`raymarchOutput`, 2026-09-03) — surface AND volume marcher in ONE node** (it replaced the separate SDF Output and Volume Output the same day; nothing shipped in between). Category `output` (moved there from `sdf` on 2026-09-09 — see the registry counts above), its own flow type and component (`nodes/RaymarchOutputNode.tsx`, `MARCH_NODE_CONFIG`, the Output node's chrome via OutputNode.css, tile `MarchOutputCardContent`, footprint in `layoutEngine`). Sockets: **Surface** Field (sphere-traced to a hit), Color, Emissive; **Volume** Density (integrated front to back), Glow; **Sky** Background; **Settings** Steps 64, Step size 0.03, Epsilon 0.002, Bend 0 (gravity: the direction is pulled toward the origin by `bend·step / max(r², 0.01)` each step), Horizon 0 (a ray inside this radius is absorbed: alpha 1, black), **Window 1** (the radius of the sphere the preview renders through — LARGE puts the camera INSIDE it, the material is double-sided and the march starts at the camera on a back face, so the sky fills the view), **Field radius 1** (outside it a pure-surface march jumps straight to that bubble). It DRIVES when Field OR Density is wired (`drivingMarchOutput`, the ONE predicate: PreviewLink's wire, the preview's window `MARCH_WINDOW_GEOMETRY` = `'marchSphere'` sized by `marchWindowRadius` and never persisted, `marchMaterialSettings`' double side, the A-Frame tab's `<a-sphere radius>`, the cost seeds, useSyncEngine's badge). **Emission is ONE IIFE returning ONE vec4** (final RGB + coverage) with all shading INSIDE — measured on r184: a `struct` return recursed to a stack overflow, a `mat4` pack mis-typed, and outer `.toVar()` variables written from inside a Fn have no stack — so the surface is lit inside the march by a fixed key + ambient lambert over the gradient normal (four Field taps) and the result goes out as `{ color: color(0x000000), emissive: rm1Col, roughness: float(1) }`; the scene lights do not reach a marched surface (a known regression from the old SDF Output's normal channel, accepted for one node). Per channel `const rm1<Channel> = …`: a `Fn(([p]) => …)` (Background: `Fn(([dir]) => …)`, the FINAL bent direction in world space) when the chain depends on the scope's root, a captured identifier otherwise, `color(0x…)` for the Color swatch, a literal fallback when unwired; the numbers ride `const stepSize = float(…)` lines inside the IIFE (eps, bend, horizon, win, fieldR) so codeToGraph reads them back (`MARCH_PARAM_HANDLES`); a bend/horizon at 0 and unwired emits no steer/absorb line. Field-only advances `max(max(d, eps), gap)` (sphere tracing, plus the jump to the field bubble); any Density switches to fixed `stepSize`. `Discard(rm1.w < 0.01)` only when NO Background is wired. `raymarchOutput.test.ts` pins surface / volume / both emission and byte-identical round trips; `marchWindow.test.ts` the window, the `<a-sphere>`, double side and the camera start. **The VR popup renders what the PANE renders**: `handleOpenVR` passes `previewGeometry` + `marchWindow`, never the persisted Model choice — that choice is PARKED while a march drives, and passing it projected the black hole onto the teapot in VR (2026-09-03); `marchWindow.test.ts` pins the call and the xr document's window sphere. The cost pill aims at the driving node (`costFocusId`, above). Per-step partition: `utils/sdfPartition.ts` (`MARCH_SCOPES`, `marchPartition`). Cost: Field × (steps + 3), Density and Glow × (steps − 1), + 16 — plus Field × 5 while Occlusion is on and Field × 24 while a soft Shadow is on. **The march's own LIGHT section (2026-09-03)**: `lightX/Y/Z` (the key direction, default 0.6 0.8 0.5), `lightColor` and `ambient` (colour swatches or captured chains — declarators `rm1LightColor`/`rm1Ambient`; an untouched socket emits NO declarator and the literal 0.85 / 0.15 greys inline, so an untouched node shades exactly as the fixed light did), `ao` (IQ's 5-tap occlusion along the normal, unrolled, scaling the AMBIENT only; 0 = off and no extra taps), `shadow` (a second `Loop(int(24))` from the hit toward the light — penumbra = closest miss ÷ (travel × softness), scaling the KEY only; 0 = off), and `stepScale` (multiplies the sphere-trace advance, never the jump to the field bubble — lower it on bound-only fields: deformed, scaled, smooth-combined). All six ride `const <name> = float(…)` lines inside the IIFE (`MARCH_PARAM_HANDLES`), and the parser takes the FIRST `Loop(int(…))` as Steps — the shadow loop is a second one and must not overwrite it. The scene lights still never reach a marched surface (one vec4 return); this section is what the Light dropdown is to an ordinary shader. **The node shows its MAIN sockets only** (2026-09-04): Field, Color, Density and Background are exposed by default (`MARCH_DEFAULT_EXPOSED`, utils/exposedPorts.ts — the node is in `usesExposedPorts`); **Emissive and Glow left that set on 2026-09-09** (owner request), each being the second channel of a surface and of a volume — reached for once the shape is on screen — so they start hidden with the numbers and the light settings, and every number and light setting is hidden until ticked in its own right-click menu, `menus/RaymarchSettingsMenu.tsx` — the Output's `ShaderSettingsMenu` shape with VALUES: each row is a show-socket checkbox plus the setting's editor (a number field with the node's step and clamp, or a colour swatch), grouped as the node groups them. Hiding a socket drops its wires (`toggleExposedPort`) but KEEPS the value — a setting applies whether or not it is wired, and emission reads every value regardless of exposure — the one place this differs from the Output, which clears a hidden channel's value because its emission is exposure-gated. A wire landing on a hidden setting exposes it (`autoExposeConnectedParamPorts` + `exposeConnectedTarget`), the node re-measures its handles on the exposed set (`useUpdateNodeInternals`), a section with every socket hidden is skipped, and the palette tile shows the default set. `raymarchExposure.test.ts` pins all of it. Which Raymarch Output drives is the ACTIVE SINK (several outputs, one active — see that convention): a flagged Raymarch Output drives even with nothing wired (it then emits the "nothing wired" sentinel), a flagged plain Output silences every march, and a document with no flag keeps the historical rule (the first WIRED march, else the first Output). **Limits, deliberate**: no depth write; only `positionLocal`/`positionGeometry` are position roots and `rayDirection` the direction root; a node feeding two per-step sockets is emitted into both Fns and parses back as two nodes; `rayDirection` is a MODULE HELPER (`moduleHelpers.ts`) and the Image node's `dir` input (equirect sampling, LAST in its inputs so the splice order is unchanged) is how a sky image reaches Background. **Predecessors** (2026-09-02/03, both folded into this node within a day, neither ever shipped): an **SDF Output** (`sdfOutput` — surface marching only, rendered through a 2-unit `sdfBox` window, driven by Field alone) and a **Volume Output** (`volumeOutput` — density/emission/background). Nothing on disk carries either any more: no `SdfOutputNode.tsx`, no `sdfOut1`/`volOut1` emitted variable bases, no `sdfOutput.test.ts`/`volumeOutput.test.ts`, no `SDF_WINDOW_GEOMETRY`/`VOLUME_WINDOW_GEOMETRY` — so a comment, a memory note or a commit message naming one is describing text, not a file. The ONE survivor is codeToGraph's local `sdfOutputId`, which holds the Raymarch Output's id and is only named that way because renaming it is churn across nine call sites in the middle of a parser (it says so in a comment beside itself). Two of their rules read plausibly and are WRONG for this node: the window is a SPHERE (`MARCH_WINDOW_GEOMETRY` = `'marchSphere'`, and an `<a-sphere radius>` on the A-Frame tab), not a box; and it DRIVES on Field **or** Density (`drivingMarchOutput`), not on Field alone.
