### English is the DEFAULT UI language

- **English is the DEFAULT UI language** (`fs:lang` fallback `'en'`, 2026-09-08). It was Latvian from 2026-08-29, on the reasoning that this is a Latvian research project whose user study runs in Latvian — but the study arms carry their OWN language switch on the consent dialog, so that need is met without starting every other visitor in a language they may not read. A preference stored before the change still wins, so no existing session flips. The toolbar button labels the language it switches TO ("LV" while English is on), so it is an ACTION and carries no `aria-pressed` — a flipping label beside that attribute reads as a contradiction in a screen reader, the same trap the WGSL/GLSL toggle documents. The eval consent dialog carries its own copy of the switch: it is modal, so the toolbar's button sits unreachable behind the backdrop, and a consent form nobody can read in their language is not consent. `i18n.test.ts` pins both the fallback and the action-style label.

### Latvian i18n is a display-only overlay

- **Latvian i18n is a display-only overlay** (`src/i18n/`): node types, TSL identifiers, generated code, and `data.label` stay canonical English — canvas node headers deliberately show the generated varName (`mul1`), so bilingual "Latviešu (English)" labels appear only where you pick/read about a node (Add-node menu, content browser, tooltips, settings menus, node designer). `language: 'en' | 'lv'` lives in the store, persists to `fs:lang`, stamps `<html lang>`, and is toggled by the Toolbar LV button; missing translations fall back to English. **The two output nodes render their own markup, so they do not get ShaderNode's `portLabel` path for free** — `OutputNode`, `RaymarchOutputNode` and their tile replicas in NodePreviewCard each translate the header (the Latvian node name, `formatNodeLabel(…, false)`), the section labels (`t()`) and the socket labels (`portLabel`); they printed raw English until 2026-09-11, and `outputNodeI18n.test.ts` pins all four files plus a Latvian entry for every label they draw.

### Node search is RANKED, and `description` is part of the corpus

- **Node search is RANKED, and `description` is part of the corpus**: `nodeMatchRank` in `nodeRegistry.ts` is the ONE match+order rule, shared by the AddNodeMenu (`searchNodes`) and the ContentBrowser (`rankDefs`) so both surfaces order a query identically. Tiers, lower wins: exact name (label / type / `tslFunction` / Latvian label) → name prefix → name substring → the `Also: …` alias tail → English prose → Latvian prose; `NO_MATCH` filters out. Ties keep registry order (stable sort). This exists because results used to come back in raw registry order, so a node that merely MENTIONED the query in its prose could outrank the node actually named that — writing "speed multiplier" into the Time description put Time above Multiply for "multip". So: keep UI-instruction wording out of `description`, put search aliases in the `Also:` tail (`displayDescription` strips it from the UI), and never let prose repeat another node's name casually. `nodeSearch.test.ts` pins the ordering and sweeps every description for name collisions.

### Hiding an unfinished node is an ADD-SURFACE filter, never a registry filter

- **Hiding an unfinished node is an ADD-SURFACE filter, never a registry filter** (`registry/editorVisibility.{ts,json}` + node-editor.html's **In editor** checkbox column). The JSON lists what is HIDDEN — default-visible, so a node added tomorrow appears without anyone remembering the file exists; an allow-list would make every new node invisible until someone edited it, which is the failure nobody would think to look for. `NODE_REGISTRY` and `getAllDefinitions()` keep every definition, so a hidden node still resolves for `codeToGraph`, `graphToCode`, `cpuEvaluator`, `loadGraph`, the built-in textures/presets that contain it, the Node Designer (you hide a node precisely so you can finish designing it) and node-editor.html itself — which is where it gets switched back on. Filtering the registry instead would turn every saved `.fastshader` holding that node into `unknown` nodes. **Exactly two accessors carry the filter** — `getEditorDefinitions()` (which `searchNodes()` also ranks over, so the search box can't type a hidden node back into existence) and `isTextureHiddenFromEditor` — plus `categoryEmptiedByHiding()`, which drops a content-browser tab whose every node is now hidden (guarded on "had any addable defs", or hiding anything would delete the def-less Presets/Textures tabs) and which `BROWSER_TABS` must be built from too, or a persisted `fs:assetTab` boots a returning user into a strip that renders nothing. **Hidden means "never OFFERED", not "unreachable"**: the code panel's Monaco completions stay unfiltered (a node's `tslFunction` is usually a real three/tsl symbol — `mod`, `abs`, `mx_noise_float` — and the code panel edits TSL, not the palette), "Convert to Property/Constant" transforms an existing node rather than adding one, and a built-in preset authored with the node still contains it (the overview row says **⚠ in N built-ins** rather than letting the checkbox imply it rewrote shipped artwork). `output` is not hideable — its Add-node row is hardcoded and its tile doubles as "take me to the Output" (the singleton rule, `outputFocus.ts`), so the checkbox is locked with the reason on hover and the endpoint refuses the key. Saves go through the dev-only `POST /__nd/visibility` (the `citations.json` whole-file-rewrite shape; keys validated against `locateRegistryDescriptions`/`locateTextureDescriptions`, deduped + sorted, compare-before-write since the file is imported by `nodeRegistry` and a touch reloads the app through HMR), so this is project SOURCE that ships in the build — deliberately not a per-browser preference, or a shared `.fastshader` would reference a node the recipient can't see the tile for. `editorVisibility.test.ts` proves the filtering with a MOCKED non-empty file (the shipped one was empty until GLB Phase 4, so every direct assertion would have been vacuous) and greps source for the two ways it rots: an add surface built from `getAllDefinitions()`, and any `engine/`/`store/`/`utils/`/`hooks/` module importing the visibility set at all. **The suite must stay green with nodes actually hidden** — `release.yml` runs `npm test` before it builds binaries or deploys, so a test that only holds in the empty shipped state makes the feature unusable in the one way it is meant to be used. **The shipped file is EMPTY again**: `imageNode` was the first (and so far only) node ever listed here, and the owner unhid it on 2026-09-18, so CI is back to the mocked branch of `editorVisibility.test.ts` for the filtering itself (`registry/textureNodeOffered.test.ts` pins that ONE decision — see the Texture-node bullet). Every figure that node moves still follows the FILE rather than a literal: `registry/imageNodeAddable.test.ts` asserts its visibility facts against it, and `contentBrowserVirtual.test.ts`'s boot counts add one when it is unhidden (they were literals, and three tests failed the moment the node was unhidden). So ticking it back on keeps the suite green — checked by running the whole suite with the JSON served unhidden. Three things follow. `getEditorDefinitions()` is computed ONCE at module init, not `filter()`ed per call: every consumer memoizes on its identity, and a per-call array both breaks those memos and hands one render two different "the editor set" arrays (`editorVisibility.test.ts` asserts identity stability under the MOCKED file — the empty state can't see it, since there the filter never runs). The per-browser layer above it — `getEditorDefinitions(hidden)`, the optional categories the user has not switched on — keeps the same rule by memoizing per set (see the optional-categories convention). `nodeSearch.test.ts` ranks `getAllDefinitions()` through `nodeMatchRank` directly rather than through `searchNodes()`, because those pins are about ORDERING and hiding Perlin must not mean "noise" stops ranking Perlin first — one subsequence assertion bridges the two. And `nodeLabelRename.test.ts`'s findability sweep is scoped to the editor set (ranking still checks every def): a hidden node is *meant* to be unfindable.

### The Texture (Image) node is OFFERED

- **The Texture (Image) node is OFFERED** (2026-09-18, owner: "Why there is no texture node, where I can select from existing?"). It shipped HIDDEN through `editorVisibility.json` while it was unfinished (GLB Phase 4), so the palette, the Add-node menu and the search box did not carry it and the only way to get one was to drop an image FILE — while its picker, the settings menu's **Texture** row, had been able to fill one from every image the project holds since Phase 4 Step 6. Unhiding it is the whole fix: the node was already complete. VERIFIED end to end in Chrome — Shift+A → "texture" lists it (through the `Also: texture, sampler, picture, bitmap` alias tail, second after UV, whose prose also mentions textures), adding it lands an EMPTY node whose slot reads "No image" with the title naming the Texture row (`IMAGE_EMPTY_HINT`), a PBR `.glb` import then builds four Image nodes, and that empty node's Texture row offers all four as thumbnails and fills from one in a single undo entry. The palette is 79 tiles instead of 78. `registry/textureNodeOffered.test.ts` pins this ONE node's visibility, and nothing else: `imageNodeAddable.test.ts` and `contentBrowserVirtual.test.ts` still derive from `isNodeHiddenFromEditor`, so the **In editor** checkbox stays usable for every other node without reddening CI. Re-hiding THIS node is now a deliberate decision that deletes an assertion first. The node's LABEL is still "Image" (renaming it is a registry-source change with search-collision rules of its own), so the palette tile and the menu row say Image while the control that fills it says Texture.

### Textures and Distance fields are OPTIONAL categories — OFF by default, switched on from the toolbar's right-cl…

- **Textures and Distance fields are OPTIONAL categories — OFF by default, switched on from the toolbar's right-click list** (`registry/optionalCategories.ts`, 2026-09-04). It replaced the `/textures` one-load session unlock, whose consume-once mechanism existed only because there was no visible control: `public/textures/`, `utils/texturesUnlock.ts` and its `PUBLIC_ENTRY_DIRS` entry are gone, and `HARD_RELOAD_CLEARED_KEYS` is now an empty (still explicit) list. Off means the editor never OFFERS them: no content-browser tab, no texture cards or distance-field nodes in a live search, no rows in the Add-node menu, none floated into its Recent list. The flags live in the STORE (`optionalCategories` + `setOptionalCategory`, the `trackpadScroll` precedent — several surfaces read them, so React state in any one of them is the wrong home) and persist per key (`fs:showTextures`, `fs:showDistanceFields`; only the exact string `'1'` is on — validated, never coerced), because a switch you flip in a settings list is expected to stay flipped. Five rules. (1) **It is an ADD-SURFACE filter, never a registry filter** — the `editorVisibility` rule verbatim, and a SECOND layer above it: `editorVisibility.json` hides individual UNFINISHED nodes as project source (the same answer for every user of a build), this hides whole FINISHED categories per browser — plus each family's COMPANIONS, node types that live in another category but exist for the family (`OPTIONAL_CATEGORY_COMPANIONS`: Distance fields takes the Raymarch Output and Ray Direction with it; `withheldNodeTypes` is applied INSIDE `getEditorDefinitions(hidden)` beside the category test, so every consumer of the narrowed set gets both without a second call). `getEditorDefinitions()` is still the FILE's answer — what `nodeSearch.test.ts`/`nodeLabelRename.test.ts` rank over, so flipping a switch cannot redden them — and `getEditorDefinitions(hidden)` / `searchNodes(query, hidden)` narrow it by the set `hiddenOptionalCategories(flags)` returns, memoized per set so the identity rule holds there too (a consumer builds a fresh `Set` per render and must get the SAME array back). **An add surface passes the set on EVERY call** — `optionalCategories.test.ts` fails on a bare `getEditorDefinitions()` or a one-argument `searchNodes()` anywhere under `components/NodeEditor/`, because the default is the family walking back in through the search box. (2) **Two gate sites in the content browser, not one** — three, counting the measurement: the tab strip renders `visibleCategories` (= the pure `visibleTabs(displayCategories, flags)`), but a live SEARCH appends texture cards to the generic strip on EVERY tab, so `filteredTextures` returns `[]` while Textures is off, ABOVE its lazy build — a session that never switches the library on never pays the ~84 ms texture parse. And the tallest-tile high-water mark effect takes the flags as a dep: a family switched on lands its tiles in the All strip with NO tab change, and without the dep the strip never re-measures and a taller newcomer is clipped. (3) **A stored `fs:assetTab` naming a switched-off category stays VALID and is DERIVED to `'all'` at render (`effectiveTab`, pure), never written back**: `displayCategories`, `BROWSER_TABS` and the validator stay module-scope (usePersistedState needs stable identities) and list every tab the BUILD allows; the user's switches are applied per render. Writing `'all'` back would discard the user's tab for good (usePersistedState persists every value); deriving it means the tab returns the moment the switch does. (4) **Nothing under `engine/`, `utils/` or `hooks/` may import the module** (the store is the one exception — it holds the flag), so a `.fastshader` holding those nodes loads, renders, compiles and exports byte-identically whether the switch is on or off; `instantiateBuiltinTexture` is ungated, and node-editor.html + the Node Designer keep seeing everything. (5) **The study clean slate resets both** (`cleanSlateForStudy` removes the keys and restores `DEFAULT_OPTIONAL_CATEGORIES`): what the palette offers is part of the condition every participant must meet identically, so the previous user's switches are dropped with the rest of their state. The DESKTOP build follows the same default — the old desktop-unlocked exception existed only because `/textures` was unreachable there, and the switch is not. The rows are labelled with the category's own tab name (`formatCategoryLabel`, Latvian-aware) so the switch and the tab it summons read as one thing, and each hint is the row's `title`.

### "Hard reload" is the reload button's right-click menu

- **"Hard reload" is the reload button's right-click menu** (`utils/hardReload.ts` + the `.toolbar__local toolbar__reload-wrap` wrapper in Toolbar.tsx). Right-click — or a sustained press on touch, where there is no second button — opens two rows, Reload and Hard reload. It exists because the desktop shell has no browser chrome at all and an iPad's has no hard-reload gesture. **What it actually does is navigate to `?fsreload=<stamp>`**, which `main.tsx` then strips from the address bar with `replaceState` so the parameter isn't carried into every bookmark: a different document URL is a different HTTP cache entry, so index.html is refetched, and since Vite content-hashes the JS/CSS it references that is exactly how a newly deployed build gets picked up. The unhashed `public/` assets (the A-Frame bundle, the shaderloader, the `.obj` models) keep their cached copies — the honest limit, and the tooltip says so. Four traps, all pinned by `hardReload.test.ts`: `location.reload(true)` does NOTHING (the Location IDL takes no arguments; TS declares `reload(): void`, so the compile error tends to get cast away and ship a right-click identical to the left-click); the cleared-keys list is EXPLICIT and names no eval key, because a `sessionStorage.clear()` there would drop a participant's telemetry journal and return them to the consent screen mid-study; the wrapper must stay inside `openPrefs`' `closest()` guard (APPEND only — `trackpadScroll.test.ts` anchors that string at its opening quote) or the trackpad-prefs popover opens on top of it while the bar is expanded, and only then, since `.toolbar__overflow` is already guarded; and the long-press binds to the ELEMENT held in state, never a ref, because React remounts this button into the ☰ menu when the toolbar collapses and `useLongPress` keys on the target's identity — a ref object's identity never changes, so the gesture would die silently on the first collapse (the hook was widened to accept either). The wrapper reuses `.toolbar__local` for its `position: relative`, the ☰ re-anchoring rule and the dark-theme shadow, which is an explicit selector list a bespoke class would miss.

### Asset tiles are spaced by SILHOUETTE, not by frame

- **Asset tiles are spaced by SILHOUETTE, not by frame** (`components/NodeEditor/tileSilhouette.ts`, 2026-09-11, owner: "the spacing in assets between nodes is not even"). The frames were already evenly spaced (12.2–12.9 px, measured), but the eye reads the gap from the outermost thing drawn, and sockets straddle the frame: a node with inputs has dots out on its left, the colour swatch's perimeter socket is 1.5× (`CARD_COLOR_SCALE`), the Output's preview socket is twice a socket — so the visible gaps ran 3.5–10.3 px. ContentBrowser's tile-measurement rAF now runs `applyTileSilhouettes(strip)`: read every tile's frame and socket rects, THEN write `--fs-sock-l`/`-r` on each (one layout, not one per tile), which `.node-preview-card`'s padding adds to its 8px. Measured rather than tabled per node type, because the overhang depends on the socket token, the cost scale, the swatch counter-scale and each node's own insets, and a tile added tomorrow would be missing from a table. The values are in the tile's OWN px (screen ÷ rendered scale), so they are zoom-independent and dragging the bar's top edge never re-measures them. The node-editor.html overview draws the same cards without the pass, so its tiles keep the plain 8px.

### Asset-browser ordering

- **Asset-browser ordering**: node tiles sort by GPU points (cheapest first, every tab — not just Noise). **Presets sort by GPU points too** (`byCost`, 2026-08-27), on the SAME `totalCost` their tile's `AssetCostBadge` prints — so the strip reads as a price ladder (4 for gradient up to 76 for studio-shine), which is the point of a library whose pedagogy is that a tier-3 look need not be expensive. Deliberately NOT `nodeCostPoints`: that re-derives a variadic fold as base × (N−1) and disagrees with the badge by a point or two (studio-shine 78 vs 76), and a sort contradicting the number on screen reads as a bug. **Textures sort by GPU points too** (2026-08-29): they already PRINT `totalCost` on their tiles, and a strip ordered by something its own tiles do not show reads as unordered. They used to sort by member count on the reasoning that a texture is a graph you open and read — but node count turns out to be a poor proxy for the price anyway (Static Noise is the smallest texture at 16 nodes and the third most expensive of the cheap half), and two ready-made strips sorted by two different rules was the thing actually causing confusion. One ladder now: Grid 22 → Crumpled Fabric 510. `bySize` is gone, and `noUnusedLocals` is what would have caught it lingering. Consequence to accept: the Presets strip is no longer the easy→advanced ladder — cost orders ACROSS tiers (tier-2 Vertex Wave at 8 sits third; tier-3 Teleport Beam at 29 precedes tier-1 Stripes at 30), so the tier now lives only in each preset's blurb and in-frame note. Both are display-layer sorts in `ContentBrowser` — `builtinPresets.ts` keeps its tier order (and the test that pins it), and `builtinPresets.test.ts` source-pins that BOTH strips use `byCost`, that `byCost` reads the same `totalCost` the badge draws, that `bySize` is gone, and that every preset AND texture costs > 0, since a zero-cost asset would clump at the head with no badge to explain it.
