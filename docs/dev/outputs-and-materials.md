### glTF material-index parts (`materialParts`, loader 0.8): the index is RECORDED AT PARSE, and a model signature…

- **glTF material-index parts (`materialParts`, loader 0.8): the index is RECORDED AT PARSE, and a model signature decides whether it applies** (`a-frame-shaderloader-0.8.js` section 13a; `src/engine/materialPartsContract.ts`). Import-built sections target a glTF material INDEX rather than a mesh name (GLB Phase 5 Step 5 emits and parses them — see the index-sections paragraph of the per-mesh bullet; only a graph carrying index sections emits anything new, and the ONE thing that creates them is the GLB import dialog's Build — see the GLB-import convention; before that dialog shipped nothing but a hand-edited file could). The loader has to know which index each mesh came from, and after a parse only GLTFLoader's `parser.associations` knows — which A-Frame's `gltf-model` throws away together with `gltf.userData`, root extras included. Seven rules. (1) **`FastShaders.gltfPlugin` records it in `afterRoot`** (GLTFLoader awaits that before `onLoad`, so the record exists at `model-loaded`) into plugin-private WeakMaps — scene root → `{ materialCount, materialNames, embedded }`, object → `{ record, index }`. **Never into `userData`**: userData is JSON-copied on clone and GLTFExporter writes it back out as `extras`, so a re-export would bake a stale index into the file. The plugin never throws or rejects (GLTFLoader would turn a rejection into the MODEL's load error) and never mutates the model; `scene.clone()` loses every record, by design. (2) **The index comes from the MESH association first** (`{meshes, primitives}` → that primitive's `material`) and from the material association only as a fallback. MEASURED against r184: GLTFLoader gives Points/Lines a fresh un-associated material, and an `EXT_mesh_gpu_instancing` InstancedMesh has the reverse gap; the tangent-less clone (`normalScale.y *= -1`) and instanced node refs keep theirs. A material-less primitive has no index. (3) **Registration is on `gltf-model`'s PROTOTYPE init, wrapped ONCE when the file is evaluated** (`installGltfModelHook`; the flag is `Symbol.for('fastshaders.gltfModelHook')`, non-enumerable and agent-wide, so even two copies of the file wrap it once), followed by an evaluation-time sweep of the `[gltf-model]` elements that initialised earlier; the shader component's init and its `componentinitialized` listener register as well, as a fallback (`register()` dedupes by identity). Registering from the shader component alone loses the race whenever the MODEL component initialises first, and it does on 3 of the 4 documents — the preview's model feed, the XR popup and podest's VR popup (gltf-model in markup, shader attached after boot), podest's stage (either drop order) — and `componentinitialized` does not bubble. `attachGltfModel(comp)` is the ONE function all three paths call (the mesh decoders' install goes there too). Nothing re-parses a model: one parsed before the plugin reports `no-record`. (4) **Precedence per mesh**: an explicit `parts` NAME claim, then `materialParts[index]`, then the default material, then the single-mesh first-part fallback (NAME parts only), then the authored material. It fills the existing dispatch seam (`_indexPartMaterials` + `_indexPartResolver`), so `applyMaterialToMesh` keeps 0.6's 3-argument signature and `_appliedMaterials` records exactly what 0.6 records. ONE material per applied index, built by the same `buildMaterial` as the default and every part, and shared by every mesh of that glTF material; the resolver honours an index only when it was recorded by the SAME parse whose signature matched. (5) **`materialParts` applies only when `modelSignature` (glTF material count plus raw names, in order, no normalisation) equals the parse** — a different glTF also has materials 0, 1, 2. Otherwise the index table contributes NOTHING (name parts and the default still apply) and the loader logs one console.warn per apply. The status (`applied`/`mismatch`/`no-record`/`no-signature`/`invalid`/`not-gltf`, with `applied`/`dropped`/`expected`/`found` counts) is `binding.materialParts` on plain three and the `shader-material-parts` event on A-Frame, emitted BEFORE `shader-applied`. That event is FORGEABLE (the sandboxed document runs the shader), so the editor must derive index-section dormancy trusted-side from its own GLB reader, never from it. `not-gltf` — an A-Frame entity without `gltf-model` (a primitive, an OBJ), a plain-three primitive — is silent. Keys are canonical decimal indices below the material count, capped at 256 per apply. (6) **Export guard, because 0.6 is frozen**: a `materialParts` module MUST carry a `parts` object (`{}` at minimum) and a `modelSignature`. A materialParts-ONLY module takes 0.6's Simple-API branch — the whole return object becomes every mesh's `colorNode` and compiles to a zero `vec4`: near-black, no error — while a truthy `parts` keeps 0.6 on the object path, where unclaimed meshes stay authored. `parts` also carries name-keyed MIRRORS of the index entries (byte-identical bodies, mesh names from the trusted-side reader, authored name claims win), listed in `materialPartsMirror`; 0.8 drops mirror keys in EVERY status (in `buildMaterials`), so on a mismatched model a mirror cannot paint unrelated meshes that share a name. codeToGraph and scriptToTSL strip mirrors before the byte-identical-body merge (`materialPartsMirror` names are skipped as name sections; `stripMirrorParts`). `materialPartsContract.ts` holds the key names, the bounds, the ONE editor-side copy of the signature helpers (`sanitizeModelSignature` — 1..1024 names of at most 1024 characters, summing to at most `SIGNATURE_TOTAL_CHARS_MAX` 65536, an editor-only bound stricter than the loader's `validSignature`, never trimmed or normalised, the SAME object back when clean — and `modelSignatureMatches`, the loader's `sameSignature` rule; `materialPartsContract.test.ts`) and `checkLegacyGuard` (rules R1–R7); `shaderloaderMaterialParts.test.ts` proves the 0.6 half against the frozen file and pins the loader's restated bounds to the contract. (7) The plugin also stashes embedded FastShaders image bytes for Phase 7 (`extras.fastshaders = { v: 1, assets: { key: imageIndex } }`, a provisional schema that may only grow): bufferView images only (a `uri` image is refused and never fetched), mime-whitelisted, magic-checked, capped at 16 MB each, 64 MB and 64 images per model; nothing in extras is decoded or executed, and `releaseEmbedded` drops the bytes. Plain three.js: `loader.register(FastShaders.gltfPlugin)` before loading, or materialParts reports `no-record`. `shaderloaderGltfPlugin.test.ts` runs the REAL GLTFLoader in node over in-memory fixtures (`src/gltfTestFixtures.ts`, whose `self`/`createImageBitmap`/`ProgressEvent` stubs a suite must undo) and pins the A-Frame bundle's gltf-model shape the hook depends on.

### A GLB can carry its own shader, and loader 0.8 runs it ONLY on `shader="src: model"`

- **A GLB can carry its own shader, and loader 0.8 runs it ONLY on `shader="src: model"`** (or `FastShaders.loadFromGltf` / `applyFromGltf` on plain three; section 13c, Phase 7 Step 5, folded into 0.8.0 because 0.8 is unpushed). The single-GLB export stores the module as UTF-8 text in a BIN bufferView named by ROOT `extras.fastshaders.module` (the format is `engine/glbShaderContract.ts`, whose `FS_FORMAT`/`MODULE_MIME`/`EMBED_MODULE_BYTES_MAX`/`MODEL_PLACEHOLDER_RE` literals `glbShaderContract.test.ts` text-pins against the loader). The glTF plugin reads the bytes at parse (`stashModule`) and nothing runs until a page asks. Five rules. (1) Every `"fs-asset:<key>"` literal becomes a `blob:` URL of the GLB's OWN image bytes (the P3b stash moves into Blobs on first read, so `embeddedAssets(root)` is null afterwards). The URLs belong to the BINDING, not the import: `disposeShaderMaterial` revokes them (the next apply's commit, `remove()`, `binding.dispose()`), because a hand-written module may start a texture load after its import settles; a failed or stale apply revokes at once. `apply()` never adopts, so a `loadFromGltf` result is released by its caller. (2) It fails CLOSED, before a line of the module runs, on: no `gltf-model` on the entity, no parse record, no module, another format version, a view that is not a plain BIN or `data:` view (GLTFLoader would FETCH a `uri` buffer and DECODE a meshopt view, so both are refused before any read), over 16 MiB, cut short, not UTF-8, or (after the import) no default export — one console.error, `shader-error {src: 'model'}`, authored PBR back. A signature mismatch is not a failure. (3) Staleness is a TOKEN (`_modelApplyToken`) in both the success and the catch guard: two models' applies both say `'model'`. An entity whose `mesh` is not yet its gltf-model waits quietly for `model-loaded`. (4) The editor preview, its XR popup and both podest documents NEVER use it: each closes the one-way `FastShaders.disableModelModules()` latch (`MODEL_MODULE_LATCH` in tslToPreviewHTML.ts, spelled identically in podest.html) as the first statement of its URL-modifier script, and none of those sources spells the opt-in; `embeddedModuleNeverRuns.test.ts` is the ONE suite pinning both and runs the latch script against the real loader. The keyword pin is scoped to tslToPreviewHTML.ts, ShaderPreview.tsx and podest.html, because the GLB-mode module header (`engine/glbUsage.ts`) DOES spell it for recipients. (5) It is a `.js` in a model's clothing: a page that loads user-supplied GLBs must never say `src: model` (both READMEs say so in bold). The export itself says it too: the module carries the six-line GLB usage header (`engine/glbUsage.ts`), the EXPORT popover's note repeats it, and the README's *Single-GLB export* section states what other tools show and which round trips drop the shader silently. `src/shaderloaderModelSrc.test.ts` runs the real 0.8 over the hand fixture AND a GLB `utils/glbRepack.ts` wrote (the writer↔loader contract), asserting lifetime with `node:buffer`'s `resolveObjectURL`. TRAP for a mutation check: vitest runs the `fs-vendor-sync` plugin, which re-copies the SUBMODULE loader over `public/js` at start — edit the submodule copy, never the vendored one.

### Per-mesh materials (ONE Output NODE per material → `parts` / `materialParts` → shaderloader 0.6 and 0.8)

- **Per-mesh materials (ONE Output NODE per material → `parts` / `materialParts` → shaderloader 0.6 and 0.8)**: a dropped multi-mesh glTF can have a DIFFERENT shader per sub-mesh, and **each material is its own Output node** (2026-09-18, owner: "do not stack all meshes into one, keep them as separate nodes"). Until then there was exactly ONE Output node and per-mesh shading lived INSIDE it as stacked material sections; `data.materials` is gone from the live graph, every node wears the BARE channel handles (`color`, `emissive`, …) that material 0 always used and every saved edge already spells, and a node's binding is node-level: `meshTargets: string[]`, or `gltfMaterialIndex` beside `modelSignature` for an import-built INDEX node. **An UNTARGETED plain Output is the DEFAULT material** — it owns the module's top-level channels, i.e. the whole-model behaviour that predates the feature — while a TARGETED one emits its own `parts` / `materialParts` entry. The name list is still read ONLY through `materialTargetNames`, which also still reads the older single `meshTarget: { name }`, never written any more, so a graph or a saved group from before the list keeps what it shaded. A surface showing ONE label for a material goes through `sectionLabel` (utils/outputMaterials.ts, which decides what the label IS: the default, the first mesh plus whether there are more, an empty one's "No mesh", or an index one's material name) and `formatSectionLabel` (nodes/sectionLabelText.ts, which words it) — the node's picker, the settings menu's scope line and the preview wire's hover chip (`linkLabelText`) all read that pair, so they cannot name one material three ways. **THE EMITTED MODULE TEXT DID NOT CHANGE, and that is the gate the whole split was built behind**: the same logical content emits byte-identically, so loader 0.6/0.8, the single-GLB export, `materialPartsMirror`, the GLB contract and every committed snapshot were untouched and ONLY the graph shape moved. `engine/unfoldEmissionParity.test.ts` is the mechanical proof rather than the claim: it asserts STRING EQUALITY of the editor TSL and of the built module between the folded and the split shape over the Blender-, scan-, AI-shaped and interleaved GLB fixtures plus hand-built name documents, with a vacuity guard (a real three-entry `materialParts` table, its signature, all three 0.6 mirror keys) and a permanent `outputsReversed` case, and it runs folded / split / restored through a test-only `refold()` — both producers build the split shape directly now, but a saved `.fastshader` still carries a folded one, and the byte-identity claim is about THOSE. That reversal is not decoration: it FOUND a real defect. After the split an EMPTY material and the DEFAULT are indistinguishable — both are untargeted Outputs — so picking the default by ARRAY order silently dropped `colorNode:` from the module when the two were reordered, which `liftChildrenAfterParents` does on an ordinary drag-into-a-group (see `defaultOutput` in the several-outputs convention). **`unfoldOutputMaterials` replaces `foldExtraOutputs`, which is DELETED**, and runs on all four restore paths in the order sanitize → unfold → normalize, with `sanitizeEdgeExtras` ABOVE it since the unfold walks and re-points the edge list. A sibling inherits `parentId` through the `{ ...out }` spread and is stacked in the PARENT's space, so the unfold GROWS any frame it overflows (`growGroupFrames`, utils/groupFrame.ts — scoped to the ids that call minted, unpadded, height only, never a collapsed group, and returning the SAME array when nothing grew): `extent: 'parent'` is stripped on load and never re-attached, so React Flow DRAWS an overflowing child outside the frame rather than clamping it, and nothing else in the app resizes a frame after nodes are added to it programmatically — a folded Output saved inside a group came back with its materials strewn below it, repairable only by a collapse/expand round trip nobody would think to try. Node 0 IS the original node — same id, same position, same values, ports, settings and targets, minus `materials` — so no edge on a bare handle moves and the node keeps its place in the user's layout; each further material becomes a sibling at a DETERMINISTIC id (`<outputId>#m01`, zero-padded, a counter appended on collision) stacked `UNFOLD_DY` (180) below it, because a `.fastshader` that opened with different ids each time would re-lay-out a saved group on every `instantiateSavedGroup` and rewrite `fs:graph` on every boot. Every moved edge is re-derived with `generateEdgeId` (an id is a function of its endpoints, so a stale one collides with the next edge that really connects that pair) and its channel is VALIDATED against the Output's port list — `parseChannelHandle` returns `{ index: 0, channel: <the whole string> }` for anything it does not match, so without that a tampered `m1:zzz` would land on a sibling wearing a bare handle no port has: invisible, un-hit-testable, and a permanent 008. It returns the SAME arrays when no Output carries `materials` (the autosave subscriber and `selectionOnlyGraphChange` compare by reference, so a new array on a clean document rewrites `fs:graph` on every boot), with `materials: []` deliberately NOT clean — the key itself is what the split retires, and the app never writes an empty list, so that costs one array on a hand-edited file only. Legacy one-Output-per-mesh documents now load NATIVELY, which is what `foldExtraOutputs` used to absorb — and it capped that fold at `MAX_PARTS`, so a document with more than 9 targeted Outputs used to emit only 9, where all of them contribute now. **`channelHandle` / `parseChannelHandle` therefore do NOT retire**: a saved `.fastshader` always carries the folded shape, so the unfold is a permanent consumer. `pruneOrphanMaterialEdges` survives with its job narrowed to what still reaches it — an `m<k>:` handle on an Output the unfold did not touch, i.e. only a hand-edited or foreign file. Rules that are load-bearing. (1) **Every handle is BARE, on every node** (`color`, `emissive`, …): the `m<n>:<channel>` namespace survives ONLY inside `unfoldOutputMaterials`, which reads it off a folded file and writes bare handles out. That is what let the split keep every saved edge, every `generateEdgeId` string and every `targetHandle === 'color'` reader working unchanged — and it is why `toggleExposedPort`'s explicit `handleId` parameter, which existed so hiding a channel on material 2 could not delete the DEFAULT's wire, is now simply `channelHandle(0, …)` at every call site. `shiftMaterialHandles` (renumber a stack after a removal) has NO production caller left: a material is a NODE, so removing one deletes the node and there is no later section to renumber. It is kept as a tested primitive on the same terms the materials-form plans are — a folded `.fastshader` can still carry `m<n>:` handles, and any future code that renumbers them must not re-derive this by hand. (2) **The UI CAN author a parts-only module** — by targeting every plain Output, or by leaving the default unwired — and that is a supported shape, not a hazard. A document with no default, or one whose default is unwired, emits `parts` ALONE (the loader, 0.6 and 0.8 alike, then leaves unclaimed meshes on their AUTHORED glTF materials, the KHR_materials_variants fallback shape): the red `vec3(1, 0, 0)` sentinel is deliberately NOT emitted beside parts, because it means "nothing is wired yet" for a shader with nothing else to say, and once a mesh material exists the user HAS said something — painting every other mesh red would throw the model's own materials away to announce a state visible on the node. It also round-trips: parts-only parses back to an empty default NODE plus one node per part, and re-emits parts-only. **That is why a graph whose ONLY Output is TARGETED grows by one node on its FIRST Apply, and never again**: a `parts` map has nowhere to record which material was the default, so `{ parts: { Body } }` is the same text whether one node named Body or an empty default sat beside a Body node — the parse resolves it the historical way and MINTS the empty default. Nothing is lost (every wire is re-created from the code, the module re-emits byte-identically, and the shape is a fixed point from then on), and the alternative — giving the first part to the default — would collapse the far more common "unwired default + one mesh material" instead. `outputPartsFixes.test.ts` pins both halves, and the round-trip suite pins the fixed point. A lone unwired Output still emits `return vec3(1, 0, 0);` exactly as it always has. **An emitted part with NO channels is dropped by `buildShaderModule`** (`props.length > 0`), so an Output you have pointed at a mesh but not yet wired changes nothing in the preview — pre-existing, and deliberate: the alternative is that adding one throws every other mesh back onto its authored material to announce it. **It is MARKED rather than prevented** (`addedMaterialContributes` in utils/outputMaterials.ts — the `outputDefaultContributes` test applied to one material, over its own values and its own exposed list; `silent` in OutputNode, now scoped to a node that is neither the default nor PARKED, since after the split its old `index === 0 → false` form was simply unreachable): while such a node sets nothing, its mesh picker takes the orange `mesh-picker--silent` with its own sentence — this material sets no channel yet, so the meshes it names keep their current look — and every unset COLOUR row on it draws the UNSET swatch instead of the channel default — a white the preview never paints, which is what made "point an Output at a mesh" read as a colour assignment that silently failed (owner, 2026-09-18). Both clear themselves the moment anything on the node emits, and the channel default is truthful again then: a part that DOES emit really does render three's white for an unset `color`. The DEFAULT is never in this state — an Output contributing nothing emits the red sentinel, which `emitsNothing` marks instead, and that predicate is now scoped to the default node AND asked across every CONTRIBUTING node (both halves matter after the split). KNOWN and pre-existing: a driving Raymarch Output silences every plain Output, but `emitsNothing` does not consult it, so a silenced default can still show the red swatch. `outputSilentSection.test.ts` pins the predicate, both surfaces and the dropped part it describes. A part's material settings do not keep it alive either — the loader (0.6 and 0.8) skips a part with no channel (`hasChannels`), and emission mirrors that. (3) **Emission and the parse must land in ONE commit.** Emission alone is byte-stable, node-count-stable and `errors: []` while silently deleting every secondary binding on the first code-panel Apply — no pre-existing round-trip invariant can fail on it, so `outputParts.test.ts` asserts parts SURVIVE an Apply and that the graph does not grow across TWO successive ones. A targeted material with nothing wired still emits its `{}` entry, or the parse cannot re-create it and the material plus its edges vanish. **The pairing key is the BINDING, and that is the whole correctness of the resync since one Output node became one material** (`matchKey` in utils/resyncPairing.ts, extracted PURE so the failure is an executable attack rather than a source pin — `useSyncEngine` is a React hook and the vitest env is `node`). Every parsed Output is labelled the literal string `"Output"`, so the historical `registryType + label` key puts every one of them in ONE bucket and they pair by ARRAY ORDER — which on a multi-mesh document silently moves one material's id, position, exposedPorts, stored values and settings ONTO ANOTHER MESH, with `errors: []` and byte-identical emitted output. Nothing downstream notices: the module is the same text, the preview renders the same picture, and the only evidence is that the node the user was editing is now shading something else. The label carries no information for this type at all, so the binding REPLACES it rather than joining it (`output` plus `default` / `i<index>` / the SORTED names, so a material naming the same set in a different order is the same material — the parse rebuilds `meshTargets` in `parts` key order, which the user can change by re-ordering the code panel's text without meaning to re-bind anything). A Raymarch Output keeps the label form: it has no binding and the parse mints at most one. Two carries move with it. `carryInactiveSinks` carries a TARGETED plain Output ONLY when the parse produced no plain Output at all (`parseHasPlainOutput`, read off the PARSE and never off the old graph). Normally it does not — a targeted Output CONTRIBUTES, so the parse rebuilds it from the code, and carrying it too would add a node BESIDE the parse's copy, growing a GLB document by one Output per mesh ON EVERY APPLY while emitting each part twice. **That premise fails in exactly one state, and it cost the feature silently**: under a DRIVING Raymarch Output `graphToCode` empties the whole Output pass (`outputs = marchNode ? [] : contributingOutputs(nodes)`), so the module carries no `parts`, no `materialParts` and no top-level channels, nothing pairs, and every targeted Output plus its incoming edges was DELETED on Apply with `errors: []` — PARTIALLY, since the untargeted default came back through this very carry, so the graph went on working with some materials simply gone. The gate is what the PARSE holds rather than "does a march drive" for two reasons: a module with no plain Output has nothing a carried node could collide with BY CONSTRUCTION, which is what keeps the widening from re-opening the duplication above, and asking the old graph would resurrect a material the user had just deleted from the code panel by hand, on every Apply. It is NOT a complete answer to the march case, and the limit is the CALLER's: the carry runs inside `if (unpositioned.length === 0)`, so an Apply that also adds a node reaches none of it — one new `const` typed into the panel does that, and so does a feeder SHARED between the march and an Output, which `marchPartition` emits into both the per-step Fn and the flat body so the parse returns it twice and one copy is unpaired. And an unpaired plain Output is PLACED rather than handed to the relayout (`placeParsedOutputs`: below the lowest positioned Output, `UNFOLD_DY` apart, in emit order, so a built column and a restored column are the same column) — **at ROOT level and in ABSOLUTE coordinates, never adopting the anchor's frame**. It takes `oldNodes` as a third argument because that is the only place a positioned Output's frame still is: `mergeMatch` spreads the PARSED node and copies `id` and `position` alone, so `positioned` carries PARENT-RELATIVE coordinates with no `parentId` on them, and reading those as absolute put a new material a whole group-origin away while ranking them against a root Output's y picked the wrong anchor outright (`absoluteNodePosition`, utils/groupFrame.ts, resolves both). It does not INHERIT the frame for four reasons: `unpositioned.length > 0` sends it through `autoLayout`, which writes absolute positions while the group block that would re-add the frame is gated OFF on the same condition; that block restores `parentId` only for ids the OLD graph had, which a parsed id never is; a COLLAPSED anchor group hides members by className, so an adopted node would draw on top of the pill; and React Flow's own drop-into-group does the adoption, with the frame maths that goes with it, the moment the user drags it in — because the orphan-property carry, the inactive-sink carry and the ENTIRE group-preservation block are gated on `unpositioned.length === 0`, so ONE unpaired node DELETES EVERY GROUP FRAME on the canvas. That was tolerable while a new node meant one Multiply typed into the code panel; with one Output per material an ordinary GLB import mints a dozen at once. (4) **A part's discard is a KEY, never a statement** — a `Discard()` statement belongs to the module, so it is the DEFAULT material's cutout and lands on the DEFAULT node's bare `discard` handle — and `buildShaderModule` gives each part its own INDEXED `__partPixel<n>` wrapper (indexed because a mesh name is not an identifier: `Body.001` and `my mesh` are both legal). That builder also maps every part's inner keys through the SAME `CHANNEL_TO_PROP` table as the default; re-emitting them verbatim hands the loader keys it does not know and silently renders the default material on every mesh — right-looking source, wrong picture, no error. A part's wrapper falls back to the part's own **emissive** before white, exactly as the default path's `discardColor` does and for the same reason (the loader copies emissiveNode→colorNode only when colorNode is undefined, and a wrapper always defines it): falling straight to white made the ordinary glow-cutout wiring — Emissive + Discard, no Colour — render correctly on the default and wash out to lit white on a targeted material. **A material's Transparent / Side / Alpha clip / Depth write / Shading ride INSIDE its `parts` entry** (`engine/materialSettingsCode.ts`). The loader's `buildMaterial` has always applied all four per part (the frozen 0.6's lines 351-362, carried verbatim into 0.8's core), so this needed no loader change. What was missing was every step on the app side: graphToCode never wrote them, buildShaderModule's part loop dropped any key CHANNEL_TO_PROP did not know, and the parse wrote none. So an added material's settings did nothing (preview and export alike), and every Apply deleted them, because the mergeMatch carry only ever covered material 0. graphToCode now appends `materialSettingProps(material.materialSettings)` after a part's channels and discard, in the LOADER's spelling (`side: 2`), so the code panel, the module and a bare-script import speak one vocabulary. buildShaderModule re-validates the text with `materialSettingsFromSource` (the same sanitizer scriptToTSL uses) and re-emits it canonically after the channel props. That sanitizer strips a value's comments first (`settingValueText`), and the part loop reads a quoted key as the name it spells, because the parse does both: `transparent: true /* glass */` and `"transparent": true` otherwise reached the node but not the module, so after an Apply the preview rendered opaque under a node showing Transparent ticked. codeToGraph reads them back onto that material. There is ONE emitter (it also writes the default's top-level keys) and ONE text sanitizer, so the per-part rules cannot drift from the default's: alphaTest capped at 0.99, depthWrite:false only under transparency, a tampered side emits `side: 0`. Only those PART keys: `mergeVertices` is a module-level geometry directive (0.6.js:715; 0.8's `shouldWeld`), and `displacementMode` has no loader key, so a targeted node's Displacement rows follow the default — which is why both now render only on `moduleSettingsOutput`'s node rather than inertly on every one. **`flatShading` joined the part keys on 2026-09-18** (Blender's Shade Smooth / Shade Flat, a `Shading` select beside Side): it is a THREE.Material property three's node materials honour — `NodeBuilder.isFlatShading()` swaps `normalViewGeometry` for `normalFlat`, a face normal from the DERIVATIVES of the view position, so it needs no vertex normals and works on a welded displaced primitive — and it is per-material, so two materials on one model may differ. Only the FLAT case is stored and emitted (smooth is three's default), which keeps every graph and export made before it byte-identical. **0.8 applies it and the frozen 0.6 does NOT**: 0.6 reads its known keys by name and ignores the rest, so such a shader renders SMOOTH on an old loader rather than failing — `perMeshMaterials.test.ts` pins that split in both directions, and `shaderloader08Core.test.ts` drives 0.8 against a real three material. Settings that emit nothing leave the part byte-identical. On an UNTARGETED Output it is a `<button>` carrying `nodrag` with its pointerdown stopped, so a press activates without dragging, panning or selecting — solid while active, hollow while parked, and the hollow state is drawn with an INSET shadow rather than a border so the outer white rim and the disc's size stay identical and only the fill changes. On a TARGETED or index-bound one it is an INERT `<span>`: activation only means anything among UNTARGETED Outputs, so a click here would write a flag `normalizeActiveOutput` then strips and — worse — would silently stop the whole-model material emitting. It is drawn SOLID, because such a node always contributes and hollow only ever means parked, and it keeps REAL pointer-events so its `title` can open (TooltipLayer resolves its host from `elementFromPoint`, so a title on a `pointer-events: none` element never fires), with `cursor: default` the only signal that it is not a button. The BASE rule is `pointer-events: none` and only `.react-flow` opts back in, because the palette tiles and the node-editor overview render this same class as an inert `<span>` inside `pointer-events: none` cards, and a control must never be reachable from a static replica. **The right-click scope is the NODE**: `onNodeContextMenu` passes the node id alone, and the `data-material-index` walk that used to pick a SECTION out of a stack has nothing left to choose between. `openContextMenu`'s three pin fields became ONE named object (`pin?: ContextMenuPin`) rather than shifting its 8th positional argument — that slot sat immediately before `sourceHandleType`, and a slide there would silently flip the wire-drop direction, which renders as nothing while still emitting code. **Cost is seeded from the whole CONTRIBUTING SET** (`costSeeds` in utils/nodeCost.ts: a driving Raymarch Output alone, else `contributingOutputs`), unioned inside ONE `computeReachableCost` walk, so a feeder shared by two materials is counted once and the total never exceeds the sum of the per-node prices. Seeding one sink was right while one node held every material; with per-material nodes it would have priced one mesh's chain and left the rest free — and it also replaces `activeSink`'s retired last-resort term, since a document whose every Output is targeted has no sink at all and used to price at 0 with an inert cost pill while graphToCode emitted its parts perfectly. Each sink still carries its OWN badge (`sinkCosts` — what the shader would cost with THAT node driving, muted to 0.45 opacity on an inactive one so it reads as a comparison figure rather than as the meter's total), and an Output's badge is drawn at TWICE the usual size (owner request 2026-09-18: an Output's number is not one node's price among fifty, it is what the shader would cost with that sink driving). That rule is SCOPED `.react-flow`, the cost-badge-colour precedent, and here the scope is load-bearing rather than tidy: `NodePreviewCard` renders this exact markup for the palette tile, which lives outside the canvas inside `.content-browser__items`' `overflow-y: hidden`, and that never measures an absolutely-positioned badge, so an unscoped rule would silently clip the tile's number. `top` moves with the size (the badge is `line-height: 1`, so 12px/-14px leaves 2px of clearance and 24px keeps that 2px at -26px), and 26px was CHECKED against the group frame's badge band and FITS with 8-12px of slack — so `BADGE_CLEARANCE` does not have to move, which matters because raising it would re-lay-out every built-in group's committed snapshot. In POINTS PER PIXEL the summed total is an UPPER bound (a pixel runs exactly one material), while it UNDER-counts the other currency: compile work, pipelines and memory (every material compiles its own pipeline, shared nodes included, and texture memory is not priced at all). Two Image nodes holding the same image price twice (two samples), while the module builds them ONE texture when their texture settings (colour space, filter, repeat, flipY) match, and one image element either way; see the Image node bullet. NOT done yet: the preview-pane assignment TABLE, a per-material displacement mode (a part follows the default's), and real per-part budgeting in the CostBar (needs a ShaderCarousel calibration entry). A bare-script import (a `.js` with no project block) of a parts module still does not reverse the node-prop names inside `parts` (`colorNode:` lands on a dead `colorNode` handle on that node) — part settings pass through that path intact, the channels do not. **Never verified on a screen**: whether a 16-material GLB import reads as a usable column of cards or as a wall of them (`UNFOLD_DY` is 180 against a one-material Output's ~137px estimate, so such an import unfolds into a ~2900px column), and what N Output nodes each carrying a replicated `modelSignature` do to `fs:graph` in WebKit, which charges localStorage by the STORED WIDTH — measure a 16-material document with `scripts/verify-webkit-storage.mjs` before shipping.


### Environment maps (`env` socket on the Output node) + `metalness`

- **Environment maps (`env` socket on the Output node) + `metalness`**: an image wired into Environment becomes real IBL (from its Color socket; Alpha/R/G/B are scalars and take the ordinary non-image path, or an Alpha wire would silently become full-colour IBL) — graphToCode emits the TEXTURE, never the sampled vec3 (`env: texture(_imageN_tex)` referencing the texture the image's share group declared, which for a sharer is ANOTHER node's var, always read through `imagePlanner.get`), tslCodeProcessor maps it to `envNode:` and the loader's `nodeProps` assigns `material.envNode` (added in 0.5, carried by the 0.8 every export references); three's `EnvironmentNode` auto-wraps a texture-valued envNode in `pmremTexture()` (per-renderer cached prefiltered radiance + irradiance, blur driven by the Roughness channel, reflectivity by the new Metalness channel — the loader always accepted `metalnessNode`, the graph just never emitted one). The image-source emission is GUARDED on the planner having placed that node, i.e. on a texture var that was actually declared: the invalid-payload fallback declares NO `_tex` var, and referencing it would be a module-killing ReferenceError — that case, and any non-image source, passes through as a plain node ref instead (legal envNode; a Color node = uniform ambient environment), vec3-widened when its shape isn't 3. Unlike image→normal, connecting image→env does NOT flip colorSpace — the map stays sRGB (PMREM decodes it). `OUTPUT_CHANNELS` appends `metalness` at the END so existing return-object key order stays byte-identical; the REGISTRY input order is the separate, user-facing arrangement (Color, Emissive, Roughness, Metalness, Opacity, Discard, Normal, Environment in the Pixel section, Displacement alone in Vertex) which `PIXEL_PORTS` and the ShaderSettingsMenu's `OPTIONAL_OUTPUT_PORTS` mirror — keep all three sequences aligned. Both new sockets are opt-in (not in `OUTPUT_DEFAULT_EXPOSED`), enabled via the Output node’s Material Settings menu or auto-exposed when an edge arrives. **The preview's Light dropdown grows an env entry** named after the attached image (`envMapName` string-selector in ShaderPreview — the cheap-string subscription pattern; falls back to the generic "Environment" label for non-image env sources AND for an image wired from its Alpha/R/G/B socket, which is a scalar ambient rather than IBL): selecting it applies `LIGHT_PRESETS.env`, an EMPTY rig on purpose, because envNode supplies radiance+irradiance itself and analytic lights on top would double-light; `effLighting` degrades a persisted `'env'` to studio the moment the map is unwired, so a stored pref can never boot a lightless void. Verified headless (Chrome, three r184 WebGL2 fallback — the Safari path): the real generated module lights an unlit sphere with correct angular mapping and roughness blur. Two caveats: PMREM needs a real-sized map (mip count is log2(height)−2, so a tiny test texture renders BLACK — an 8×4 did; real equirects are fine), and the canvas import pipeline is LDR, so no HDR sun intensities. Env cost is invisible to the point system (it is a channel, not a node) — pricing it needs a ShaderCarousel calibration entry.

### Output node stored channel values (the on-node widgets)

- **Output node stored channel values (the on-node widgets)**: every exposed channel row carries a value cell — unwired `roughness`/`metalness`/`opacity`/`discard`/`position` render a compact DragNumberInput (shown defaults 1/0/1/0/0; 0-1-clamped except Displacement, which may go negative), unwired `color`/`emissive`/`normal`/`env` render a swatch showing the channel default (color WHITE, emissive/env BLACK, normal the flat tangent-space `#8080ff` — no unset state; every color popover leads with a "Default (none)" entry that CLEARS the stored key — the way a picked normal is re-applied back to default/none) opening `components/inputs/PaletteColorPicker` (the app-wide picker, see its own convention below). A wired channel shows the incoming value instead (`edgeValueLabel`, plain text, blue when live) via the two-step cheap-string selector — built on **`getTargetEdges`, never raw `s.edges`**, or a feeder inside a collapsed group degrades every row to a grey `…` (the group id has no registry def). Values live on `OutputNodeData.values` (**`getNodeValues()` still hard-returns `{}` for output — readers access the field directly**), and every cell shares ONE fixed width (`.output-node__val`, 20px — the compact box's step arrows are hidden at that width; drag-scrub and click-to-edit remain) so the label column stays perfectly vertical ("1" and "0.35" would otherwise render different box widths). The codegen contract, in order of precedence: an ABSENT key emits nothing (byte-stability — every pre-widget graph and builtin emits identically); a WIRED edge always wins; emission is EXPOSURE-GATED (what the node shows is what emits — a tampered file can't emit from a hidden channel, and ShaderSettingsMenu clears a channel's value when hiding it, incl. the auto-managed opacity path); values emit as inline `float(<num>)`/`color(0x<hex>)` (adversarial: Number()+num(), hexLiteral whitelist); a stored DISCARD emits the statement `Discard(float(v));`, a stored env color is a constant ambient envNode, and a stored NORMAL color emits `normalMap(color(0x…))` — DECODED as a normal-map texel ([0,1]→[-1,1] + TBN), never fed raw to normalNode — **zero discard/displacement and the default normal `#8080ff` (the identity texel) are literal no-ops and deliberately emit NOTHING**, so the widget default and an absent key are indistinguishable in code (a non-zero discard is an unconditional truthiness cull — the mesh vanishes, by design). codeToGraph's `matchStoredChannelValue` collapses exactly those inline shapes (and the bare `return color(0x…)` color-only form) back into stored values — identifiers stay real nodes — and `applyStoredOutputValues` seeds exposure for valued channels. Two resync rules in `mergeMatch` keep Apply honest: old exposedPorts union in only the VALUED channels (unioning the parse's whole seeded list resurrected defaults the user explicitly hid), and stored values SHADOWED by a wire are carried from the old node (they can't appear in the code text, so the parse could never legitimately clear them — without the carry, any Apply wiped the value a disconnect is supposed to restore). `scriptToTSL`'s `NODE_PROP_TO_CHANNEL` maps `metalnessNode`/`envNode` back to editor channels (missing entries made Load Script silently drop them). The asset-card mirror renders the real widgets inert (`.node-preview-card__inert` pointer-events wrapper, unset swatch span).

### Several output nodes — the ACTIVE flag governs only the UNTARGETED ones

- **Several output nodes — the ACTIVE flag governs only the UNTARGETED ones** (2026-09-03; narrowed by the per-material Output split, 2026-09-18; `utils/sdfPartition.ts` `activeSink`, `utils/outputMaterials.ts` `defaultOutput` / `contributingOutputs`). Any mix of plain Outputs and Raymarch Outputs may coexist on the canvas. **A TARGETED plain Output ALWAYS contributes** — it shades the meshes it names and nothing else, so parking it behind another node's flag would silently drop a material the canvas still shows, and would make "which meshes does this shader paint" depend on a choice the user made about a DIFFERENT node. Among UNTARGETED plain Outputs exactly ONE contributes (the flagged one, else the lowest-ranked), which is what still lets a whole-model variant be PARKED beside the one in use; and a DRIVING Raymarch Output still suppresses every plain Output. So **"THE Output" is FOUR questions now**, each with its own function and each call site picking one deliberately — they were ONE function (`flagged ?? outputs[0]`), blind to whether the node names a mesh, which is safe only while one node holds every material. `defaultOutput` = who owns the module's TOP-LEVEL channels: the flagged-and-untargeted node, else the LOWEST-RANKED untargeted one, else **null** — a real answer rather than a gap, since a document whose every Output is targeted emits `parts` alone and loader 0.6/0.8 then leaves each unclaimed mesh on its authored material. `contributingOutputs` = the node SET whose materials reach the module, `defaultOutput` plus every targeted plain Output, returned in emit order — the ONE answer emission, both export plans, the code panel's tabs, the preview and its XR popup all read, with `costSeeds` the same shape for the cost total. `moduleSettingsOutput` = whose four `materialSettings` keys the module writes at top level (owner decision D1's fallback chain: `buildShaderModule` always writes them, so unlike the channels this must answer while ANY Output exists — `defaultOutput`, else the first Output of any kind; a Raymarch Output is not a candidate, its settings coming from `marchMaterialSettings`, which layers over this). And `findDefaultOutput` = "where do I point the USER" — the flagged Output else the first in array order, targeting deliberately NOT consulted — which the focus and glide helpers ask. **The failure they were split to prevent takes one more step than it looks, and the measurement is worth keeping.** A FRESHLY built GLB document does put its untargeted default first (measured: `gi_output`, then `gi_output_m0`, `gi_output_m1`), so array order happens to answer correctly there — but array order is NOT stable: `liftChildrenAfterParents` splices a node into a new slot on an ordinary drag-into-a-group and `useSyncEngine` reorders on every Apply. The moment a TARGETED index node reaches the front, a single blind predicate hands it the module's top-level channels — the same material painted twice, the module-level copy repainting every unclaimed mesh — while it also becomes the cost seed, the Uniforms scope, the preview window's owner and Preview mode's target. (`sdfPartition.ts`'s own comment still states the stronger "an import-built document's FIRST Output node is a targeted one", which the measurement above contradicts; the RULE it justifies is right either way.) `activeSink` narrowed the same way (flagged-and-eligible → first wired march → lowest-ranked untargeted), and `normalizeActiveOutput` STRIPS the flag from a targeted node, so the two rules cannot disagree about who is eligible. Both pick the lowest RANK with ties keeping array order, so a document that has never been split elects exactly what it always did. **The choice is node data**: clicking an untargeted node's preview SOCKET (`setActiveOutput`, one history entry, telemetry `output-activate`) writes `activeOutput: true` on it and deletes the key from every other sink — on a TARGETED node that socket is INERT, and why is D2 in the per-mesh convention. **An ABSENT key means "never chose"**, and then the historical rule decides — that absence is what keeps every saved graph, every built-in and every exported `.js` emitting byte-identically, the noise-`signed` precedent; a document acquires the key only when someone clicks. `normalizeActiveOutput` (first literal `true` wins, junk stripped, an ineligible holder stripped, same-array-when-clean) runs on every restore path beside `sanitizeOutputMaterials` and on the resync's final list; a saved group has its flag CLEARED at load (a fragment does not own the choice) and `instantiateSavedGroup` normalises the combined list with the live graph FIRST, so its choice wins; a paste strips the flag off the clones. Deleting the active node just removes its flag, so the fallback takes over — no re-election anywhere. **The resync is the subtle half** (`useSyncEngine` plus the pure `utils/resyncPairing.ts` and `utils/sinkCarry.ts`): a PARKED sink is absent from the code BY CONSTRUCTION (never deleted by the user — it was never in the text) and `carryInactiveSinks` brings it back whole together with its incoming edges whose source survived, while a TARGETED plain Output is NOT carried, because it CONTRIBUTES and the parse rebuilds it from the code — carrying it too would add a node BESIDE the parse's copy and grow a GLB document by one Output per mesh ON EVERY APPLY while emitting each part twice. `pairable` therefore excludes only PARKED sinks from the pairing buckets, every contributing Output being a candidate on its own, and `matchKey`'s BINDING tier does the rest (rule 3 of the per-mesh convention — without it an Apply moves one material's identity onto another mesh). `oldActive` is plain `activeSink` with NO last-resort term: the `contributingOutputs(oldNodes)[0]` fallback that stood there while an all-targeted document had no sink at all is gone, because both halves it patched are now done properly — every targeted Output pairs on its own binding, and `placeParsedOutputs` PLACES an unpaired plain Output below the lowest positioned one (`UNFOLD_DY` apart, in emit order, so a built column and a restored column are the same column) rather than handing it to the relayout, which is what keeps it clear of the `unpositioned.length === 0` gate that would otherwise take every group frame on the canvas with it. A parked march's feeder chain survives on its own because an inactive march is NOT partitioned (`drivingMarchOutput` gates the partition), so its position-dependent nodes emit in the flat body as ordinary consts. `activeOutput.test.ts` pins apply∘apply stability through the pure carry. Every sink's badge is its OWN price (`sinkCosts` — what the shader would cost with that node driving, muted on one that is not), while the meter is the UNION of every contributing seed; the Uniforms overlay lists only sliders that reach them. `foldExtraOutputs` is GONE — `unfoldOutputMaterials` replaced it, so a legacy one-Output-per-mesh document now loads natively as one node per mesh rather than being folded into one. Podest still knows nothing about any of this — it renders an exported module on its own picker. One RESIDUE, display-only and documented rather than fixed: `envMapName` (the preview's Light dropdown entry named after an attached environment image) reads `defaultOutput`, so on a document where EVERY Output is targeted that named entry is absent.
